# 菜单、页面与操作权限设计

## 1. 设计结论

当前系统约定“一个菜单项对应一个页面”，因此不再单独抽象页面资源表。

菜单项同时承担以下职责：

- 页面导航入口。
- 页面路由信息。
- 页面访问权限的授权对象。
- 页面操作权限的归属对象。

整体关系如下：

```text
t_system_menu（菜单 / 页面）
        │
        └── t_system_menu_action（页面操作）
                        │
                        └── t_role_menu_action（角色操作授权）

t_role_menu（角色菜单 / 页面访问授权）
```

## 2. 核心概念

### 2.1 菜单就是页面

`t_system_menu` 中的 `menu_type = 'item'` 表示一个可访问页面，页面路由直接保存在菜单记录中。

目录只负责菜单树分组，不代表独立页面；目录通常不配置页面操作。

示例：

```text
平台管理             directory
└── 用户管理         item，页面路由 /platform/users
租户管理             item，页面路由 /platform/tenants
知识库管理           item，页面路由 /knowledge-bases
```

### 2.2 页面操作

一个页面可以拥有多个业务操作，例如：

```text
知识库管理页面
├── 查看知识库
├── 新增知识库
├── 编辑知识库
├── 删除知识库
├── 导入文档
└── 导出文档
```

操作必须归属于一个菜单页面，通过 `menu_id` 关联。

### 2.3 角色授权

角色授权拆成两类：

| 授权关系 | 作用 |
|---|---|
| `t_role_menu` | 角色是否可以看到菜单、进入页面 |
| `t_role_menu_action` | 角色是否可以执行页面中的具体操作 |

角色拥有操作权限时，不自动推导菜单权限；业务授权时应同时确保角色拥有对应页面的菜单权限。

## 3. 表结构设计

### 3.1 `t_system_menu`

继续使用现有菜单表，不新增页面资源表。

关键字段：

| 字段 | 说明 |
|---|---|
| `id` | 菜单 / 页面主键 |
| `parent_id` | 父目录主键 |
| `code` | 菜单编码，全局唯一 |
| `name` | 菜单或页面名称 |
| `menu_type` | `directory` 目录，`item` 页面 |
| `route_path` | 页面路由；目录为空 |
| `icon` | 菜单图标 |
| `sort_order` | 同级菜单排序 |
| `visible` | 是否在导航中显示 |
| `status` | `active` 或 `disabled` |
| `meta` | 页面扩展配置 |

页面访问通过 `t_role_menu` 控制。

### 3.2 `t_system_menu_action`

保存页面下的操作定义。

```sql
create table if not exists t_system_menu_action (
    id bigint generated by default as identity primary key,
    menu_id bigint not null,
    code varchar(128) not null,
    name varchar(100) not null,
    action_type varchar(32) not null default 'business',
    sort_order integer not null default 0,
    status varchar(32) not null default 'active',
    meta jsonb not null default '{}'::jsonb,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    check (action_type in ('button', 'business'))
);
```

约束和索引：

- `code` 全局唯一，作为前后端统一权限编码。
- 同一个页面下的操作名称不能重复。
- `menu_id` 必须关联 `menu_type = 'item'` 的页面菜单；该规则由 Service 层校验。
- `idx_t_system_menu_action_menu(menu_id, status)` 用于查询页面下的有效操作。

推荐操作编码：

| 页面 | 操作编码 | 操作名称 |
|---|---|---|
| 知识库管理 | `knowledge_base:view` | 查看知识库 |
| 知识库管理 | `knowledge_base:create` | 新增知识库 |
| 知识库管理 | `knowledge_base:update` | 编辑知识库 |
| 知识库管理 | `knowledge_base:delete` | 删除知识库 |
| 文档管理 | `document:upload` | 上传文档 |
| 文档管理 | `document:delete` | 删除文档 |

### 3.3 `t_role_menu`

继续使用现有角色菜单关系表，表示角色的页面访问权限：

```text
角色 → 菜单 / 页面
```

已有字段 `role_scope`、`role_code`、`menu_id` 和 `status` 可以继续使用。

### 3.4 `t_role_menu_action`

保存角色对页面操作的授权。

```sql
create table if not exists t_role_menu_action (
    id bigint generated by default as identity primary key,
    role_scope varchar(32) not null,
    role_code varchar(64) not null,
    action_id bigint not null,
    status varchar(32) not null default 'active',
    created_at timestamptz not null default now(),
    created_by bigint,
    updated_at timestamptz not null default now(),
    check (role_scope in ('platform', 'tenant', 'organization'))
);
```

约束和索引：

- 同一作用域、角色和操作只能有一条有效关系。
- `idx_t_role_menu_action_role(role_scope, role_code, status)` 用于获取角色操作权限。
- `idx_t_role_menu_action_action(action_id, status)` 用于查询操作授权角色。
- 授权时由 Service 校验该操作所属页面，同时角色拥有该页面的 `t_role_menu` 权限。

## 4. 权限判断规则

### 4.1 页面访问

用户请求页面时：

1. 根据当前租户和角色作用域获取有效 `t_role_menu`。
2. 只有 `menu_type = 'item'` 且存在有效角色菜单关系时，才允许进入页面。
3. 未授权页面不出现在前端菜单树中。
4. 用户直接输入路由时，后端或路由守卫仍需重新校验。

### 4.2 操作权限

用户执行操作时：

1. 根据操作编码查询 `t_system_menu_action`。
2. 确认操作属于当前页面。
3. 查询当前用户角色是否存在有效 `t_role_menu_action`。
4. 校验用户的数据范围、租户范围和组织范围。
5. 前端显示按钮只是交互优化，后端接口必须再次鉴权。

### 4.3 页面和操作的组合

| 页面权限 | 操作权限 | 结果 |
|---|---|---|
| 无 | 无 | 不显示菜单，不能进入页面 |
| 有 | 无 | 可以进入页面，但隐藏操作按钮 |
| 有 | 有 | 可以看到并执行对应操作 |
| 无 | 有 | 视为配置异常，不能执行操作 |

最后一种情况由授权 Service 阻止，不能依赖前端处理。

## 5. 前端使用方式

前端权限上下文统一提供操作判断：

```ts
const { can } = usePermission();

can('knowledge_base:create');
can('knowledge_base:delete');
```

按钮示例：

```vue
<el-button v-if="can('knowledge_base:create')">
  新增知识库
</el-button>
```

### 5.1 `v-permission` 自定义指令

Vue 3 继续支持自定义指令。前端统一注册 `v-permission`，用于根据操作编码控制按钮或操作入口的显示：

```vue
<el-button v-permission="'knowledge_base:create'">
  新增知识库
</el-button>
```

指令内部统一调用 Pinia 权限 Store，不在业务页面重复编写角色判断：

```ts
app.directive("permission", {
  mounted(el, binding) {
    const actionCode = binding.value;

    if (!permissionStore.can(actionCode)) {
      el.remove();
    }
  },
});
```

多权限场景支持显式声明匹配模式：

```vue
<el-button
  v-permission="{
    codes: ['knowledge_base:update', 'knowledge_base:delete'],
    mode: 'all',
  }"
>
  批量操作
</el-button>
```

建议约定：

- 字符串值表示单个操作权限。
- `mode = 'all'` 表示必须同时拥有所有操作权限。
- `mode = 'any'` 表示拥有任意一个操作权限即可。
- 无权限时默认移除按钮节点，避免留下空白操作入口。
- 指令只控制前端展示，不能替代路由守卫、API 权限验证或 Service 层的 `@require_action()` 装饰器。

路由进入权限使用菜单编码或菜单路由权限：

```ts
{
  path: '/knowledge-bases',
  meta: {
    menuCode: 'knowledge_bases',
  },
}
```

## 6. 后端操作权限验证接口

后端权限验证分为两类接口，职责不能混淆：

1. 权限查询接口：给前端加载当前用户可用的菜单和操作，用于显示或隐藏按钮。
2. 业务接口内部鉴权：每个真实业务接口在执行前强制校验操作权限，这是最终安全边界。

前端传入的 `action_code` 只能用于展示层查询，不能由前端通过传参决定业务接口实际使用的权限。真实业务接口应由后端路由或 Service 固定绑定操作编码。

### 6.1 获取当前权限

```http
GET /api/v1/auth/permissions
```

请求上下文：

- 用户身份从登录 Token 获取。
- 当前 `tenant_id` 从登录会话或当前租户上下文获取，不信任普通请求参数。
- 组织范围由用户在当前租户下的有效组织成员关系确定。

响应示例：

```json
{
  "menus": [
    {
      "code": "knowledge_bases",
      "route_path": "/knowledge-bases",
      "actions": [
        "knowledge_base:view",
        "knowledge_base:create",
        "knowledge_base:update",
        "knowledge_base:delete"
      ]
    }
  ],
  "action_codes": [
    "knowledge_base:view",
    "knowledge_base:create",
    "knowledge_base:update",
    "knowledge_base:delete"
  ]
}
```

该接口用于初始化前端权限上下文和菜单树，不替代业务接口鉴权。切换租户后必须重新调用，不能复用上一个租户的权限结果。

### 6.2 批量检查操作权限

当页面需要根据动态条件判断多个按钮时，可以提供批量检查接口：

```http
POST /api/v1/auth/permissions/check
Content-Type: application/json
```

请求体：

```json
{
  "action_codes": [
    "knowledge_base:create",
    "knowledge_base:delete"
  ]
}
```

响应体：

```json
{
  "items": [
    {
      "action_code": "knowledge_base:create",
      "allowed": true
    },
    {
      "action_code": "knowledge_base:delete",
      "allowed": false
    }
  ]
}
```

约束：

- `action_codes` 数量限制由接口统一规定，避免被用于大规模枚举权限。
- 未定义、已禁用或不属于当前有效页面的操作返回 `allowed: false`，不泄露额外资源信息。
- 该接口只返回当前用户的授权结果，不返回角色、授权记录或内部判定细节。
- 业务接口不能因为前端事先调用过该接口就跳过自身鉴权。

### 6.3 业务接口内部强制鉴权

每个需要保护的 API 必须在 Service 执行写操作或敏感查询前调用统一权限服务。推荐使用固定的服务方法：

```python
await permission_service.require_action(
    context=current_user_context,
    action_code="knowledge_base:create",
)
```

### 6.4 操作权限装饰器

为了避免每个 Service 方法重复编写操作权限校验，可以提供统一的 `require_action` 装饰器：

```python
@require_action("knowledge_base:create")
async def create(
    self,
    payload: CreateKnowledgeBaseRequest,
    auth_context: AuthContext,
):
    async with self.db.transaction():
        ...
```

装饰器负责：

1. 从 Service 方法的显式 `auth_context` 参数获取当前用户上下文。
2. 调用统一 `permission_service.require_action()` 校验操作编码。
3. 权限通过后才执行原 Service 方法。
4. 权限失败时抛出领域权限异常，由 API 层统一转换为 HTTP `403`。

装饰器不依赖 FastAPI 的 `Request`、`Response` 或 `HTTPException`，Service 仍可被 API、Worker 或其他内部流程调用和测试。

推荐的装饰器调用形式：

```python
from functools import wraps
from typing import Any, Awaitable, Callable


def require_action(action_code: str):
    def decorator(func: Callable[..., Awaitable[Any]]):
        @wraps(func)
        async def wrapper(*args: Any, **kwargs: Any) -> Any:
            auth_context = kwargs.get("auth_context")
            if auth_context is None:
                raise PermissionContextMissingError()

            await permission_service.require_action(
                context=auth_context,
                action_code=action_code,
            )
            return await func(*args, **kwargs)

        return wrapper

    return decorator
```

装饰器只验证固定的操作权限，不负责查询目标业务数据。涉及具体资源时，Service 还必须继续校验租户、组织和数据范围：

```python
@require_action("knowledge_base:delete")
async def delete(
    self,
    knowledge_base_id: int,
    auth_context: AuthContext,
):
    knowledge_base = await knowledge_base_db.get(id=knowledge_base_id)

    await permission_service.require_resource_scope(
        context=auth_context,
        tenant_id=knowledge_base.tenant_id,
        organization_id=knowledge_base.organization_id,
    )

    async with self.db.transaction():
        ...
```

两类校验的职责如下：

| 校验方式 | 校验内容 |
|---|---|
| `@require_action()` | 当前角色能否执行固定操作 |
| `require_resource_scope()` | 当前用户能否操作指定业务数据 |

约束：

- 操作编码必须固定写在后端装饰器或 Service 调用中，不能从请求体读取或由前端覆盖。
- Service 层必须保留最终鉴权，不能只依赖 API 层装饰器。
- 权限校验必须发生在事务和数据库写操作之前。
- Worker 或定时任务必须显式传入系统身份或任务身份，不能隐式绕过权限。

带资源的数据操作还需要传入目标资源或数据范围：

```python
await permission_service.require_action(
    context=current_user_context,
    action_code="knowledge_base:delete",
    tenant_id=tenant_id,
    organization_id=organization_id,
    resource_id=knowledge_base_id,
)
```

Service 至少按以下顺序校验：

1. Token 对应用户是否有效。
2. 当前租户上下文是否有效，用户是否仍是当前租户成员。
3. 当前角色作用域和角色编码是否有效。
4. `action_code` 是否存在、启用，并归属于当前页面。
5. 角色是否存在有效 `t_role_menu_action` 授权。
6. 角色是否同时拥有该操作所属页面的 `t_role_menu` 权限。
7. 目标资源是否属于当前租户和组织数据范围。
8. 业务状态是否允许执行该操作。

业务接口与操作编码示例：

| HTTP 接口 | Service 操作 | 操作编码 |
|---|---|---|
| `POST /knowledge-bases` | 新建知识库 | `knowledge_base:create` |
| `PATCH /knowledge-bases/{id}` | 修改知识库 | `knowledge_base:update` |
| `DELETE /knowledge-bases/{id}` | 删除知识库 | `knowledge_base:delete` |
| `POST /documents` | 上传文档 | `document:upload` |
| `DELETE /documents/{id}` | 删除文档 | `document:delete` |

操作编码应在后端代码中固定，不允许使用请求体中的 `action_code` 覆盖。例如删除接口只能检查 `document:delete`，不能让调用方传入 `document:view` 来改变校验目标。

### 6.5 验证结果与错误响应

统一权限服务不建议返回布尔值后由业务代码自行决定是否继续执行；强制鉴权方法应在失败时直接抛出领域权限异常。

| 场景 | HTTP 状态 | 说明 |
|---|---:|---|
| 未登录、Token 无效 | `401` | 认证失败 |
| 没有页面或操作权限 | `403` | 不允许执行 |
| 有权限但资源不属于当前范围 | `403` | 不暴露资源是否存在 |
| 操作编码不存在或已禁用 | `403` | 对调用方统一视为无权操作 |
| 目标资源不存在 | `404` | 仅在已通过权限和范围校验后返回 |
| 业务状态不允许 | `409` | 权限通过，但状态冲突 |

推荐错误响应：

```json
{
  "code": "FORBIDDEN",
  "message": "无权执行该操作",
  "request_id": "req_xxx"
}
```

不得把角色列表、授权表 ID、数据范围细节或内部 SQL 信息返回给客户端。

## 7. 评审重点

本次评审需要确认：

1. 是否确认菜单项与页面一一对应。
2. 是否确认页面操作直接通过 `menu_id` 关联菜单。
3. 是否采用全局唯一操作编码。
4. 是否保留 `button` 和 `business` 两种操作类型。
5. 是否采用 `GET /api/v1/auth/permissions` 作为前端权限初始化接口。
6. 是否提供批量操作权限检查接口。
7. 是否允许角色拥有操作权限但没有页面菜单权限；建议禁止。
