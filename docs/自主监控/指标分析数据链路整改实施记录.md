# 指标分析数据链路整改实施记录

## 整改背景

2026年08月01日核查指标分析页面时发现，16 个已发布指标全部显示“无法判定”，其中多数同时显示“暂无数据”。数据库实际已有指标结果和监控事件，因此对指标定义、规则、事件采集、五分钟聚合、范围隔离、时间范围查询和页面合同进行了全链路整改。

## 原因结论

| 原因 | 原有表现 | 整改结果 |
| --- | --- | --- |
| 判定规则缺失 | `t_monitor_metric_rule` 为 0 条，所有有效值也写为 `unknown` | 为 16 个指标发布方向、预警、严重、恢复和最小样本规则 |
| 范围聚合单一 | 单租户窗口只生成租户指标，多租户窗口只生成平台指标 | 每个窗口固定生成平台汇总，并按定义为每个实际租户生成独立结果 |
| 时间口径错误 | 最近一小时只取最新五分钟结果，最新空窗口覆盖早期有效值 | 比例按分子分母汇总、计数求和、容量取最新有效值、P95 按窗口样本加权计算 |
| 空值过滤失效 | DB 通用过滤忽略 `None`，平台查询混入租户结果并重复统计 | 指标查询改用明确的 `scope_key=platform` 或 `scope_key=tenant:<id>` |
| 终态重复采集 | 失败问答先记录 `qa_failed`，随后又记录 `qa_degraded` | 失败降级只保留一个最终终态；历史近邻终态在回填时受控去重 |
| 历史结果未重算 | 新规则发布后旧窗口仍保留 `unknown` | 增加最近 1 至 24 小时的五分钟窗口受控回填能力，不触发历史告警和通知 |

## 规则口径

规则统一使用现有 `trigger_type` 字段：

- `higher_than`：值越高风险越大，适用于错误率、超时率、P95、容量和积压。
- `lower_than`：值越低风险越大，适用于成功率、引用率、可用率和证据完整率。
- `informational`：只判断数据可用性，适用于问答请求量。

比例值在数据库中统一使用 0 至 1，耗时统一使用毫秒。规则以 `scope_type=all` 发布，平台和租户可共享默认规则；后续明确发布同指标的平台或租户规则时，精确范围规则优先。

## 聚合口径

Worker 仍按五分钟保存基础窗口，但页面按用户选择的时间范围进行业务汇总：

- 比例：累计分子除以累计分母，不能平均各窗口比例。
- 计数：累计有效窗口计数。
- 容量、积压：使用范围内最近一个有效采样值。
- P95：按各窗口有效样本数加权计算，避免最新空窗口覆盖已有样本。
- 数据状态：全窗口有效为“已完成”，有效与空窗口并存为“部分数据”，没有任何有效样本才是“暂无数据”。
- 判定状态：有有效值且样本达到规则要求后返回达标、预警或不达标；只有没有规则、没有值或样本不足时才返回无法判定。

## 数据执行

已在单一数据库事务中重新执行 `scripts/db/data_table_dml.sql`，成功发布 16 条启用规则。随后执行当前窗口聚合和最近一小时回填，完成历史规则状态、平台范围和租户范围结果重算。

真实知识库问答使用知识库 28 执行成功，返回 5 条命中和 5 条引用；该调用通过统一采集链生成 `qa_completed`，用于验证问答请求量、成功率、错误率、超时率、引用率和 P95 的后续五分钟聚合。

没有评测结束、任务结束或成功问答样本的窗口继续显示“暂无数据”，这是对真实业务空闲状态的准确表达，不使用演示数据伪造达标结果。

## 测试结果

- 指标专项、告警生命周期、查询分页和知识 Agent 相关测试通过。
- 后端全量自动化 `217 passed`。
- Ruff、Python 编译和差异格式检查通过。
- 数据库规则数由 0 条恢复为 16 条启用。
- 当前真实平台指标已经能够返回达标、不达标、部分数据和暂无数据，不再把所有指标统一写为无法判定。

最终真实窗口验证中，16 个平台指标分布为 9 项达标、2 项依据真实失败请求判定为不达标、5 项无法判定。其中问答请求量、成功率、错误率、超时率、引用率和 P95 已全部取得真实值；P95 因当前只有 1 个成功样本、未达到 20 个最小样本要求而保持无法判定。其余无法判定项来自当前一小时没有评测结束或任务结束事实，属于真实业务空闲，而非采集失败。

同一个成功问答窗口已同时写入 16 条平台结果和 12 条租户结果；六项问答指标均同时存在 `platform` 与 `tenant:103` 两个范围，证明平台汇总和租户隔离链路均已生效。
