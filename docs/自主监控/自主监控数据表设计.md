# 监控数据表设计（评审稿）

## 1. 设计说明

本文档只定义自主监控的数据模型、字段、索引、状态和数据关系，不执行 DDL，不新增数据库表，不进入后端编码。当前为评审稿，数据库设计评审通过后，再将确认结果统一落入 `scripts/db/data_table_ddl.sql`。

本轮同步范围：自主监控不再提供“权限配置”业务页面；权限校验仍作为 API、Service 和数据访问层的横向安全能力保留。页面列表的四字字段要求只约束前端展示名称，不改变数据库字段的英文命名约定。

自主监控数据分为六类：

| 数据类别 | 作用 | 保留原则 |
| --- | --- | --- |
| 运行事实 | 保存问答、评测、文档、索引、Worker 和服务的结构化事件 | 不保存完整问题、答案、文档片段、Token 或 API Key |
| 统计指标 | 保存固定时间窗口内的指标聚合结果 | 保留样本数、分子、分母、数据状态和规则版本 |
| 告警证据 | 保存规则触发、恢复和关联证据 | 必须能回溯事件、指标、任务、Trace ID 或版本 |
| 配置规则 | 保存采集目标、指标定义、阈值和通知策略 | 数据库为唯一配置源，变更必须审计 |
| 管理审计 | 保存菜单、配置、告警处理和查询操作 | 记录操作人、范围、结果和脱敏摘要 |
| 分析会话 | 保存自主监控 Agent 的分析会话、消息和证据上下文 | 优先复用现有知识库会话模型，不独立新增会话表 |

## 2. 命名约定

- 表名统一使用 `t_monitor_` 前缀，业务主键统一为 `id bigint generated by default as identity primary key`。
- 所有表包含 `created_at`；有状态或可修改配置的表增加 `updated_at`。
- 关联字段只保存业务关联 ID，不创建数据库外键；租户边界和数据存在性由 Service / Repository 校验。
- 时间统一使用 `timestamptz`；耗时统一使用毫秒，计数统一使用整数，比例统一使用小数或百分数并明确单位。
- 事件、指标和告警均保存 `tenant_id`；平台级数据使用空租户范围，但查询必须经过权限范围判断。

## 3. 数据关系

```text
采集目标 ──采集事件配置──> 运行事件 ──聚合──> 指标结果
                                  │              │
                                  └────规则判断──> 告警实例
                                                   │
                                          告警证据/通知记录

指标定义 ──指标规则版本──> 指标结果 ──规则版本──> 告警实例

现有会话 ──消息──> 分析对话消息 ──元数据──> 监控上下文、证据引用和 Agent 运行标识
```

### 3.1 表清单

| 数据域 | 建议表名 | 主要职责 | 来源或消费者 |
| --- | --- | --- | --- |
| 运行事实 | `t_monitor_event` | 保存问答、任务、评测、Worker、探针和依赖事件 | 采集器、指标聚合、告警规则、事件中心 |
| 状态快照 | `t_monitor_state_snapshot` | 保存服务、依赖和 Worker 的当前状态 | 采集器、监控总览、环境快照 |
| 指标定义 | `t_monitor_metric_definition` | 保存指标编码、口径、维度和单位 | 指标聚合、指标查询 |
| 指标结果 | `t_monitor_metric_value` | 保存时间窗口内的聚合结果 | 指标分析、告警规则、总览图表 |
| 采集目标 | `t_monitor_gather_target` | 保存系统发布的采集目标配置 | 采集器、运维发布流程 |
| 采集动作 | `t_monitor_gather_action` | 保存目标到事件字段的采集映射 | 采集器 |
| 指标规则 | `t_monitor_metric_rule` | 保存阈值、连续周期和恢复条件 | 告警规则、指标考核 |
| 告警实例 | `t_monitor_alert` | 保存告警触发、确认、恢复和关闭状态 | 告警中心、总览、智能分析 |
| 告警证据 | `t_monitor_alert_evidence` | 保存告警与事件、指标、任务和 Trace 的关联 | 告警详情、智能分析 |
| 分析会话 | 复用 `t_conversation` | 通过会话类型和范围字段承载自主监控 Agent 的分析会话 | 智能分析、会话列表 |
| 分析消息 | 复用 `t_conversation_message` | 保存用户追问和自主监控 Agent 回复，`metadata` 保存监控上下文与证据引用 | 智能分析、历史会话 |
| 分析引用 | 复用消息 `metadata` | 保存告警、指标、事件、任务、评测运行和 Trace ID 的引用，不新增独立引用表 | 分析对话、证据面板 |
| 通知渠道 | `t_monitor_notification_channel` | 保存站内通知和 Webhook 渠道配置 | 告警通知、通知发送器 |
| 通知策略 | `t_monitor_notification_policy` | 保存告警级别、范围和生命周期通知规则 | 告警通知、通知发送器 |
| 策略渠道 | `t_monitor_notification_policy_channel` | 支持一条策略关联多个通知渠道 | 通知发送器 |
| 通知记录 | `t_monitor_notification_record` | 保存每次通知发送及失败结果 | 告警通知、审计 |
| 管理审计 | 复用 `t_audit_log` | 保存查询、规则、采集发布和告警处理操作 | 审计管理、安全审计 |

不单独为监控总览、状态趋势、状态分布、域状态图、任务积压、告警生命周期和异常传播建立表；这些内容均从事件、快照、指标和告警数据实时聚合得到。

## 4. 事件数据

### 4.1 事件主表

建议表名：`t_monitor_event`

| 字段 | 类型建议 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint identity | 是 | 数据库主键 |
| `event_id` | varchar(128) | 是 | 外部幂等事件 ID，全局唯一 |
| `event_type` | varchar(96) | 是 | 如 `qa_completed`、`evaluation_case_completed` |
| `source_type` | varchar(32) | 是 | `api`、`db`、`worker`、`agent`、`probe`、`middleware` |
| `source_code` | varchar(128) | 是 | 采集目标或服务编码 |
| `tenant_id` | bigint | 否 | 租户范围，平台事件为空 |
| `kb_id` | bigint | 否 | 知识库范围 |
| `task_id` | bigint | 否 | 异步任务范围 |
| `run_id` | bigint | 否 | 评测运行范围 |
| `trace_id` | varchar(128) | 否 | 链路追踪 ID |
| `request_id` | varchar(128) | 否 | 请求 ID |
| `status` | varchar(32) | 是 | `started`、`completed`、`failed` 等事件状态 |
| `stage` | varchar(64) | 否 | 业务阶段 |
| `occurred_at` | timestamptz | 是 | 事件实际发生时间 |
| `duration_ms` | bigint | 否 | 阶段耗时 |
| `error_category` | varchar(64) | 否 | 结构化失败分类 |
| `payload` | jsonb | 是 | 脱敏结构化字段，不存自然语言业务正文 |
| `data_status` | varchar(32) | 是 | `ready`、`partial`、`error`，表示本条事件是否完整可用 |
| `created_at` | timestamptz | 是 | 入库时间 |

约束和索引：

- `event_id` 必须建立唯一索引，重复事件只保留一次，不重复聚合。
- 按 `(event_type, occurred_at)`、`(tenant_id, occurred_at)`、`(trace_id)`、`(task_id, occurred_at)` 建立查询索引。
- `payload` 只保存字段白名单；服务端拒绝完整问题、完整答案、文档片段、密码、Token 和 API Key。
- 事件数据按时间分区或归档，归档策略由保留周期配置决定。

### 4.2 状态快照

建议表名：`t_monitor_state_snapshot`

用于保存服务、数据库、依赖服务和 Worker 的最新状态，不替代事件主表。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint identity | 主键 |
| `resource_type` | varchar(32) | `service`、`database`、`dependency`、`worker` |
| `resource_code` | varchar(128) | 资源编码 |
| `tenant_id` | bigint | 租户范围，可为空 |
| `status` | varchar(32) | `healthy`、`idle`、`busy`、`stale`、`stopped`、`error`、`unknown` |
| `status_value` | jsonb | 探测结果摘要、版本、实例等结构化字段 |
| `checked_at` | timestamptz | 最近采集时间 |
| `expires_at` | timestamptz | 数据新鲜度截止时间 |
| `error_category` | varchar(64) | 采集失败分类 |
| `updated_at` | timestamptz | 更新时间 |

同一资源和租户范围只保留一条当前快照；历史变化通过事件主表记录。

## 8. 分析会话

### 8.1 复用原则

分析对话由自主监控 Agent 负责，历史会话归自主监控域管理。数据库设计优先复用现有知识库问答会话模型，不新增 `t_monitor_analysis_session`、`t_monitor_analysis_message` 或独立的分析引用表。

复用范围如下：

| 现有模型 | 分析对话用途 | 需要补充或调整的内容 |
| --- | --- | --- |
| `t_conversation` | 保存分析会话、标题、用户和会话状态 | 增加会话类型/业务域标识、监控范围键和会话级上下文摘要；监控会话不强制绑定 `kb_id` |
| `t_conversation_message` | 保存用户问题、Agent 回复和系统消息 | 复用 `metadata` 保存 Agent 运行 ID、Trace ID、消息状态、上下文快照和证据引用 |
| `t_message_citation` | 现有表专用于文档分块引用 | 不直接用于监控证据；监控证据以消息 `metadata` 中的结构化引用保存，避免把告警、指标误建模为文档分块 |

建议在现有会话模型中补充以下语义字段，具体字段名和兼容方式待评审确认：

- `conversation_type`：区分知识库问答、监控分析等会话类型。
- `scope_key`：保存平台、租户、监控域、资源和异常范围等统一范围标识。
- `metadata`：保存当前分析上下文摘要、最近一次 Agent 运行状态和页面展示所需的脱敏信息。
- `t_conversation_message.metadata`：保存 `agent_code=monitoring`、消息状态、运行 ID、Trace ID、上下文快照和证据引用。
- `kb_id`：现有知识库会话字段需要允许监控会话为空，不能使用虚拟知识库冒充监控范围。

### 8.2 会话消息

一条用户追问或自主监控 Agent 回复对应一条 `t_conversation_message` 记录。消息正文保存可展示的脱敏内容；`metadata` 保存结构化信息，例如：

```json
{
  "agent_code": "monitoring",
  "message_status": "completed",
  "run_id": "monitor-run-20260730-001",
  "trace_id": "trace-7ac9",
  "context_snapshot": {
    "alert_ids": ["alert-10021"],
    "metric_codes": ["qa_p95"],
    "event_ids": ["event-8831"],
    "task_ids": ["index-241"],
    "evaluation_run_ids": ["run-3008"],
    "window_start": "2026-07-30T09:20:00+08:00",
    "window_end": "2026-07-30T09:30:00+08:00"
  },
  "evidence_refs": [
    {"type": "alert", "id": "alert-10021", "relation": "direct", "rank": 1},
    {"type": "metric", "id": "qa_p95", "relation": "related", "rank": 2}
  ]
}
```

上下文只保存证据对象 ID、时间窗口和脱敏摘要，不复制完整问题、答案、文档片段、Token 或 API Key。历史会话恢复时，Service 先校验当前用户的数据范围，再向自主监控 Agent 提供限定数量的历史消息和证据引用。

### 8.3 历史恢复

```text
选择历史会话
      ↓
读取 t_conversation
      ↓
读取 t_conversation_message
      ↓
校验租户、用户和监控范围
      ↓
恢复消息 metadata 中的上下文和证据引用
      ↓
自主监控 Agent 继续分析
```

历史消息不写入 `t_monitor_alert.analysis_summary`。告警表中的摘要仍只表示监控侧异常摘要；对话中的每轮问题、回答、运行状态和证据引用均保存在通用会话模型中。

### 8.4 复用边界

- 不新增独立的分析会话表、分析消息表和分析引用表。
- 不直接复用 `t_message_citation` 表保存告警、指标或 Trace，因为该表字段语义固定为知识库文档分块引用。
- 如果后续监控证据元数据超过消息 `metadata` 的可维护范围，再单独评审是否增加关联表；本轮不预设新增。
- 自主评测 Agent 的运行表、评测结果表和报告表继续作为监控证据来源，不承载分析对话历史。

## 9. 通知审计

### 8.1 通知渠道

建议表名：`t_monitor_notification_channel`

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint identity | 主键 |
| `channel_code` | varchar(128) | 渠道编码，全局唯一 |
| `channel_name` | varchar(128) | 渠道名称 |
| `channel_type` | varchar(32) | `in_app`、`webhook` |
| `endpoint_ref` | varchar(255) | 站内通知标识或脱敏地址引用，不保存密钥 |
| `receiver_scope` | jsonb | 平台、租户、角色或值班组范围 |
| `status` | varchar(32) | `enabled`、`disabled` |
| `version` | integer | 渠道配置版本 |
| `effective_at` | timestamptz | 生效时间 |
| `created_by` / `updated_by` | varchar(128) | 操作人 |
| `created_at` / `updated_at` | timestamptz | 创建和更新时间 |

Webhook 密钥、Token 和完整认证信息不落本表；如必须接入外部密钥系统，只保存密钥引用标识。

### 8.2 通知策略

建议表名：`t_monitor_notification_policy`

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint identity | 主键 |
| `policy_code` | varchar(128) | 策略编码，全局唯一 |
| `policy_name` | varchar(128) | 策略名称 |
| `severity_scope` | jsonb | 严重、警告、提示等级范围 |
| `tenant_scope` | jsonb | 平台或租户范围 |
| `domain_scope` | jsonb | 监控领域范围 |
| `event_scope` | jsonb | `firing`、`持续`、`resolved` 等生命周期事件 |
| `mute_period` | jsonb | 静默时间段和重复通知抑制配置 |
| `enabled` | boolean | 是否启用 |
| `version` | integer | 策略版本 |
| `effective_at` | timestamptz | 生效时间 |
| `created_by` / `updated_by` | varchar(128) | 操作人 |
| `created_at` / `updated_at` | timestamptz | 创建和更新时间 |

策略保存范围条件和发送规则，不复制告警正文；策略变更通过既有审计表记录。

### 8.3 策略渠道

建议表名：`t_monitor_notification_policy_channel`

用于支持一条策略同时关联站内通知和 Webhook 等多个渠道。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint identity | 主键 |
| `policy_id` | bigint | 通知策略 ID |
| `channel_id` | bigint | 通知渠道 ID |
| `created_at` | timestamptz | 关联时间 |

唯一性建议为 `policy_id + channel_id`，删除策略或渠道前由 Service 校验关联状态。

### 8.4 通知记录

建议表名：`t_monitor_notification_record`

保存告警触发、持续、恢复和失败通知的发送事实：告警 ID、通知渠道、接收范围、模板版本、发送状态、失败分类、发送时间和重试次数。通知记录不能保存 Token、Webhook 密钥或完整业务内容。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint identity | 主键 |
| `alert_id` | bigint | 告警实例 ID |
| `channel_id` | bigint | 通知渠道 ID |
| `policy_id` | bigint | 命中的通知策略 ID |
| `event_type` | varchar(32) | `firing`、`持续`、`resolved`、`failed` |
| `receiver_scope` | jsonb | 实际发送范围摘要 |
| `status` | varchar(32) | `pending`、`sent`、`failed`、`retrying` |
| `failure_category` | varchar(64) | 失败分类，不保存密钥和完整响应 |
| `retry_count` | integer | 已重试次数 |
| `sent_at` | timestamptz | 发送时间 |
| `created_at` | timestamptz | 创建时间 |

唯一性建议为 `alert_id + channel_id + policy_id + event_type + 发送批次标识`，避免同一生命周期事件重复发送；具体批次键待通知重试策略评审后确认。

### 8.5 操作审计

复用现有 `t_audit_log`，`target_type` 增加 `monitor_target`、`monitor_metric_rule`、`monitor_alert`、`monitor_notification` 等类型。记录菜单访问、系统采集配置发布、指标规则变更、告警确认、关闭、静默和权限变更；采集配置不作为业务用户页面操作对象。

## 10. 数据保留

| 数据 | 在线保留 | 归档建议 | 删除要求 |
| --- | --- | --- | --- |
| 原始事件 | 30 天 | 归档 180 天 | 到期按事件类型和租户范围清理 |
| 指标结果 | 180 天 | 汇总到日粒度长期保留 | 删除前保留规则版本和统计口径 |
| 告警实例 | 1 年 | 可选长期归档 | 不删除未关闭告警 |
| 告警证据 | 与告警实例一致 | 与告警一起归档 | 告警删除前不得孤立删除 |
| 配置和审计 | 长期 | 不归档或独立归档 | 保留版本、操作人和生效时间 |

以上周期只是设计默认值，具体保留期限需结合租户合规要求、存储成本和运维策略审核确认。

## 11. 审核事项

1. 是否确认自主监控使用独立一级菜单 `monitoring`，与平台管理同级。
2. 是否确认事件原始数据、指标结果、告警实例和告警证据分表保存。
3. 是否确认指标规则、采集目标和采集动作全部数据库配置化。
4. 是否确认事件不保存完整问题、答案和文档片段。
5. 是否确认一条通知策略可以通过关联表绑定多个通知渠道。
6. 是否确认原始事件、指标和告警的默认保留周期。
7. 是否确认分析对话复用 `t_conversation`、`t_conversation_message` 和消息 `metadata`，不新增独立会话表。
8. 是否确认监控会话允许 `kb_id` 为空，并使用会话类型和 `scope_key` 区分监控范围。
9. 是否确认监控证据暂不复用 `t_message_citation`，而由消息 `metadata.evidence_refs` 保存。
