# 数据采集状态链路整改实施记录

## 问题现象

2026年08月01日核查数据采集页面时，部分目标显示“暂无采集”或“暂无数据”，但事件中心已经持续收到 Worker 心跳和周期探针事件。

## 原因分析

1. 采集总览只用目标编码和资源编码关联事件。Worker 事件的 `source_code` 是 `indexing`、`evaluation` 等具体节点名称，无法匹配统一目标 `worker.lifecycle`。
2. 总览查询没有过滤禁用目标，导致禁用的主动问答探针被计入目标数并显示为空。
3. 文档入库、文档索引和自主评测属于事件触发型采集，没有业务运行时显示“暂无数据”会被误解为周期采集故障。
4. `idle`、`recovered`、`retrying` 等真实运行状态没有完整映射到采集页面状态，可能被降成空数据。
5. API、数据库和业务方法已经成功采集到失败事件时，页面错误地把业务失败解释为采集器失败，混淆了业务状态与采集状态。
6. 真实上传验证发现 `add()` 已创建索引任务后，`upload()` 又调用 `create_task()`；在 Worker 快速领取完成的并发窗口内会为同一文档重复创建索引任务。

## 整改内容

- 按 `t_monitor_gather_action.event_type` 建立采集目标与事件的主关联，目标编码和资源编码保留为兼容关联键。
- 采集总览、趋势、热力图和目标分页只读取启用目标及启用动作。
- 事件触发型方法目标没有业务运行时返回 `idle/等待触发`；周期目标没有结果时仍返回 `empty/暂无数据`。
- `idle` 和 `recovered` 映射为正常结果，`retrying`、`stopped` 和 `cancelled` 映射为需要关注的中间状态。
- API、数据库、问答、索引、评测和 Worker 事件以 `data_status` 判断采集是否成功；业务执行失败仍由事件、指标和告警解释。探针与采集器自身继续按运行状态判断采集异常。
- 删除 `upload()` 中重复的索引任务创建调用，统一由 `add()` 的同一数据库事务创建文档和唯一初始索引任务，并增加回归测试。
- 前端状态分布、趋势、热力图、查询条件、目标列表和详情统一支持“等待触发”。

## 真实验证

| 验证链路 | 真实结果 |
| --- | --- |
| 周期采集 | 手工执行采集器，处理 13 个到期周期目标 |
| Worker 生命周期 | `worker.lifecycle` 返回正常，最近心跳可追溯到具体 Worker |
| 文档入库 | 文档 35 上传成功，写入入库开始与完成事件 |
| 文档索引 | 验证时暴露的索引任务 50、51 均执行成功；随后已修复重复创建入口，后续单次上传只创建一个初始索引任务 |
| 唯一任务复测 | 再次上传文档 36，仅创建索引任务 52，任务执行状态为 `succeeded` |
| 自主评测 | 运行 540 完成，阶段为 `report`，问题数为 1，完整写入评测阶段事件 |
| 最终总览 | 21 个启用采集目标全部为正常，禁用目标不进入统计 |

事件触发目标在后续业务空闲窗口显示“等待触发”是正常状态，不会再显示为“暂无采集”或“暂无数据”；该语义不依赖演示数据，也不会把未执行任务伪装为成功。
