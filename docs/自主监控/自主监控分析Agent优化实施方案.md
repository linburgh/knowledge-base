# 自主监控分析 Agent 优化实施方案

## 目标说明

本方案把现有基于告警数量返回固定文案的分析入口，升级为能够理解用户问题、解析时间与资源范围、调用授权只读工具、综合多源运行事实并返回可追溯结论的自主监控分析 Agent。

优化后的 Agent 必须完整支持平台健康判断、异常原因、影响范围、直接证据、检查建议、任务失败、时间窗口事件回顾和身份介绍。没有未恢复告警只能作为一项事实，不能单独证明平台正常；数据缺失、过期或查询失败时必须明确返回无法判断。

## 功能模块

| 一级模块 | 子模块 | 职责边界 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| 问题理解 | 意图识别 | 识别健康、原因、影响、证据、建议、任务、回顾和身份问题 | 用户问题、会话上下文 | 标准意图 |
| 范围解析 | 时间解析 | 解析昨天、今天、最近时长和明确日期；未指定时继承会话默认范围 | 问题、时区、会话范围 | 起止时间、时间说明 |
| 范围解析 | 资源解析 | 继承平台或租户授权范围，不接受问题覆盖可信身份字段 | 会话范围、认证上下文 | 授权资源范围 |
| 查询计划 | 工具选择 | 根据意图选择健康、告警、指标、事件和任务工具 | 标准意图 | 只读工具计划 |
| 工具执行 | 事实查询 | 在权限、数据范围、次数和超时预算内查询结构化事实 | 查询计划、授权上下文 | 分来源事实与工具轨迹 |
| 健康判定 | 规则计算 | 根据数据完整性、状态、告警和指标生成 normal、warning、abnormal、unknown | 多源事实 | 结构化结论与限制 |
| 回答生成 | 证据表达 | 用自然语言说明结论、时间范围、关键事实、限制和建议 | 结构化结论 | 回答、引用、限制 |
| 结果校验 | 引用校验 | 保证引用属于本轮授权工具结果，结论不超出证据 | 回答、证据集合 | 合法分析结果 |
| 会话审计 | 历史保存 | 保存问题、解析范围、结果、工具轨迹和证据摘要 | Agent 结果 | 可恢复、可审计消息 |

模块关系固定为：`API -> Monitoring Analysis Service -> Monitoring Agent -> Monitoring Tools -> DB Repository`。Agent 不解析 HTTP，不管理数据库事务；工具只能通过本 Agent 的显式注册表调用。

## Harness 选型

整改前生产链路为“结构化 Planner 单次模型调用 → Python 按计划顺序调用工具 → Answer Composer 再次模型调用”。该实现的工具选择、观察和终止由自研代码控制，没有官方 Agent 创建 API 进入生产链，属于模型驱动 Workflow，不满足自主监控 Agent 目标。

本次选用当前项目已锁定 Deep Agents 版本的 `create_deep_agent`，原因是自主监控已有两个专属 Skill，并需要模型根据中间证据自主选择后续只读查询。`create_agent` 可以完成基础工具循环，但需要项目自行注入 Skill；`create_deep_agent` 可直接使用官方 Skills Middleware，并与自主评测的 Harness 管理方式保持一致。自定义 LangGraph 不采用，因为当前没有官方循环无法表达的特殊节点语义。

目标 Harness 必须：

- 生产入口实际调用 `create_deep_agent(...)`，而不是直接 `model.ainvoke()` 后手写工具循环。
- 通过官方 Skills Middleware 读取 `monitoring-analysis` 和 `answer-writing` Skill。
- 通过 `context_schema` 和 `ToolRuntime` 注入租户、用户、角色、范围和工具注册表，不将这些可信字段暴露为模型工具参数。
- 使用官方模型调用上限、工具调用上限和重试 Middleware；项目 Runtime 只保留取消、单工具超时、权限复核和轨迹收集。
- 通过受限 Harness Profile 和 Permissions 禁用 Todo、文件写入、Shell、Subagents 和长期 Memory，只允许读取 Skill 和调用五类监控查询工具。
- 模型返回结构化分析和回答；程序仍根据实际工具事实计算结论，模型不能覆盖 `normal`、`warning`、`abnormal` 或 `unknown` 门禁。

## 意图定义

分析意图统一使用以下编码：

| 意图编码 | 中文名称 | 示例 | 默认工具 |
| --- | --- | --- | --- |
| `platform_health` | 平台健康 | 昨天平台运行正常吗 | 健康、告警、指标、事件、任务 |
| `incident_cause` | 异常原因 | 为什么触发告警 | 告警、指标、事件、任务 |
| `impact_scope` | 影响范围 | 影响了哪些资源 | 告警、事件、任务 |
| `evidence_review` | 证据查看 | 有哪些直接证据 | 告警、指标、事件 |
| `next_action` | 检查建议 | 下一步检查什么 | 告警、指标、事件、任务 |
| `task_diagnosis` | 任务诊断 | 昨天哪些任务失败了 | 任务、事件、Trace |
| `period_review` | 时段回顾 | 昨天发生了什么 | 健康、告警、指标、事件、任务 |
| `identity` | 身份介绍 | 你是谁 | 不调用事实工具 |

未命中专用意图的问题按 `period_review` 处理，但不得变成脱离监控数据的通用聊天。

## 语义规划

分析计划、工具选择、中间观察和终止由 `create_deep_agent` 的官方模型—工具循环完成。用户问题保持自由文本，Agent 根据两个官方加载的 Skill 与已取得事实决定是否继续查询。最终 Structured Output 包含 `intent`、`goal`、`time_expression`、`entities`、`dimensions`、`uncertainties`、`confidence`、回答及引用；实际工具列表和时间窗口从 ToolRuntime Session 记录获取，不信任模型自报值。

面向客户的默认语言为中文。Agent 生成的目标、时间标签和不确定项等自然语言字段必须使用中文；最终回答、身份介绍、限制说明、检查建议、智能体名称和页面提示必须使用中文。接口字段、稳定枚举、工具名称、资源编码和时区编码可以保留英文，但不得直接拼接到面向客户的回答中；确需展示的行业缩写或产品专名应同时提供中文解释。

最终回答使用中文 Markdown，不返回连续堆叠的长段落。模型只能依据程序已经确定的结论、授权事实、时间范围和判断边界组织表达，不得新增事实或改变结论。版式根据问题和证据动态选择，可使用标题、引用结论、重点强调、项目列表、编号步骤和紧凑表格，不强制每次输出相同章节；内容较少时不得为了排版堆叠空章节。模型生成失败、超时、内容越界或格式校验失败时，回退到确定性的轻量分析报告。

回答编排采用独立结构化合同，字段包括 `answer_markdown`、`conclusion_ack`、`evidence_refs`、`fact_refs` 和 `layout_reason`。结构化字段只用于验证结论、证据引用和排版决策，不限制 Markdown 的章节名称、数量和顺序。`answer_markdown` 由模型自由组织；`conclusion_ack` 必须与程序结论编码一致；`evidence_refs` 只能引用本轮授权事实；`fact_refs` 记录回答使用的关键事实；`layout_reason` 仅用于调试、审计和评测，不展示给客户。

回答校验不得要求模型逐字复述固定结论句。校验重点为结论编码一致、证据引用合法、中文表达、中国标准时间、内部编码保护和内容长度。首次输出存在结构、格式或轻微校验问题时，在同一总超时预算内携带错误原因执行一次自动修复；修复仍失败或模型不可用时才进入降级回答。降级回答也必须依据事实形态动态选择排版：多维数据使用表格，原因定位使用证据链或编号步骤，信息较少使用简短引用结论，数据不足使用覆盖情况和待确认项，不再统一套用四段式。

面向客户的所有时间文案统一标注“中国标准时间”，包括回答正文、会话标题下方的实际查询范围和时间相关提示。内部计算及接口元数据仍使用稳定时区编码 `Asia/Shanghai`，该编码只用于程序解析，不直接展示给客户。

规划结果进入执行前必须完成以下确定性校验：

- 未知意图归一为 `general_analysis`，不因缺少新意图编码拒绝用户问题。
- 工具只能从自主监控只读白名单选择，未知工具直接剔除并记录限制。
- 模型给出的时间必须包含时区、起点早于终点且跨度不超过允许范围；校验失败时使用本地时间解析器重新解析。
- 租户、用户、角色和授权资源范围不属于模型输出字段，只接受 Service 注入的可信上下文。
- 非身份问题没有合法工具时，根据粗粒度意图补齐安全默认工具，不能执行空计划后编造结论。

LLM 未配置且 Agent 无法启动时，Service 返回结构化不可用结果。Agent 已取得监控事实后，如果外部模型在最终结构化收敛阶段超时、未返回结构化输出，或模型回答与确定性结论、证据引用、输出安全规则冲突，Harness 必须保留工具事实和调用轨迹，并用确定性规则生成受控降级回答；不得因最终模型响应失败丢弃已完成的真实查询结果。不再保留另一套关键词 Planner 生产主链。

## 时间解析

系统时区固定使用 `Asia/Shanghai` 解释业务自然日，查询 DB 前转换为带时区时间。解析规则如下：

- “昨天”解析为昨天 `00:00:00` 至今天 `00:00:00`，不是滚动 24 小时。
- “今天”解析为今天 `00:00:00` 至当前时间。
- “最近一小时、六小时、一天、七天”解析为截至当前时间的滚动窗口。
- `YYYY-MM-DD`、`YYYY年MM月DD日` 解析为对应自然日。
- 问题未指定时间时继承会话默认范围；默认范围仅作为兜底，不能覆盖问题中的显式时间。
- 解析后的 `window_start`、`window_end`、`timezone` 和 `time_range_label` 必须写入回答元数据。

时间范围属于服务端可信上下文。Service/Agent 在进入 Deep Agent 工具循环前使用同一个 UTC 瞬间转换为中国标准时间并解析问题，模型只能选择调用哪些事实工具，工具 Schema 不暴露 `window_start`、`window_end` 或 `time_label`，所有查询统一读取服务端绑定窗口。`utils.utc_now()` 继续用于数据库、审计、超时和持续时间计算；任何业务自然日、Prompt 当前日期或客户展示都必须先调用公共 `to_china_standard_time()` 显式转换，不得直接对 UTC 时间取日期或标注为中国标准时间。

上一轮事实只在问题包含“这些、刚才、前面、第 N 条”等明确指代表达时提供给模型。普通的“今天系统有异常吗”等新查询不得注入旧事实和旧时间范围，避免跨自然日锚定。

## 工具设计

监控 Agent 注册以下只读工具：

| 工具名称 | 查询内容 | 关键限制 |
| --- | --- | --- |
| `query_health_snapshots` | 服务、数据库、Worker、外部依赖状态快照 | 只返回授权范围和窗口内快照 |
| `query_alerts` | 触发、确认、已恢复、已关闭告警 | 不只查询未恢复告警 |
| `query_metrics` | 指标值、样本量、数据状态和考核状态 | 最多返回 Runtime 允许的上下文数量 |
| `query_events` | 异常、失败、降级和关联 Trace 事件 | 内容脱敏，不返回完整问答和密钥 |
| `query_tasks` | 索引、评测及其他已采集任务运行事实 | 只读，不提供重试或修改工具 |

每次工具调用记录名称、开始时间、结果数量、状态和耗时，不记录完整问题、答案、Token、API Key 或未脱敏载荷。问题参数不得覆盖认证上下文中的租户、用户和权限范围。

告警与指标事实的客户可见名称必须来自指标定义表的 `metric_name`。`metric_code` 只用于内部关联、查询、审计和脱敏日志，不得直接进入 Agent 回答、告警列表、详情、总览证据或规则展示；中文业务名称缺失时统一显示“未配置中文名称”，不得回退显示内部编码。该转换在事实工具和 Service 数据组装层完成，不能依赖模型自行翻译。新生成的指标告警直接以“指标异常：{中文指标名称}”持久化；历史英文标题在读取时按当前有效指标定义转换。

## 判定规则

健康结论由确定性规则生成，自然语言模型或模板只能负责表达，不能修改事实状态：

| 结论 | 判定规则 |
| --- | --- |
| `abnormal` | 存在严重未恢复告警，或核心状态失败，或核心指标考核失败 |
| `warning` | 存在警告、降级、过期状态，存在已恢复异常，或非核心指标预警 |
| `normal` | 数据完整，核心状态和指标均正常，且无窗口内异常告警 |
| `unknown` | 关键来源无数据、数据过期、样本不足或工具查询失败，无法形成可靠判断 |

数据完整性优先于状态判断。不得将空数据、采集失败、样本不足或仅无未恢复告警显示为正常。

## 回答协议

分析消息结果包含：

```json
{
  "intent": "platform_health",
  "answer": "根据指定时间范围内的授权监控数据……",
  "conclusion": "warning",
  "data_status": "complete",
  "time_range": {
    "start": "2026-07-31T00:00:00+08:00",
    "end": "2026-08-01T00:00:00+08:00",
    "timezone": "Asia/Shanghai",
    "label": "昨天"
  },
  "scope": {"type": "platform", "name": "全平台"},
  "evidence": [],
  "limitations": [],
  "tool_calls": [],
  "status": "completed",
  "agent": "自主监控Agent"
}
```

Service 将除完整工具内部结果外的结构化字段写入助手消息 `metadata`。前端继续使用消息正文展示回答，右栏展示证据，并可从元数据恢复本轮实际时间范围和结论。

### 事实驱动

监控问法不再依赖持续扩张的固定意图枚举覆盖。“告警分别是什么”“这几条具体是什么”“把刚才那条展开”等表达由以下通用机制处理：

- 每个只读工具在 Registry 中同时声明事实类型和安全展示协议，包括标题、允许展示字段、中文列名及值转换规则。
- Deep Agent 使用开放式 `requested_view` 保留用户希望看到的结果形态，并使用真实 `fact_refs` 引用事实；固定 `intent` 仅用于审计、统计和历史兼容，不作为明细渲染的唯一开关。
- Runtime 在模型终态缺失、超时或供应商异常时，根据已取得的单类事实和工具展示协议生成明细表，不需要为每一种自然语言问法增加关键词分支。
- 每轮结果生成带稳定 ID 的 `fact_set`。Service 只从同一授权会话的服务端助手消息读取上一轮事实，客户端不能覆盖；追问中的通用指代表达用于选择该事实集合。
- 多类事实的综合健康分析继续使用确定性综合报告，避免把健康判断退化为原始数据罗列。
- 模型超时、供应商异常和结构化终态缺失只记录在 `planning`、`answering` 和 Runtime 日志中；已取得业务事实可以回答时，不把这些内部故障写入面向用户的判断边界。

## 异常处理

- 时间无法解析：继承会话默认范围，并在 `limitations` 中说明。
- 单个工具失败：保留其他工具事实，结论降为 `unknown` 或 `warning`，记录失败工具。
- 全部工具失败：返回“分析暂不可用”，不删除原始告警或历史消息。
- 数据为空：返回证据不足和实际查询范围，不返回“运行正常”。
- 超出预算：停止后续工具调用，使用已取得事实生成受限结论。
- 越权参数：拒绝调用并记录失败审计，不执行降级越权查询。

## 前端配合

分析对话保持三栏布局和自适应高度。消息区展示 Agent 回答；标题范围优先展示最近一轮消息解析出的时间标签，未发送问题时展示会话默认范围；参考资料仅展示本轮返回证据。输入区保持多行问题、Enter 发送、Shift+Enter 换行和发送加载状态。

## 验收标准

- “昨天平台运行正常吗”查询昨天自然日，不使用会话默认最近一小时覆盖显式时间。
- 回答同时检查健康、告警、指标、事件和任务，能够区分正常、预警、异常和无法判断。
- 已恢复告警纳入时间窗口事实；没有未恢复告警不直接推导为正常。
- 回答展示实际时间范围、关键事实和限制，每条引用均来自本轮授权工具结果。
- 工具调用经过注册、权限、范围、预算和超时校验，并留下结构化日志与消息元数据。
- Agent 不创建告警、不修改配置、不重试任务、不执行处置。

历史上曾将确定性规划器调整为降级路径，并以 LLM Structured Output Planner 作为主路径。该实现仍由 Python 代码按计划顺序执行工具，已在 2026年08月08日的 Deep Agent 改造中删除。

真实模型联调已验证“昨晚平台是不是抖了一下”“发布之后服务稳不稳”“用户反馈很慢，系统侧有异常吗”三种非固定表达，均返回 `planning.mode=llm`，并生成不同的分析目标、时间、维度、歧义和只读工具计划。发布问题因缺少发布时间保留歧义并继承会话范围，没有伪造发布时间。

### Harness 整改补充

2026年08月08日，监控分析链完成受限版 `create_deep_agent` Harness 改造。健康、告警、指标、事件和任务五类查询实现位于 `app/agents/monitoring/tools/queries.py`，模型工具适配位于 `app/agents/monitoring/tools/analysis.py`；`monitoring_analysis_tools.py` 仅保留兼容导出。官方 Middleware 负责 Skills、模型/工具调用上限和重试，Monitoring Runtime 负责项目特有的取消、单工具超时、查询预算、权限复核和结构化轨迹。最终结论由程序根据实际事实计算，并通过 Monitoring Schema 后再交给 Service。详细验证见 [`三个 Agent Harness 整改实施记录`](../三个Agent%20Harness整改实施记录.md)。

同日补充事实驱动回答协议：`presentation.py` 统一管理工具事实展示、事实集合和模型失败时的确定性明细渲染；`AnalysisPlan` 增加开放式结果视图和事实引用；分析 Service 持久化并按授权会话恢复上一轮事实。针对“4条都是什么样子的告警”的故障注入验证表明，即使外部模型在取得 4 条告警后超时，回答仍逐条展示名称、级别、状态、资源类型、当前值和触发时间，且不向用户暴露模型超时文案。

2026年08月09日修复跨 UTC 日期边界的“今天”解析：原实现将 UTC ISO 时间与“中国标准时间”说明同时提供给模型，并允许模型填写工具窗口，导致北京时间已进入 8 月 9 日时仍可能查询 8 月 8 日。整改后服务端预先绑定中国标准时间窗口，工具不再接受模型时间参数；无指代的新问题不再注入上一轮事实。自动化模拟 UTC `2026-08-08 23:30`、中国标准时间 `2026-08-09 07:30`，确认窗口为 8 月 9 日自然日；真实数据库与真实模型复测得到同一结果。
