# 自主监控数据采集方案

## 1. 文档说明

本文档定义自主监控模块的数据采集、标准化、聚合、告警判断和监控智能体分析方案，作为自主监控需求设计、接口设计、数据表设计、Agent Harness 和后续实施的配套文档。

本文档只定义采集方案和职责边界，不直接实现具体 API、数据库表、Worker 或监控 Agent。数据库 DDL 仍统一维护在 `scripts/db/data_table_ddl.sql`，监控智能体仍必须独立放在 `app/agents/monitoring/` 下。

## 2. 方案目标

1. 记录问答、评测、文档处理、API 和 Worker 的可验证运行事实。
2. 通过统一事件协议形成问答错误率、响应耗时、任务积压和评测执行证明等监控指标。
3. 通过确定性规则生成、去重、恢复和关闭告警。
4. 由监控智能体关联告警证据、分析影响范围并生成处理建议。
5. 保证采集失败不影响问答、文档处理和评测主流程。
6. 保证租户边界、敏感内容脱敏、事件幂等和监控数据可追溯。

## 3. 非目标

- 不把监控智能体作为每次请求的同步调用方。
- 不仅依赖自然语言日志或模型判断生成告警。
- 不在采集层自动修改 Prompt、模型、索引、评测配置或业务任务。
- 不把监控探针结果混入真实用户问答、租户用量和自主评测统计。
- 不在本方案中引入通用 APM、日志平台或主机监控平台。

## 4. 总体架构

```text
问答智能体 / 评测智能体 / 文档处理链路 / API / Worker
                  │
        结构化事件、状态快照、指标、健康探针
                  ↓
            监控采集与标准化
                  ↓
              去重、聚合、校验
                  ↓
              监控规则判断
                  ↓
                告警实例
                  ↓
       监控智能体关联分析和生成建议
                  ↓
             告警展示、通知、审计
```

采集方案采用三种方式组合：

| 采集方式 | 适用范围 | 主要特点 |
| --- | --- | --- |
| `monitor_gather` 装饰器采集 | 问答、评测、文档处理和索引目标方法 | 通过目标登记和配置表达业务阶段 |
| 通用中间件采集 | API、数据库访问、Worker 公共循环 | 覆盖通用运行事实，不依赖业务方法逐一登记 |
| 周期状态采集 | 服务、依赖、队列、任务积压和容量 | 获取当前状态，不依赖业务请求发生 |

## 5. 采集目标关联机制：`monitor_gather`

### 5.1 设计定位

`monitor_gather` 是监控数据采集装饰器，用于将稳定的业务方法登记为可采集目标。它只负责目标方法关联和采集入口注册，不在装饰器中写死具体事件、字段或告警逻辑。

示例：

```python
@monitor_gather("knowledge.qa")
async def run_knowledge_agent(task, context):
    ...
```

装饰器登记目标编码和目标方法路径；应用启动时只完成静态目标注册，不调用模型、不直接写入监控事件，也不加载采集配置。采集配置统一保存在数据库中，由目标方法调用时根据 `target_code` 动态查询。

### 5.2 配置驱动采集

数据库是采集配置的唯一事实来源，不使用配置文件保存采集规则，也不在应用进程中长期缓存完整采集配置。采集包装器每次执行时根据目标编码查询当前有效配置；本次调用使用查询到的配置快照，调用结束后释放，不写入长期内存缓存。

采集配置至少包括：

| 配置项 | 说明 |
| --- | --- |
| `target_code` | 与 `monitor_gather` 对应的目标编码 |
| `enabled` | 是否启用采集 |
| `hook` | `before`、`after`、`around` 或 `exception` |
| `collector` | 预置采集器名称，不允许执行任意代码 |
| `events` | 允许采集的事件列表 |
| `input_mapping` | 从方法入参提取租户、知识库、任务等字段 |
| `output_mapping` | 从返回结果提取耗时、命中数、引用数等字段 |
| `exception_mapping` | 从异常提取错误分类和失败阶段 |
| `sampling` | 全量、比例、按租户或按错误采集策略 |
| `config_version` | 配置版本，用于审计和结果追溯 |

`collector` 只能从预置采集器注册表中选择；字段映射只能使用受控字段路径和转换规则，配置不能执行任意 Python 模块、函数、表达式或脚本。

采集配置由独立的监控配置表维护，Repository 按 `target_code`、启用状态和生效版本查询当前配置。`target_code` 应建立索引；配置新增、修改、停用、版本递增由系统发布和运维流程完成，并保留版本审计，不通过自主监控页面向业务用户开放。目标方法调用只读取当前目标所需的一份配置，不加载全部监控配置。

### 5.3 运行流程

```text
应用启动
  ↓
monitor_gather 登记目标方法
  ↓
根据 target_code 查询数据库中的有效采集配置
  ↓
校验配置并创建本次调用的采集上下文
  ↓
业务调用目标方法
  ├─ before：采集开始事件
  ├─ after：采集成功结果
  ├─ exception：采集异常结果
  └─ around：统一包裹完整调用生命周期
  ↓
统一事件协议、指标聚合和告警规则
```

系统发布或运维流程变更配置后，后端在事务中保存数据库配置和配置版本；后续目标方法调用自动读取新配置，不需要刷新配置文件或重启应用。自主监控页面只读展示目标运行状态、采集结果和异常证据，配置版本仅用于后端审计和结果追溯，不在目标明细列表或目标详情中展示。页面不提供用户修改、启停或立即执行采集的入口。数据库查询失败、目标没有配置或配置校验失败时，默认跳过本次采集并记录采集器自身错误，不得阻断业务方法执行。

### 5.4 装饰器、采集器与中间件边界

- `monitor_gather`：登记目标方法，不承载具体采集业务。
- `MonitorGatherRegistry`：保存目标编码、方法路径和当前包装状态。
- `MonitorGatherConfig`：从数据库查询、校验和生成当前调用的采集配置快照，不承担长期缓存。
- 预置 Collector：按目标类型提取结构化字段，例如问答、评测和索引采集器。
- 统一事件写入层：执行脱敏、租户校验、幂等和持久化。
- FastAPI 中间件、数据库访问层和 Worker 公共循环：对通用能力进行自动采集，不要求每个方法添加装饰器。

装饰器只在稳定业务入口增加一次轻量目标标记，不在业务方法内部重复编写事件采集代码。无法修改源码的外部依赖使用中间件、适配器或周期探针采集，不使用任意运行时代码注入。

### 5.5 通用中间件采集示例

通用中间件采集覆盖 API、数据库访问和 Worker 生命周期，不要求每个业务方法重复添加采集代码。以下代码为方案示意，实际实现必须复用统一事件写入层，并确保采集失败不影响主流程。

#### 5.5.1 FastAPI 请求中间件

所有 HTTP 请求经过统一中间件，采集接口路径、状态码、耗时和 Trace ID：

```python
@app.middleware("http")
async def monitor_http_request(request: Request, call_next):
    trace_id = request.headers.get("X-Trace-Id") or create_trace_id()
    started_at = time.perf_counter()

    try:
        response = await call_next(request)
        await emit_monitor_event(
            target_code="api.http",
            event_type="http_request_completed",
            payload={
                "method": request.method,
                "path": request.url.path,
                "status_code": response.status_code,
                "duration_ms": elapsed_ms(started_at),
                "trace_id": trace_id,
            },
        )
        response.headers["X-Trace-Id"] = trace_id
        return response
    except Exception as exc:
        await emit_monitor_event(
            target_code="api.http",
            event_type="http_request_failed",
            payload={
                "method": request.method,
                "path": request.url.path,
                "error_code": type(exc).__name__,
                "trace_id": trace_id,
            },
        )
        raise
```

对应数据库配置：

```text
target_code: api.http
collector: http_request_collector
events: http_request_completed, http_request_failed
```

请求体、密码、Token、完整问题和完整答案不得写入事件。

#### 5.5.2 数据库访问层采集

统一数据库访问封装可以在 SQL 执行入口采集操作类型、耗时、结果和脱敏 SQL 摘要：

```python
async def execute_sql(operation, query, params=None):
    started_at = time.perf_counter()
    try:
        result = await database.execute(query, params)
        await emit_monitor_event(
            target_code="db.execute",
            event_type="db_operation_completed",
            payload={
                "operation": operation,
                "duration_ms": elapsed_ms(started_at),
                "result": "success",
                "query_summary": summarize_sql(query),
            },
        )
        return result
    except Exception as exc:
        await emit_monitor_event(
            target_code="db.execute",
            event_type="db_operation_failed",
            payload={
                "operation": operation,
                "duration_ms": elapsed_ms(started_at),
                "result": "failed",
                "error_code": type(exc).__name__,
                "query_summary": summarize_sql(query),
            },
        )
        raise
```

对应配置：

```text
target_code: db.execute
collector: sql_operation_collector
events: db_operation_completed, db_operation_failed
slow_threshold_ms: 500
```

`query_summary` 只能保存 SQL 类型、表名或脱敏模板，不能保存完整参数。监控事件写入数据库时必须排除监控事件表，避免监控写入再次触发数据库采集形成递归。

#### 5.5.3 Worker 生命周期采集

Worker 公共循环统一采集启动、停止、心跳、空闲、领取任务和异常，不要求每个任务实现自己的心跳逻辑：

```python
async def run_worker(worker_name, poll_interval, process_task):
    await emit_monitor_event(
        target_code="worker.lifecycle",
        event_type="worker_started",
        payload={"worker_name": worker_name},
    )
    try:
        while True:
            await emit_monitor_event(
                target_code="worker.lifecycle",
                event_type="worker_heartbeat",
                payload={"worker_name": worker_name},
            )
            task = await claim_next_task(worker_name)
            if task is None:
                await emit_monitor_event(
                    target_code="worker.lifecycle",
                    event_type="worker_idle",
                    payload={"worker_name": worker_name},
                )
                await asyncio.sleep(poll_interval)
                continue
            await emit_monitor_event(
                target_code="worker.lifecycle",
                event_type="worker_task_claimed",
                payload={"worker_name": worker_name, "task_id": task["id"]},
            )
            await process_task(task)
    except asyncio.CancelledError:
        await emit_monitor_event(
            target_code="worker.lifecycle",
            event_type="worker_stopped",
            payload={"worker_name": worker_name},
        )
        raise
    except Exception as exc:
        await emit_monitor_event(
            target_code="worker.lifecycle",
            event_type="worker_failed",
            payload={
                "worker_name": worker_name,
                "error_code": type(exc).__name__,
            },
        )
        raise
```

对应配置：

```text
target_code: worker.lifecycle
collector: worker_lifecycle_collector
events: worker_started, worker_heartbeat, worker_idle, worker_task_claimed, worker_stopped, worker_failed
heartbeat_interval_seconds: 30
```

`worker_idle` 是正常状态，不能单独触发告警；只有心跳过期、Worker 停止或消费异常时才进入异常判断。

#### 5.5.4 三类采集方式统一出口

```text
业务 Agent 方法       ── @monitor_gather("knowledge.qa")
FastAPI               ── HTTP Middleware -> api.http
数据库统一访问层       ── DB Adapter -> db.execute
Worker 公共循环        ── Worker Adapter -> worker.lifecycle
```

以上目标最终都写入统一监控事件协议，使用相同的数据库配置查询、字段脱敏、租户校验、幂等处理、指标聚合和告警规则。

## 6. 数据采集边界

### 6.1 配置驱动的目标方法采集

目标方法通过 `monitor_gather` 登记后，由配置决定采集时机、事件类型、预置采集器和字段映射。采集器只生成结构化事件，不接收完整问题、答案、文档片段或任意自然语言日志。

#### 6.1.1 问答智能体事件

问答智能体至少采集以下事件：

| 事件 | 中文含义 | 触发时机 | 终态 | 说明 |
| --- | --- | --- | --- | --- |
| `qa_started` | 问答开始 | 系统接受请求并开始执行时 | 否 | 一次问答运行记录一次；重试通过 `attempt` 区分 |
| `qa_retrieval_completed` | 知识库检索完成 | Retriever 返回结果后 | 否 | 仅表示检索结束，命中数可以为 0 |
| `qa_model_completed` | 模型调用完成 | LLM 返回结果后 | 否 | 后续仍需进行结构化输出和引用校验 |
| `qa_completed` | 问答完成 | 最终答案和引用校验通过后 | 是 | 表示本次问答正常完成 |
| `qa_degraded` | 问答降级 | 使用备用回答、部分能力缺失或结果质量受限时 | 否 | 通常与 `qa_completed` 同时出现，是补充状态 |
| `qa_timeout` | 问答超时 | 超过总超时或关键阶段超时时 | 是 | 无法按正常路径完成；必须记录超时阶段 |
| `qa_failed` | 问答失败 | 非超时异常且无法返回有效结果时 | 是 | 例如检索失败、模型失败、权限拒绝或输出校验失败 |

正常流程示例：

```text
qa_started -> qa_retrieval_completed -> qa_model_completed -> qa_completed
```

降级流程示例：

```text
qa_started -> qa_retrieval_completed -> qa_model_completed
            -> qa_degraded -> qa_completed
```

`qa_completed`、`qa_timeout`、`qa_failed` 是互斥的最终结果；`qa_degraded` 不是最终结果，不能单独作为成功或失败统计。关键字段包括租户、知识库、Trace ID、索引版本、模型版本、配置版本、总耗时、检索耗时、模型耗时、命中数、引用数、终止原因、降级原因和错误分类。

#### 6.1.2 自主评测智能体与 Worker 事件

自主评测智能体与评测 Worker 至少采集以下事件：

| 事件 | 中文含义 | 触发时机 | 终态 | 说明 |
| --- | --- | --- | --- | --- |
| `evaluation_task_claimed` | 评测任务已领取 | Worker 成功领取待执行任务时 | 否 | 记录 Worker 实例和领取时间 |
| `evaluation_run_started` | 评测运行开始 | 运行状态进入 `running` 且开始执行时 | 否 | 不能只依赖数据库状态变化 |
| `evaluation_config_validated` | 评测配置校验完成 | 数据集、知识库、模型和评测规则校验完成时 | 否 | 失败时记录配置错误分类 |
| `evaluation_questions_ready` | 评测问题准备完成 | 问题加载或自主生成完成时 | 否 | 记录问题数量和来源，不记录问题正文 |
| `evaluation_case_started` | 单题评测开始 | 开始执行某一道评测题时 | 否 | 记录题目序号或脱敏 Case ID |
| `evaluation_case_retry` | 单题评测重试 | 单题失败并进入重试时 | 否 | 记录尝试次数和错误分类 |
| `evaluation_case_completed` | 单题评测完成 | 单题问答和指标所需结果采集完成时 | 否 | 记录状态、耗时、命中数和引用数 |
| `evaluation_metrics_completed` | 评测指标计算完成 | 全部有效题目指标计算完成时 | 否 | 记录指标摘要和有效样本数 |
| `evaluation_report_persisted` | 评测报告持久化完成 | 报告成功写入数据库或存储后 | 否 | 证明报告已可查询 |
| `evaluation_run_completed` | 评测运行完成 | 评测完整结束且结果成功保存时 | 是 | 可进一步区分质量通过或不通过 |
| `evaluation_run_failed` | 评测运行失败 | 无法继续执行且未被取消或超时时 | 是 | 记录失败阶段和错误分类 |
| `evaluation_run_timeout` | 评测运行超时 | 超过配置的评测运行时限时 | 是 | 记录超时阶段和已完成题数 |
| `evaluation_run_cancelled` | 评测运行取消 | 用户或平台明确取消运行时 | 是 | 记录操作者或取消来源 |

这些事件必须能够证明评测 Agent 确实执行过，不能只记录评测运行表从 `pending` 变为 `completed`。`evaluation_run_completed`、`evaluation_run_failed`、`evaluation_run_timeout` 和 `evaluation_run_cancelled` 互斥；单题事件不能替代运行级终态事件。

#### 6.1.3 文档处理与索引链路事件

文档处理与索引链路不是独立 Agent，只作为被监控的 Service、任务和 Worker 链路采集以下事件：

| 事件 | 中文含义 | 触发时机 | 终态 | 说明 |
| --- | --- | --- | --- | --- |
| `document_ingestion_started` | 文档入库开始 | 文档处理任务开始执行时 | 否 | 记录文档和入库任务 ID |
| `document_ingestion_completed` | 文档入库完成 | 文档内容和基础元数据成功入库时 | 是 | 不等同于索引完成 |
| `document_ingestion_failed` | 文档入库失败 | 入库处理无法完成时 | 是 | 记录失败阶段和错误分类 |
| `indexing_task_claimed` | 索引任务已领取 | Worker 成功领取索引任务时 | 否 | 记录 Worker 实例 |
| `indexing_started` | 索引构建开始 | 开始切分、Embedding 或向量写入时 | 否 | 记录索引版本 |
| `indexing_completed` | 索引构建完成 | 索引数据成功写入并可用时 | 是 | 记录索引版本和处理耗时 |
| `indexing_failed` | 索引构建失败 | 索引处理无法完成时 | 是 | 记录失败阶段和错误分类 |
| `indexing_timeout` | 索引构建超时 | 超过索引任务时限时 | 是 | 记录超时阶段和已处理数量 |

至少记录文档 ID、知识库 ID、任务 ID、索引版本、Worker 实例、处理耗时、失败分类和最终状态；不记录完整文档内容。

#### 6.1.4 事件状态约束

- 采集包装器只能记录实际发生的事件，不允许为了满足流程伪造完成事件。
- 一个运行或任务只能有一个最终终态；重试必须保留尝试次数和原始失败原因。
- 事件记录失败不能反向导致问答、评测或索引主流程失败。
- 事件名称、状态、错误分类和版本字段使用公共字典或结构化 Schema，禁止各业务模块自行创造同义事件名。

### 6.2 通用中间件采集

通用采集应优先放在已有公共层，不在每个业务函数重复实现：

- FastAPI 中间件记录请求路径、方法、状态码、耗时、Trace ID 和脱敏错误分类。
- 统一数据库访问封装记录 SQL 操作类型、耗时、执行结果和参数脱敏摘要。
- Worker 公共循环记录启动、停止、心跳、领取任务、空闲和未捕获异常。
- 统一任务状态更新入口记录状态变化，避免每个 Worker 自己拼接状态日志。

### 6.3 周期状态采集

监控采集器按固定周期读取或探测 API、数据库、模型、Embedding、Rerank、向量库、存储、Worker、任务积压和容量状态。采集结果必须包含采集时间、数据来源、数据范围和采集状态。采集失败返回 `error` 或 `stale`，不能转换成健康或零值。

## 7. 统一事件协议

### 7.1 事件字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `event_id` | 是 | 事件唯一 ID，用于幂等去重 |
| `event_type` | 是 | 事件类型 |
| `source_type` | 是 | `api`、`knowledge_agent`、`evaluation_agent`、`worker`、`document_index` 等 |
| `source_id` | 否 | 来源实例或业务资源 ID |
| `tenant_id` | 条件必填 | 租户业务事件必须携带，平台事件需明确平台范围 |
| `kb_id` | 否 | 关联知识库 ID |
| `task_id` / `run_id` | 否 | 异步任务或 Agent 运行 ID |
| `trace_id` | 否 | 关联调用链 ID |
| `status` | 是 | 事件对应状态 |
| `occurred_at` | 是 | 事件发生时间，UTC 存储 |
| `duration_ms` | 否 | 阶段或任务耗时 |
| `error_code` | 否 | 脱敏错误分类 |
| `version_context` | 否 | 索引、模型、配置和规则版本摘要 |
| `payload_summary` | 否 | 仅允许脱敏后的结构化摘要 |

事件不得记录密码、Token、API Key、完整用户问题、完整答案、文档片段和其他敏感请求体。

### 7.2 事件示例

```json
{
  "event_id": "qa-20260729-000001",
  "event_type": "qa_completed",
  "source_type": "knowledge_agent",
  "tenant_id": 12,
  "kb_id": 35,
  "trace_id": "trace-abc-123",
  "status": "completed",
  "occurred_at": "2026-07-29T10:01:22Z",
  "duration_ms": 1840,
  "payload_summary": {
    "hit_count": 5,
    "citation_count": 3,
    "degraded": false
  }
}
```

该事件只能说明一次问答事实，不直接表示告警。

## 8. 事件写入可靠性

- 监控事件写入失败不能导致问答、文档处理或评测任务失败。
- 涉及业务状态和监控事件同时写入时，Service 可以在同一事务中写入；纯运行阶段事件可以独立写入。
- 相同 `event_id` 重复上报只保留一次，指标聚合必须基于去重后的事件。
- Worker 重启不能重复制造任务完成事件。
- 采集器自身必须记录最近成功采集时间、最近失败时间、失败次数和当前状态。

## 9. 指标聚合

事件经过去重后，按时间窗口、租户、知识库、任务类型、资源和版本上下文聚合。

问答指标示例：

```text
最近 5 分钟：请求 120 次，失败 8 次，错误率 6.67%，P95 3200ms，引用返回率 91%
```

评测指标示例：

```text
运行中 2 个，已完成题目 180 个，失败 6 个，平均单题耗时 2100ms，执行证据完整率 100%
```

每个聚合结果必须保存统计时间、窗口、数据范围、样本量、计算状态和更新时间。无样本、采集失败、部分采集、数据过期和样本不足必须分别标记，不得统一显示为 0 或健康。

## 10. 告警规则与监控智能体边界

规则引擎负责确定性判断：触发阈值、最小样本数、连续周期、恢复条件、去重和告警生命周期。例如：

```text
问答错误率 > 10%
且样本数 >= 30
且连续 3 个统计周期满足
=> 触发严重告警
```

监控智能体负责读取已触发告警及其证据，执行跨来源关联、影响分析、异常摘要和人工建议。监控智能体不替代规则引擎，也不自动修改或重试业务任务。

告警实例至少保存：

```text
alert_id
rule_id
severity
scope
resource
first_fired_at
last_fired_at
current_value
threshold
status
evidence_event_ids
resolved_at
acknowledged_by
```

每条告警必须可以关联指标窗口、事件 ID、任务、评测运行、Worker、索引版本或 Trace ID。相同规则、相同范围和相同资源在未恢复前只能保留一个告警实例，重复触发只更新次数和最近发生时间。

## 11. 主动探针

主动探针用于验证 API、模型、向量库和问答链路是否真实可用。问答探针必须使用专用监控租户、专用知识库和固定测试问题，并使用 `purpose=monitor_probe` 标识。

探针不得创建普通用户会话、写入聊天历史、计入业务问答量、租户用量、自主评测统计或质量报表。探针必须有独立的频率、并发、超时和资源预算；探针失败只说明探针范围异常，不能直接推断所有租户或所有知识库不可用。

## 12. 实施顺序

1. 定义事件类型、错误分类、来源类型和版本上下文字典。
2. 建立 `monitor_gather` 装饰器、目标注册表和预置采集器协议。
3. 建立数据库采集配置、按 `target_code` 动态查询、版本校验和审计机制。
4. 建立统一事件记录协议和事件幂等校验。
5. 在问答 Agent、评测 Worker、文档索引 Worker 和 API/DB 公共层接入目标适配器。
6. 实现事件查询、时间窗口聚合和数据状态返回。
7. 实现告警规则、告警去重、恢复和证据关联。
8. 接入主动探针和监控智能体的告警分析。
9. 完成权限、脱敏、故障注入和监控自身异常验收。

## 13. 验收标准

- 一次问答能够产生可追踪的开始、完成或失败事件。
- 一次评测能够证明 Worker、Agent、逐题执行、指标计算和报告持久化过程。
- 文档处理与索引链路可以被监控，但不被误识别为独立 Agent。
- 事件重复上报不重复计数，业务主流程不因监控写入失败而失败。
- 事件可以聚合为按租户、知识库和时间窗口统计的指标。
- 规则可以根据最小样本数和连续周期触发、去重和恢复告警。
- 告警能够关联原始事件、指标窗口、任务和 Trace ID。
- 监控智能体只分析告警证据，不直接替代规则或修改业务数据。
- 无数据、采集失败、数据过期和样本不足均能独立表达。
