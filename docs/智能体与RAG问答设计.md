# 智能体与 RAG 问答设计

## 1. 设计结论

当前聊天系统应当考虑引入 Agent，但 Agent 定位为后端内部固定的“知识库问答智能体”，不是面向用户的“创建智能体”业务。

聊天接口仍然保持现有调用方式，所有问答请求统一进入 Knowledge Agent。Knowledge Agent 负责问题分析、检索工具编排和答案生成，不保留独立的 RAG Chain，也不在简单问题和复杂问题之间维护两套问答入口。

推荐架构：

```text
Chat API
   ↓
Chat Service
   ↓
Knowledge Agent
   ├── 问题分析与执行策略选择
   ├── 调用授权知识检索工具
   ├── 必要时进入多步工具流程
   ├── 基于工具结果调用模型生成答案
   ├── 会话历史读取
   ├── 多步检索与结果整理
   └── 答案和引用输出
```

## 2. Agent 和普通 RAG 的区别

### 2.1 传统 RAG 问答流程

传统 RAG 的流程相对固定，作为对比概念保留，不作为本系统的目标实现：

```text
用户问题
  ↓
问题向量化
  ↓
召回知识库分块
  ↓
组装 Prompt
  ↓
调用模型生成答案
```

它适合单次、明确、只需要知识库上下文的问题。

### 2.2 Agent 问答

Agent 不只是生成答案，而是由模型根据目标自主选择下一步动作：

```text
用户问题
  ↓
Agent 分析任务
  ↓
选择工具或直接回答
  ↓
执行工具
  ↓
判断结果是否足够
  ├── 不足：继续调用工具
  └── 足够：组织最终答案
```

Agent 的核心是“决策和编排”，RAG 只是 Agent 可以调用的一种工具。

### 2.3 对比矩阵

| 对比项 | 传统 RAG 问答流程 | Knowledge Agent |
|---|---|---|
| 执行流程 | 固定流程 | 动态规划和工具调用 |
| 检索次数 | 通常一次 | 可以多次检索 |
| 工具选择 | 不具备自主选择能力 | 根据问题选择工具 |
| 简单问题 | 稳定、快速 | 可能产生额外开销 |
| 复杂问题 | 需要业务代码提前编排 | 可以拆分任务逐步处理 |
| 可控性 | 高 | 需要限制工具和最大步数 |
| 延迟 | 较低 | 通常更高 |
| 成本 | 较低 | 可能多次调用模型 |
| 调试难度 | 较低 | 需要记录决策和工具轨迹 |
| 权限风险 | 较容易控制 | 每个工具都必须单独鉴权 |
| 适合场景 | 单知识库事实问答 | 多步检索、复杂分析和任务编排 |

## 3. 当前系统现状

当前聊天流程位于（其中 `app/rag/chains.py` 是待迁移和移除的过渡实现）：

- `app/core/services/chat.py`
- `app/rag/chains.py`（目标方案不再保留）

当前流程是：

```text
问题校验
  ↓
会话创建或复用
  ↓
保存用户问题
  ↓
知识库检索与 `generate_answer()`（现有过渡实现）
  ↓
保存助手回答
  ↓
保存引用
```

目标实现将“知识库检索”和答案生成统一纳入 Knowledge Agent；迁移完成后删除 `app/rag/chains.py`，由 Agent 调用检索工具并直接生成最终答案。

当前实现的优点：

- 流程简单，容易维护。
- 回答严格依赖知识库上下文。
- 引用生成路径明确。
- 延迟和模型调用次数容易控制。
- 权限边界容易在检索前置处理。

当前实现的不足：

- 所有问题都使用相同的检索和回答流程。
- 不支持根据问题类型动态选择工具。
- 复杂问题通常只能依赖一次检索结果。
- 多知识库、多数据源和多步骤分析需要继续增加固定分支。
- 会话历史、检索策略和回答步骤之间缺少统一编排层。

## 4. 为什么需要考虑 Agent

以下问题适合由 Agent 编排：

- “比较两个文档中关于报销标准的差异。”
- “先查找制度，再根据制度判断这个场景是否符合要求。”
- “结合当前会话上下文，继续分析上一条回答。”
- “从多个知识库检索资料后合并回答。”
- “先判断用户问题属于制度、技术还是流程，再选择对应知识库。”

这些问题不是单次检索和一次生成能够稳定覆盖的，通常需要：

1. 分析用户问题。
2. 选择一个或多个检索工具。
3. 根据检索结果判断是否需要继续查询。
4. 合并多个结果。
5. 生成带引用的最终答案。

## 5. 推荐的内部 Knowledge Agent

### 5.1 定位

Knowledge Agent 是系统内部固定的知识库问答智能体：

- 不允许用户创建或配置任意 Agent。
- 不新增智能体管理菜单。
- 不新增智能体创建、编辑、删除接口。
- 不改变当前 Chat API 的请求和响应协议。
- 只在后端内部负责问题分析、工具选择和答案编排。

### 5.2 工具边界

第一阶段只允许 Agent 使用受控工具：

| 工具 | 作用 |
|---|---|
| `retrieve_knowledge` | 检索当前用户有权限访问的知识库 |
| `load_conversation_history` | 读取当前会话历史 |
| `build_citations` | 根据检索结果整理文档引用 |

最终答案由 Knowledge Agent 统一基于授权检索结果、会话上下文和工具返回结果生成，不再封装为独立的 `generate_answer` Chain 或工具。

暂时禁止 Agent 使用以下能力：

- 任意 SQL 查询。
- 任意 HTTP 请求。
- 任意文件系统访问。
- 修改知识库配置。
- 删除或修改文档。
- 创建用户、租户或智能体。
- 跨租户检索。
- 调用未经登记和鉴权的外部工具。

### 5.3 工具权限

每个工具都必须在执行前进行权限和数据范围校验：

```text
Agent 选择工具
  ↓
工具权限校验
  ↓
当前租户和组织范围校验
  ↓
知识库访问权限校验
  ↓
执行工具
```

不能因为工具调用发生在 Agent 内部，就跳过用户权限验证。

## 6. 推荐的执行策略

所有问题都必须经过 Knowledge Agent，Chat Service 不暴露两个问答入口。Knowledge Agent 只在内部选择检索次数、检索策略和工具调用顺序，不选择 RAG Chain：

```text
用户问题
  ↓
Knowledge Agent
  └── 简单或复杂问题 → 调用检索工具，必要时启动工具循环
                         ↓
                    Agent 生成最终答案
```

Agent 可以根据问题复杂度决定检索策略。简单问题可以包括：

- 只涉及一个明确主题。
- 不要求比较、汇总或多步推理。
- 一次检索结果能够覆盖问题，但仍通过统一检索工具和 Agent 生成流程处理。
- 不需要读取多轮历史。

复杂问题可以交给 Agent：

- 比较多个文档。
- 汇总多个主题。
- 需要多次检索。
- 需要利用会话历史补足上下文。
- 需要选择不同检索策略。

## 7. 事务边界调整

当前聊天流程把模型调用放在数据库事务内部：

```text
开启事务
  ↓
保存用户问题
  ↓
检索和调用模型
  ↓
保存回答和引用
  ↓
提交事务
```

引入 Agent 后，模型可能多次调用工具和模型，不应长时间占用数据库事务。建议调整为：

```text
事务一：保存用户问题
  ↓
Agent 执行检索、推理和工具调用
  ↓
事务二：保存助手回答和引用
```

事务要求：

- 用户消息保存失败时，不启动 Agent。
- Agent 失败时，记录失败状态或错误信息，不产生不完整回答。
- 助手回答、引用和检索摘要必须在同一个最终事务中写入。
- Agent 不应该持有数据库事务连接执行模型调用。

## 8. 输出协议

对外仍然保持当前聊天响应结构：

```json
{
  "conversation_id": 1001,
  "message_id": 2001,
  "answer": "回答内容",
  "citations": [],
  "retrieval": {
    "top_k": 5,
    "hit_count": 3,
    "mode": "agent"
  }
}
```

内部可以额外记录：

- Agent 执行模式。
- 工具调用名称。
- 工具调用次数。
- 每次检索命中数量。
- 最终停止原因。
- 执行耗时。
- 模型调用次数。

内部轨迹不能直接把敏感 Prompt、Token、完整内部上下文返回给前端。

## 9. 失败和安全控制

Agent 必须设置：

- 最大工具调用次数。
- 最大推理轮数。
- 单次工具超时时间。
- 总体执行超时时间。
- 最大上下文长度。
- 工具白名单。

异常处理建议：

| 场景 | 处理方式 |
|---|---|
| 检索无结果 | 明确回答资料不足，不编造事实 |
| 工具权限不足 | 终止当前工具调用，返回无权限结果 |
| 工具超时 | 记录失败并返回可解释错误 |
| 达到最大步数 | 停止 Agent，返回当前可验证结果 |
| 模型输出为空 | 返回统一模型错误 |
| 引用生成失败 | 整体回答事务回滚或标记失败 |

## 10. 实施路线

详细的阶段目标、交付物和验收标准见第 12.8 节。本路线的前置约束是：不新增用户可配置的 Agent 业务，不保留独立 RAG Chain，所有问答统一通过 Knowledge Agent 完成。

## 11. 最终结论

当前系统不需要增加“创建智能体”业务，但后端聊天能力应当预留并逐步接入内部 Knowledge Agent。

推荐最终形态：

```text
Chat API
  ↓
Chat Service
  ↓
Knowledge Agent
  └── 简单或复杂问题 → 选择检索策略并调用受控工具
                         ├── 授权检索
                         ├── 会话历史
                         ├── 多步推理
                         ├── 引用整理
                         └── Agent 生成答案
```

这样可以保留 RAG 的检索能力，同时由统一的 Knowledge Agent 覆盖简单问答、复杂问答、多步检索和未来工具编排，不维护独立的 RAG Chain。

##### 12.1.1.2 与当前轻量结构的关系

该参考结构将运行上下文、状态、预算、Harness 测试和 Skill 附属资源都显式拆出，适合 Agent 工具数量增加、执行时间变长、需要回放和持续评测的阶段。当前轻量结构则把这些职责暂时合并到 `agent.py`、`runtime.py`、`policies.py`、`tests/agents/` 和简单的 Skill 文件中。

评审时需要重点决定：

1. 是否需要现在就拆分 `context.py`、`state.py` 和 `budgets.py`。
2. 是否需要标准化 Skill 的 `references/`、`scripts/` 和 `assets/` 子目录。
3. 是否需要独立的 `tests/harness/` 和 `tests/evals/`。
4. 是否需要通过 `scripts/checks/` 对目录边界和依赖方向进行机械检查。
5. 是否需要为 Agent 运行状态、事件和回放建立持久化能力。

最终落地方案不在本节预先确定，以评审结论为准。

### 12.2 目录和文件职责

#### 12.2.1 项目与 Agent 规范

| 文件 | 职责 |
|---|---|
| `AGENTS.md` | 项目级工程约束、调用方向、数据库和前后端边界。 |
| `app/agents/AGENTS.md` | Agent 子工程专属约束：运行循环、工具白名单、技能加载、权限校验、预算、输出和敏感信息处理。 |
| `docs/agent/` | Agent 的工具说明、技能说明、运行协议和评测记录等设计文档。 |

`app/agents/AGENTS.md` 不替代根目录规则。发生冲突时，根目录规则优先；未冲突的 Agent 专属要求由子目录内文件补充。Agent 代码、工具和技能变更前，应先检查这两个文件。

#### 12.2.2 API 与业务编排

| 文件 | 职责 |
|---|---|
| `app/api/v1/chat.py` | 解析聊天请求、获取认证上下文、调用 Chat Service、转换响应和异常；不实现 Agent Loop，不直接访问 DB、RAG 或 LLM。 |
| `app/core/services/chat.py` | 校验会话、租户、知识库和用户权限，管理用户消息与助手消息的事务边界，调用 Agent，并保存最终结果。 |
| `app/schemas/agent.py` | 定义 Agent 输入、运行上下文、工具调用结果、最终答案、引用和运行摘要等 Pydantic 协议。 |

调用方向保持为：

```text
API → Chat Service → Agent → Tools → RAG / DB
```

#### 12.2.3 `app/agents/`

| 文件或目录 | 职责 |
|---|---|
| `agent.py` | Agent 主入口。所有聊天请求的统一处理入口；接收结构化任务和上下文，选择检索策略并调用工具，最后生成结构化答案。 |
| `runtime.py` | 执行循环、超时、最大步数、停止、失败收敛和必要的重试控制。 |
| `policies.py` | 工具白名单、操作权限、租户和知识库范围、输入输出约束、预算和敏感数据策略。 |
| `tools/registry.py` | 显式注册工具并按策略暴露工具；未注册工具不能被 Agent 调用。 |
| `tools/retrieval.py` | 在当前用户授权范围内调用知识库检索能力，只读。 |
| `tools/history.py` | 读取当前会话允许访问的历史消息，只读。 |
| `tools/citations.py` | 根据实际检索结果整理、去重和校验引用，只读。 |
| `skills/query-analysis/SKILL.md` | 指导问题分类、检索意图识别和是否需要多步处理。它是执行指导，不是权限边界。 |
| `skills/answer-writing/SKILL.md` | 指导基于检索事实组织答案、处理资料不足和输出引用。它不能覆盖安全策略。 |

第一阶段只开放 `retrieval`、`history`、`citations` 三个只读工具，不注册修改知识库、文档、角色或权限的写操作工具。

#### 12.2.4 `app/rag/`

保留 RAG 的检索能力，包括 Loader、Splitter、Embedding 和 Retriever；不再保留 `chains.py` 或其他独立 RAG Chain。RAG 只负责文档处理、向量化和检索，不负责答案生成，也不负责用户权限决策；权限和知识库范围由 Chat Service 与 Agent Policy 在调用工具前确定。

#### 12.2.5 测试、脚本与配置

| 目录或文件 | 职责 |
|---|---|
| `tests/agents/` | 覆盖 Agent 入口、运行循环、工具注册、权限策略、超时、步数限制、引用校验和异常收敛。 |
| `scripts/` | 存放 Agent 调试、回放、评测和数据检查脚本；脚本不能绕过正式权限策略。 |
| `.env.example` | 记录模型、超时、步数和工具配置的变量名与示例值，不包含密钥。 |

评测初期可直接放在 `tests/agents/` 或 `scripts/` 中；当评测数据和评分器达到独立维护规模时，再拆出专门的 `evals/` 目录。

#### 12.2.6 当前不单独拆分的能力

以下能力仍然必须设计，但暂时合并到轻量结构中：

- 输入、工具参数、答案和引用校验：先由 `runtime.py` 与 `policies.py` 负责。
- 状态、预算和错误模型：先由 `runtime.py`、`policies.py` 和 `schemas/agent.py` 负责。
- Prompt 和回答规则：先放在 Agent 实现或 `skills/*/SKILL.md` 的可审查约束中。
- Trace 和运行审计：先输出结构化日志；只有确认需要持久化、查询和恢复时再增加独立模块或表。
- 评测：先使用 `tests/agents/` 和 `scripts/`，不在 `app/agents/` 下创建 `evals/`。

因此，旧方案中的 `contracts`、`prompts`、`guardrails`、`tracing`、`evals`、`agent_run.py` 和 `agent_event.py` 不属于本次推荐目录，也不应作为当前实施前置项。

### 12.3 Agent Harness 运行流程

```text
1. API 解析请求并获取认证上下文
2. Chat Service 校验用户、租户、知识库和会话
3. 保存用户消息
4. 创建本次 Agent 运行上下文
5. 初始化 Policy、预算和运行状态
6. Knowledge Agent 分析问题并确定检索策略
7. 如需工具调用，由 Agent 选择白名单工具
8. 校验工具权限、参数和数据范围
9. 执行工具并记录事件
10. 判断继续、重试或生成答案
11. 校验答案格式和引用完整性
12. 在最终事务中保存助手消息、引用和运行结果
13. 返回当前聊天响应协议
```

### 12.4 事务边界

模型调用和 Agent 工具调用不能长期占用数据库事务。

推荐使用两个事务：

```text
事务一：保存用户问题
  ↓
Agent Harness 执行模型调用和工具调用
  ↓
事务二：保存助手回答、引用和执行摘要
```

要求：

- 用户消息保存失败时不启动 Agent。
- Agent 失败时记录结构化错误，不保存不完整助手回答。
- 助手回答和引用必须在同一事务中提交。
- Agent 不持有数据库连接执行模型调用。
- Agent 运行状态先保存在本次运行上下文中；如果未来增加持久化，再要求状态更新幂等，避免重试产生重复消息或重复引用。

### 12.5 权限和安全边界

Agent 不能绕过普通业务权限：

```text
选择工具
  ↓
require_action()
  ↓
校验租户和组织范围
  ↓
校验知识库访问权限
  ↓
执行工具
```

安全控制至少包括：

- 工具白名单。
- 操作权限验证。
- 当前租户和组织范围验证。
- 知识库授权验证。
- 最大工具调用次数。
- 最大 Agent 步数。
- 最大执行时间。
- 单工具超时和重试次数。
- 最大上下文长度。
- 输出和引用校验。
- 敏感数据脱敏和 Trace 清理。

第一阶段只开放只读工具，不开放任何会修改业务数据的 Agent 工具。

### 12.6 输出协议

对外继续兼容现有聊天响应：

```json
{
  "conversation_id": 1001,
  "message_id": 2001,
  "answer": "回答内容",
  "citations": [],
  "retrieval": {
    "top_k": 5,
    "hit_count": 3,
    "mode": "agent"
  }
}
```

内部运行结果建议包含：

- `run_id`。
- `mode`：`chain` 或 `agent`。
- `status`：`created`、`running`、`completed`、`failed`、`stopped`。
- `tool_call_count`。
- `model_call_count`。
- `termination_reason`。
- `citation_count`。
- `duration_ms`。

内部执行轨迹不直接返回给前端，必要时通过受控的调试或审计接口查看。

### 12.7 测试和评测目录

#### 12.7.1 单元测试

测试 Harness 的确定性行为：

- 预算是否正确限制步数。
- 未注册工具是否被拒绝。
- 缺少权限是否无法调用工具。
- 工具参数错误是否提前失败。
- Agent 状态转换是否符合状态机。
- 引用不在检索结果中时是否拒绝输出。

#### 12.7.2 合同测试

验证工具和模型适配器遵守输入输出 Schema：

- 工具输入字段完整。
- 工具输出结构稳定。
- 模型结构化输出可以被解析。
- 异常可以转换成统一错误类型。

#### 12.7.3 场景评测

评测集至少包括：

- 单文档事实查询。
- 多文档比较。
- 多轮上下文追问。
- 检索无结果。
- 用户无知识库权限。
- 跨租户越权请求。
- 模型生成无引用结论。
- 工具超时和模型失败。

核心指标：

- 答案正确率。
- 引用准确率。
- 引用覆盖率。
- 越权拦截率。
- 平均延迟和 P95 延迟。
- 平均模型调用次数。
- 平均 Token 成本。
- Agent 异常终止率。

### 12.8 分阶段实施计划

#### 阶段一：建立 Harness 契约

目标：先固定 Agent 与 Chat Service、工具、模型之间的协议和安全边界，不改变对外 Chat API。

实施内容：

- 定义 `app/schemas/agent.py`：Agent 输入、运行上下文、用户/租户范围、工具请求、工具结果、答案、引用、运行摘要和统一错误模型。
- 定义运行状态：`created`、`running`、`completed`、`failed`、`stopped`，明确每个状态的进入条件和不可逆转换。
- 定义工具协议：工具名称、版本、输入 Schema、输出 Schema、超时、是否只读和所需权限；未注册工具不得执行。
- 在 `app/agents/tools/registry.py` 建立显式注册表，第一阶段只登记 `retrieve_knowledge`、`load_conversation_history`、`build_citations`。
- 在 `runtime.py` 定义最大步数、最大工具调用次数、单工具超时、总体超时、上下文长度和停止原因。
- 在 `policies.py` 定义租户、组织、知识库和会话范围校验，以及敏感字段不得进入前端响应和普通日志的规则。
- 将现有 `generate_answer()` 的 Prompt、模型适配和输出校验拆分为 Agent 的答案生成步骤；不再以独立 RAG Chain 形式保留。

交付物：

- `app/schemas/agent.py` 协议模型。
- Agent 状态、停止原因、错误码和预算配置说明。
- 工具注册表及每个只读工具的输入输出定义。
- Agent 子目录的 `AGENTS.md` 和最小单元测试。

验收标准：

- Chat Service 可以构造完整、可校验的 Agent 输入。
- 未注册工具、越权范围和超预算请求能够在执行前被拒绝。
- 答案和引用可以通过 Schema 校验。
- 代码和文档中不再设计 `direct_chain` 等独立 Chain 执行模式；内部策略只允许使用统一入口下的单次检索或多步工具流程，也不新增 RAG Chain。

阶段边界：本阶段只建立契约和确定性校验，不接入真实 Agent Loop，不新增 Agent 运行数据库表。

#### 阶段二：接入只读 Knowledge Agent

目标：将现有聊天流程接入统一 Knowledge Agent，并完成一次可用的只读问答闭环。

实施内容：

- 在 `app/agents/agent.py` 建立统一入口，由 Chat Service 传入认证上下文、会话上下文和问题。
- 将 Loader、Splitter、Embedding、Retriever 等 RAG 能力封装为 `retrieve_knowledge` 工具；RAG 层只返回结构化检索结果，不生成最终答案。
- 将会话历史读取封装为 `load_conversation_history`，只允许读取当前租户、当前用户可访问的会话。
- 将引用去重、来源字段校验和检索结果到引用的映射封装为 `build_citations`。
- 在工具执行前完成权限、租户、组织、知识库和会话范围校验；工具内部不得依赖前端传入的可信用户标识。
- 调整 Chat Service 事务边界：事务一保存用户消息，Agent 执行模型和工具调用，事务二保存助手消息、引用和运行摘要。
- 保持现有 Chat API 请求和响应结构不变；失败时返回统一错误，不使用演示数据或本地伪造答案兜底。

交付物：

- Knowledge Agent 主入口和只读工具实现。
- Chat Service 与 Agent 的联调实现。
- 真实检索、会话历史、引用返回的集成测试。
- 工具权限、跨租户访问、无权限知识库和无检索结果测试用例。

验收标准：

- 一次普通问答必须经过 Knowledge Agent。
- 回答内容只能使用 Agent 获取的授权上下文，引用必须来自实际检索结果。
- Agent 执行期间不持有数据库事务连接。
- 无权限、跨租户、工具超时和模型异常均能收敛为明确错误状态。
- `app/rag/chains.py` 不再被 Chat Service 或 Agent 引用；迁移完成后删除该文件。

阶段边界：只开放检索、历史和引用三个只读工具，不开放写操作、任意 SQL、任意 HTTP 或文件系统工具。

#### 阶段三：完善 Knowledge Agent 内部执行策略

目标：在统一入口下支持单次检索和多步检索两种内部策略，但不拆分为两个对外问答接口。

实施内容：

- 建立问题分析步骤，识别单主题事实查询、多文档比较、多轮追问、多知识库检索和资料不足等场景。
- 对简单问题采用“问题分析 → 一次授权检索 → 答案生成 → 引用校验”的单次检索策略。
- 对复杂问题采用“问题分析 → 工具调用 → 结果判断 → 继续检索或生成答案”的多步工具流程。
- 明确 Agent 继续调用工具的条件：结果为空、证据不足、需要比较多个来源或用户问题包含多个独立子任务。
- 明确 Agent 停止条件：证据足够、达到最大步数、达到总体超时、工具连续失败或无法满足权限范围。
- 增加结构化答案约束：资料不足时明确说明，禁止无依据补全；每个引用必须能回溯到检索结果。
- 增加重试规则，只允许对幂等只读工具进行有限重试，并区分工具失败、模型失败和权限失败。
- 记录执行模式、工具调用次数、检索命中数、模型调用次数、停止原因、延迟和 Token 使用量。

交付物：

- Agent Loop、停止条件、重试策略和预算控制实现。
- 单次检索与多步工具流程的场景测试。
- 结构化运行日志和脱敏后的工具调用轨迹。
- 答案 grounding、引用完整性和异常收敛测试。

验收标准：

- 简单问题不会因为策略选择而进入不必要的多步循环。
- 复杂问题可以在预算范围内完成多次检索和结果合并。
- 达到步数、时间或上下文预算时能够稳定停止，并返回可解释结果。
- 任意工具调用都经过统一权限策略，Agent 不能通过多步调用扩大数据范围。
- 日志可以定位一次运行的关键决策，但不泄露 Token、完整 Prompt、敏感上下文或未授权文档内容。

阶段边界：本阶段只优化只读检索和答案生成，不增加写操作工具，不建立用户可配置的 Agent。

#### 阶段四：评测、观测和优化

目标：用可重复的评测和运行数据决定单次检索、多步检索及后续扩展的适用范围。

实施内容：

- 建立脱敏评测集，覆盖单文档事实查询、多文档比较、多轮追问、跨知识库检索、无结果、无权限、跨租户、超时和模型失败。
- 为每个样例维护问题、授权范围、期望结论、必需引用、禁止引用和预期停止原因。
- 分别评测单次检索和多步工具流程，不再与 RAG Chain 做目标方案对比。
- 建立答案正确率、引用准确率、引用覆盖率、越权拦截率、平均/P95 延迟、模型调用次数、Token 成本和异常终止率指标。
- 增加结构测试，检查调用方向、工具白名单、事务边界、Schema 校验和 RAG 层不生成答案等架构不变量。
- 先以结构化日志记录运行轨迹；只有在确有查询、恢复和审计需求时，才增加 Agent Run 和事件持久化。
- 根据评测结果调整问题分类规则、检索参数、上下文拼接、预算和停止策略，并记录每次调整的原因和指标变化。

交付物：

- 版本化评测集、评分规则和评测脚本。
- 质量、权限、延迟和成本指标报告。
- Agent 运行日志查询和脱敏审计方案。
- 上线前问题清单、回归结果和参数调整记录。

验收标准：

- 评测结果可重复，能够区分答案质量问题、检索问题、权限问题和 Agent 编排问题。
- 所有越权样例均被拦截，引用错误和无依据结论能够被发现。
- 性能和成本指标达到评审确定的阈值；未达到时明确限制适用场景，而不是通过伪造数据兜底。
- 每次策略变更都有回归评测结果，且不会破坏现有 Chat API 协议。

阶段边界：本阶段只做只读 Agent 的质量和运行优化，不以评测结果为由自动开放新工具或修改业务数据。

#### 阶段五：谨慎扩展工具

目标：在只读 Agent 稳定后，评估是否需要引入写操作或外部系统工具；本阶段默认不实施写操作。

实施内容：

- 逐个梳理候选工具的业务目的、调用人、资源范围、权限、审批、幂等键、事务边界、失败补偿和审计字段。
- 为每个候选工具单独定义输入确认、权限校验、敏感操作拦截、超时、重试和回滚策略。
- 将写操作与只读检索工具分开注册、分开授权和分开评测，禁止通过扩大现有白名单直接开放。
- 对涉及知识库、文档、角色或权限的操作，先由普通 Service 完成业务校验和事务处理，Agent 只负责提出结构化操作意图。
- 增加人工确认或审批节点；未获得明确确认时，Agent 只能返回待确认结果，不得执行写操作。
- 先在隔离环境和有限租户范围灰度，验证幂等、审计、回滚和异常恢复后再评审扩大范围。

交付物：

- 候选工具评估表和安全评审记录。
- 工具权限、审批、幂等、审计和回滚设计。
- 隔离环境测试报告和灰度方案。
- 是否开放该工具的明确决策记录。

验收标准：

- 每个写工具都有明确的授权主体、资源范围、审批方式和失败处理方式。
- 重试不会造成重复写入，异常时可以恢复或人工介入。
- 所有写操作都能审计到用户、租户、Agent Run、工具版本和最终结果。
- 未通过安全和业务评审的工具仍不可注册、不可调用。

阶段边界：阶段五不是默认的功能开发承诺；没有明确业务需求和评审结论时，系统保持只读 Knowledge Agent。

### 12.9 评审重点

1. 是否确认 Knowledge Agent 是后端内部固定能力，而不是用户创建的业务资源。
2. 是否确认所有问答请求统一进入 Knowledge Agent，由 Agent 统一负责答案生成，并根据问题决定单次检索或多步工具流程。
3. 是否确认第一阶段只开放只读工具。
4. 是否确认每个工具执行前必须进行操作权限和数据范围校验。
5. 是否确认 Agent 调用期间不持有数据库事务。
6. 是否确认答案必须经过 Schema 和引用完整性校验。
7. 是否确认 Trace、评测和预算属于 Harness 的必需组成部分。
8. 是否确认先完成 Harness 契约，再逐步接入 Agent Loop。
