# 数据库表结构设计

## 1. 设计目标

本文定义知识库问答系统第一阶段的关系数据库表结构，用于支撑：

- 平台用户、平台角色、租户成员和租户角色。
- 组织层级、组织成员和组织角色。
- 知识库管理。
- 文档上传、解析、索引状态跟踪。
- 文本分块和引用信息保存。
- 问答会话与消息记录。
- 检索结果引用落库。
- 入库任务、评测反馈和审计追踪。

本文同时定义平台用户、租户、组织与知识库之间的逻辑关联和权限边界。

本文面向 PostgreSQL 16 + pgvector 设计，字段类型、JSON、全文检索和向量索引均以 PostgreSQL 能力为准；具体字段以 `scripts/db/data_table_ddl.sql` 为准。

## 2. 命名约定

- 表名使用小写蛇形命名，并统一增加 `t_` 前缀。
- 每张表必须包含一个名为 `id` 的自增主键，禁止使用其他名称替代表主键。
- 主键字段统一命名为 `id`。`id` 不是 PostgreSQL 保留关键字，不需要改成 `t_id`；表名前缀已经通过 `t_` 体现业务表命名空间。
- 主键统一使用 PostgreSQL 自增序列，字段类型为 `bigint`，主键列使用 `generated by default as identity`。
- 各表的 `xxx_id` 字段只表示逻辑关联，不创建实际外键约束，由 Service / DB Repository 层保证引用关系、租户边界和删除策略。
- 时间字段统一使用 `created_at`、`updated_at`，删除场景优先使用软删除状态。
- 枚举字段使用短字符串，枚举值由代码常量统一维护。
- 大文本、元数据、请求摘要使用 `text` 或 `jsonb`。
- DDL 统一维护在 `scripts/db/data_table_ddl.sql`。

### 2.1 主键类型说明

本文主键统一采用 PostgreSQL 自增序列：

```sql
id bigint generated by default as identity primary key
```

选择原因：

- `bigint` 主键索引更小，写入和关联查询性能更稳定。
- PostgreSQL 原生 identity 列比业务侧字符串 ID 更简单，DDL 和迁移语义清晰。
- 当前阶段服务以单 PostgreSQL 为中心，不需要跨库提前生成全局 ID。
- 表之间的逻辑关联字段统一使用 `bigint`，减少类型转换和索引膨胀。

约束：

- 不在 ID 中携带业务语义，业务排障依赖表名、日志、审计和唯一业务字段。
- 如果未来需要分布式 ID、跨库写入或离线预生成 ID，再评估切换为 `uuid` 或业务字符串 ID。

## 4. 表结构

### 4.1 `t_knowledge_base`

知识库主表，保存知识库基础信息和默认检索参数。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK, generated by default as identity | 知识库 ID |
| `name` | varchar(255) | not null | 知识库名称 |
| `description` | varchar(500) | not null, default '' | 描述 |
| `tenant_id` | bigint | not null, logical reference + composite FK | 所属租户 ID |
| `created_by` | bigint | not null, logical reference | 创建用户 ID |
| `owner_id` | varchar(128) | not null | 所有者用户 ID |
| `visibility` | varchar(32) | not null | 可见范围：`private`、`team`、`public` |
| `embedding_model` | varchar(128) | not null | 默认 Embedding 模型 |
| `chunk_size` | integer | not null | 默认切片大小 |
| `chunk_overlap` | integer | not null | 默认切片重叠 |
| `retrieval_top_k` | integer | not null | 默认召回数量 |
| `system_prompt` | text | not null, default '' | 当前生效的系统提示词 |
| `system_prompt_version` | integer | not null, default 1 | 当前系统提示词版本 |
| `system_prompt_updated_at` | timestamptz | not null, default now() | 系统提示词更新时间 |
| `status` | varchar(32) | not null | 状态：`active`、`disabled`、`deleted` |
| `created_at` | timestamptz | not null, default now() | 创建时间 |
| `updated_at` | timestamptz | not null, default now() | 更新时间 |

建议索引：

- `idx_t_knowledge_base_tenant_id(tenant_id)`
- `idx_t_knowledge_base_owner_id(owner_id)`
- `idx_t_knowledge_base_status(status)`

### 4.2 `t_knowledge_base_organization`

知识库与授权组织的多对多关系表。用于记录哪些组织可以访问当前知识库；该关系不改变知识库的租户归属或组织归属。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK, generated by default as identity | 授权关系 ID |
| `kb_id` | bigint | not null, logical reference | 知识库 ID |
| `organization_id` | bigint | not null, logical reference | 被授权组织 ID |
| `created_by` | bigint | not null, logical reference | 授权操作人 ID |
| `created_at` | timestamptz | not null, default now() | 授权时间 |

约束和索引：

- `kb_id + organization_id` 唯一。
- `idx_t_knowledge_base_organization_kb_id(kb_id)`。
- `idx_t_knowledge_base_organization_org_id(organization_id)`。

### 4.3 `t_knowledge_base_prompt`

知识库系统提示词版本表，保存提示词历史版本，便于审计和回溯。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK, generated by default as identity | 提示词版本 ID |
| `kb_id` | bigint | not null, logical reference | 知识库 ID |
| `version` | integer | not null | 提示词版本号 |
| `system_prompt` | text | not null | 系统提示词内容 |
| `created_by` | varchar(128) | not null | 创建人 ID |
| `created_at` | timestamptz | not null, default now() | 创建时间 |

约束和索引：

- `kb_id + version` 唯一。
- `idx_t_knowledge_base_prompt_kb_version(kb_id, version)`。

### 4.4 `t_knowledge_base_user`

知识库与直接授权用户的多对多关系表。用户必须是知识库所属租户的有效成员，直接授权不改变用户的组织归属。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK, generated by default as identity | 授权关系 ID |

约束和索引：

- `kb_id + user_id` 唯一。
- `idx_t_knowledge_base_user_kb_id(kb_id)`。
- `idx_t_knowledge_base_user_user_id(user_id)`。

### 4.5 `t_document`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

| `kb_id` | bigint | not null, logical reference | 知识库 ID |

| `source_uri` | text |  | 原始 URL 或外部来源 URI |

| `file_size` | bigint | not null, default 0 | 文件大小 |
| `content_hash` | varchar(128) | not null | 文件或内容 hash |
| `parser` | varchar(128) |  | 使用的解析器 |
| `status` | varchar(32) | not null | `pending`、`processing`、`ready`、`failed`、`deleted` |

- `idx_t_document_created_by(created_by)`

### 4.6 `t_document_chunk`

文档分块表，保存用于检索、引用和上下文组装的文本片段。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK, generated by default as identity | 分块 ID |
| `kb_id` | bigint | not null, logical reference | 知识库 ID |
| `document_id` | bigint | not null, logical reference | 文档 ID |
| `parent_id` | bigint |  | Parent-Child Retriever 父块 ID |
| `chunk_index` | integer | not null | 文档内分块序号 |
| `content` | text | not null | 分块文本 |
| `content_hash` | varchar(128) | not null | 分块内容 hash |
| `source_name` | varchar(512) | not null | 来源名称 |
| `page` | integer |  | 页码 |
| `section` | varchar(512) |  | 章节标题 |
| `start_index` | integer |  | 原文起始位置 |
| `token_count` | integer |  | 估算 token 数 |
| `metadata` | jsonb | not null, default '{}'::jsonb | Loader 和 Splitter 元数据 |
| `embedding_model` | varchar(128) | not null | 向量模型 |
| `embedding` | vector |  | pgvector 向量，维度按模型确定 |
| `created_at` | timestamptz | not null, default now() | 创建时间 |

建议索引：

- `idx_t_document_chunk_kb_doc(kb_id, document_id)`
- `idx_t_document_chunk_kb_index(kb_id, chunk_index)`
- `idx_t_document_chunk_content_hash(content_hash)`
- `idx_t_document_chunk_metadata_gin(metadata)`，PostgreSQL 使用 GIN。
- 向量索引按实际模型维度创建，例如 HNSW 或 IVFFlat。

说明：

- 如果向量维度不固定，可以先不在关系表内存向量，改由独立向量库或按模型拆表。
- 如果使用 Parent-Child Retriever，子块用于召回，父块用于上下文，二者都可保存在本表，通过 `parent_id` 关联。

## 6. 约束和注意事项

- 不把 PDF、Word、图片等大文件直接存入数据库，只保存对象存储路径。
- 不在日志、审计、错误字段中保存 Token、密码、完整身份证号等敏感信息。
- 检索权限过滤必须在召回阶段前置，不能先全库召回再过滤。
- 文档删除优先软删除，同时异步删除对象存储和向量数据。
- `content_hash` 用于幂等入库和重复索引检测。
- JSON 字段只保存结构化元数据，不承载核心查询条件；高频查询条件应提升为独立字段。

## 8. 平台用户、租户与组织模型

### 8.1 角色分层

系统角色按作用范围分为三类：

| 角色类型 | 作用范围 | 存储位置 |
|---|---|---|
| 平台角色 | 整个平台 | `t_platform_role`、`t_platform_user_role` |
| 租户角色 | 单个租户 | `t_tenant_member.role_code` |
| 组织角色 | 单个组织 | `t_organization_member.role_code` |

平台角色、租户角色和组织角色不能混用。一个用户可以同时拥有平台角色、多个租户角色和多个组织角色，但每个角色都必须在对应作用域内判断。

当前角色编码：

- 平台角色：`p_super_admin`。
- 租户角色：`tenant_owner`、`tenant_admin`、`tenant_member`、`tenant_guest`。
- 组织角色：`org_admin`、`org_member`。

平台超级管理员约束：

- 全平台只能有一个有效的 `p_super_admin` 用户，不允许多个用户同时具备该角色。
- `p_super_admin` 拥有平台下所有数据和资源的查看权限，不受租户、组织或知识库授权范围限制。
- 平台超级管理员进入具体租户资源时，仍需设置当前目标 `tenant_id`，用于页面上下文、租户级操作和审计记录；这不改变其全平台查看范围。
- 唯一性由数据库部分唯一索引和 Service 层事务校验共同保证，前端只能提供交互提示，不能作为唯一保障。

职责边界：

- `tenant_owner` 管理当前租户配置、成员、组织、知识库和租户管理员，一个租户只能有一个有效所有者。
- `tenant_admin` 管理当前租户内的用户、组织和知识库日常业务，不得操作其他租户或平台配置。
- `tenant_member` 按授权使用当前租户的知识库、文档和问答能力。
- `tenant_guest` 只访问明确授权的知识库或问答功能，不参与文档、成员和配置管理。
- `org_admin` 管理当前组织成员、组织资料、成员角色和组织知识库授权，不得操作其他组织或租户配置。
- `org_member` 使用当前组织已授权的知识库、文档和问答能力。

## 9. 菜单、页面与操作权限表

当前权限模型采用“菜单项即页面”的设计，不再增加独立页面资源层。

### 9.1 页面访问

现有 `t_system_menu` 负责保存目录和页面菜单。`menu_type = 'item'` 的菜单项同时代表一个页面，`route_path` 保存页面路由。`t_role_menu` 保存角色与菜单页面的授权关系。

页面访问关系：

```text
角色 → t_role_menu → t_system_menu（页面）
```

### 9.2 页面操作

新增 `t_system_menu_action`，操作通过 `menu_id` 直接归属于页面菜单。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 操作主键 |
| `menu_id` | bigint | 所属页面菜单，逻辑关联 `t_system_menu.id` |
| `code` | varchar(128) | 全局唯一操作编码 |
| `name` | varchar(100) | 操作名称 |
| `action_type` | varchar(32) | `button` 或 `business` |
| `sort_order` | integer | 页面内操作排序 |
| `status` | varchar(32) | `active` 或 `disabled` |
| `meta` | jsonb | 操作扩展配置 |

### 9.3 角色操作授权

新增 `t_role_menu_action`，保存角色和页面操作的授权关系。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 授权关系主键 |
| `role_scope` | varchar(32) | `platform`、`tenant`、`organization` |
| `role_code` | varchar(64) | 角色编码 |
| `action_id` | bigint | 操作主键，逻辑关联 `t_system_menu_action.id` |
| `status` | varchar(32) | `active` 或 `disabled` |
| `created_at` | timestamptz | 创建时间 |
| `created_by` | bigint | 创建人 |
| `updated_at` | timestamptz | 更新时间 |

角色授权关系：

```text
角色 → t_role_menu → 页面
角色 → t_role_menu_action → 页面操作
```

授权 Service 必须保证：角色拥有页面的 `t_role_menu` 权限后，才能授予该页面下的操作权限。页面操作编码同时用于前端按钮控制和后端接口鉴权，例如 `knowledge_base:create`、`knowledge_base:delete`。

详细设计见《[菜单、页面与操作权限设计](菜单页面与操作权限设计.md)》。

## 10. 平台与知识库数据规则

- `p_super_admin` 写入 `t_platform_user_role`，不需要写入 `t_tenant_member` 才能操作平台资源。
- 平台超级管理员进入租户资源时必须明确目标 `tenant_id`。
- 普通租户管理员不能查询其他租户数据。
- `t_knowledge_base.tenant_id` 是知识库数据隔离的强制条件。
- `t_knowledge_base` 只维护租户归属，不维护直接组织归属。
- `t_knowledge_base_organization` 表示组织授权，`t_knowledge_base_user` 表示用户直接授权，二者任一满足即可获得访问资格。
- `created_by` 表示实际创建人，`owner_id` 表示当前知识库负责人。
- 文档、分片、会话、消息和引用通过 `kb_id` 继承知识库租户边界。
- 授权组织只控制组织成员访问知识库的范围，不改变知识库所属租户。
