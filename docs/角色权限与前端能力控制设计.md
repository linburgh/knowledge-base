# 角色权限与前端能力控制设计

## 1. 文档目的

本文档定义平台超级管理员、租户角色和组织角色在前端模块、页面入口、操作按钮及后端接口上的权限边界，作为前端页面设计、路由控制、接口设计和联调验收的统一依据。

权限控制遵循以下原则：

1. 角色决定可进入的模块。
2. 权限决定页面中的具体操作能力。
3. 数据范围决定用户可以看到和操作的数据。
4. 前端负责改善交互体验，后端负责最终权限校验。
5. 任何隐藏按钮都不能替代后端接口鉴权。

## 2. 角色范围

### 2.1 平台角色

| 角色 | 作用范围 |
| --- | --- |
| `p_super_admin` | 整个平台的全部租户、用户、组织、知识库和平台资源 |

平台超级管理员是平台级角色。整个平台只能存在一个有效的平台超级管理员，能够查看和管理平台下的全部数据与资源。

### 2.2 租户角色

| 角色 | 职责 |
| --- | --- |
| `tenant_admin` | 当前租户内用户、组织、知识库和自主评测的管理；角色只能由平台超级管理员分配 |
| `tenant_member` | 当前租户普通成员，按照已授予的知识库和组织权限开展查看、问答和协作 |
| `tenant_guest` | 当前租户受限访问成员，只能访问明确授权的知识库或问答功能 |

约束：

- 每个租户只能有一个有效的 `tenant_admin`，且只能由 `p_super_admin` 分配或调整。
- `tenant_admin` 具有平台管理目录及平台概览、用户管理、组织管理、自主评测四个子菜单的操作权限，不包含租户管理和开发者中心；数据操作范围限制在当前租户。
- `tenant_admin` 不能通过修改请求参数访问其他租户数据。
- `tenant_member` 和 `tenant_guest` 不能管理租户成员、组织结构或租户配置。

### 2.3 组织角色

| 角色 | 职责 |
| --- | --- |
| `org_admin` | 当前组织成员管理、组织资料维护、成员角色调整和组织知识库授权 |
| `org_member` | 使用当前组织已授权的知识库、文档和问答能力 |

约束：

- `org_admin` 只能管理自己负责的组织。
- `org_admin` 不能操作其他组织，也不能修改租户级配置。
- `org_admin` 不能改变租户组织层级，除非同时具备相应的租户管理权限。
- `org_member` 不能管理组织成员、组织层级和组织授权。

## 3. 模块访问矩阵

| 模块 | 平台超级管理员 | 租户管理员 | 组织管理员 | 租户成员 | 租户访客 |
| --- | --- | --- | --- | --- | --- | --- |
| 平台概览 | 全部 | 当前租户范围 | 不开放 | 不开放 | 不开放 |
| 平台用户管理 | 全部租户 | 当前租户 | 不开放 | 不开放 | 不开放 |
| 租户管理 | 全部租户 | 不开放 | 不开放 | 不开放 | 不开放 |
| 自主评测 | 全部评测 | 当前租户范围 | 不开放 | 不开放 | 不开放 |
| 开发者中心 | 全部 | 不开放 | 不开放 | 不开放 | 不开放 |
| 租户用户管理 | 全部租户 | 当前租户 | 不开放 | 不开放 | 不开放 |
| 组织管理 | 全部组织 | 当前租户 | 自己负责的组织 | 只读授权范围 | 不开放 |
| 知识库管理 | 全部知识库 | 当前租户 | 组织授权范围 | 授权范围 | 明确授权范围 |
| 文档管理 | 全部知识库 | 当前租户 | 按知识库授权范围 | 只读 | 只读或不开放 |
| 问答 | 全部知识库 | 当前租户 | 授权范围 | 授权范围 | 明确授权范围 |

其中“当前租户”必须取登录上下文中的当前租户，不允许由前端任意传入其他租户 ID 来扩大数据范围。

## 4. 页面与操作权限

### 4.1 租户管理

#### `p_super_admin`

- 查看全部租户。
- 新建、修改和删除租户。
- 管理租户成员。
- 设置租户管理员。
- 查看租户资源统计。

#### `tenant_admin`

- 平台管理目录及四个业务子菜单均可访问，不包含租户管理和开发者中心。
- 可管理当前租户用户、组织、自主评测和知识库数据。
- 不得通过请求参数访问其他租户数据。

### 4.2 组织管理

#### `tenant_admin`

- 当前租户下显示组织列表。
- 可按权限新建、修改和删除组织。
- 可管理组织成员。
- 可维护组织与知识库的授权关系。

#### `org_admin`

- 只显示自己负责的组织。
- 可维护组织资料。
- 可添加、移除和调整组织成员角色。
- 可管理本组织的知识库授权。
- 不显示跨组织操作入口。
- 不显示租户配置和租户级角色配置入口。

#### `org_member`

- 只能查看所属组织及授权资源。
- 隐藏新增、修改、删除、成员管理和授权按钮。

### 4.3 知识库管理

#### `tenant_admin`

- 新建、修改和删除当前租户知识库。
- 管理知识库用户授权和组织授权。
- 上传和删除知识库文档。

#### `org_admin`

- 不负责知识库生命周期管理。
- 只能管理本组织对知识库的授权。
- 是否允许上传文档，必须由知识库或租户业务权限另行授予，不能仅凭 `org_admin` 自动获得。

#### `tenant_member`

- 查看已授权知识库和文档。
- 发起问答和参与业务协作。
- 隐藏新建、修改、删除、授权和文档上传按钮。

#### `tenant_guest`

- 只能访问明确授权的知识库。
- 可使用被允许的问答功能。
- 隐藏文档上传、删除、知识库配置和授权功能。

## 5. 前端控制方案

### 5.1 统一权限上下文

前端应统一从 Pinia 用户上下文读取权限，不在各页面重复编写角色判断。建议提供 `usePermission` composable，统一暴露：

```ts
const {
  isPlatformSuperAdmin,
  isTenantOwner,
  isTenantAdmin,
  isOrgAdmin,
  can,
} = usePermission();
```

页面按钮使用操作权限控制：

```vue
<el-button v-if="can('knowledge_base:create')">
  新建知识库
</el-button>
```

不建议在模板中散落以下形式的判断：

```vue
<el-button v-if="user.role === 'tenant_admin'">...</el-button>
```

### 5.2 路由守卫

路由通过 `meta.permissions` 声明进入要求：

```ts
{
  path: "/knowledge-bases",
  meta: {
    permissions: ["knowledge_base:view"],
  },
}
```

路由守卫负责：

- 未登录用户跳转登录页。
- 无模块权限用户跳转到默认工作区。
- `tenant_guest` 禁止进入租户管理、组织管理和平台管理路由。
- 非平台超级管理员禁止进入平台级管理页面。
- 当前租户切换后重新计算路由和操作权限。

### 5.3 按钮与操作控制

按钮控制至少覆盖：

- 新建。
- 修改。
- 删除。
- 上传文档。
- 用户授权。
- 组织授权。
- 成员管理。
- 角色调整。
- 租户管理员配置。

无权限时优先隐藏按钮；对于用户可能通过其他入口触发的操作，还应在点击时再次校验并处理后端 `403` 响应。

Vue 3 页面统一使用自定义指令控制操作入口：

```vue
<el-button v-permission="'knowledge_base:create'">
  新增知识库
</el-button>
```

`v-permission` 只负责读取 Pinia 权限 Store 并控制按钮展示，不在页面中直接判断角色；后端接口仍必须通过 Service 层的 `@require_action()` 完成最终权限验证。多权限按钮使用显式 `codes` 和 `mode` 声明，避免不同页面自行定义判断规则。

## 6. 登录上下文要求

`/auth/me` 返回的数据应能够支持租户范围和组织范围判断，建议包含：

```json
{
  "platform_roles": [],
  "current_tenant": {},
  "tenant_role": "tenant_admin",
  "tenants": [
    {
      "id": 1,
      "role_code": "tenant_admin"
    }
  ],
  "organizations": [
    {
      "id": 10,
      "tenant_id": 1,
      "role_code": "org_admin"
    }
  ],
  "permissions": [
    "tenant:view",
    "organization:manage",
    "knowledge_base:create"
  ]
}
```

至少需要提供：

- 平台角色。
- 用户加入的租户及其租户角色。
- 当前选择的租户。
- 用户所属组织及其组织角色。
- 当前租户下的有效操作权限。

如果用户拥有多个租户，切换租户后必须重新获取或重新计算当前租户权限，不能沿用上一个租户的权限状态。

## 7. 后端接口兜底要求

前端权限控制只用于界面体验，后端必须对所有写操作和敏感查询再次鉴权。

后端必须校验：

- 用户是否具备目标模块权限。
- 用户是否属于当前租户数据范围。
- 用户是否属于目标组织数据范围。
- 用户是否拥有目标知识库访问权限。
- 用户是否可以执行文档上传、删除和授权操作。
- 租户角色调整是否合法。

典型规则：

| 接口操作 | 最低要求 |
| --- | --- |
| 新建租户 | `p_super_admin` |
| 查看全部租户 | `p_super_admin` |
| 管理租户成员 | `p_super_admin` |
| 分配或调整 `tenant_admin` | `p_super_admin` |
| 管理组织结构 | `tenant_admin` |
| 管理组织成员 | 对应组织 `org_admin`，或具备租户管理权限的角色 |
| 知识库授权 | `tenant_admin` 或对应组织 `org_admin` |
| 上传文档 | 知识库文档写入权限 |
| 删除文档 | 知识库文档删除权限 |

无权限统一返回 HTTP `403`，前端展示明确的无权限提示，不使用本地演示数据或静默忽略失败。

### 7.1 操作权限验证接口

前端权限初始化接口：

```http
GET /api/v1/auth/permissions
```

接口根据登录用户、当前租户上下文和有效角色，返回可访问菜单及其操作编码。该接口只用于初始化菜单和按钮展示；切换租户后必须重新获取权限。

页面需要动态判断多个操作时，可调用：

```http
POST /api/v1/auth/permissions/check
```

请求体传入 `action_codes` 数组，响应每个操作的 `allowed` 结果。该接口同样不能替代真实业务接口的鉴权。

所有业务 API 必须在 Service 执行前固定绑定并校验操作编码，例如：

| 业务接口 | 固定操作编码 |
|---|---|
| `POST /knowledge-bases` | `knowledge_base:create` |
| `PATCH /knowledge-bases/{id}` | `knowledge_base:update` |
| `DELETE /knowledge-bases/{id}` | `knowledge_base:delete` |
| `POST /documents` | `document:upload` |
| `DELETE /documents/{id}` | `document:delete` |

操作编码不能从请求体中读取，也不能由前端传参覆盖。统一权限服务需要依次校验用户身份、当前租户成员关系、操作是否启用、角色操作授权、页面菜单授权、租户/组织数据范围和业务状态。

Service 层可以使用统一装饰器减少重复代码：

```python
@require_action("knowledge_base:create")
async def create(
    self,
    payload: CreateKnowledgeBaseRequest,
    auth_context: AuthContext,
):
    ...
```

装饰器只校验固定操作权限；涉及具体知识库、文档或组织时，Service 仍需继续校验目标资源的数据范围。装饰器不得依赖 FastAPI `Request` 或 `HTTPException`，权限失败统一抛出领域异常，再由 API 层转换为 `403`。

- 未登录或 Token 无效返回 `401`。
- 无操作权限、页面权限或数据范围权限返回 `403`。
- 已通过权限但目标资源不存在返回 `404`。
- 权限通过但业务状态不允许返回 `409`。

详细请求、响应和校验顺序见《[菜单、页面与操作权限设计](菜单页面与操作权限设计.md)》第 6 节。

### 2.3 公共字典维护

角色编码、状态编码、权限编码及其中文展示名称统一维护在前端公共字典模块中。业务页面和组件不得重复编写相同的编码映射；新增或调整字典项时，需要同步维护公共选项、展示转换方法及相关接口文档，确保列表、表单和详情展示使用同一套定义。

## 8. 当前系统调整重点

当前系统已具备平台超级管理员、租户角色、当前租户和知识库用户/组织授权的基础能力，但仍需重点补齐以下内容：

1. 将平台用户管理、平台组织管理与租户用户/组织管理的权限范围拆开。
2. 为 `tenant_admin` 增加明确的租户内管理权限判断。
3. 为 `org_admin` 增加组织范围判断，限制只能操作负责组织。
4. 为文档上传、删除、知识库授权按钮增加统一权限控制。
5. 扩展 `/auth/me` 返回组织角色和操作权限。
6. 为路由和按钮建立统一的权限字典，避免页面自行拼接角色判断。
7. 对所有知识库、文档、组织和成员接口增加后端数据范围校验。

## 9. 验收标准

- 不同角色登录后只能看到允许访问的模块。
- 直接输入无权限路由时会被拦截。
- 页面中无权限按钮不显示。
- 用户切换租户后，模块和按钮权限立即按新租户刷新。
- 用户不能通过修改请求参数访问其他租户或组织数据。
- 前端隐藏按钮后，直接调用接口仍会被后端拒绝。
- 每个租户只能存在一个有效的 `tenant_admin`，角色只能由平台超级管理员分配或调整。
- `tenant_guest` 不能上传或删除文档，也不能修改租户、组织和知识库配置。

## 10. 菜单、页面与操作权限模型

当前系统按“一个菜单项对应一个页面”设计，不再单独维护页面资源层。

- `t_system_menu`：同时表示菜单入口和页面资源。
- `t_role_menu`：控制角色是否可以看到和进入页面。
- `t_system_menu_action`：定义页面下的新增、编辑、删除、导入、导出等操作。
- `t_role_menu_action`：控制角色是否可以执行具体操作。

页面操作通过 `t_system_menu_action.menu_id` 直接关联页面菜单，角色操作权限通过 `action_id` 关联操作。前端按钮控制和后端接口鉴权统一使用操作编码，例如 `knowledge_base:create`。

详细表结构、授权规则和评审事项见《[菜单、页面与操作权限设计](菜单页面与操作权限设计.md)》。
