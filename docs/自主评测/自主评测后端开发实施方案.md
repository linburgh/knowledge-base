# 自主评测后端开发实施方案

## 1. 文档定位

本文档依据《知识库问答评测Agent需求与实施方案.md》编写，用于指导自主评测模块的后端、两个 Agent、LangGraph、Worker、数据库和平台接口开发。

自主评测不是知识库问答 Agent 的替代品，而是独立的评测编排和结果分析能力：

```text
知识库问答 Agent       负责回答用户问题
知识库问答评测 Agent   负责组织测试、采集结果、计算指标和判断是否合格
```

实现必须保持两个 Agent 的独立目录、独立入口和独立职责边界。评测 Agent 不直接拼接业务答案、不修改知识库内容、不绕过知识库问答 Agent 直接调用 LLM。

## 2. 建设目标和非目标

### 2.1 建设目标

- 支持 TXT、JSON、JSONL 问题文件导入。
- 支持根据外部业务描述、指定知识库或两者共同生成测试问题。
- 支持指定知识库、评测用户、并发数、单题超时、重试次数和门禁配置。
- 通过唯一的知识库问答 Agent 入口批量执行问题。
- 采集答案、引用、检索命中、状态、终止原因、响应时间和错误。
- 计算成功率、错误率、降级率、引用率、P50/P95/P99 等指标，并执行门禁。
- 持久化逐题结果、运行快照、评测报告、失败样品和优化建议。
- 支持候选优化方案、同批问题复测、前后指标对比和保存草稿。

### 2.2 非目标

- 不在评测 Agent 中复制普通 RAG、检索、重排、Prompt 或答案生成链路。
- 不自动修改 `app.yaml`、数据库正式配置、Prompt、文档、索引或知识库范围。
- 不把降级摘要当作正常 Agent 答案统计。
- 没有标准答案、标准文档或人工标注时，不伪造 Recall@K、MRR、Answer Correctness 等高级指标。

## 3. 配置和运行入口

### 3.1 独立 YAML 配置

评测配置独立于 `app.yaml`，默认使用 `etc/evaluation.yaml`，模板为 `etc/evaluation.yaml.example`。评测 Agent 通过 `--config` 显式加载；优先级为：命令行配置文件 > YAML 文件 > 系统默认值。配置中不得保存密码、Token、API Key 和本机绝对路径。

```yaml
evaluation:
  kb_id: 28
  questions:
    source: generated
    count: 20
    file: null
    instruction: "问题表达自然、避免重复。"
  business_scope:
    source: description_and_knowledge_base
    description: "测试客户希望了解产品能力、部署方式、使用流程和售后服务。"
  execution:
    user_id: evaluation-user
    concurrency: 3
    request_timeout_seconds: 120
    retry_count: 0
    keep_conversation: false
  gates:
    success_rate: {operator: ">=", value: 0.95}
    error_rate: {operator: "<=", value: 0.01}
    fallback_rate: {operator: "<=", value: 0.05}
    citation_rate: {operator: ">=", value: 0.95}
    p95_duration_ms: {operator: "<=", value: 8000}
```

`questions.source` 为 `imported` 时读取 `questions.file`；为 `generated` 时根据 `questions.count` 生成问题。`business_scope.source` 支持 `description`、`knowledge_base`、`description_and_knowledge_base`，不在代码中预设产品或业务分类。

### 3.2 配置加载和校验

`app/agents/evaluation/config.py` 负责：

- 校验顶层 `evaluation` 节点、`kb_id`、问题来源和业务范围来源。
- 校验并发、超时、重试、会话策略和门禁比较符。
- 将 YAML 映射为统一的 `EvaluationConfig`。
- 与 `app.yaml` 解耦，不在加载阶段调用模型或数据库。
- 记录脱敏后的配置摘要，供运行快照和报告追溯。

## 4. 后端目录结构

两个 Agent 必须分别位于 `knowledge/` 和 `evaluation/`：

```text
app/
├── agents/
│   ├── AGENTS.md
│   ├── __init__.py
│   ├── knowledge/                       # 知识库问答 Agent
│   │   ├── __init__.py
│   │   ├── agent.py                     # 问答 Agent 编排入口
│   │   ├── runtime.py                   # 运行时、预算、超时和失败收敛
│   │   ├── policies.py                  # 权限、租户、知识库和工具策略
│   │   ├── tools/                       # retrieval、history、citations 等工具
│   │   └── skills/                      # query-analysis、answer-writing 等指导
│   └── evaluation/                      # 知识库问答评测 Agent Harness
│       ├── __init__.py
│       ├── agent.py                     # 评测 Agent 独立入口
│       ├── runtime.py                   # 评测运行循环、预算、超时和失败收敛
│       ├── policies.py                  # 评测权限、资源、数据脱敏和工具策略
│       ├── tools/                       # 评测 Agent 专属工具及 registry.py
│       ├── skills/                      # 评测 Agent 专属 Skill
│       ├── graph.py                     # LangGraph 图和节点编排
│       ├── state.py                     # 运行状态和 Reducer 协议
│       ├── config.py                    # evaluation.yaml 加载和校验
│       ├── models.py                    # 问题、门禁、结果和报告模型
│       ├── dataset.py                   # TXT/JSON/JSONL 加载和校验
│       ├── generator.py                 # 自主生成测试问题
│       ├── executor.py                  # 调用 knowledge Agent 的适配器
│       ├── metrics.py                   # 指标聚合和门禁判断
│       └── report.py                    # JSON/Markdown 报告生成
├── api/v1/evaluations.py                # HTTP 接口和响应转换
├── schemas/
│   ├── agent.py                         # 问答 Agent 结构化协议
│   └── evaluation.py                    # 任务、运行、结果、报告和优化协议
├── core/services/
│   ├── evaluation.py                    # 任务、运行、报告和优化业务编排
│   └── evaluation_access.py             # p_super_admin 和资源校验
├── db/
│   ├── evaluation_task.py               # 任务 Repository
│   ├── evaluation_run.py                # 运行 Repository
│   ├── evaluation_case_result.py        # 逐题结果 Repository
│   └── evaluation_optimization.py       # 优化方案 Repository
├── rag/                                 # 复用现有检索、Embedding、Rerank 能力
└── config/evaluation.py                 # 服务级评测运行参数
workers/
└── evaluation.py                        # 运行和复测的异步调度入口
scripts/db/data_table_ddl.sql            # 唯一 DDL 来源
```

每个 Agent 都必须是独立 Harness 子工程。当前 Agent 规范下不新增 `contracts/`、`prompts/`、`guardrails/`、`tracing/` 或 `evals/` 目录；跨层协议放入 `app/schemas/`，安全约束由两个 Agent 各自的 `policies.py` 和 `runtime.py` 承担。评测 Agent 的 LangGraph、状态、数据集、指标、报告和优化模块只能作为 `app/agents/evaluation/` Harness 内的领域模块存在。

## 5. LangGraph 评测流程

### 5.1 总体流程

```text
读取问题文件或生成问题
  -> 校验问题和门禁
  -> 冻结模型、知识库、问题和运行配置
  -> 调用唯一 knowledge Agent
  -> 保存逐题答案、引用、状态和耗时
  -> 计算基础/高级可用指标
  -> 执行门禁
  -> 生成报告、失败样品和优化建议
  -> 保存结论
```

### 5.2 LangGraph 节点

| 节点 | 职责 | 失败处理 |
|---|---|---|
| `load_task` | 读取任务和运行记录 | 任务不存在则 `failed` |
| `validate_task` | 校验任务、知识库、用户和配置 | 配置错误不进入问答 |
| `prepare_questions` | 导入或生成 N 个问题并去重 | `DATASET_INVALID` |
| `freeze_run` | 固化问题、模型、知识库和门禁快照 | 持久化失败则 `failed` |
| `dispatch_cases` | 按并发限制用 `Send` 分发 | 不直接调用 LLM |
| `execute_case` | 调用 `knowledge/agent.py` | 单题异常转逐题结果 |
| `collect_case_result` | 保存逐题结果并更新进度 | 落库失败升级为任务错误 |
| `calculate_metrics` | 聚合基础和高级指标 | 无法计算标记 `indeterminate` |
| `evaluate_gates` | 比较实际值与门禁 | 门禁不通过仍可完成运行 |
| `persist_report` | 保存指标、报告和结论 | 持久化失败则 `failed` |

单题错误、超时和降级必须继续其他问题；任务级配置、数据库或 Worker 故障才终止整批任务。并发、节点超时、重试和总预算必须有明确上限。

### 5.3 State 设计

`app/agents/evaluation/state.py` 保存：`evaluation_id`、`task_id`、`config_snapshot`、`questions`、`question_index`、`case_results`、`metrics`、`conclusion`、`error` 和 `status`。不保存无关模型消息，不使用无约束 `dict` 作为跨层核心协议。

逐题结果至少包含 `case_no`、问题、问题来源、生成依据、答案状态、引用摘要、检索命中、耗时、错误编码和指标结果。完整答案是否保存由保留策略决定。

### 5.4 两个 Agent 的边界

`app/agents/evaluation/executor.py` 只能通过 `app/agents/knowledge/agent.py` 的公开结构化协议执行问答：输入问题和评测用户上下文，输出答案、引用、状态、终止原因、命中数和耗时。评测 Agent 不导入 knowledge Agent 的私有 Prompt、私有方法或直接调用聊天模型。

## 6. 数据库实施

DDL 统一维护在 `scripts/db/data_table_ddl.sql`，所有表使用 `bigint generated by default as identity primary key`，不创建实际外键。

### 6.1 核心表

| 表 | 关键内容 |
|---|---|
| `t_evaluation_task` | 名称、知识库、问题来源、问题文件、生成配置、执行配置、门禁、状态、创建人 |
| `t_evaluation_run` | 任务 ID、运行序号、状态、结论、配置快照、问题数、成功/错误/降级数、指标、时间 |
| `t_evaluation_case_result` | 运行 ID、题号、问题、来源、答案、状态、终止原因、引用数、命中数、耗时、错误和指标 |
| `t_evaluation_optimization` | 运行 ID、建议、证据、当前/候选配置、影响指标、复测运行、前后指标和方案状态 |

建议约束：任务运行序号唯一、逐题 `(run_id, case_no)` 唯一；运行详情和逐题查询分别建立任务、状态、结论和运行题号索引。表之间只保存逻辑关联字段，由 Service 保证租户边界、任务归属和删除策略。

### 6.2 状态

- 任务：`active`、`deleted`。
- 运行：`pending`、`running`、`completed`、`failed`、`cancelled`。
- 结论：`passed`、`failed`、`indeterminate`。
- 逐题：`completed`、`error`、`timeout`、`fallback`。
- 优化方案：`suggested`、`retesting`、`adopted`、`ineffective`、`regressed`、`draft_saved`、`ended`。

### 6.3 事务和幂等

- 创建任务、创建运行、运行收尾、删除任务均显式使用 `async with db.transaction()`。
- 创建运行时校验同一任务没有 `pending/running` 记录，并在事务内分配 `run_no`。
- 逐题写入使用 `(run_id, case_no)` 幂等，Worker 重启后可恢复。
- 删除任务使用逻辑删除，历史运行和逐题结果默认保留。
- 历史运行的 `config_snapshot` 只读，后续任务配置不能覆盖。

## 7. 指标、报告和优化

### 7.1 指标范围

基础问题模式可计算总问题数、成功率、错误率、超时率、降级率、有引用回答率、引用字段完整率、P50/P95/P99、5xx、Agent 完成率和 GraphRecursionError 率。

Recall@K、Precision@K、MRR、NDCG、Context Precision/Recall、Faithfulness、Answer Relevancy、Answer Correctness、Citation Accuracy、Abstention Accuracy 和 Must-contain Rate，只有在存在标准文档、标准分块、标准答案或人工标注时计算；否则明确标记“无法评估”。

### 7.2 门禁

指标是实际测量结果，门禁是合格标准。所有强制门禁通过后才能判定 `passed`；指标不可计算时总体结论为 `indeterminate`，不得默认通过。

### 7.3 评测报告

`report.py` 输出 JSON 和 Markdown 两种报告，至少包括任务信息、数据集摘要、知识库/Embedding/Rerank/Chat Model 配置摘要、指标实际值和阈值、可选分组指标、不合格指标、影响最大的测试样品、错误/超时/降级/引用异常列表、基线对比和总体结论。

### 7.4 优化建议和“帮我优化”

优化建议必须包含问题现象、指标证据、失败题号、建议措施、预期影响指标、优先级、置信度和人工确认要求。涉及配置发布、索引重建、文档修改、知识库范围或业务规则时必须人工确认。

流程为：

```text
评测报告 -> 生成候选优化方案 -> 使用同一批问题复测
         -> 对比优化前后指标 -> 用户确认 -> 保存为草稿
```

不得自动修改或发布正式配置。复测未提升、关键指标无法计算或出现退化时，不得标记为“建议采用”。

## 8. 平台接口

统一前缀 `/api/v1/platform/evaluations`，API 只负责请求解析、认证上下文、参数校验和响应转换；权限、事务、状态变更和 Agent 调用由 Service 负责。

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/page` | 任务分页查询 |
| `POST` | `/` | 新增任务 |
| `GET` | `/{id}` | 任务配置和最新摘要 |
| `POST` | `/{id}/runs` | 创建一次异步运行 |
| `GET` | `/{id}/runs` | 查询运行历史 |
| `GET` | `/{id}/runs/{run_id}` | 运行报告和总体结果 |
| `GET` | `/{id}/runs/{run_id}/cases` | 逐题分页 |
| `GET` | `/{id}/runs/{run_id}/cases/{case_id}` | 单题详情 |
| `DELETE` | `/{id}` | 逻辑删除任务 |
| `POST` | `/{id}/runs/{run_id}/optimizations` | 生成优化建议/候选方案 |
| `POST` | `/{id}/runs/{run_id}/optimizations/{optimization_id}/retest` | 同批问题复测 |
| `POST` | `/{id}/runs/{run_id}/optimizations/{optimization_id}/save-draft` | 保存优化草稿 |

执行接口在事务中创建 `pending` 运行记录后立即返回 `run_id`，由 `workers/evaluation.py` 启动评测 Agent。前端通过运行详情和逐题接口查询进度。

## 9. 权限、安全和异常

- 所有接口要求登录并由 Service 校验 `p_super_admin`。
- 普通平台角色、租户角色、组织角色和访客统一返回 403，不泄露任务是否存在。
- 评测使用专用 `evaluation.user_id`，不能使用超级管理员身份绕过知识库权限。
- 只有只读检索、历史和引用工具可被 knowledge Agent 使用，不注册修改知识库、文档、角色或权限的工具。
- 密钥、Token、完整敏感上下文和本机路径不得进入日志、报告、配置快照或引用。
- 配置错误使用 `CONFIG_INVALID`，问题文件错误使用 `DATASET_INVALID`，指标不可用使用 `METRIC_UNAVAILABLE`；错误必须可识别、可追踪、不可伪造为通过。
- 新增、执行、查看结果、生成优化、复测、保存草稿和删除均记录审计日志。

## 10. 测试和实施顺序

### 10.1 实施顺序

1. 冻结两个 Agent 的目录、入口、结构化协议和错误码。
2. 将知识库问答 Agent 迁移到 `app/agents/knowledge/`，保持对外调用协议不变。
3. 建立 `app/agents/evaluation/`，实现配置、模型、数据集和问题生成。
4. 实现评测 LangGraph、唯一问答 Agent 调用、单题错误收敛和恢复。
5. 实现指标、门禁、报告、优化建议和复测。
6. 实现 DDL、Repository、Service、API 和 Worker。
7. 接入平台权限、审计、运行进度和前端联调。

### 10.2 测试验收

- TXT、JSON、JSONL 导入，空问题、重复问题和非法格式可拒绝。
- 外部描述、知识库、两者结合三种生成依据可运行并记录 `question_basis`。
- 两个 Agent 有独立目录和入口，评测 Agent 不创建第二套普通 RAG 链路。
- 单题异常、超时和降级继续执行，任务级异常正确失败。
- 指标有实际值、阈值、样本数和比较结果；无法计算明确为 `indeterminate`。
- 报告、逐题结果、配置快照和优化建议可追溯。
- “创建 → 执行 → 查看报告 → 查看逐题 → 帮我优化 → 复测 → 保存草稿”闭环可用。
- 非超级管理员无法查看或操作模块。

## 11. 交付物

- `app/agents/knowledge/` 和 `app/agents/evaluation/` 两个独立 Agent 目录。
- `app/schemas/evaluation.py`、Repository、Service、API 和 Worker。
- `scripts/db/data_table_ddl.sql` 中的评测表 DDL。
- `etc/evaluation.yaml.example` 和配置说明。
- LangGraph 状态、流程图、指标、报告和优化方案测试。
- 接口示例、联调记录、迁移说明和后端验收报告。
