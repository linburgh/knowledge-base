# 知识库问答评估与调优实施方案

## 1. 实施目标

本方案根据《知识库问答评估与调优方案》落地当前知识库问答系统，重点解决以下问题：

1. 解决 `GraphRecursionError`，避免 Agent 在没有结束条件时反复执行。
2. 让检索、答案生成、引用和降级回答可以分别观测和评估。
3. 建立以 Recall@K、MRR、NDCG、Faithfulness、Answer Relevancy 和 Citation Accuracy 为核心的评测闭环。
4. 通过固定评测集验证 Embedding、Chunk、Top-K、Rerank 和 Prompt 调整是否真正有效。
5. 保证访客权限、产品归属、公司名称、价格和合规等高风险事实不被模型猜测。

## 2. 当前问题判断

### 2.1 `GraphRecursionError` 的直接原因

当前 Agent 使用 `create_deep_agent`，即使已经排除了 `write_todos` 工具，DeepAgents 默认仍会加载 Todo List 中间件。日志显示循环节点为：

```text
TodoListMiddleware.after_model
GraphRecursionError: Recursion limit of 16 reached without hitting a stop condition
```

当前配置为：

```yaml
agent:
  max_steps: 8
```

运行时递归上限为：

```python
max_steps * 2 = 16
```

这说明 Agent 没有在预期的“检索一次并生成答案”流程内结束。继续提高 `max_steps` 只能延后异常，还会增加模型调用次数、响应时间和费用。

### 2.2 当前 Agent 设计与业务复杂度不匹配

当前问答主要需要：

```text
问题 + 会话上下文
    ↓
知识库检索
    ↓
基于资料生成结构化答案
```

并不需要任务拆解、子 Agent、文件系统、Todo List 或无限工具循环。过度使用通用 Deep Agent 能力会引入额外状态节点和停止条件，增加递归异常概率。

### 2.3 当前评测不能直接作为模型结论

此前知识库名称为“访客服务与使用指南”时的自测还发现：

- 当时将知识库名称误作为文档主题判断依据；实际应将知识库名称视为业务容器名称。目前名称为“医签通产品与使用指南”，但一个知识库可以合法包含同一企业多个产品及相关服务文档。
- `build_citations` 工具曾因模型传入数据缺少 `document_id` 导致引用失败；该工具已从 Agent 工具列表移除，后端现在根据真实检索结果生成引用。
- 当前部分回答来自降级摘要，必须与正常 Agent 回答分开统计。

因此应先修复执行链路和评测数据，再比较模型或检索参数。

## 3. 推荐目标架构

### 3.1 推荐流程

```text
请求校验
    ↓
读取最近会话上下文
    ↓
确定当前问题和检索问题
    ↓
执行一次受控知识库检索
    ↓
固定上下文调用 Chat Model
    ↓
解析 AgentAnswer
    ↓
后端根据真实检索结果生成引用
    ↓
保存正常答案
```

### 3.2 与当前流程的主要区别

| 项目 | 当前方式 | 调整后方式 |
|---|---|---|
| Agent 形态 | 通用 Deep Agent 循环 | 受控问答流程 |
| 检索次数 | 模型可重复调用 | 默认一次，必要时由明确策略决定 |
| 历史上下文 | Agent 可自行调用历史工具 | 后端提前注入最近会话 |
| 引用生成 | 曾由模型调用 `build_citations` | 后端根据真实检索结果生成 |
| 停止条件 | 依赖 Agent 图和中间件 | 检索完成后只允许一次答案生成 |
| 失败处理 | 递归、结构化输出异常后降级 | 每个阶段独立超时并降级 |
| 可评估性 | 中间状态不稳定 | 检索结果、答案和引用均可独立记录 |

## 4. `GraphRecursionError` 处理方案

### 4.1 第一项处理：移除无关中间件

在当前 Deep Agent 过渡实现中，先在 Harness 配置中排除 Todo List 中间件：

```python
HarnessProfile(
    excluded_tools=EXCLUDED_BUILTIN_TOOLS,
    excluded_middleware=frozenset({"TodoListMiddleware"}),
    general_purpose_subagent=GeneralPurposeSubagentProfile(enabled=False),
)
```

同时保留当前已经排除的文件系统、子 Agent 和命令执行工具。

这一步用于消除日志中已经确认的循环节点，但不能单独保证所有模型都能稳定结束。

### 4.2 第二项处理：减少可调用工具

当前已经移除 `build_citations`，下一步建议只保留：

```text
retrieve_knowledge
```

会话历史已经由后端注入，不再让模型自行调用 `load_conversation_history`。这样可以减少一次工具决策，也避免模型在“检索”和“读取历史”之间循环。

### 4.3 第三项处理：设置明确的单轮预算

简单事实问题的执行预算建议为：

```text
检索工具：最多 1 次
模型生成：最多 1 次
总图执行：不超过 4 个节点
```

复杂问题不能通过无限循环解决。需要多个检索问题时，应由后端明确拆分并执行有限次数，例如最多 3 个检索问题，然后统一交给一次模型生成。

### 4.4 推荐最终处理：Knowledge Agent 作为唯一问答入口

对外和业务层只保留 Knowledge Agent 这一条问答链路，不新增普通 RAG 问答入口，也不让调用方在 Agent 和 RAG 之间选择。

```text
问答 API
    ↓
Chat Service
    ↓
Knowledge Agent
    ↓
受控检索 → 固定上下文 → Chat Model → AgentAnswer
```

Knowledge Agent 内部可以使用确定性的检索和答案生成步骤，但这些步骤属于同一个 Agent 的内部执行过程。调用方始终只调用同一个问答入口，引用、会话、权限和降级策略也统一由该入口处理。

这样可以在不拆分入口的前提下收敛执行边界，消除不必要的 Agent 循环，同时保留未来扩展复杂问题的空间。

## 5. 正常回答与降级回答

### 5.1 正常回答

正常回答必须满足：

- 检索成功。
- Chat Model 返回有效的 `AgentAnswer`。
- 答案使用当前检索上下文。
- 引用由后端从真实检索结果生成。
- `citation_chunk_ids` 为空时，由后端按检索结果策略处理，并记录原因。

### 5.2 降级回答

降级只处理以下异常：

- Embedding 服务不可用。
- pgvector 检索失败。
- Chat Model 超时或调用失败。
- 结构化输出解析失败。
- Agent 执行超预算。

降级顺序：

```text
优先使用已经成功召回的资料调用一次普通摘要模型
    ↓
摘要模型失败时返回资料摘要和来源
    ↓
检索也失败时返回友好提示
```

降级回答必须写入：

```text
termination_reason = fallback
status = failed
fallback_reason = 具体异常分类
```

评测报告中必须单独统计降级率，不能把降级成功计入正常答案准确率。

## 6. 评测数据实施

### 6.1 首批评测集

每个目标知识库先建立 100 条人工审核问题，建议分布如下：

| 问题类型 | 数量 | 说明 |
|---|---:|---|
| 事实查询 | 25 | 产品、角色、功能和规则事实 |
| 流程查询 | 20 | 登录、授权、签名和业务操作流程 |
| 权限边界 | 15 | 未授权、角色限制和数据范围 |
| 多轮追问 | 15 | “这家公司”“这个功能”等上下文问题 |
| 多文档综合 | 10 | 需要多个章节或文档共同回答 |
| 无答案拒答 | 10 | 资料没有明确答案的问题 |
| 噪声问题 | 5 | 与当前知识库无关的问题 |
| 合计 | 100 | 每题经过人工审核 |

### 6.2 评测集文件

建议目录：

```text
tests/evals/
├── datasets/
│   ├── visitor_service.jsonl
│   └── medical_signature.jsonl
├── runners/
│   ├── retrieval_eval.py
│   └── chat_eval.py
├── metrics/

```

每道题至少包含：

```json
{
  "case_id": "visitor-0001",
  "kb_id": 28,
  "question": "未授权用户能否访问知识库？",
  "category": "permission_boundary",
  "expected_answer": "未授权用户不能访问。",
  "expected_chunk_ids": [101, 102],
  "answerable": true,
  "must_contain": ["授权"],
  "must_not_contain": ["直接访问"],
  "review_status": "approved"
}
```

### 6.3 数据前置检查

在运行评测前自动检查：

- 知识库状态为 active。
- 文档状态为 ready。
- 所有分块存在向量。
- 分块包含 `id`、`document_id`、`content` 和 `source_name`。
- 评测集引用的文档和分块仍然存在。
- 文档属于当前知识库的业务范围；不要求知识库名称与单个文档名称一致。
- 租户、知识库和文档归属关系正确，不能跨租户或跨知识库检索。

前置检查失败时，不生成模型质量分数，只生成数据质量报告。

## 7. 指标实施

### 7.1 检索层指标

第一阶段实现：

- Recall@1、Recall@3、Recall@5、Recall@10：K 值召回率。
- Precision@K：K 值精确率。
- MRR：平均倒数排名。
- NDCG@K：K 值归一化折损累计增益。
- Context Precision：上下文精确率。
- Context Recall：上下文召回率。

检索评测直接调用检索服务，保存每道题的完整 Top-K 结果，不经过 Chat Model。

### 7.2 生成层指标

第二阶段实现：

- Faithfulness：忠实度。
- Answer Relevancy：答案相关性。
- Answer Correctness：答案正确性。
- Citation Accuracy：引用准确率。
- Answer Abstention：无答案拒答率。

其中 Faithfulness 和 Answer Relevancy 可以先使用人工 1～5 分，之后再引入模型辅助评审。高风险问题必须人工复核。

### 7.3 业务和稳定性指标

- 问题解决率。
- 用户满意度。
- 无引用回答率。
- Agent 正常完成率。
- 降级率。
- P50/P95/P99 响应时间。
- Embedding、检索和 Chat Model 分阶段耗时。
- 结构化输出失败率。
- GraphRecursionError 发生率。

## 9. 调优顺序

### 9.1 第一步：修复数据和协议

- 统一检索分块字段协议。
- 确认引用始终来自真实检索结果。
- 持续核验“医签通产品与使用指南”中的文档标题、内容和评测集是否一致；知识库名称只用于标识整体业务范围，不作为单个文档的匹配条件。
- 清理无关文档、重复文档和旧版本文档。
- 确认所有文档已重新使用 `bge-m3` 生成向量。

### 9.2 第二步：修复 Agent 稳定性

- 排除 `TodoListMiddleware`。
- 移除不必要的历史工具调用。
- 限制单轮工具调用次数。
- Knowledge Agent 内部切换为受控检索和生成步骤，不新增第二个问答入口。
- 验证 DeepSeek 的 `ToolStrategy` 结构化输出。
- 记录每次循环的节点和调用次数。

### 9.3 第三步：建立检索基线

固定以下参数：

```text
Embedding = bge-m3
Chunk size = 600
Chunk overlap = 100
Top-K = 5
Rerank = hans-tech/bge-reranker-v2-m3:260522 (/api/rerank)
Rerank fail-open = true
```

计算 Recall@K、MRR、NDCG、Context Precision 和 Context Recall，生成第一版报告。

### 9.4 第四步：优化文档和 Chunk

依次比较：

```text
文档清洗
章节标题保留
Chunk size = 400 / 600 / 800
Chunk overlap = 50 / 100 / 150
```

每次只调整一个变量，并观察检索指标、Faithfulness 和 P95 延迟。

### 9.5 第五步：比较 Embedding

在相同文档、相同分块和相同评测集上比较旧模型与 `bge-m3`：

- 重新生成全量向量。
- 不混用不同模型生成的向量。
- 比较 Recall@5、MRR、NDCG@5 和检索耗时。
- 单独检查产品名、公司名、编号和中文专业术语。

### 9.6 第六步：引入混合检索和 Rerank

只有向量检索基线稳定后才引入：

```text
向量召回 + 关键词召回 + 去重 + Rerank
```

以 MRR、NDCG@K、Context Precision、Faithfulness 和 P95 延迟共同判断是否保留。

### 9.7 第七步：优化回答和提示词

最后才调整 Prompt：

- 先直接回答问题。
- 资料不足时明确说明。
- 不补充资料没有的公司、价格、交付和合规结论。
- 追问结合会话上下文，但最终事实仍以当前检索结果为准。
- 引用由后端生成，不由模型拼接。

### 10.2 生成门禁

| 指标 | 初始目标 |
|---|---:|
| Faithfulness（忠实度） | ≥ 90% |
| Answer Relevancy（答案相关性） | ≥ 85% |
| Citation Accuracy（引用准确率） | ≥ 95% |
| 无答案问题幻觉率 | ≤ 3% |

### 10.3 稳定性门禁

| 指标 | 初始目标 |
|---|---:|

| 降级率 | ≤ 5% |
| P95 总响应时间 | ≤ 8 秒 |
| 5xx 错误率 | ≤ 1% |

高风险问题即使总分达标，也必须人工审核通过。

## 11. 具体实施阶段

### 阶段一：Agent 稳定性修复

目标：消除简单问答的递归循环。

工作项：

1. 排除 `TodoListMiddleware`。
2. 减少 Agent 工具，只保留必要的检索工具。
3. 校验工具调用次数和模型调用次数。
4. 对 `GraphRecursionError` 增加独立错误分类和降级记录。
5. 使用访客知识库执行 20 条简单问答回归测试。

验收：

- `GraphRecursionError` 发生率为 0%。
- 正常问题至少 95% 返回结构化答案。
- 正常引用不再出现 `document_id` 缺失。

### 阶段二：评测集和基线

目标：获得当前系统的可比较数据。

工作项：

1. 建立 100 条人工审核评测集。
2. 完成检索层指标计算。
3. 完成答案、引用和降级结果采集。
4. 输出第一版基线报告。

验收：

- 每道题都能定位到知识库、文档、分块和模型版本。
- 检索指标与生成指标可以分开查看。
- 失败请求不会混入正常答案统计。

### 阶段三：检索和 Embedding 调优

目标：提升召回准确率和排序质量。

工作项：

1. 对文档清洗和 Chunk 参数做单变量评测。
2. 对 `bge-m3` 与旧模型做同集比较。
3. 引入关键词混合检索。
4. 评估 Rerank 的收益和性能成本。

验收：

- Recall@5、MRR 和 NDCG 达到检索门禁。
- P95 延迟没有超过系统预算。
- 产品归属、公司名称、权限边界等高风险问题没有退化。

### 阶段四：生成质量和线上闭环

目标：提升答案可信度和业务可用性。

工作项：

1. 评估 Faithfulness、Answer Relevancy 和 Citation Accuracy。
2. 增加前端点赞、点踩和未解决原因。
3. 将低分问题回流人工评测集。
4. 建立发布前自动评测门禁。

验收：

- 生成层达到发布门禁。
- 降级回答与正常回答独立统计。
- 用户反馈、引用、知识库版本和模型版本可关联。

## 12. 实施结论

当前最优先的不是继续提高 `max_steps`，而是收敛 Agent 的执行范围：

```text
移除无关中间件
    ↓
限制工具和调用次数
    ↓
Knowledge Agent 内部使用受控检索
    ↓
建立离线评测基线
    ↓
再调 Chunk、Embedding、Rerank 和 Prompt
```

这样既能处理当前 `GraphRecursionError`，也能按照评估指标判断每次调优是否有效，而不是依赖个别问题的主观感受。

## 14. 重排模型切换与复测说明

本次将原有自定义轻量重排算法完全移除，新增以下配置：

```env
KB_RAG_RERANK_ENABLED=true
KB_RAG_RERANK_MODEL=hans-tech/bge-reranker-v2-m3:260522
KB_RAG_RERANK_BASE_URL=http://127.0.0.1:11434
KB_RAG_RERANK_ENDPOINT=/api/rerank
KB_RAG_RERANK_API_KEY=ollama
KB_RAG_RERANK_TIMEOUT_SECONDS=30
KB_RAG_RERANK_FAIL_OPEN=true
KB_RAG_RERANK_CANDIDATE_MULTIPLIER=3
```

`etc/app.yaml`、`etc/app.yaml.example`、`.env` 和 `.env.example` 已同步上述配置。实际验证发现当前 Ollama 实例中的模型名称带有 `:260522` 标签，且原生服务对 `/api/rerank` 返回 404；直接通过 `/api/generate` 调用该 BERT 重排模型还触发了 Ollama 服务端断言。因此本轮复测会验证“标准重排接口调用 + 不可用时安全回退”，不能把原生 Ollama 当前的向量排序结果冒充为 Cross-Encoder 重排结果。

本轮真实复测报告为 `tests/evals/reports/medical_signature-rerank-live.json`，使用加载新代码的本地 28004 实例执行。20 条用例结果如下：Recall@5 0.95、MRR 0.95、NDCG@5 0.95、Faithfulness 1.00、Citation Accuracy 1.00、P95 3517 ms、5xx 错误率 0、降级率 0。由于当前 Ollama 没有 `/api/rerank`，本轮服务实际记录了重排调用失败并按 `rerank_fail_open=true` 回退向量候选集，因此这些结果是“模型重排配置已接入、服务不可用安全回退”的复测结果，不是 Cross-Encoder 重排收益结果。

要完成真正的模型重排收益对比，需要先启动一个兼容接口，例如：

```text
POST http://<rerank-gateway>/api/rerank
{
  "model": "hans-tech/bge-reranker-v2-m3:260522",
  "query": "用户问题",
  "documents": ["候选分块 1", "候选分块 2"],
  "top_n": 5
}
```

返回格式要求为 `{"results": [{"index": 0, "relevance_score": 0.98}]}`。将 `KB_RAG_RERANK_BASE_URL` 指向该网关并重启后端，再执行同一评测命令即可得到真实 Rerank 对比结果。
