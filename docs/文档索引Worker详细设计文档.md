# 文档索引 Worker 详细设计文档

## 1. 文档定位

本文档定义知识库文档索引 Worker 的需求背景、业务边界、任务模型、执行流程、状态流转、调度方式、异常恢复、权限安全、部署架构、可观测性和验收标准。

本文档同时区分两种状态：

- 当前实施：数据库持久化任务 + `app/workers/indexing.py` 中的 APScheduler 周期任务 + 数据库条件更新原子领取 + `updated_at` 失联恢复。多个后端进程可以同时调度，只有原子领取成功的进程执行任务。
- 独立 Worker 服务、任务租约和消息队列不属于本次轻量改造范围，本文中的相关内容仅作为后续扩展参考。

当前轻量改造方案见[Worker轻量级改造方案](Worker轻量级改造方案.md)，本文档作为索引业务、状态模型和异常规则的补充设计依据。

## 2. 需求背景

### 2.1 先理解什么是“文档索引”

这里的“索引”不是给文件名建立一个简单的目录，也不只是把文档保存到数据库。它是把用户上传的原始文档转换成一组可以被问答系统高效查找、召回和引用的知识数据。

可以把文档索引理解为图书馆的整理过程：原始文件是刚收到的书；解析是读懂文件格式并提取正文；分块是把正文整理成适合查找的小段；Embedding 是为每个小段生成用于语义检索的向量；向量和文本写入检索存储后，问答系统才能根据用户问题找到相关内容。

索引完成后，系统通常同时保留以下几类数据：

| 数据 | 作用 | 是否直接展示给用户 |
| --- | --- | --- |
| 原始文件 | 保留用户上传的 PDF、Word、Markdown 等原始资料 | 通常作为下载或追溯依据 |
| 文档元数据 | 保存文件名、所属知识库、状态、版本和处理结果 | 部分字段展示在文档列表 |
| 文本分块 | 保存从文档中提取的可读文本片段 | 作为回答引用和内容溯源依据 |
| Embedding 向量 | 将文本片段转换为可计算相似度的数字表示 | 通常不直接展示 |
| 索引关系和版本 | 记录哪些分块、向量和配置属于当前可用版本 | 用于检索范围控制和版本切换 |

文档索引与问答检索的关系是：索引负责“提前整理和建库”，检索负责“用户提问时查找相关内容”。没有成功索引的文档，即使原始文件已经上传，也不能被问答链路当作有效知识使用。

一次完整的索引处理可以表示为：

```text
上传原始文件
    ↓
保存文档元数据和原始文件地址
    ↓
解析文件，提取文本和必要的页码/段落信息
    ↓
清洗文本并切分为多个知识片段
    ↓
为每个片段生成 Embedding 向量
    ↓
保存片段、向量及其文档关联关系
    ↓
校验写入结果并激活索引版本
    ↓
文档状态变为 ready，可参与问答检索
```

因此，文档索引 Worker 的职责不仅是调用 Embedding，而是负责推动这条完整链路，并记录每个阶段的状态、进度、错误和最终结果。

### 2.2 业务背景

企业知识库中的文档不能在上传完成后立即被问答检索。文档进入知识库后，还需要完成文件解析、文本清洗、分块、Embedding、向量写入、索引版本激活等处理。

完整链路如下：

```text
原始文件
  → 对象存储
  → 文件解析
  → 文本清洗
  → 文本分块
  → Embedding
  → 保存文档分块和向量
  → 激活索引版本
  → 文档进入 ready
```

上述过程可能持续数秒、数分钟甚至更久，并且会受文件大小、分块数量、模型响应速度、网络、限流和服务故障影响。如果在上传 HTTP 请求内同步完成，会造成请求超时、连接长期占用、用户无法获知真实进度和失败原因。

因此系统需要将“上传文档”和“执行文档索引”解耦：上传接口只负责保存文档元数据、上传原始文件和创建索引任务；Worker 在后台读取任务并执行耗时处理，前端通过任务状态接口查询进度。

### 2.3 当前问题

旧的进程内临时协程方式存在以下问题：

```python
asyncio.create_task(ingestion_service.run_task(task_id))
```

- 协程只存在于当前应用进程，进程重启后任务执行会中断。
- 数据库任务可能停留在 `running`，文档可能停留在 `processing`。
- 没有统一的任务领取、并发控制、超时、重试和恢复机制。
- HTTP 请求生命周期与模型调用、对象存储和向量写入生命周期耦合。
- 多实例部署时可能出现同一个任务被多个进程重复执行。

### 2.4 建设必要性

建设索引 Worker 的目标不是简单地“把代码放到后台执行”，而是建立一套可追踪、可恢复、可控制的异步任务处理能力，使系统能够：

- 快速响应上传请求。
- 明确展示任务状态、当前阶段、进度和失败原因。
- 在 Worker 重启或异常退出后识别失联任务。
- 保证同一文档不会同时运行多个冲突索引任务。
- 在 Embedding 和外部服务不稳定时执行受控重试。
- 保证失败不会把文档错误地标记为可检索状态。
- 支持后续扩展为独立 Worker 集群和可靠任务队列。

## 3. 设计目标与非目标

### 3.1 设计目标

1. 将文档上传请求与索引执行彻底解耦。
2. 使用数据库任务记录保存状态、进度、版本和失败信息。
3. 通过任务领取、版本号或租约避免重复执行和状态覆盖。
4. 支持解析、分块、Embedding、写入和索引激活的阶段化进度。
5. 支持任务总超时、单批超时、有限重试和失联恢复。
6. 支持用户查询当前任务、历史任务、中断任务和重试任务。
7. 任务成功后才允许文档进入 `ready` 并被检索。
8. 支持单实例运行和后续多实例生产部署。

### 3.2 非目标

- Worker 不负责 HTTP 请求解析和前端页面展示。
- Worker 不负责用户权限决策，权限由 API/Service 在任务创建和查询时校验。
- Worker 不负责生成自然语言回答。
- Worker 不直接修改知识库问答配置，不绕过配置发布流程。
- Worker 不把模型 Token、API Key 或本机路径写入任务记录和日志。
- Worker 不以定时任务替代可靠的事件任务处理。

### 3.3 Worker 能力清单

Worker 的核心定位是“可靠执行已持久化的文档索引任务”。它不直接面向用户提供业务接口，也不负责决定哪些用户可以访问哪些知识库；这些职责分别属于 API 和 Service。Worker 接收任务后，负责把任务从待处理状态推进到成功、失败或可恢复的中断状态。

#### 3.3.1 核心业务能力

| 能力 | 说明 | 当前状态 |
| --- | --- | --- |
| 任务执行 | 领取索引任务并执行文档解析、清洗、分块、Embedding 和写入 | 已有基础实现 |
| 阶段推进 | 按准备、解析、切分、向量化、写入、完成等阶段更新任务状态 | 已有基础实现，生产需进一步细化 |
| 进度更新 | 根据已处理分块数、总分块数和当前阶段更新进度 | 已有基础字段和流程 |
| 文档状态收口 | 只有索引数据写入并校验成功后，才将文档置为 `ready` | 已有基础实现 |
| 索引版本处理 | 将本次构建结果关联到指定索引版本，并在校验成功后激活 | 已有数据模型，流程需完善版本化切换 |
| 任务结果记录 | 保存成功、失败、中断、取消、耗时和错误原因 | 已有基础实现 |

#### 3.3.2 可靠性能力

| 能力 | 说明 | 当前状态 |
| --- | --- | --- |
| 任务持久化 | 任务先写入数据库，避免任务只存在于 Python 内存中 | 已有 |
| 原子领取 | 多个 Worker 同时运行时，同一任务只能被一个 Worker 领取 | 生产目标，当前轮询实现需补充原子领取 |
| 幂等执行 | 重复投递或 Worker 重启后重试，不产生重复分块和错误的索引结果 | 部分已有，生产需完善唯一约束和版本隔离 |
| 心跳与租约 | Worker 定期证明仍在执行，超过租约时间后允许恢复失联任务 | 生产目标 |
| 异常恢复 | 进程崩溃、机器重启、模型超时或网络失败后，识别并恢复任务 | 已有基础恢复逻辑，生产需独立调度补偿 |
| 受控重试 | 按最大次数、错误类型和退避策略重试，避免无限重试 | 已有基础重试，需补充错误分类和退避 |
| 状态一致性 | 任务状态、文档状态、分块数据和索引版本保持一致 | 已有基础收口，生产需强化事务和补偿 |

#### 3.3.3 调度与执行能力

| 能力 | 说明 | 当前状态 |
| --- | --- | --- |
| 实时触发 | 任务创建后通过消息或事件唤醒 Worker，不依赖固定周期扫描 | 生产目标 |
| 任务领取 | 从队列或任务存储中获得执行权，并记录执行者信息 | 当前通过数据库轮询，生产建议队列触发 |
| 并发控制 | 控制 Worker 数量、单知识库并发数、Embedding 并发数和批量大小 | 已有部分配置，需生产化治理 |
| 背压控制 | 队列积压、模型限流、数据库压力过高时降低消费速度 | 生产目标 |
| 超时控制 | 支持任务总超时、单阶段超时和单批次模型调用超时 | 已有基础配置 |
| 优先级处理 | 在需要时支持按任务类型、知识库或用户级别安排处理优先级 | 预留能力，当前未启用 |
| 取消处理 | 用户取消任务后，Worker 在安全边界停止后续处理并更新状态 | 已有基础能力，需完善外部调用中断 |

#### 3.3.4 运维与管理能力

| 能力 | 说明 | 当前状态 |
| --- | --- | --- |
| 状态查询 | 提供任务当前阶段、进度、耗时、重试次数和失败原因 | 由 API 提供，Worker负责维护数据 |
| 任务补偿 | 对投递失败、失联和可重试失败任务进行重新投递 | 生产目标 |
| 死信处理 | 超过最大重试次数的任务进入人工处理或死信队列 | 生产目标 |
| 日志追踪 | 以任务 ID、文档 ID、知识库 ID 和索引版本关联完整执行日志 | 部分已有，需统一结构化字段 |
| 指标监控 | 统计成功率、失败率、耗时、积压量、重试量和外部依赖错误 | 生产目标 |
| 健康检查 | 区分 Worker 进程存活、任务消费能力和外部依赖可用性 | 生产目标 |
| 优雅关闭 | 停止领取新任务，等待当前安全阶段结束或释放租约 | 生产目标 |

#### 3.3.5 Worker 不承担的能力

以下能力不属于 Worker：

- 不负责接收上传请求、鉴权和前端响应转换。
- 不负责创建业务任务；任务由 API/Service 在事务中创建并持久化，Worker 负责领取和执行。
- 不负责生成自然语言问答答案，也不负责决定检索权限。
- 不负责把队列消息当作业务事实；任务状态以数据库记录为准。
- 不负责无限重试或静默吞掉异常；不可恢复失败必须记录并进入明确终态。

#### 3.3.6 当前版本与目标版本边界

当前版本已经具备“数据库任务记录 + 应用进程内轮询 + 基础索引执行 + 状态更新 + 超时/恢复”的验证能力，但尚不等于完整的生产级 Worker 平台。生产目标应进一步补齐“事件触发、原子领取、租约心跳、幂等约束、队列背压、死信处理、独立部署和完整监控”。

推荐的最终能力组合是：

```text
任务持久化
    + 事件/消息触发
    + Worker 原子领取
    + 阶段化执行和进度
    + 租约、心跳和超时恢复
    + 幂等写入和索引版本隔离
    + 失败重试和死信处理
    + 监控、告警和优雅关闭
```

### 3.4 关键问题记录：Worker 重启后的任务恢复

#### 3.4.1 问题背景

当前索引流程包含文件解析、文本切分、Embedding 和向量写入等耗时操作。Worker 执行期间如果发生后端重启、进程崩溃、容器重建、机器故障或发布切换，正在执行的 Python 协程会被终止，但数据库中的任务记录仍然保留。

因此需要明确区分两个概念：

- 任务记录不丢失：任务数据已经持久化在 `t_indexing_task` 中。
- 任务能够自动恢复：Worker 重启后能够识别中断任务，并重新获得执行机会。

当前实现已经具备前者，但后者还不完整。

#### 3.4.2 当前实现的实际行为

当前 Worker 重启后的行为如下：

| 重启时任务状态 | 当前行为 | 结论 |
| --- | --- | --- |
| `pending` | Worker 重新扫描并执行 | 可以继续处理 |
| `running` 且最近有更新时间 | 不会被 `pending` 查询重新领取 | 可能长期停留在 `running` |
| `running` 且超过失联阈值 | 尝试进入失联恢复逻辑 | 当前恢复流程仍需修复和完善 |
| `succeeded` | 保持已完成状态 | 不会重复执行 |
| 正在 Embedding 或解析 | 协程终止，不能从原执行点继续 | 需要重新执行 |

当前实现不会从某个 Embedding 批次或具体分块位置断点续跑。索引中间阶段的临时结果也不会作为完整任务进度自动恢复。由于分块和向量通常在流程末尾的短事务中统一写入，重试策略应优先设计为“从头执行 + 幂等写入”。

#### 3.4.3 当前风险

1. `running` 任务不会自然回到 `pending`，可能形成永久处理中状态。
2. Worker 重启后，任务虽然仍在数据库中，但不一定能够再次执行。
3. 多个 Worker 同时运行时，查询和状态更新不是完整的原子领取流程，存在重复执行风险。
4. 失联恢复与用户主动取消共用相近的状态处理逻辑，容易出现参数、权限和状态语义混淆。
5. 仅依赖 `updated_at` 判断任务是否存活，无法明确区分 Worker 身份和当前执行租约。

#### 3.4.4 目标行为

生产环境中，Worker 重启后应达到以下结果：

```text
任务已持久化
    ↓
Worker 执行期间持续更新心跳和租约
    ↓
Worker 异常退出或重启
    ↓
租约超时，任务被识别为失联
    ↓
未超过重试上限：恢复为 pending
超过重试上限：标记为 failed
    ↓
Worker 重新原子领取 pending 任务
    ↓
从头幂等执行并完成索引
```

这里的“恢复”默认指重新执行整个索引任务，不承诺从解析、分块或 Embedding 的中间批次继续。只有在后续确认大文件处理耗时较长、从头重试成本不可接受时，才增加阶段检查点和批次级断点续跑能力。

#### 3.4.5 建议解决方案

1. 在 `t_indexing_task` 增加 `worker_id`、`lease_expires_at` 和 `last_heartbeat_at` 等租约字段。
2. Worker 领取任务时，在同一事务中通过条件更新或 `FOR UPDATE SKIP LOCKED` 完成原子抢占。
3. 执行期间定期刷新心跳和租约；租约过期后，其他 Worker 才能重新领取任务。
4. Worker 启动时和定时补偿任务中，扫描租约过期的 `running` 任务。
5. 新增独立的失联恢复方法，不复用用户手动取消方法；恢复时使用任务版本号做 CAS 校验。
6. 失败重试时复用原始文档和索引版本，从头执行，并在写入前按文档和索引版本清理或替换旧分块。
7. 为文档分块和任务增加必要的唯一性约束或等价幂等策略，避免重复投递产生重复向量。
8. 正常关闭时停止领取新任务，并等待当前安全阶段结束；强制退出时依赖租约超时恢复。

#### 3.4.6 验收标准

- Worker 执行任务期间被强制终止，任务记录不会丢失。
- 新 Worker 启动后能够识别租约过期的 `running` 任务。
- 未超过最大重试次数的失联任务能够自动重新进入执行流程。
- 超过最大重试次数的任务进入 `failed`，并记录明确失败原因。
- 重试后不会产生重复分块、重复向量或错误的索引版本激活。
- 同一任务在多个 Worker 并发运行时，最多只有一个 Worker 获得有效执行租约。
- 任务恢复期间，文档不会被错误标记为 `ready`。

## 4. 术语和角色

| 术语 | 定义 |
| --- | --- |
| 文档 | 用户上传并归属于某个知识库的原始资料 |
| 索引任务 | 对单个文档或单个索引版本执行解析、分块和向量化的持久化任务 |
| Worker | 从任务来源领取任务并执行索引流程的后台进程 |
| Dispatcher | 将数据库中的待处理任务投递到任务队列或触发执行器的调度组件 |
| 索引版本 | 一组使用固定问答配置和文档范围构建的可切换索引代次 |
| 任务租约 | Worker 在限定时间内对任务的处理权，租约过期后任务可以被恢复 |
| 任务心跳 | Worker 更新 `updated_at` 或租约时间，用于证明任务仍在执行 |
| 失联任务 | 状态为 `running` 且超过心跳阈值没有更新的任务 |

## 5. 总体架构

### 5.1 当前实施架构

当前代码使用后端内置 APScheduler Worker：

```text
FastAPI 启动
    ↓
app.main 启动 app/workers/indexing.py
    ↓
APScheduler 每 5 秒触发 process_pending_tasks()
    ↓
数据库条件更新领取 pending 任务
    ↓
app.core.services.knowledge_base.ingestion.run_claimed_task()
    ↓
MinIO / Loader / Splitter / Embedding / PostgreSQL
```

当前实现的优点是结构简单、部署成本低，Worker 代码直接属于后端模块。多个 Gunicorn 进程或后端实例可以同时运行调度器，任务唯一性由数据库条件更新保证；服务突然中断后，`updated_at` 超过失联阈值的 `running` 任务会恢复为 `pending` 并从头执行。

### 5.2 生产目标架构

生产环境建议将 API、任务调度和任务执行拆分：

```text
                     ┌────────────────────┐
上传/重建 API ───────→│ PostgreSQL 任务表   │
                     └─────────┬──────────┘
                               │ outbox / 投递
                               ↓
                     ┌────────────────────┐
                     │ Redis/Arq 或统一调度 │
                     └─────────┬──────────┘
                               ↓
                     ┌────────────────────┐
                     │ 独立 Python Worker 集群│
                     └─────────┬──────────┘
                               ↓
       MinIO → Loader → Splitter → Embedding → PostgreSQL/Vector Store
```

任务表是业务状态的最终事实来源，队列只负责唤醒和分发，不以队列消息替代任务状态。Worker 重启后可以根据任务表和租约恢复任务。

### 5.3 XXL-JOB 的适用边界

XXL-JOB 可以作为企业统一调度平台接入，但应区分调度和执行：

- 可以使用 XXL-JOB 定时触发失联任务恢复、任务补偿、清理和统计任务。
- 可以使用一个周期性 Dispatcher 扫描 `pending` 任务并投递到独立 Python 执行器。
- 不建议为每个文档创建一个 XXL-JOB 定时任务。
- 不建议每 2 秒通过 XXL-JOB 触发一次数据库扫描。
- 不建议让 XXL-JOB 的调度记录替代 PostgreSQL 任务表。

如果公司已有 XXL-JOB 基础设施，可以采用“XXL-JOB 调度 + Python Executor 执行 + PostgreSQL 保存状态”的方案；如果没有既有平台，当前 Python 异步项目优先评估 Arq + Redis，减少跨语言执行器和调度管理成本。

## 6. 任务模型

### 6.1 任务粒度

默认一条索引任务对应一个文档和一个索引版本。任务必须保存：

- `document_id`：文档 ID。
- `kb_id`：知识库 ID。
- `index_version_id`：目标索引版本，可为空（兼容旧任务）。
- `config_version_id`：构建索引时使用的问答配置版本，可为空（兼容旧任务）。
- `retry_of_task_id`：重试来源任务 ID，可为空。

同一文档在同一时间只能存在一条有效的 `pending` 或 `running` 任务。重试创建新任务，不覆盖原任务历史。

### 6.2 任务核心字段

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `id` | 任务主键 | 自增主键 |
| `document_id` | 文档 ID | 由 Service 校验归属，不创建数据库外键 |
| `kb_id` | 知识库 ID | 由 Service 校验租户和权限边界 |
| `status` | 任务状态 | `pending/running/succeeded/failed/interrupted/canceled` |
| `progress` | 当前进度 | 0 到 100，必须来自实际处理结果 |
| `current_step` | 当前阶段 | 解析、切分、Embedding、写入、完成等 |
| `attempts` | 已执行次数 | 每次实际领取执行时递增 |
| `max_attempts` | 最大执行次数 | 默认 3，可按任务类型配置 |
| `version` | 乐观锁版本 | 中断、重试和状态更新使用 CAS |
| `error_message` | 最后一次错误摘要 | 限制长度，不保存敏感信息 |
| `started_at` | 本次执行开始时间 | Worker 领取任务时写入 |
| `finished_at` | 结束时间 | 终态时写入 |
| `updated_at` | 最近更新时间 | 作为心跳和失联判断依据 |
| `worker_id` | 执行 Worker 标识 | 生产目标增加，用于排查和租约释放 |
| `lease_until` | 租约过期时间 | 生产目标增加，用于任务恢复 |

### 6.3 文档状态关系

```text
文档 pending
    ↓ 创建索引任务
文档 processing
    ├─ 任务 succeeded → 文档 ready
    ├─ 任务 failed → 文档 failed
    ├─ 任务 interrupted/canceled → 文档保持可重试状态
    └─ 新任务重试 → 文档 processing
```

只有当前有效索引任务成功完成，并且索引版本满足激活条件时，文档才可以进入 `ready`。旧索引版本不能因为新任务失败而被错误删除或替换。

## 7. 状态机设计

### 7.1 主状态流转

```text
pending ──领取──→ running ──成功──→ succeeded
   │                 │
   │                 ├─业务失败/超时──→ failed
   │                 ├─进程失联──────→ interrupted
   │                 └─用户中断──────→ canceled
   │
   └─用户取消──────→ canceled
```

### 7.2 状态流转约束

| 当前状态 | 允许操作 | 禁止操作 |
| --- | --- | --- |
| `pending` | 领取、用户中断、查询 | 重复创建同文档任务 |
| `running` | 更新心跳、更新进度、用户中断、查询 | 第二个 Worker 同时执行 |
| `succeeded` | 查询、查看分块、重新索引 | 直接覆盖历史任务 |
| `failed` | 查询、重建索引、查看错误 | 伪造为成功 |
| `interrupted` | 查询、重试 | 直接覆盖原任务 |
| `canceled` | 查询、重试 | 继续执行原任务 |

任何状态更新都必须带任务 ID、当前状态和版本条件；条件不满足时返回冲突，不覆盖更新后的状态。

## 8. Worker 执行流程

### 8.1 领取任务

当前实现是查询一个 `pending` 任务后直接执行。生产目标必须实现原子领取：

```sql
update t_indexing_task
set status = 'running',
    attempts = attempts + 1,
    worker_id = :worker_id,
    lease_until = :lease_until,
    started_at = coalesce(started_at, now()),
    updated_at = now(),
    version = version + 1
where id = (
    select id
    from t_indexing_task
    where status = 'pending'
    order by created_at, id
    for update skip locked
    limit 1
)
returning *;
```

如果使用 Arq 或其他可靠队列，队列消费成功后仍必须在数据库中执行同等的状态和租约校验。

### 8.2 执行阶段

| 阶段 | 主要动作 | 进度示例 |
| --- | --- | ---: |
| `prepare` | 校验文档、知识库、索引版本和配置快照 | 0%～5% |
| `download` | 从 MinIO 获取原始文件 | 5%～15% |
| `parse` | Loader 解析 PDF、Markdown、TXT、DOCX 等文件 | 15%～25% |
| `split` | 清洗文本并生成文档分块 | 25%～40% |
| `embed` | 批量调用 Embedding，持续更新批次进度 | 40%～90% |
| `persist` | 写入分块、向量和索引元数据 | 90%～98% |
| `activate` | 校验索引版本并切换 active 索引 | 98%～100% |
| `complete` | 更新任务 `succeeded` 和文档 `ready` | 100% |

进度只能来自已完成的实际处理量。不能使用轮询次数、固定时间或前端计时器推算业务进度。

### 8.3 成功收尾

成功收尾需要在事务中完成：

1. 写入或确认文档分块。
2. 写入向量数据或向量索引引用。
3. 更新索引版本完成状态。
4. 满足全量构建条件时激活新索引版本。
5. 更新任务为 `succeeded`、进度 100%、当前阶段“完成”。
6. 将文档更新为 `ready`。
7. 写入必要的审计和运行摘要。

任一步骤失败时，不能把文档更新为 `ready`。

### 8.4 失败收尾

失败收尾需要：

- 记录结构化错误编码和脱敏错误摘要。
- 记录失败阶段、当前进度、尝试次数和 Worker 标识。
- 任务更新为 `failed` 或 `interrupted`。
- 文档更新为 `failed` 或可重试状态。
- 保留原始文件和历史任务，避免失败时无法诊断。
- 根据错误分类决定是否允许自动重试。

## 9. 调度与执行策略

### 9.1 当前调度策略

当前 `app/workers/indexing.py` 提供：

- `start()`：启动 APScheduler。
- `stop()`：关闭 APScheduler。
- `process_pending_tasks()`：通过数据库条件更新原子领取并执行任务。
- `recover_stale_tasks()`：恢复超过 `updated_at` 失联阈值的 `running` 任务。

多个后端进程可以同时触发周期 Job；数据库条件更新和 `RETURNING` 决定哪个进程获得执行权，不使用 `FOR UPDATE`。

### 9.2 方案对比

| 方案 | 适用场景 | 优点 | 主要问题 | 建议 |
| --- | --- | --- | --- | --- |
| 应用内轮询 | 旧实现 | 简单、依赖少 | 手写循环和进程生命周期耦合 | 迁移到 APScheduler |
| APScheduler + 数据库条件更新 | 当前轻量方案 | Python 集成简单、无需外部队列、支持多进程原子领取 | 任务状态仍依赖数据库，不能断点续跑 | 当前采用 |
| XXL-JOB | 企业已有统一调度平台 | 统一调度、运维和执行记录 | Python 执行器生态和实时任务模型需额外适配 | 可做 Dispatcher 和周期维护 |
| Arq + Redis | Python 异步任务队列 | 与当前异步架构匹配，支持重试和任务执行 | 需要 Redis、高可用和任务幂等设计 | 优先评估生产方案 |
| Celery | 跨语言、复杂分布式任务 | 生态成熟、调度能力强 | 组件较重，和当前架构改造量较大 | 有既有 Celery 体系时采用 |

### 9.3 推荐方案

如果公司已有 XXL-JOB，推荐：

```text
XXL-JOB
  → 周期触发 Dispatcher / 失联恢复
  → Python Executor 领取和执行任务
  → PostgreSQL 保存最终状态
```

如果没有统一调度平台，推荐：

```text
API 事务写入任务和 outbox
  → Arq/Redis 投递
  → 独立 Python Worker 消费
  → PostgreSQL CAS 更新状态
```

无论采用哪种方案，都必须保留数据库任务表、任务幂等和恢复机制。

## 10. 并发、限流与资源预算

### 10.1 Worker 并发

并发参数至少包括：

- Worker 实例数。
- 单实例同时执行的文档数。
- 单文档 Embedding 批次并发数。
- 单批分块数量。
- 数据库连接池大小。
- 对象存储并发下载数。

不能只提高 Worker 数量而不调整模型服务、数据库连接池和 Redis/队列容量。

### 10.2 Embedding 控制

Embedding 必须采用批量、信号量和有限重试：

```text
分块列表
  → 按 batch_size 分批
  → Semaphore 限制并发
  → 单批超时
  → 指数退避重试
  → 更新任务心跳和进度
```

遇到限流、超时和临时网络错误可以重试；遇到文件格式错误、配置错误和权限错误不应无限重试。

### 10.3 背压

当待处理任务持续增加时，系统应具备：

- 队列长度或 `pending` 数量监控。
- 单知识库或租户的并发上限。
- 模型服务限流和熔断。
- 大文件单独队列或低优先级队列。
- 超过阈值后的上传提示或任务排队提示。

## 11. 超时、重试与恢复

### 11.1 超时层级

| 超时 | 说明 | 处理 |
| --- | --- | --- |
| HTTP 超时 | 上传接口只创建任务，不等待索引 | 返回任务 ID，前端异步查询 |
| 单批模型超时 | 单次 Embedding 或外部服务请求 | 有限重试，超过后记录批次失败 |
| 单阶段超时 | 解析、写入或激活阶段异常耗时 | 中止当前任务并记录阶段 |
| 任务总超时 | 整个索引任务超过上限 | 任务失败，释放租约 |
| 失联阈值 | `updated_at` 长时间不更新 | 标记 `interrupted`，允许重试 |

### 11.2 错误分类

| 错误类型 | 示例 | 是否自动重试 |
| --- | --- | --- |
| 临时外部错误 | 网络超时、模型 429、对象存储临时不可用 | 有限重试 |
| 资源错误 | 数据库连接池耗尽、模型服务过载 | 延迟后重试，触发告警 |
| 数据错误 | 文件损坏、无法解析、内容为空 | 不自动无限重试，进入 failed |
| 配置错误 | Embedding 模型不存在、配置版本失效 | 不自动重试，要求修复配置 |
| 权限错误 | Worker 无法访问知识库或对象 | 不自动重试，记录安全事件 |
| 代码错误 | 未捕获异常、数据结构不兼容 | 失败并告警，禁止静默吞掉 |

### 11.3 失联恢复

恢复流程：

1. Worker 启动或周期维护时查询 `running` 任务。
2. 判断 `updated_at` 或 `lease_until` 是否超过失联阈值。
3. 使用 CAS 将任务标记为 `interrupted`，不覆盖已进入终态的任务。
4. 释放 Worker 租约。
5. 由用户重试或按明确策略自动重新入队。
6. 原任务保留历史，新任务使用 `retry_of_task_id` 关联。

恢复操作必须幂等，多个 Worker 同时发现同一失联任务时只能有一个成功更新。

## 12. 幂等和数据一致性

### 12.1 任务幂等

- 同一文档不能同时有多个 `pending/running` 任务。
- 重建索引请求必须在事务内检查活动任务。
- Worker 重复收到同一任务消息时，读取任务状态；非 `pending/running` 直接结束。
- 任务领取必须使用行锁、租约或版本号。

### 12.2 分块和向量幂等

- 分块保存使用 `document_id + index_version_id + chunk_index` 或内容哈希作为幂等依据。
- 重试不能把同一版本的向量无限重复写入。
- 新索引版本构建期间不能破坏旧的 active 索引。
- 索引激活必须满足该版本要求的所有任务成功。

### 12.3 事务边界

数据库写入遵守：

- 创建任务、更新文档状态和审计记录使用同一事务。
- 模型调用和大文件处理不持有数据库长事务。
- 成功收尾的元数据切换使用短事务。
- 失败收尾使用独立事务，保证错误状态可落库。

## 13. API 与权限

Worker 不直接暴露页面接口，相关 API 由文档 Service 提供：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/documents/{id}/index` | 创建或重建索引任务 |
| `GET` | `/api/v1/documents/{id}/index-progress` | 查询当前任务和历史任务分页 |
| `POST` | `/api/v1/documents/{id}/index-tasks/{task_id}/interrupt` | 中断任务 |
| `POST` | `/api/v1/documents/{id}/index-tasks/{task_id}/retry` | 重试中断任务 |
| `GET` | `/api/v1/open/documents/{document_id}/tasks/{task_id}` | 开放接口查询公开任务状态（按公开接口权限） |

权限要求：

- 创建、查询、中断、重试都必须校验当前用户对文档所属知识库的访问权限。
- 不能仅凭 `document_id` 或 `task_id` 直接返回任务信息。
- 跨租户、跨组织和无知识库权限访问统一返回无权或资源不存在，不泄露任务存在性。
- Worker 使用独立服务身份访问对象存储、数据库和模型服务，不使用用户 Token 代替服务凭证。

## 14. 安全设计

- 原始文件只通过安全对象键访问，不接受用户提供的本机路径。
- Loader 必须限制允许的扩展名、文件大小和解析资源消耗。
- 压缩包、恶意文档和异常嵌套结构必须防止路径穿越、资源耗尽和临时文件泄漏。
- 文档内容、问题文本、错误信息和模型返回不能直接拼接为日志查询语句或 Prompt 控制指令。
- 日志脱敏 Token、API Key、Authorization、数据库连接串和对象存储凭证。
- 任务错误摘要限制长度，详细堆栈只进入受控日志系统。
- Worker 工具白名单只允许读取文档、解析、分块、Embedding 和写入对应索引数据，不允许修改用户、权限或知识库配置。

## 15. 可观测性

### 15.1 日志字段

每条 Worker 关键日志至少包含：

- `request_id` 或任务触发上下文。
- `task_id`、`document_id`、`kb_id`、`index_version_id`。
- `worker_id`、`attempts`、`status`、`current_step`。
- `progress`、分块数量、批次号和耗时。
- `error_code`、是否可重试和重试次数。

日志不得包含完整文档内容、Token、API Key、密码和敏感业务文本。

### 15.2 指标

至少监控：

- `pending/running/failed/interrupted` 任务数量。
- 任务等待时长、执行时长和端到端成功率。
- 每个阶段耗时。
- Embedding 请求数量、延迟、超时、429 和失败率。
- 单文档分块数量、向量写入数量和吞吐量。
- 任务重试次数、失联恢复次数和重复领取冲突次数。
- 队列长度、Worker 存活数和数据库连接池使用率。

### 15.3 告警

- `pending` 持续堆积超过阈值。
- `running` 失联任务数量大于 0。
- Worker 心跳停止。
- 任务失败率或模型超时率持续升高。
- MinIO、PostgreSQL、Redis 或模型服务不可用。
- 磁盘、对象存储容量或数据库连接池接近上限。

## 16. 部署设计

### 16.1 开发环境

允许使用应用进程内 Worker：

```text
FastAPI + indexing Worker + evaluation Worker + PostgreSQL + MinIO
```

开发环境必须能够通过日志观察任务领取、阶段变化和失败原因。

### 16.2 单实例验证环境

可以继续使用单实例服务，但必须满足：

- `WORKERS_NUM=1`，避免多个 Gunicorn 进程重复启动 Worker。
- 任务表已执行最新 DDL。
- PostgreSQL、MinIO 和模型服务均有健康检查。
- 已验证服务重启后的失联任务恢复。
- 已验证一个任务不会被重复执行。

### 16.3 生产环境

生产环境建议拆分为：

```text
web/API 实例
  → PostgreSQL / Redis
独立 indexing Worker 集群
独立 evaluation Worker 集群
  → MinIO / Embedding / Vector Store
```

生产部署必须补充：

- 多实例任务领取锁或租约。
- 独立 Worker 扩缩容策略。
- 数据库迁移版本管理和回滚方案。
- PostgreSQL、MinIO、Redis 备份及恢复演练。
- 密钥管理和网络隔离。
- 监控、告警、日志集中采集和追踪。
- 灰度发布、Worker 优雅退出和正在执行任务的处理策略。

## 17. 验收标准

### 17.1 功能验收

- 上传接口创建 `pending` 任务后立即返回，不等待索引完成。
- Worker 能领取任务并执行完整索引链路。
- 任务阶段、进度、当前步骤和更新时间真实可查询。
- 成功后任务为 `succeeded`，文档为 `ready`，向量可检索。
- 失败后任务为 `failed`，文档不会错误进入 `ready`。
- 中断和重试不会覆盖原历史任务。
- 同一文档不能同时产生多个有效索引任务。

### 17.2 可靠性验收

- Worker 重启后运行任务不会永久卡死。
- 失联任务可以被识别、标记并按策略重试。
- 模型超时、限流和临时网络错误按策略有限重试。
- 重复消息、重复领取和重复回调不会产生重复分块或错误状态。
- 数据库写入异常能够回滚，不留下半成功状态。

### 17.3 权限和安全验收

- 无权用户不能查询、取消或重试其他知识库任务。
- Worker 不使用用户身份绕过知识库权限。
- 任务日志不泄露敏感凭证和完整文档内容。
- 非法文件、超大文件和恶意路径不会进入索引流程。

### 17.4 运维验收

- API、数据库、对象存储、队列和 Worker 均有健康状态。
- 任务积压、失败、失联和 Worker 停止能够触发告警。
- 能查询任务执行历史、错误摘要、尝试次数和 Worker 标识。
- 完成数据库备份恢复和服务重启演练。

## 18. 实施顺序

1. 冻结任务状态、错误编码、进度阶段和 API 协议。
2. 补充任务领取的 CAS/行锁/租约机制。
3. 将 Worker 从应用进程中拆出，建立独立启动入口。
4. 根据现有基础设施选择 Arq + Redis 或 XXL-JOB + Python Executor。
5. 完善任务幂等、分块幂等、重试和失联恢复。
6. 完善阶段指标、结构化日志、监控和告警。
7. 建立数据库版本迁移、备份和恢复流程。
8. 执行真实 PostgreSQL、MinIO、Embedding、Vector Store 和前端联调。
9. 完成单实例、故障注入、多实例和灰度验收后再进入生产发布。

## 19. 当前实现与生产目标差距

| 能力 | 当前实现 | 生产目标 |
| --- | --- | --- |
| 执行方式 | 应用进程内常驻轮询 | 独立 Worker 服务 |
| 任务领取 | 查询 pending 后执行 | 原子领取、行锁或租约 |
| 调度 | 数据库轮询 | Arq/Redis 或企业统一调度平台 |
| 状态 | 已有状态、进度和更新时间 | 增加 Worker 标识、租约和结构化错误 |
| 恢复 | 单实例失联恢复 | 多实例 CAS 恢复和死信处理 |
| 幂等 | Service 层部分约束 | 任务、分块、向量和回调全链路幂等 |
| 监控 | 日志和接口查询 | 指标、追踪、告警和容量监控 |
| 部署 | Docker Compose 单节点 | API/Worker 分离、可扩缩容和备份恢复 |

当前 Worker 可以作为开发和单实例验证基础，但完成上述差距项前，不应将其作为多实例生产索引服务直接上线。
