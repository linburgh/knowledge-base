# 知识库独立用户数据需求设计

## 1. 文档目标

知识库系统需要具备独立的用户数据和权限边界，不能继续使用固定的 `dev-user` 作为所有数据的归属用户。

系统需要同时支持：

1. 用户管理。
2. 租户管理。
3. 组织管理。
4. 知识库与租户、组织、用户之间的独立归属关系。
5. 用户在不同租户和组织中的不同权限。
6. 平台概览和知识库概览的数据统计与图表展示。

本文用于确认业务范围、数据关系和权限模型，确认后再进入数据库和接口设计。

相关设计文档：

- [数据库表结构设计](数据库表结构设计.md)
- [平台管理前端原型设计](前端原型设计/平台管理原型设计.md)

## 2. 核心数据关系

```text
平台
└── 租户 Tenant
    ├── 用户 User
    ├── 组织 Organization
    │   └── 组织成员 Organization Member
    ├── 租户成员 Tenant Member
    └── 知识库 Knowledge Base
        ├── 知识库成员 Knowledge Base Member
        ├── 文档
        ├── 会话
        ├── 消息
        └── 引用
```

### 2.1 数据隔离原则

- 用户数据必须绑定租户，不能跨租户查询。
- 组织必须属于一个租户。
- 知识库必须属于一个租户。
- 知识库可以归属于一个组织，也可以归属于租户公共空间。
- 文档、分片、会话、消息、引用和检索结果必须继承知识库的数据隔离边界。
- 所有接口都必须从认证上下文获取当前用户和租户，不能仅依赖前端传入的 `tenant_id` 或 `user_id`。
- 管理员也必须在明确的租户范围内操作数据，平台管理员跨租户操作需要单独权限和审计记录。

## 3. 用户管理

### 3.1 用户信息

用户是平台中的自然人账号，建议包含：

- 用户 ID。
- 登录名或邮箱。
- 手机号，可选。
- 显示名称。
- 头像。
- 密码摘要或外部身份标识。
- 账号状态：正常、禁用、锁定、已删除。
- 最后登录时间。
- 创建时间和更新时间。

### 3.1 平台超级管理员

平台设置独立角色 `p_super_admin`，该角色不属于任何具体租户，可以操作平台范围内的全部资源。

平台超级管理员是全平台唯一的特殊账号：系统任何时刻只能存在一个具备 `p_super_admin` 角色的有效用户。该唯一性必须由数据库约束和 Service 层业务校验共同保证，不能只依赖前端限制。

平台超级管理员可以：

- 管理全部租户。
- 管理全部用户。
- 管理全部组织。
- 查看和管理全部知识库。
- 管理平台级配置。
- 处理租户、用户、组织和知识库的异常数据。
- 执行平台范围内的数据维护和资源管理操作。

平台超级管理员与租户角色分开定义，不使用普通租户管理员角色替代。建议认证上下文单独保存平台角色：

```json
{
  "user_id": "platform-admin-001",
  "platform_roles": ["p_super_admin"],
  "tenant_id": null,
  "tenant_roles": []
}
```

平台超级管理员默认拥有平台下所有数据和资源的查看权限，不受租户、组织或知识库授权范围限制。进入具体租户资源时，系统上下文仍需要明确当前目标租户，用于页面上下文、操作审计和租户级写入；未选择目标租户时，只允许执行平台级管理操作。

密码、Token 和第三方密钥不得以明文保存。

### 3.2 用户能力

- 用户注册或由管理员创建。
- 用户登录、退出和刷新登录状态。
- 修改个人资料。
- 修改密码或绑定外部身份源。
- 查看自己所属的租户和组织。
- 切换当前工作租户。
- 查看自己有权访问的知识库。
- 查看个人操作记录。

### 3.3 用户登录功能

系统需要支持用户通过账号密码完成登录，并为后续知识库、租户和组织资源访问提供统一认证上下文。

#### 3.3.1 登录方式

第一阶段支持本地账号登录：

- 使用用户名或邮箱作为登录账号。
- 使用用户输入的密码与 `t_user.password_hash` 进行校验。
- 登录成功后返回登录凭证和当前用户基本信息。
- 登录凭证中包含用户 ID、平台角色、当前租户和租户角色等上下文信息。
- 用户状态为 `pending`、`disabled` 或 `deleted` 时不能正常登录。
- 登录成功后更新 `last_login_at`。

后续可以扩展 LDAP、OIDC、SSO 等外部身份源。外部身份登录通过 `external_subject` 关联平台用户，不要求必须存在本地密码摘要。

#### 3.3.2 登录上下文

登录成功后，认证上下文至少包含：

```json
{
  "user_id": "user-001",
  "username": "zhangsan",
  "platform_roles": ["p_super_admin"],
  "tenant_id": null,
  "tenant_roles": [],
  "organization_ids": []
}
```

普通租户用户登录后，系统根据用户所属租户确定默认租户；用户属于多个租户时，需要支持切换当前租户。平台超级管理员可以没有默认租户，但进入租户资源前必须选择当前目标租户。

#### 3.3.3 登录后功能

- 获取当前登录用户信息。
- 获取用户可访问的租户列表和组织列表。
- 切换当前工作租户。
- 根据当前角色和作用域展示平台管理、租户管理、组织管理及知识库功能。
- 退出登录，使当前登录凭证失效或结束当前会话。
- 在凭证有效期内刷新登录状态。

#### 3.3.4 密码管理

- 用户可以修改自己的登录密码。
- 管理员可以为用户发起密码重置流程。
- 重置密码后，用户需要使用新密码登录。
- `password_hash` 只保存密码摘要，不保存明文密码。
- 外部身份源用户可以不设置本地密码，但必须存在有效的外部身份标识。

#### 3.3.5 登录失败处理

- 账号不存在、密码错误和账号不可用统一返回登录失败结果，避免暴露账号是否存在。
- 登录失败需要记录日志和必要的审计信息。
- 登录接口不应返回密码摘要、外部身份标识等内部字段。

#### 3.3.6 登录日志

系统需要保存用户登录相关日志，用于登录问题排查、账号状态分析和后续审计追踪。

登录日志至少记录：

- 登录用户 ID；账号不存在时允许为空。
- 用户输入的登录账号，便于排查账号问题。
- 登录方式，例如 `password`、`oidc`、`ldap`。
- 登录结果，例如 `success`、`failed`、`logout`、`refresh`。
- 失败原因分类，例如账号不存在、密码错误、账号禁用、账号已删除。
- IP 地址。
- User-Agent 或客户端信息。
- 请求 ID。
- 发生时间。

登录日志要求：

- 登录成功、登录失败、退出登录和登录状态刷新都应记录日志。
- 登录失败日志不能保存用户输入的密码。
- 日志不能保存密码摘要、Token、Cookie 或第三方密钥。
- 日志记录应支持按用户、账号、结果、登录方式和时间范围查询。
- 登录日志属于审计数据，不能被普通租户成员修改或删除。

### 3.4 用户状态

```text
pending → active → disabled
                    └→ deleted
```

禁用用户后：

- 不能登录。
- 不能创建会话和发起问答。
- 不能上传或删除文档。
- 既有数据保留其历史归属。
- 管理员可以恢复禁用用户，但不能恢复已删除账号，除非系统明确提供恢复能力。

## 4. 角色分层与权限范围

系统角色分为平台角色、租户角色和组织角色三层，三者的区别是作用范围不同，不是简单地把所有角色放在同一个角色表中。

### 4.1 平台角色

平台角色作用于整个系统平台，当前设计只有：

| 角色编码 | 角色名称 | 作用范围 |
|---|---|---|
| `p_super_admin` | 平台超级管理员 | 全部平台资源 |

平台超级管理员可以不属于任何租户，但进入具体租户资源时必须明确当前目标 `tenant_id`。

`p_super_admin` 只能授予一个有效用户。平台超级管理员的数据范围为全平台，至少覆盖全部租户、用户、组织、知识库、文档及平台统计资源的查看权限；普通租户角色和组织角色的权限判断不得缩小该平台级查看范围。涉及具体租户的写操作仍需记录当前目标租户和审计信息。

平台角色存储在 `t_platform_role` 和 `t_platform_user_role` 中。

### 4.2 租户角色

租户角色只在指定租户范围内生效。同一个用户加入多个租户时，可以在不同租户中拥有不同角色：

| 角色编码 | 说明 |
|---|---|
| `tenant_admin` | 租户管理员，管理租户内用户、组织、知识库和自主评测；只能由平台超级管理员分配 |
| `tenant_member` | 租户普通成员，按授权使用租户资源 |
| `tenant_guest` | 租户访客，只能访问明确授权的资源 |

租户角色存储在 `t_tenant_member.role_code` 中。

租户角色职责：

- `tenant_admin`：负责当前租户内的用户、组织、知识库和自主评测日常管理，但不能管理其他租户，也不能修改平台级角色和平台级配置；角色分配和调整只能由平台超级管理员完成。
- `tenant_member`：作为当前租户的普通成员，按照被授予的知识库和组织权限查看文档、发起问答、参与业务协作，不能管理租户成员和组织结构。
- `tenant_guest`：作为当前租户的受限访问成员，只能访问明确授权的知识库或问答功能，不能上传、删除文档，也不能修改租户和组织配置。

### 4.3 组织角色

组织角色只在指定组织范围内生效：

| 角色编码 | 说明 |
|---|---|
| `org_admin` | 组织管理员，管理组织成员和组织授权资源 |
| `org_member` | 组织成员，使用组织被授权的资源 |

组织角色存储在 `t_organization_member.role_code` 中。

组织角色职责：

- `org_admin`：负责当前组织的成员管理、组织资料维护、成员角色调整以及组织可访问知识库的授权管理，不能操作其他组织或修改租户级配置。
- `org_member`：作为当前组织成员，使用组织被授权的知识库、文档和问答能力，不能管理组织成员、组织层级和组织授权。

### 4.4 角色范围边界

```text
平台角色：全平台
    ↓
租户角色：当前租户
    ↓
组织角色：当前组织
```

上述层级表示作用范围，不表示所有角色自动继承下级权限：

- 平台超级管理员可以跨租户操作平台资源。
- 租户管理员只能管理当前租户，不能查询其他租户数据。
- 组织管理员只能管理当前组织，不能管理其他组织或修改租户级配置。
- 用户在不同租户或组织中的角色应分别判断，不能使用一个全局角色替代。

## 5. 租户管理

租户是数据隔离和计费的基本边界，通常对应一个企业、团队或独立客户。

### 5.1 租户信息

- 租户 ID。
- 租户名称。
- 租户编码，系统内唯一。
- Logo 和品牌配置。
- 联系人和联系方式。
- 租户状态：试用、正常、停用、已删除。
- 配额配置。
- 创建时间和更新时间。

### 5.2 租户配额

租户可以配置或限制：

- 用户数量。
- 组织数量。
- 知识库数量。
- 文档数量。
- 存储容量。
- 单个文件大小。
- 月度问答次数。
- 模型调用预算。
- 向量存储容量。

### 5.3 租户角色

建议至少包含：

| 角色 | 说明 |
|---|---|
| 租户管理员 | 管理租户内用户、组织、知识库和自主评测 |
| 普通成员 | 按授权访问组织和知识库 |
| 访客 | 仅访问被授权的知识库或问答能力 |

租户删除建议采用软删除。删除租户后，禁止新增业务操作，但保留数据和审计记录。

## 6. 组织管理

组织用于表达租户内部的部门、团队或业务单元，并承担批量授权和数据归属能力。

### 6.1 组织信息

- 组织 ID。
- 租户 ID。
- 父组织 ID。
- 组织名称。
- 组织编码。
- 组织负责人。
- 组织状态。
- 创建时间和更新时间。

组织支持树形结构：

```text
企业总部
├── 人力资源部
├── 财务部
└── 技术中心
    ├── 平台组
    └── 算法组
```

### 6.2 组织成员

同一个用户可以加入同一租户下的多个组织，但需要明确主组织：

- 用户 ID。
- 组织 ID。
- 是否主组织。
- 组织内角色。
- 加入时间。
- 离开时间。
- 成员状态。

### 6.3 组织操作

- 创建组织。
- 修改组织名称和负责人。
- 调整父子组织关系。
- 添加、移除和批量导入成员。
- 将知识库授权给组织。
- 查看组织可访问的知识库。
- 禁止删除仍包含有效子组织的组织，或提供明确的迁移流程。

## 7. 知识库归属与授权

知识库不再只依赖 `owner_id` 判断权限，建议增加明确的租户和组织归属。

### 7.1 知识库归属

每个知识库至少包含：

- `tenant_id`：所属租户。
- `organization_id`：所属组织，可为空，表示租户公共知识库。
- `created_by`：创建用户。
- `owner_id`：知识库负责人，可保留作为业务负责人字段。

### 7.2 知识库成员权限

建议增加知识库成员授权关系：

| 权限 | 说明 |
|---|---|
| 查看 | 查看知识库基本信息和授权范围 |
| 文档查看 | 查看文档、索引状态和分片信息 |
| 文档管理 | 上传、重新索引、删除文档 |
| 问答 | 发起问答和查看引用 |
| 配置管理 | 修改知识库配置和系统提示词 |
| 成员管理 | 管理知识库成员和权限 |
| 删除 | 删除知识库 |

知识库权限可以授予：

- 指定用户。
- 指定组织。
- 租户内全部成员。

权限计算优先级建议为：

```text
用户直接授权
    + 所属组织授权
    + 租户默认授权
    → 汇总有效权限
```

撤销权限时需要明确直接授权和组织继承授权的优先级，不能只删除一条关系就误判为无权限。

## 8. 平台概览与知识库概览

### 8.1 平台概览

平台概览面向 `p_super_admin` 和 `tenant_admin`，两种角色共用页面入口和基础布局，但统计范围和卡片不同。`p_super_admin` 展示平台范围内的运营和资源数据：

- 用户总数、正常用户数、租户总数、正常租户数、组织总数、知识库总数。
- 用户增长趋势：按日、月统计新增用户和活跃用户。
- 租户资源分布：展示各租户的用户数、组织数和知识库数。
- 知识库创建趋势：按时间统计新增知识库数量。
- 文档处理状态：统计已完成、处理中、失败和待处理文档数量。
- 最近平台活动：展示用户、租户、组织、知识库和文档的近期操作。

平台图表必须遵守当前平台管理员的数据范围，`p_super_admin` 即使存在当前租户上下文，也默认展示全部平台数据；当前租户上下文只用于页面标识和需要明确选择租户的业务操作，不得将平台超级管理员降级为租户管理员范围。

`tenant_admin` 只展示当前租户范围的数据，前端不展示“租户总数”和“正常租户”卡片；当前租户状态在页面顶部上下文展示。其余统计卡片改为当前租户的用户、组织和知识库数据。接口保持统一统计字段，不能通过删除字段破坏既有响应契约。

### 8.2 知识库概览

知识库概览只展示当前 `kb_id` 的数据：

- 文档总数、分片总数、向量数量、索引失败数。
- 文档处理趋势：统计每日新增文档和索引完成数量。
- 文档状态分布：展示待处理、处理中、已完成和失败数量。
- 问答趋势：统计问答次数和活跃会话数。
- 检索质量：展示平均相似度、低相似度问题数量和无引用回答数量。
- 热门问题：按出现次数展示近期高频问题。
- 文档贡献排行：按被引用次数展示热门文档或分片。
- 最近活动：展示上传文档、索引完成、问答和配置修改记录。

### 8.3 图表通用要求

- 支持近 7 天、近 30 天、近 90 天和自定义时间范围。
- 图表点击后可以跳转到对应列表，并带入对应筛选条件。
- 状态继续使用中文文字和文字颜色区分，不使用大面积状态背景。
- 没有数据时显示明确的空状态、数据范围和更新时间。
- 失败数量、低相似度问题、无向量分片等异常指标需要突出显示。
- 图表数据应由统计接口提供，前端不得根据列表分页数据自行推算全量统计结果。
- 前端图表组件统一使用 ECharts，页面通过公共 `TrendLineChart` 组件封装折线图；图表样式与现有 Bootstrap 基础样式、Element Plus 交互组件保持一致。

## 9. 认证与当前上下文

后续认证上下文至少应包含：

```json
{
  "user_id": "user-001",
  "tenant_id": "tenant-001",
  "organization_ids": ["org-001", "org-002"],
  "roles": ["tenant_admin"],
  "permissions": ["knowledge_base:read", "document:write"]
}
```

后端业务 Service 必须使用认证上下文完成：

1. 当前用户身份校验。
2. 当前租户校验。
3. 组织关系校验。
4. 知识库权限校验。
5. 文档、会话和引用的继承权限校验。

前端传入的 `user_id`、`tenant_id` 只能作为展示或调试信息，不能作为最终授权依据。

## 11. 审计要求

用户、租户、组织和知识库权限变更都必须记录审计日志：

- 操作用户。
- 租户 ID。
- 组织 ID，可为空。
- 操作类型。
- 目标资源类型和 ID。
- 变更前内容摘要。
- 变更后内容摘要。
- 请求 ID。
- IP 和客户端信息。
- 操作时间。

提示词修改、知识库成员调整、租户管理员变更和用户禁用属于重点审计事件。

## 12. 待确认事项

进入数据库和 API 设计前，需要确认：

- 一个用户是否允许加入多个租户。
- 一个用户在不同租户中是否可以使用不同角色。
- 知识库是否允许同时归属于组织和指定用户。
- 是否支持租户公共知识库。
- 组织授权和用户直接授权冲突时的优先级。
- 是否需要邀请注册和邮箱验证。
- 是否需要接入 LDAP、OIDC 或 SSO。
- 租户配额是否第一期就启用。
- 是否需要保留完整权限变更审计。
