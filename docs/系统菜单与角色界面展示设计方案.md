# 系统菜单与角色界面展示设计方案

## 1. 文档目的

本文设计系统菜单以及不同角色登录后的界面展示内容，为数据库、后端接口和前端动态菜单改造提供评审依据。

当前系统角色分为三层：

- 平台角色：`p_super_admin`
- 租户角色：`tenant_admin`、`tenant_member`、`tenant_guest`
- 组织角色：`org_admin`、`org_member`

### 1.1 角色作用域与关系

三层角色按照平台、租户和组织划分作用域，不是简单的上下级继承关系：

```text
平台
└── p_super_admin
    └── 管理全部租户
        └── 租户
            ├── tenant_admin
            ├── tenant_member
            ├── tenant_guest
            └── 组织
                ├── org_admin
                └── org_member
```

| 角色层级 | 角色 | 作用范围 | 角色定位 |
|---|---|---|---|
| 平台级 | `p_super_admin` | 全平台 | 管理所有租户及平台资源，不属于具体租户 |
| 租户级 | `tenant_admin` | 当前租户 | 管理租户用户、组织和知识库；只能由平台超级管理员分配 |
| 租户级 | `tenant_member` | 当前租户 | 普通租户成员，访问已授权资源 |
| 租户级 | `tenant_guest` | 当前租户 | 受限访问租户资源 |
| 组织级 | `org_admin` | 当前组织 | 管理组织成员及组织授权资源 |
| 组织级 | `org_member` | 当前组织 | 访问组织授权资源 |

角色关系约束如下：

- `p_super_admin` 与 `tenant_admin` 作用域不同；平台管理员进入具体租户时仍需明确当前租户上下文。

### 多角色有效角色规则

用户可以同时关联多个层级角色，但权限不按较低角色覆盖较高角色。统一以最高权限角色作为有效角色，优先级为：

```text
p_super_admin > tenant_admin > tenant_member / 组织角色 > tenant_guest
```

例如 `linburgh` 同时具备 `p_super_admin` 和 `tenant_admin` 时，系统必须按 `p_super_admin` 处理：展示平台超级管理员视角，平台概览使用全平台数据，允许平台范围菜单和操作，不得因为当前租户上下文降级为租户管理员视角。认证上下文通过 `effective_role` 返回最终角色，前后端均以该字段或等价的统一判断方法作为角色分支依据。
- 一个用户可以同时拥有租户角色和组织角色，例如 `tenant_member + org_admin`。
- 一个用户可以在不同租户拥有不同租户角色，也可以在不同组织拥有不同组织角色。
- 组织角色不能超出所属租户范围。
- 租户角色确定用户在租户中的基础范围，组织角色用于补充和细化组织内的菜单展示范围。
- 菜单展示根据用户当前租户、组织上下文和角色菜单关系合并生成。

## 2. 核心设计结论

系统菜单用于定义导航层级和菜单展示范围。

```text
系统菜单
  └─ 关联前端路由（可选）

角色
  └─ 关联菜单
```

数据职责如下：

| 数据 | 职责 |
|---|---|
| 系统菜单 | 保存实际展示在导航中的目录和菜单项 |
| 角色菜单关系 | 保存角色可展示的菜单范围 |

菜单负责“有什么导航入口”。

## 3. 系统菜单结构

系统菜单只保留两种节点：

| 类型 | 说明 |
|---|---|
| `directory` | 菜单目录或导航分组 |
| `item` | 可点击的菜单项，可关联前端路由 |

| 层级 | 菜单编码 | 菜单名称 | 类型 | 上级菜单 |
|---|---|---|---|---|
| 一级 | `platform` | 平台管理 | `directory` | — |
| 二级 | `platform_overview` | 平台概览 | `item` | 平台管理 |
| 二级 | `platform_users` | 用户管理 | `item` | 平台管理 |
| 二级 | `platform_tenants` | 租户管理 | `item` | 平台管理 |
| 二级 | `platform_organizations` | 组织管理 | `item` | 平台管理 |
| 二级 | `developer_api` | 开发者中心 | `item` | 平台管理 |
| 一级 | `knowledge_base` | 知识库管理 | `directory` | — |
| 二级 | `knowledge_base_list` | 知识库列表 | `item` | 知识库管理 |
| 三级 | `knowledge_base_workspace` | 知识库工作区 | `directory` | 知识库列表 |
| 四级 | `knowledge_base_overview` | 概览 | `item` | 知识库工作区 |
| 四级 | `knowledge_base_documents` | 文档 | `item` | 知识库工作区 |
| 四级 | `knowledge_base_chat` | 问答 | `item` | 知识库工作区 |
| 一级 | `independent_chat` | 独立问答 | `item` | — |

开发者中心继续作为平台管理下的页面，不作为左侧独立一级菜单。

## 4. 数据表设计

### 4.1 系统菜单表 `t_system_menu`

该表保存导航层级和菜单跳转信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 自增主键 |
| `parent_id` | bigint | 父菜单 ID，顶级菜单为空 |
| `code` | varchar(100) | 菜单编码，全局唯一 |
| `name` | varchar(100) | 菜单名称 |
| `menu_type` | varchar(32) | `directory`、`item` |
| `route_path` | varchar(255) | 菜单跳转路径，目录为空 |
| `icon` | varchar(100) | 菜单图标 |
| `sort_order` | integer | 同级排序 |
| `visible` | boolean | 是否展示在导航中 |
| `status` | varchar(32) | `active`、`disabled` |
| `meta` | jsonb | 菜单扩展配置 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 更新时间 |

约束建议：

- `code` 全局唯一。
- `parent_id` 只能指向 `t_system_menu.id`。
- 禁止形成菜单父子循环。
- 已被引用的菜单不物理删除，只允许停用。

### 4.2 角色菜单关系表 `t_role_menu`

该表保存平台、租户和组织角色与系统菜单之间的多对多关系，用于生成当前用户可见的菜单树。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 自增主键 |
| `role_scope` | varchar(32) | `platform`、`tenant`、`organization` |
| `role_code` | varchar(64) | 角色编码 |
| `menu_id` | bigint | 关联系统菜单 ID |
| `status` | varchar(32) | `active`、`disabled` |
| `created_at` | timestamptz | 创建时间 |
| `created_by` | bigint | 创建人 |
| `updated_at` | timestamptz | 更新时间 |

约束建议：

```sql
unique (role_scope, role_code, menu_id)
```

`role_scope + role_code` 的合法性由 Service 层根据平台、租户和组织角色校验；`menu_id` 只能关联有效的系统菜单记录。

## 6. 登录后的菜单生成流程

```text
用户登录
  ↓
加载当前用户上下文
  ↓
获取平台角色、当前租户角色、组织角色
  ↓
查询角色与菜单关系
  ↓
获取角色可见的菜单项
  ↓
过滤 disabled、visible=false 节点
  ↓
组装菜单树
  ↓
返回前端
```

建议新增接口：

```http
GET /api/v1/auth/menus
```

返回示例：

```json
{
  "default_path": "/knowledge-bases",
  "menus": [
    {
      "code": "knowledge_base",
      "name": "知识库管理",
      "type": "directory",
      "children": [
        {
          "code": "knowledge_base_list",
          "name": "知识库列表",
          "type": "item",
          "route_path": "/knowledge-bases"
        }
      ]
    }
  ]
}
```

## 7. 菜单展示边界

菜单接口只负责返回当前登录用户有权展示的菜单。前端隐藏菜单不能作为后端安全控制，后端接口必须独立执行：

```text
请求 API
  → 登录认证
  → 当前角色校验
  → 租户 / 组织范围校验
  → 资源归属校验
  → 执行业务请求
```

菜单服务只负责查询和组装导航数据，API 层不得直接查询数据库，Service 层负责角色合并、菜单过滤、树形组装和默认首页计算。

## 8. 角色合并规则

1. 只计算当前登录上下文中的角色。
2. 用户切换租户后，重新计算租户和组织范围菜单。
3. 同一菜单被多个角色允许时，只保留一份菜单项。
4. 父目录只有在存在可见子菜单时才展示。
5. 平台超级管理员可以获得平台级菜单，但具体租户页面仍需设置当前租户上下文。

## 9. 前端改造范围

1. 登录完成后调用 `/auth/menus`。
2. 左侧菜单只根据菜单接口生成，不维护完整业务菜单硬编码。
3. 用户切换租户后刷新菜单和默认首页。
4. 无权限访问页面时跳转到无权限页或知识库首页。

前端动态菜单只负责用户体验，后端接口必须继续执行实际授权校验。

## 10. 后端改造范围

1. `scripts/db/data_table_ddl.sql`：新增系统菜单表和角色菜单关系表。
2. `scripts/db/data_table_dml.sql`：初始化菜单数据和角色菜单关系。
3. `app/db/system_menu.py`：菜单查询和菜单树节点查询。
4. `app/db/role_menu.py`：角色菜单关系查询和维护。
5. `app/core/services/system_menu.py`：角色合并、菜单过滤和菜单树组装。
6. `app/api/v1/auth.py`：新增当前用户菜单接口。
7. `app/schemas/`：新增菜单树响应模型。
8. 审计记录：记录菜单和角色菜单关系变更。

所有新增、修改和删除菜单的 Service 写操作必须显式使用事务。

## 11. 实施阶段

### 第一阶段：菜单基础能力

- 新增系统菜单表。
- 新增角色菜单关系表。
- 初始化当前菜单和菜单路由数据。
- 初始化平台、租户和组织角色的菜单关系。

### 第二阶段：菜单接口和前端接入

#### 11.2.1 后端菜单接口

- 新增 `GET /api/v1/auth/menus`，只允许已登录用户访问。
- 接口从认证上下文读取 `user_id`、平台角色、当前 `tenant_id` 和组织角色，不接受前端直接传入的角色或菜单范围作为授权依据。
- 返回当前用户可见的菜单树，节点至少包含 `code`、`name`、`menu_type`、`route_path`、`icon`、`sort_order` 和 `children`。
- 过滤 `status != active`、`visible = false` 的菜单；父目录只有在存在可见子菜单时才返回。
- 合并平台角色、当前租户角色和当前组织角色对应的 `t_role_menu` 关系，同一个菜单只返回一次。
- 根据角色菜单结果计算 `default_path`：优先使用当前上下文可见的角色默认首页，其次使用第一个可访问的 `item` 菜单路径；没有可访问菜单时返回无权限状态。
- 平台超级管理员未选择租户时，只返回平台范围菜单；选择租户后，追加当前租户范围内的知识库菜单。

建议响应结构：

```json
{
  "default_path": "/platform/overview",
  "menus": [
    {
      "code": "platform",
      "name": "平台管理",
      "menu_type": "directory",
      "route_path": null,
      "children": []
    }
  ]
}
```

接口异常处理：

- 未登录或 Token 失效返回 `401`。
- 当前租户上下文无效时返回 `403`，不得返回其他租户菜单。
- 菜单配置为空时返回空菜单和明确的空状态，不使用前端本地菜单兜底。

#### 11.2.2 前端动态菜单接入

- 新增菜单 API 类型、菜单树类型和 Pinia 菜单状态，统一保存 `menus`、`defaultPath`、加载状态和错误状态。
- 登录成功、刷新页面和 Token 刷新后调用 `/auth/menus`，完成后再决定默认跳转地址。
- `SidebarNav` 只渲染接口返回的可见菜单，不再硬编码平台管理和知识库管理入口。
- 前端路由组件仍由本地路由表维护，后端返回的 `route_path` 只用于匹配已注册路由，不动态执行未经前端注册的路径。
- 菜单加载失败时展示错误状态并提供重新加载入口，不使用演示菜单或静态数据替代。
- 菜单为空时跳转无权限页；用户访问未被菜单接口返回的受保护路径时，也必须跳转无权限页。

#### 11.2.3 默认首页、无权限跳转和租户切换

- 默认首页统一使用菜单接口返回的 `default_path`，登录页、根路径和 Token 恢复后的跳转逻辑都复用同一规则。
- 平台管理员默认进入 `/platform/overview`；普通租户用户默认进入 `/knowledge-bases`；访客用户进入访客问答入口。
- 路由守卫在加载当前用户、当前租户和菜单完成前不得提前放行受保护路由。
- 用户无权访问当前路径时跳转无权限页，并保留原始路径用于提示或返回；无权限页不可再次触发循环跳转。
- 租户切换成功后依次刷新认证上下文、菜单树和默认首页，再跳转到新租户可访问的首页；不得沿用旧租户菜单。
- 租户切换失败时保留原租户上下文和原菜单，并展示明确错误信息。

#### 11.2.4 第二阶段验收标准

- 不同平台、租户和组织角色登录后，左侧菜单与 `t_role_menu` 配置一致。
- 刷新浏览器后菜单能够重新从接口加载，前端不存在完整业务菜单硬编码。
- 切换租户后菜单、默认首页和路由访问范围同步变化。
- 访问未授权路径能够稳定跳转无权限页，且不出现重定向循环。
- 菜单接口失败、空菜单和 Token 失效均有明确的加载或错误状态。

### 第三阶段：菜单管理后台

#### 11.3.1 菜单树维护

- 新增平台管理员可访问的菜单管理页面，以树形结构展示一级至四级菜单。
- 支持按菜单名称、菜单编码和状态查询；树节点操作使用文本按钮，列表型查询需要提供分页或明确的树节点加载范围。
- 支持新增、编辑、启用、停用和调整同级排序；支持调整父子层级，但不能形成循环引用。
- 目录菜单必须没有 `route_path`，菜单项必须配置有效的 `route_path`；菜单编码全局唯一。
- 停用目录前必须检查是否存在启用的子菜单；已被角色关系引用的菜单不物理删除。
- 菜单写操作必须在 Service 层使用事务，并在成功后刷新菜单缓存或使菜单缓存失效。

建议管理接口：

```http
GET    /api/v1/platform/menus
POST   /api/v1/platform/menus
PUT    /api/v1/platform/menus/{menu_id}
PATCH  /api/v1/platform/menus/{menu_id}/status
DELETE /api/v1/platform/menus/{menu_id}
```

#### 11.3.2 角色菜单关系维护

- 新增角色菜单授权页面，按角色作用域分为平台角色、租户角色和组织角色。
- 页面左侧选择角色，右侧展示完整菜单树，通过勾选维护该角色可见的菜单集合。
- 保存时提交完整菜单 ID 集合，由 Service 在同一事务中校验角色范围、菜单状态和父子关系后更新 `t_role_menu`。
- 勾选子菜单时自动补齐父目录；取消父目录时同步处理无子节点的目录关系，避免产生孤立菜单。
- `p_super_admin` 只能维护平台菜单关系；租户和组织角色只能维护对应作用域的关系，不能把平台菜单授权给租户或组织角色。
- 租户切换或组织上下文变化后，关系查询必须使用当前作用域，不能跨租户读取或修改角色菜单关系。

建议管理接口：

```http
GET  /api/v1/platform/role-menus?role_scope=tenant&role_code=tenant_admin
PUT  /api/v1/platform/role-menus/{role_scope}/{role_code}
```

#### 11.3.3 菜单变更审计

- 菜单新增、修改、排序调整、启用、停用和删除必须写入审计日志。
- 角色菜单关系新增、撤销和批量替换必须写入审计日志。
- 审计记录至少包含操作人、角色作用域、租户 ID、组织 ID、操作类型、目标菜单或角色、变更前摘要、变更后摘要、请求 ID、IP、User-Agent 和操作时间。
- 菜单树和角色菜单关系的批量保存应记录整体变更摘要，同时保留新增和移除菜单编码列表，便于回溯。
- 审计失败时，菜单写操作必须回滚，不能出现数据已变更但没有审计记录的情况。

#### 11.3.4 第三阶段验收标准

- 平台管理员可以完整维护菜单树，且非法父子关系、重复编码和无效路径会被拒绝。
- 平台、租户和组织角色可以分别维护菜单关系，作用域边界校验有效。
- 保存角色菜单关系后，重新调用菜单接口即可得到最新菜单，不需要前端手工修改。
- 菜单和角色菜单关系的每类变更均能查询到对应审计记录。
- 停用菜单、撤销角色菜单关系后，前端刷新菜单不会继续展示失效入口。

## 12. 评审结论项

1. 前端是否完全通过后端接口生成左侧菜单。
2. 菜单是否由平台超级管理员维护。
