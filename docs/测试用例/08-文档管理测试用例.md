## 索引任务可靠性补充

本节用例对应[文档索引 Worker 详细设计文档](../文档索引Worker详细设计文档.md)中的任务生命周期、状态机、领取、恢复和幂等要求。

| 用例 | 场景 | 操作 | 预期结果 |
|---|---|---|---|
| 后端-003A | Worker 异步接管 | 上传文档后不依赖 HTTP 请求协程，查询任务状态 | 文档进入 `pending`，由索引 Worker 执行并最终进入 `ready` 或 `failed` |
| 后端-003B | Worker 重启恢复 | 索引执行期间停止服务并重新启动 | `running` 任务超过失联阈值后恢复为 `pending`，重新执行后进入 `succeeded` 或 `failed`，不会永久停留在 `processing` |
| 后端-003C | Embedding 受控并发 | 上传包含大量分块的文档 | Embedding 按配置批量处理并限制并发，任务更新时间持续刷新 |
| 后端-003D | 索引超时收尾 | 模拟 Embedding 持续超时 | 任务和文档进入 `failed`，记录超时原因，不保留 `running/processing` 僵尸状态 |
| 后端-003E | Worker 中断恢复 | 模拟 Worker 失联或服务重启超过阈值 | 任务恢复为 `pending`，记录恢复原因和原处理阶段，重新执行完整索引流程 |
| 后端-003F | 用户中断 | 对 `pending/running` 任务调用中断接口 | 权限和任务归属校验通过后任务进入 `canceled`，不创建新任务 |
| 后端-003G | 任务原子领取 | 模拟两个进程同时执行 `UPDATE ... WHERE status = 'pending' RETURNING *` | 只有一个进程返回任务记录并执行，另一个进程返回 0 条记录，不使用 `FOR UPDATE` |
| 后端-003H | 重复调度幂等 | 多个 APScheduler 实例同时触发同一任务 | 只有原子领取成功的进程执行，任务不重复写入分块和向量 |
| 后端-003I | 分阶段进度 | 执行解析、切分、Embedding 和写入阶段 | `current_step`、`progress`、`updated_at` 来自真实阶段进度，不由轮询次数伪造 |
| 后端-003J | 半途任务恢复 | 在解析、Embedding、写入事务和状态更新阶段强制终止后端并重启 | 任务超过 `updated_at` 失联阈值后恢复为 `pending`，从头幂等执行；已成功任务不重复执行 |
| 后端-003K | 成功收尾一致性 | 在分块、向量、索引版本激活任一步骤注入异常 | 任务不进入 `succeeded`，文档不进入 `ready`，错误状态可查询 |
| 后端-003L | 调度器生命周期 | 启动、关闭和重启后端服务 | Worker 代码位于 `app/workers`，APScheduler 正确启动/停止，原 `workers/` 目录不再被引用 |
| 后端-003M | 资源控制 | 模拟大量 `pending` 文档和 Embedding 限流 | APScheduler 单轮按批次配置执行，不无限创建并发请求 |
