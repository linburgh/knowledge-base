## 验收要求

- 单元测试不能替代真实数据库与真实模型联调。
- 外部模型不可用时记录实际错误和已完成的降级验证，不伪造通过状态。
- 所有临时数据库数据在事务中创建并回滚，测试不得污染正式业务数据。
- 测试结果需记录工具调用、事实ID、结论、降级模式和响应时间。

## 执行记录

2026年08月09日完成真实 PostgreSQL 与真实外部模型联调。24小时只读查询取得6条告警，告警详情数量一致，客户标题均使用中文指标名称。真实模型围绕“今天的告警分别是什么，这些告警是否存在重复或高度关联”自主调用 `query_alerts`、`correlate_alerts`、`get_alert_details`、`query_metric_series` 及健康或资源补充工具，证明新增工具进入 `create_deep_agent` 生产调用链。

当前模型供应商在复杂 Deep Agent 工具循环后仍可能不返回最终结构化终态，Harness 按设计保留事实并进入确定性收敛。后续共性整改已增加一次无业务工具的受限终态修复，当前真实供应商对 `MonitoringAgentOutput` 的脱敏能力探针一次通过；完整原因调查复测中修复请求受到 RPM 限流，但通用确定性收敛仍返回完整原因分析。由于模型原生结构化终态尚未稳定通过，`MON-INV-014` 保持“部分通过”，确定性客户结果单独按 `MON-INV-004`、`MON-INV-015` 和 `MON-INV-016` 验收通过。

2026年08月09日使用真实 PostgreSQL 和当前外部模型重新执行“分析一下这四条告警产生的原因吗”。Agent 自主调用告警、告警详情、告警关联、指标、事件、指标趋势和任务工具；结构修复受到供应商 RPM 限流后进入通用确定性收敛。最终返回 `incident_cause`、3 组直接触发原因、成功率与错误率的同批次候选关系、未确认底层根因、活动告警时间窗口边界，以及包含原因结论、原因发现、关系、边界、后续检查和告警列表的 6 个有序展示区块。客户回答未退化为告警明细列表。
