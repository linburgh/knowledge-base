# 智能体问答分阶段代码实施设计

## 1. 文档目的

本文是《智能体与 RAG 问答设计》的代码落地版，供技术评审和后续开发执行。

本文只设计后端内部固定的 Knowledge Agent，不新增“创建智能体”业务，不修改前端交互模式。Agent Harness 最终采用 `deepagents.create_deep_agent()`，并通过受控 Backend 和权限配置关闭不需要的文件、Shell、Todo 和子 Agent 能力。最终目标是：

```text
Chat API
  ↓
Chat Service
  ↓
Knowledge Agent
  ├── 问题分析
  ├── 受控工具调用
  ├── RAG 检索能力
  └── Agent 统一生成答案和引用
```

明确不保留 `app/rag/chains.py`。RAG 层只保留 Loader、Splitter、Embedding 和 Retriever；Prompt 组装、模型调用、工具编排和答案生成由 `app/agents/` 负责。

## 2. 当前代码基线

当前实现的主要调用链为：

```text
app/api/v1/chat.py
  → app/core/services/knowledge_base/chat.py::chat()
  → app/core/services/knowledge_base/retrieval.py::search()
  → app/rag/chains.py::generate_answer()
  → app/db/knowledge_base/conversation_message.py
  → app/db/knowledge_base/message_citation.py
```

当前关键接口：

```python
async def chat(
    kb_id: int,
    question: str,
    user_id: str,
    conversation_id: int | None = None,
    top_k: int | None = None,
) -> ChatResponse:
    ...
```

```python
async def search(
    kb_id: int,
    query: str,
    top_k: int | None = None,
    mode: str = "vector",
) -> RetrievalResponse:
    ...
```

```python
async def generate_answer(
    question: str,
    chunks: list[dict[str, Any]],
    system_prompt: str | None = None,
) -> str:
    ...
```

迁移后的职责变化：

| 当前职责 | 迁移后职责 |
|---|---|
| `Chat Service` 直接调用检索和 `generate_answer()` | `Chat Service` 只负责业务校验、消息事务和调用 Agent |
| `app/rag/chains.py` 组装 Prompt 并调用模型 | 删除该文件，答案生成代码迁移到 Agent 内部 |
| `retrieval_service.search()` 由 Chat Service 调用 | 由 `tools/retrieval.py` 调用，保留原有检索接口 |
| 检索结果直接转引用 | 由 `tools/citations.py` 校验、去重，再交给 Chat Service 落库 |
| 模型调用占用 Chat Service 数据库事务 | Agent 执行位于两个数据库事务之间 |

调用方向必须保持：

```text
API → Chat Service → Agent → Tools → Retrieval Service / RAG / DB
```

约束：

- `app/api/v1/chat.py` 不调用 Agent 内部工具，不调用模型，不访问数据库。
- `app/core/services/knowledge_base/chat.py` 不实现 Agent Loop，不组装 Prompt，不直接调用模型。
- `app/agents/` 不负责 HTTP 异常转换，不负责打开或提交 Chat Service 的数据库事务。
- `app/agents/tools/retrieval.py` 优先调用 `app/core/services/knowledge_base/retrieval.py::search()`，不直接复制向量检索 SQL。
- `app/rag/` 不生成自然语言答案，不判断用户权限。
- 跨层传递的请求、上下文、工具结果和最终结果使用 Pydantic Schema，不使用无约束 `dict`。

## 4. 核心协议设计

新增文件：`app/schemas/agent.py`。

### 4.1 枚举和基础模型

建议定义以下协议模型：

```python
from typing import Any, Literal

from pydantic import BaseModel, Field

AgentMode = Literal["single_retrieval", "tool_loop"]
AgentStatus = Literal["created", "running", "completed", "failed", "stopped"]
ToolName = Literal[
    "retrieve_knowledge",
    "load_conversation_history",
    "build_citations",
]
```

```python
class AgentTask(BaseModel):
    kb_id: int = Field(..., gt=0)
    question: str = Field(..., min_length=1, max_length=8000)
    conversation_id: int | None = Field(default=None, gt=0)
    user_id: str = Field(..., min_length=1, max_length=128)
    top_k: int | None = Field(default=None, ge=1, le=50)
```

`AgentTask` 是 Chat Service 传给 Agent 的业务任务，不直接复用 HTTP `ChatRequest`，避免 Agent 依赖 FastAPI 层模型。

```python
class AgentContext(BaseModel):
    tenant_id: int | None = None
    organization_ids: list[int] = Field(default_factory=list)
    user_id: str = Field(..., min_length=1)
    kb_id: int = Field(..., gt=0)
    conversation_id: int | None = Field(default=None, gt=0)
    knowledge_base_prompt: str | None = None
```

`AgentContext` 是确定性运行上下文。`tenant_id`、`organization_ids` 和 `user_id` 必须由认证/Service 层注入，不能由模型或用户问题生成。Skill 路径在 Agent 创建时固定为受控的 `/skills/`，不从 `AgentContext` 或用户请求读取。

### 4.2 工具协议

```python
class ToolCall(BaseModel):
    call_id: str = Field(..., min_length=1, max_length=64)
    name: ToolName
    input: dict[str, Any] = Field(default_factory=dict)


class ToolResult(BaseModel):
    call_id: str
    name: ToolName
    ok: bool
    data: dict[str, Any] = Field(default_factory=dict)
    error_code: str | None = None
    error_message: str | None = None
    hit_count: int = 0
```

工具实现内部可以使用具体 Pydantic 输入输出模型，只有在注册表中转换为统一的 `ToolCall` / `ToolResult`。不允许把异常文本直接作为成功的工具结果返回。

### 4.3 检索和引用协议

```python
class RetrievalToolInput(BaseModel):
    query: str = Field(..., min_length=1, max_length=8000)
    top_k: int | None = Field(default=None, ge=1, le=50)


class RetrievalToolOutput(BaseModel):
    kb_id: int
    query: str
    mode: str
    top_k: int
    chunks: list[dict[str, Any]]


class CitationCandidate(BaseModel):
    document_id: int
    chunk_id: int
    source_name: str
    page: int | None = None
    snippet: str
    score: float | None = None
    rank: int
```

`chunks` 的字段必须与现有 `RetrievalChunkDto` 对齐：`id`、`kb_id`、`document_id`、`content`、`source_name`、`page`、`score` 等字段不能在 Agent 内另造一套含义。

### 4.4 Agent 结果协议

```python
class AgentResult(BaseModel):
    answer: str = Field(..., min_length=1)
    citations: list[CitationCandidate] = Field(default_factory=list)
    mode: AgentMode
    status: AgentStatus
    top_k: int
    hit_count: int
    tool_call_count: int = 0
    model_call_count: int = 0
    termination_reason: str
    duration_ms: int
```

Agent 结果只包含 Chat Service 保存和返回所需的信息，不包含完整 Prompt、Token、模型原始响应和未脱敏工具轨迹。

## 5. 目标调用流程和方法签名

### 5.1 Chat Service 对 Agent 的唯一调用

新增 Agent 后，`app/core/services/knowledge_base/chat.py` 只调用一个入口：

```python
async def run(
    task: AgentTask,
    context: AgentContext,
) -> AgentResult:
    ...
```

实际实现可以是模块函数，也可以是 `KnowledgeAgent.run()`；评审时固定对外语义，不固定类名。

目标 Chat Service 流程：

```python
async def chat(...) -> ChatResponse:
    db = DB.get()
    question = await validate(db, kb_id, question, user_id)

    async with db.transaction():
        conversation = await _get_or_create_conversation(...)
        user_message = await _save_message(...)

    task = AgentTask(...)
    context = await _build_agent_context(db, conversation, ...)
    agent_result = await run(task, context)

    async with db.transaction():
        return await _save_agent_result(
            db,
            conversation,
            user_message,
            agent_result,
        )
```

`_build_agent_context()` 只做纯查询和上下文组装；Agent 执行期间不持有该连接上的事务。

### 5.2 Agent 主入口

新增文件：`app/agents/agent.py`。

```python
async def run(
    task: AgentTask,
    context: AgentContext,
) -> AgentResult:
    """统一处理一次知识库问答，不暴露第二个问答入口。"""
```

主入口内部顺序：

1. `validate_task(task, context)` 校验问题、知识库、用户和上下文一致性。
2. `policy.check_context(context)` 校验租户、组织、用户和知识库范围。
3. `load_conversation_history` 按需读取历史。
4. `analyze_question(task.question, history)` 生成确定性的执行意图。
5. 调用 `retrieve_knowledge`。
6. 根据结果判断继续检索还是进入答案生成。
7. 调用 `generate_answer(...)` 生成答案；此函数属于 Agent 内部，不是 RAG Chain。
8. 调用 `build_citations` 并校验引用只能来自实际检索结果。
9. 返回 `AgentResult`。

建议的内部函数签名：

```python
async def _generate_answer(
    task: AgentTask,
    context: AgentContext,
    history: list[dict[str, Any]],
    chunks: list[dict[str, Any]],
) -> str:
    ...
```

该函数可复用当前 `app/rag/chains.py` 中的默认系统指令和消息内容解析逻辑，但需要迁移到 Agent 代码后删除原文件。它只能接收已授权、已校验的 `chunks`。

### 5.3 Agent Runtime

新增文件：`app/agents/runtime.py`。

```python
class AgentRuntime:
    def __init__(
        self,
        *,
        max_steps: int,
        max_tool_calls: int,
        tool_timeout_seconds: float,
        total_timeout_seconds: float,
        max_context_chars: int,
    ) -> None:
        ...

    async def run_tool_loop(
        self,
        task: AgentTask,
        context: AgentContext,
    ) -> AgentResult:
        ...

    async def execute(
        self,
        call: ToolCall,
        context: AgentContext,
    ) -> ToolResult:
        """执行一次经过 Policy 授权的工具调用。"""
        ...

    def next_call_id(self) -> str:
        ...

    def can_continue(self) -> bool:
        ...

    def stop(self, reason: str) -> None:
        ...
```

Runtime 负责：

- 当前步数和工具调用次数递增。
- `asyncio.timeout()` 总体超时和单工具超时。
- 只读工具的有限重试。
- 工具异常转换为 `ToolResult(ok=False)`。
- 达到预算后停止，不再让模型继续调用工具。
- 记录脱敏运行摘要。

Runtime 不负责权限判断；每次调用工具前必须先调用 `policies.authorize_tool()`。

`authorize_tool()` 至少校验：

### 5.5 Agent 创建 API 和创建过程

#### 5.5.1 采用的 API

本项目最终采用 Deep Agents 的：

```python
from deepagents import create_deep_agent
```

项目继续使用 LangChain 作为底层模型和工具框架，但 Agent Harness 使用独立的 `deepagents` 包。`pyproject.toml` 需要新增明确版本范围，例如 `deepagents>=0.6,<0.7`，并通过 `uv add` 和 `uv lock` 更新依赖。

`create_deep_agent()` 的职责是创建一个带 Skills、上下文管理、工具循环和可配置 Backend 的 Agent Graph：

```python
agent_graph = create_deep_agent(
    model=chat_model,
    tools=tools,
    system_prompt=system_prompt,
    skills=["/skills/"],
    backend=StateBackend(),
    permissions=filesystem_permissions,
    response_format=AgentAnswer,
    context_schema=AgentContext,
    name="knowledge_agent",
)
```

它会把模型节点和工具节点组装成循环：

```text
模型分析问题
  ↓
模型返回 tool_calls？
  ├── 是：执行工具 → 把 ToolMessage 放回消息列表 → 再次调用模型
  └── 否：得到最终答案
```

因此，项目不再自行实现一套 `while True` 的模型/工具循环。`AgentRuntime` 负责调用 `agent_graph.ainvoke()`、设置超时和外层预算，Deep Agents Agent Graph 负责模型、工具、Skill 和上下文管理循环。

#### 5.5.2 Agent 不是数据库资源

本项目所说的“创建 Agent”不是用户点击按钮创建一条 Agent 数据，也不是调用 HTTP 的“创建智能体”接口。它是应用进程启动时创建一个 Python 对象：

```text
进程启动
  ↓
读取模型配置
  ↓
创建 ChatOpenAI
  ↓
创建三个受控工具
  ↓
调用 create_deep_agent(...)
  ↓
得到可复用的 CompiledStateGraph
  ↓
每次 Chat 请求调用 agent_graph.ainvoke(...)
```

Agent Graph 应当在应用生命周期内复用，不能在每一次用户提问时重复调用 `create_deep_agent()`。每次请求变化的是 `messages` 和 `context`，不是 Agent 的工具白名单和权限边界。

#### 5.5.3 模型初始化

新增或迁移到 `app/agents/agent.py` 的模型构造方法：

```python
from langchain_openai import ChatOpenAI

from app.config import CONF
from app.core.common.exception import BusiException


def _build_chat_model() -> ChatOpenAI:
    if not CONF.chat.model:
        raise BusiException("Chat 模型未配置")
    if not CONF.chat.api_key:
        raise BusiException("Chat API Key 未配置")

    return ChatOpenAI(
        model=CONF.chat.model,
        api_key=CONF.chat.api_key,
        base_url=CONF.chat.base_url,
        timeout=CONF.chat.timeout_seconds,
    )
```

模型实例只负责调用聊天模型，不负责知识库权限、会话权限或引用校验。`base_url` 继续使用项目现有 OpenAI-compatible 配置，因此不把模型供应商写死在 Agent 逻辑中。

#### 5.5.4 工具创建和注册

LangChain 1.x 推荐使用 `@tool` 把具名 Python 函数转换为工具。工具参数由函数签名生成 Schema，工具返回结构化的 Pydantic 模型：

```python
from langchain.tools import ToolRuntime, tool


@tool
async def retrieve_knowledge(
    query: str,
    top_k: int | None = None,
    *,
    runtime: ToolRuntime[AgentContext],
) -> RetrievalToolOutput:
    """检索当前用户有权限访问的知识库内容。"""
    context = runtime.context
    await policies.authorize_retrieval(context)

    retrieval = await retrieval_service.search(
        context.kb_id,
        query,
        top_k=top_k,
    )
    return RetrievalToolOutput(
        kb_id=retrieval.kb_id,
        query=retrieval.query,
        mode=retrieval.mode,
        top_k=retrieval.top_k,
        chunks=[chunk.model_dump() for chunk in retrieval.chunks],
    )
```

历史和引用工具同样创建为 `@tool` 函数：

```python
@tool
async def load_conversation_history(
    limit: int = 10,
    *,
    runtime: ToolRuntime[AgentContext],
) -> HistoryToolOutput:
    ...


@tool
async def build_citations(
    chunks: list[dict[str, Any]],
    *,
    runtime: ToolRuntime[AgentContext],
) -> CitationToolOutput:
    ...
```

工具函数中的 `runtime` 由 LangChain 注入，不能由模型传入。`runtime.context` 是本次请求的 `AgentContext`，其中的用户、租户、组织和知识库范围由 Chat Service 注入。

工具注册集中在一个方法中：

```python
def _build_tools() -> list[BaseTool]:
    return [
        retrieve_knowledge,
        load_conversation_history,
        build_citations,
    ]
```

不允许根据模型输出动态导入工具，不允许把模块路径、函数名或 HTTP 地址作为工具配置传给 Agent。

#### 5.5.5 创建 Deep Agent Graph

建议在 `app/agents/agent.py` 中实现懒加载单例或应用生命周期初始化：

```python
from functools import lru_cache

from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from langchain_core.tools import BaseTool


AGENT_SYSTEM_PROMPT = """你是企业知识库问答智能体。
必须先使用授权知识库检索工具获取事实依据，再基于工具返回内容回答。
需要比较、汇总或补充上下文时，可以继续调用只读工具。
不得编造知识库中没有的事实，不得自行声称拥有用户、租户或知识库权限。
最终答案必须简洁，并且只能使用实际检索结果生成引用。
"""


@lru_cache(maxsize=1)
def get_knowledge_agent():
    chat_model = _build_chat_model()
    tools: list[BaseTool] = _build_tools()
    return create_deep_agent(
        model=chat_model,
        tools=tools,
        system_prompt=AGENT_SYSTEM_PROMPT,
        skills=["/skills/"],
        backend=StateBackend(),
        permissions=_build_filesystem_permissions(),
        response_format=AgentAnswer,
        context_schema=AgentContext,
        name="knowledge_agent",
        debug=False,
    )
```

这里的 `get_knowledge_agent()` 返回 Deep Agents 基于 LangGraph 编译的 `CompiledStateGraph`。它不是一个 FastAPI 路由，也不直接暴露给前端。

`@lru_cache(maxsize=1)` 只是示意；如果项目使用 FastAPI lifespan，更推荐在应用启动时创建并放入 `app.state`，关闭时释放相关资源：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.knowledge_agent = build_knowledge_agent()
    yield
    app.state.knowledge_agent = None
```

Agent Graph 不应在工具函数内部创建，也不应在 `chat()` 每次请求中创建。

#### 5.5.6 一次请求如何调用 Agent

`run()` 负责把业务协议转换为 LangChain 输入，再把 LangChain 输出转换回 `AgentResult`：

```python
async def run(
    task: AgentTask,
    context: AgentContext,
) -> AgentResult:
    agent = get_knowledge_agent()
    started_at = monotonic()

    try:
        result = await asyncio.wait_for(
            agent.ainvoke(
                {
                    "messages": [
                        {"role": "user", "content": task.question},
                    ],
                },
                context=context,
                config={
                    "run_name": "knowledge_agent",
                    "tags": ["knowledge-base", f"kb:{task.kb_id}"],
                    "metadata": {
                        "kb_id": task.kb_id,
                        "conversation_id": task.conversation_id,
                    },
                    "recursion_limit": 8,
                },
            ),
            timeout=CONF.agent.total_timeout_seconds,
        )
    except TimeoutError as exc:
        raise ToolTimeout("Agent 执行超时") from exc
    except Exception as exc:
        raise AgentError("Agent 执行失败") from exc

    return _convert_agent_output(result, task, started_at)
```

调用过程中的关键数据：

```python
{
    "messages": [
        {"role": "user", "content": "请比较两个报销制度的差异"},
        # AIMessage(tool_calls=[...])
        # ToolMessage(content=...)
        # AIMessage(tool_calls=[...])
        # ToolMessage(content=...)
        # AIMessage(content="最终答案")
    ]
}
```

`context` 不放入用户消息，也不让模型生成；它通过 `context_schema=AgentContext` 和 `agent.ainvoke(..., context=context)` 注入工具运行时。

#### 5.5.7 结构化最终答案

建议使用 `response_format` 约束最终答案，而不是从自然语言中猜引用：

```python
class AgentAnswer(BaseModel):
    answer: str = Field(..., min_length=1)
    citation_chunk_ids: list[int] = Field(default_factory=list)
    termination_reason: str
```

创建时传入：

```python
create_deep_agent(
    model=chat_model,
    tools=_build_tools(),
    response_format=AgentAnswer,
    context_schema=AgentContext,
)
```

执行后从结果的 `structured_response` 读取：

```python
structured = result.get("structured_response")
if not isinstance(structured, AgentAnswer):
    raise AgentOutputInvalid("Agent 结构化输出不合法")

validate_citation_chunk_ids(
    structured.citation_chunk_ids,
    retrieved_chunks,
)
```

`citation_chunk_ids` 只能用于从已经检索到的 chunk 中筛选引用，不能直接作为数据库引用记录写入。最终仍由 `build_citations()` 读取原始检索结果并生成完整 `CitationCandidate`。

#### 5.5.8 创建 API 与业务 API 的边界

| 类型 | API/方法 | 调用时机 | 是否对前端开放 |
|---|---|---|---|
| Agent 创建 | `deepagents.create_deep_agent()` | 应用启动或首次使用时一次 | 否 |
| Agent 获取 | `get_knowledge_agent()` | Chat Service 调用前 | 否 |
| Agent 执行 | `agent.ainvoke(inputs, context=..., config=...)` | 每次问答一次 | 否 |
| 业务问答 | `app/core/services/knowledge_base/chat.py::chat()` | HTTP 请求进入后 | 是，通过现有 Chat API |
| 工具执行 | LangChain Agent Graph 内部调用 `@tool` | 模型产生工具调用时 | 否 |

本项目不存在以下接口：

```text
POST /agents
POST /agents/{agent_id}/tools
PUT /agents/{agent_id}
DELETE /agents/{agent_id}
```

#### 5.5.10 `create_deep_agent` 最终实现方案

##### 5.5.10.1 API 和依赖

`create_deep_agent` 不是 `langchain` 包中的函数，而是独立 Python 包 `deepagents` 提供的入口：

```python
from deepagents import create_deep_agent
```

官方文档给出的基本调用形式是：

```python
agent = create_deep_agent(
    model=chat_model,
    tools=[my_custom_tool],
    system_prompt="You are a research assistant.",
)
```

当前项目本地没有安装 `deepagents`，`pyproject.toml` 也没有声明该依赖。官方 PyPI 当前显示 `deepagents 0.6.12`，项目状态为 Beta；官方文档同时提供了 `skills`、`backend`、`permissions`、`context_schema`、`checkpointer` 等参数。

##### 5.5.10.2 内置 Harness 能力

`create_deep_agent` 提供完整的 Agent Harness。官方默认能力包括：

- `write_todos`：任务清单。
- `ls`、`read_file`、`write_file`、`edit_file`、`delete`、`glob`、`grep`：文件系统工具。
- `execute`：执行命令；具体是否可执行取决于 Backend。
- `task`：调用子 Agent。
- Skills 渐进式加载。
- 长上下文摘要和上下文卸载。
- 可选的 Checkpointer、Store、人机确认和持久化能力。

##### 5.5.10.3 `create_deep_agent` 的 Skill 创建过程

Skill 由 Deep Agents 内置的 `SkillsMiddleware` 负责发现、加载和渐进式披露。具体过程是：

```text
create_deep_agent(
    skills=["/skills/"],
    backend=StateBackend(),
)
  ↓
SkillsMiddleware 扫描 Skill 路径的 SKILL.md front matter
  ↓
启动时只注入 Skill 名称和描述
  ↓
模型判断当前任务需要某个 Skill
  ↓
模型调用 read_file 读取该 Skill 的完整 SKILL.md
  ↓
模型按 Skill 指令继续执行
```

官方 Skills 采用渐进式披露：启动时只加载名称和描述，Skill 激活后才读取完整 `SKILL.md`，引用的 `references/`、`scripts/`、`assets/` 也按需读取。

静态 Skill 的示意实现：

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend


def build_deep_agent():
    return create_deep_agent(
        model=_build_chat_model(),
        tools=_build_tools(),
        system_prompt=AGENT_SYSTEM_PROMPT,
        skills=["/skills/"],
        backend=StateBackend(),
        context_schema=AgentContext,
        response_format=AgentAnswer,
        name="knowledge_agent",
    )
```

如果使用 `StateBackend`，需要在 Agent 输入的虚拟文件系统中提供 Skill 文件；如果使用 `FilesystemBackend`，需要配置一个明确的根目录。不能直接让 Deep Agents 读取宿主机任意目录：

```python
skills_files = {
    "/skills/query-analysis/SKILL.md": create_file_data(
        query_analysis_skill_text
    ),
    "/skills/answer-writing/SKILL.md": create_file_data(
        answer_writing_skill_text
    ),
}

result = await agent.ainvoke(
    {
        "messages": [{"role": "user", "content": question}],
        "files": skills_files,
    },
    context=context,
)
```

这里需要新增 `deepagents.backends`、虚拟文件数据和文件权限测试，运行模型还会看到 Deep Agents 提供的文件相关工具。

##### 5.5.10.4 对本项目的最终选型

本项目正式采用 `create_deep_agent()`，使用其原生的 Skill 渐进式加载、上下文管理和 Agent Harness 能力。

但采用后必须做“能力裁剪”，不能直接使用默认安全边界：

1. 业务工具只传入 `retrieve_knowledge`、`load_conversation_history` 和 `build_citations`。
2. Backend 只提供虚拟 Skill 文件和受控引用资源，禁止指向项目根目录、数据库目录、配置目录或宿主机任意路径。
3. 文件系统工具即使由 Deep Agents 默认注册，也必须通过权限配置和工具可见性测试确认不可读写业务文件。
4. `execute`、`write_file`、`edit_file`、`delete` 和 `task` 不属于本项目的业务能力，第一阶段必须拒绝或从最终工具面移除。
5. 业务权限仍由 `policies.py` 和工具内部确定性校验负责，不能依赖 Deep Agents 的 Skill 或默认提示词。
6. 通过 `recursion_limit`、外层 `asyncio.wait_for()` 和 Agent 配置共同限制步数、工具次数和总体耗时。

最终调用关系：

```text
Chat Service
  ↓
AgentRuntime
  ↓
deepagents.create_deep_agent() 创建的 CompiledStateGraph
  ├── SkillsMiddleware：按需发现和加载 SKILL.md
  ├── SummarizationMiddleware：受控上下文压缩
  ├── 自定义只读业务工具
  └── 受权限限制的文件 Backend
```

##### 5.5.10.5 采用前置条件和验收项

- 在 `pyproject.toml` 中新增 `deepagents>=0.6,<0.7`，使用 `uv add`，并提交同步后的 `uv.lock`。
- 固定并验证 `deepagents`、`langchain`、`langgraph` 的兼容版本。
- 用 `permissions` 和工具面测试验证 `write_file`、`edit_file`、`delete`、`execute` 和 `task` 不可用。
- 明确使用 `StateBackend` 还是受控 `FilesystemBackend`；第一阶段优先使用 `StateBackend`，不读取宿主机文件。
- 为 Skill 发现、按需读取、Skill 路径越界、文件工具越权和跨请求状态建立集成测试。
- 为内置 Skills、Filesystem、Summarization 和 SubAgent Middleware 建立版本锁定和回归测试。
- 只有通过上述验收后，`create_deep_agent()` 才能接入 Chat Service 作为正式运行入口。

### 6.2 知识库检索工具

新增文件：`app/agents/tools/retrieval.py`。

```python
async def retrieve_knowledge(
    call: ToolCall,
    context: AgentContext,
) -> ToolResult:
    payload = RetrievalToolInput.model_validate(call.input)
    if payload.query.strip() == "":
        return ToolResult(
            call_id=call.call_id,
            name="retrieve_knowledge",
            ok=False,
            error_code="EMPTY_QUERY",
            error_message="检索问题不能为空",
        )

    retrieval = await retrieval_service.search(
        context.kb_id,
        payload.query,
        top_k=payload.top_k,
    )
    return ToolResult(
        call_id=call.call_id,
        name="retrieve_knowledge",
        ok=True,
        data=RetrievalToolOutput(
            kb_id=retrieval.kb_id,
            query=retrieval.query,
            mode=retrieval.mode,
            top_k=retrieval.top_k,
            chunks=[chunk.model_dump() for chunk in retrieval.chunks],
        ).model_dump(),
        hit_count=len(retrieval.chunks),
    )
```

实现要点：

- 优先复用 `app/core/services/knowledge_base/retrieval.py::search()`，不复制 `embeddings.embed_texts()` 和 `retrievers.vector_search()` 的流程。
- `context.kb_id` 是唯一可信知识库 ID，不接受模型在输入中覆盖。
- 工具失败时返回结构化失败结果；数据库错误和模型错误不能伪装为“检索无结果”。
- RAG 层只返回 `RetrievalResponse`，不组装 Prompt，不调用聊天模型。

## 7. Chat Service 改造细节

修改文件：`app/core/services/knowledge_base/chat.py`。

### 7.1 删除的逻辑

删除以下导入和调用：

```python

```

删除 `_chat_in_transaction()` 将检索、模型调用、消息写入全部包在一个事务中的实现。

### 7.2 保留和拆分的方法

保留：

- `validate()`：参数和知识库基础校验。
- `_get_or_create_conversation()`：会话创建或复用。
- `_save_message()`：消息写入。
- `_citation_values()`：将已校验的引用转换为数据库字段。

新增：

```python

    ...


async def _save_agent_result(
    db,

```

`_save_agent_result()` 必须在一个事务内完成：

1. 将 `AgentResult.answer` 保存为 assistant message。
2. 将 `result.citations` 转换为 `message_citation_db.insert_()` 参数并批量写入或逐条写入。
3. 写入 `mode`、`top_k`、`hit_count`、`tool_call_count`、`model_call_count`、`termination_reason` 等非敏感 metadata。
4. 组装现有 `ChatResponse`。

### 7.3 事务实现

推荐改为：

```python
async def chat(...) -> ChatResponse:
    db = DB.get()
    question = await validate(db, kb_id, question, user_id)

    async with db.transaction():
        conversation = await _get_or_create_conversation(...)
        user_message = await _save_message(...)

    try:
        context = await _build_agent_context(db, conversation, user_id)
        result = await run(
            AgentTask(
                kb_id=kb_id,
                question=question,
                user_id=user_id,
                conversation_id=conversation["id"],
                top_k=top_k,
            ),
            context,
        )
    except AgentError as exc:
        # 这里记录结构化失败信息；不保存不完整 assistant 消息。
        raise BusiException(exc.public_message, status_code=exc.status_code) from exc

    async with db.transaction():
        return await _save_agent_result(db, conversation, user_message, result)
```

如果当前项目的 DB 连接上下文不支持事务之间长时间复用，需要为 Agent 工具调用使用独立的短查询连接，并在每次工具内部完成连接获取和释放；不能把事务连接传入 Agent。

## 8. Agent 内部执行算法

### 8.1 单次检索模式

适用于单主题、事实型、无需比较多个来源的问题。

```python
async def _run_single_retrieval(
    task: AgentTask,
    context: AgentContext,
    runtime: AgentRuntime,
) -> AgentResult:
    retrieval_result = await runtime.execute(
        ToolCall(
            call_id=runtime.next_call_id(),
            name="retrieve_knowledge",
            input={"query": task.question, "top_k": task.top_k},
        ),
        context,
    )
    chunks = _require_retrieval_chunks(retrieval_result)
    answer = await _generate_answer(task, context, [], chunks)
    citations = await _build_and_validate_citations(chunks, context, runtime)
    return _build_result(...)
```

单次模式不能绕过检索直接回答知识库事实问题。只有明确属于闲聊、问候或不需要知识库的输入，才允许由策略决定是否返回固定的非知识库回答；当前第一阶段可以全部要求检索。

### 8.2 多步工具模式

适用于比较、汇总、多轮追问或需要多个知识库上下文的问题。以下代码是策略和结果整理的示意；真正的工具循环由 `create_deep_agent()` 返回的 Agent Graph 负责，业务代码只调用一次 `agent.ainvoke()`。

```python
async def _run_tool_loop(
    task: AgentTask,
    context: AgentContext,
    runtime: AgentRuntime,
) -> AgentResult:
    history = await _load_history_if_needed(context, runtime)
    queries = await _plan_retrieval_queries(task.question, history, runtime)
    all_chunks: list[dict[str, Any]] = []

    for query in queries:
        if not runtime.can_continue():
            break
        result = await runtime.execute(
            ToolCall(
                call_id=runtime.next_call_id(),
                name="retrieve_knowledge",
                input={"query": query, "top_k": task.top_k},
            ),
            context,
        )
        all_chunks.extend(_extract_chunks(result))

    chunks = _deduplicate_chunks(all_chunks)
    answer = await _generate_answer(task, context, history, chunks)
    citations = await _build_and_validate_citations(chunks, context, runtime)
    return _build_result(...)
```

第一阶段不允许模型直接生成任意 SQL、HTTP 请求或文件路径。多步循环中的“规划”只能生成检索关键词和受控工具调用参数。

### 8.3 选择策略的方法

```python
def choose_mode(
    question: str,
    history: list[dict[str, Any]],
) -> AgentMode:
    ...
```

初始实现建议使用确定性规则，避免一开始让模型决定完整执行流程：

- 包含“比较、差异、分别、汇总、综合、多个、上一条、继续”等词时，优先 `tool_loop`。
- 问题短、单主题且没有多轮依赖时，使用 `single_retrieval`。
- 历史消息超过上下文阈值时，先压缩或截断，不直接把全部历史交给模型。

后续可让模型输出结构化 `QuestionPlan`，但仍需经过 `policies.py` 校验，不能让模型直接决定权限和预算。

## 9. 错误模型和异常处理

新增文件或在 `app/agents/agent.py` 中定义：

```python
class AgentError(Exception):
    code: str
    public_message: str
    status_code: int = 500


class ToolPermissionDenied(AgentError):
    ...


class ToolTimeout(AgentError):
    ...


class AgentBudgetExceeded(AgentError):
    ...


class AgentOutputInvalid(AgentError):
    ...
```

处理规则：

| 错误 | Agent 行为 | Chat Service 行为 |
|---|---|---|
| 检索无结果 | 生成“资料不足”答案，引用为空 | 正常保存可验证的 assistant 消息 |
| 权限拒绝 | 停止当前运行，不继续换工具绕过 | 返回统一无权限异常，不保存不完整答案 |
| 工具超时 | 只读工具按规则重试，超过次数后停止 | 返回可解释错误或保存失败状态 |
| 模型失败 | 转换为 `AgentError` | 不保存 assistant 消息，用户消息事务已提交 |
| 引用校验失败 | 拒绝结果 | 不保存不完整答案 |
| 达到预算 | 返回当前可验证结果或停止错误 | 按评审结论决定是否保存部分结果 |

不能把所有异常都转换为“检索无结果”，否则会掩盖权限、数据库和模型故障。

建议在 `app/config/chat.py` 增加 Agent 配置模型，不把限制硬编码在业务函数中：

- `app/rag/chains.py` 删除后，完整 Chat 流程仍可运行。

### 11.6 Skill 测试

新增 `tests/agents/skills/test_deepagents_skills.py` 和 `test_deepagents_permissions.py`：

- 缺失、超大、格式错误或非法路径的 `SKILL.md` 会被 Deep Agents Skill Middleware 拒绝或报告加载错误。
- Deep Agents 只能从受控 Backend 的 `/skills/` 路径加载 Skill。
- 启动时发现 `answer-writing` 和 `query-analysis` 的 Skill 元数据，任务需要时才读取完整正文。
- Skill 路径固定来自 Agent 创建时的 `/skills/` 配置，用户请求不能注入未注册 Skill 路径。
- 内置 `SkillsMiddleware` 只负责 Skill 发现和按需读取，不会修改工具列表、Policy 或预算。
- Skill 内容不会出现在前端响应和普通业务日志中。
