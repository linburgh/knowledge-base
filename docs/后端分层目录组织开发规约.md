# 后端分层目录组织开发规约

## 文档目标

本规约统一后端 Service 与 DB Repository 的业务归属、目录结构、文件命名、导入方式和变更流程。后续新增、拆分、迁移或重命名后端模块时必须遵守本规约，不再使用业务文件根目录平铺、目录与文件重复表达同一语义或保留旧路径兼容入口的组织方式。

## 适用范围

本规约适用于：

- `app/core/services/` 下的业务编排模块。
- `app/db/` 下的 Repository 和数据库基础设施。
- 引用上述模块的 API、Worker、Agent、RAG、公共模块、测试、脚本和设计文档。
- 后续新增的平台管理、知识库管理和自主监控后端能力。

## 整改总结

本次整改分三步完成：

1. 将原来平铺在 `app/core/services/` 根目录的业务 Service，按平台管理、知识库管理和自主监控归入 `platform/`、`knowledge_base/`、`monitoring/`。
2. 将原来平铺在 `app/db/` 根目录的业务 Repository 按相同业务域归档，根目录只保留数据库基础设施。
3. 删除包内重复业务域前缀，主业务管理模块统一为 `mgr.py`，同步修正源码、动态模块路径、测试和文档引用。

整改后的结果满足以下要求：

- Service 与 DB 使用一致的一级业务域。
- 目录负责表达业务归属，文件负责表达域内职责。
- 不保留旧文件作为兼容转发入口，避免形成双路径。
- 目录结构、模块导入和全量后端测试均有自动化校验。

## 核心原则

- 业务归属优先于调用位置。同一 Repository 被多个 Service 调用时，仍按其数据实体的业务归属存放。
- 目录表达业务域，文件名不得机械重复目录已经表达的语义。
- Service 负责编排和事务，DB 负责数据访问，不因目录重构改变分层职责。
- 公共基础设施留在根目录，业务代码必须进入明确的业务域目录。
- 重命名必须一次性更新所有调用方，不得保留无期限兼容层。
- 新增业务域必须先完成设计评审，不得自行创建含义重叠的新一级目录。

## 目录规约

### 服务目录

标准结构如下：

```text
app/core/services/
├── __init__.py
├── platform/
│   ├── __init__.py
│   ├── authentication.py
│   ├── evaluation.py
│   ├── overview.py
│   └── ...
├── knowledge_base/
│   ├── __init__.py
│   ├── mgr.py
│   ├── document.py
│   ├── chat.py
│   ├── overview.py
│   ├── qa_config.py
│   └── ...
└── monitoring/
    ├── __init__.py
    ├── mgr.py
    ├── access.py
    ├── analysis.py
    ├── analysis_tools.py
    ├── rule.py
    └── ...
```

`app/core/services/` 根目录除 `__init__.py` 外不得新增业务 Service。

### 数据目录

标准结构如下：

```text
app/db/
├── __init__.py
├── api.py
├── base.py
├── models.py
├── vector_store.py
├── platform/
│   ├── __init__.py
│   ├── user.py
│   ├── tenant.py
│   ├── overview.py
│   └── ...
├── knowledge_base/
│   ├── __init__.py
│   ├── mgr.py
│   ├── document.py
│   ├── index_version.py
│   ├── qa_config.py
│   └── ...
└── monitoring/
    ├── __init__.py
    ├── alert.py
    ├── event.py
    ├── metric_rule.py
    ├── notification_policy.py
    └── ...
```

DB 根目录允许保留的文件职责如下：

| 文件 | 职责 |
| --- | --- |
| `api.py` | 通用数据库访问封装和 SQL 日志入口 |
| `base.py` | 数据库连接、上下文、事务和生命周期 |
| `models.py` | 当前项目统一的 SQLAlchemy Table 定义 |
| `vector_store.py` | 向量库基础适配入口 |
| `__init__.py` | DB 包初始化和公开基础入口 |

除上述基础设施外，不得在 `app/db/` 根目录新增业务 Repository。

## 归属规则

| 业务域 | Service 目录 | DB 目录 | 典型职责 |
| --- | --- | --- | --- |
| 平台管理 | `app/core/services/platform/` | `app/db/platform/` | 用户、租户、组织、角色、菜单、认证、审计、平台概览、自主评测管理 |
| 知识库管理 | `app/core/services/knowledge_base/` | `app/db/knowledge_base/` | 知识库、文档、索引、会话、消息、引用、检索、问答配置 |
| 自主监控 | `app/core/services/monitoring/` | `app/db/monitoring/` | 事件、指标、规则、告警、证据、通知、采集配置、分析会话编排 |

归属判断依次遵循：

1. 判断模块维护的核心业务实体。
2. 判断该实体所属的一级业务域。
3. 按业务实体归属放置，不按当前调用者所在目录放置。
4. 确实跨域且不含业务语义的纯工具，优先检查 `app/core/common/` 或现有基础设施，不得直接放回 Service、DB 根目录。

自主评测的管理 Service 与 Repository 当前归入平台管理；评测 Agent Harness 仍独立位于 `app/agents/evaluation/`，不得因 DB 和 Service 归档而合并 Agent 边界。

## 命名规约

### 基本命名

- Python 包和文件统一使用小写 snake_case。
- 目录已经表达业务域后，文件名只表达域内职责。
- `knowledge_base/` 内不得再使用 `knowledge_base_` 文件前缀。
- `monitoring/` 内不得再使用 `monitoring_` 或 `monitor_` 文件前缀。
- 文件名必须使用明确业务名词，不使用 `common.py`、`utils.py`、`helper.py` 等无法判断职责的泛化名称。

正确示例：

```text
app/core/services/knowledge_base/qa_config.py
app/core/services/monitoring/analysis.py
app/db/knowledge_base/index_version.py
app/db/monitoring/notification_policy.py
```

禁止示例：

```text
app/core/services/knowledge_base/knowledge_base_qa_config.py
app/core/services/monitoring/monitoring_analysis.py
app/db/knowledge_base/knowledge_base_index_version.py
app/db/monitoring/monitor_notification_policy.py
```

### 主干模块

`mgr.py` 表示一个业务域的主资源管理入口，适用于承担该域核心资源增删改查、授权关系和主流程编排的模块。

- 知识库主 Service：`app/core/services/knowledge_base/mgr.py`。
- 自主监控主 Service：`app/core/services/monitoring/mgr.py`。
- 知识库主 Repository：`app/db/knowledge_base/mgr.py`。
- 每个业务域、每个分层最多设置一个 `mgr.py`。
- 单一实体或专项能力不得为了缩短名称改叫 `mgr.py`，应使用 `document.py`、`rule.py`、`overview.py` 等明确名称。

### 命名例外

去前缀以不损失业务语义为前提。`platform_role.py` 等名称对应稳定的领域实体 `PlatformRole`，删除 `platform_` 后可能与组织角色、租户角色混淆，因此允许保留。新增例外必须在本规约中登记原因，不得由开发者自行扩展。

## 分层职责

### 服务职责

- 业务参数和状态校验。
- 权限、租户和数据范围校验。
- 事务边界及多步业务编排。
- 调用 DB、RAG、Agent 或外部服务。
- 将底层结果转换为内部 Schema 所需数据。

Service 不得直接解析 FastAPI `Request`、构造 `Response` 或抛出 `HTTPException`，不得绕过已有 Repository 直接操作 `models.py` 或通用 `db/api.py`。

### 数据职责

- 按表或紧密相关实体封装 `insert_`、`batch_insert`、`update_`、`delete_`、`get`、`list` 等数据操作。
- 复用 `app/db/api.py` 和 `app/db/base.py`。
- 记录统一、脱敏的 SQL 执行日志。
- 返回数据库记录或稳定的数据访问结果。

DB 不得处理 HTTP 展示、权限决策、Prompt 拼接、自然语言回答或跨步骤业务事务编排。

## 导入规约

调用方必须从最终业务包导入模块，并使用能够表达分层职责的别名：

```python
from app.core.services.knowledge_base import mgr as knowledge_base_service
from app.core.services.monitoring import analysis as analysis_service
from app.core.services.monitoring import mgr as monitoring_service

from app.db.knowledge_base import document as document_db
from app.db.knowledge_base import mgr as knowledge_base_db
from app.db.monitoring import alert as alert_db
from app.db.platform import user as user_db
```

禁止使用旧平铺路径、旧冗余文件名或模糊别名：

```python
from app.core.services import knowledge_base
from app.core.services.monitoring import monitoring
from app.db import document
from app.db.monitoring import monitor_alert
```

各业务包的 `__init__.py` 默认只作为包标识，不批量重导出业务模块，也不提供旧路径兼容。确需公开稳定入口时必须明确列出 `__all__`，并同步补充测试。

## 新增流程

新增 Service 或 Repository 时按以下顺序执行：

1. 明确核心业务实体及一级业务域。
2. 检查目标包内是否已有相同职责模块，优先扩展现有文件。
3. 判断是主资源管理、专项能力还是单表 Repository，选择 `mgr.py` 或明确的职责名。
4. Service 写操作显式使用事务，并通过对应业务域 Repository 访问数据。
5. 更新 API、Worker、Agent、测试、脚本和文档导入。
6. 更新目录结构自动化测试中的预期模块清单。
7. 执行编译、结构测试和后端全量测试。

## 迁移流程

已有模块迁移或重命名时必须一次完成：

1. 使用全仓搜索盘点静态导入、动态导入字符串、Mock/Patch 路径和文档路径。
2. 移动文件并建立必要的 `__init__.py`。
3. 更新模块内部跨层、跨域和相对导入。
4. 更新 API、Worker、Agent、RAG、公共模块和测试引用。
5. 更新 DML、配置或任务定义中的动态模块路径。
6. 更新设计文档、实施文档、测试用例和工程规约。
7. 删除旧源码和生成缓存，不保留兼容转发文件。
8. 搜索旧路径残留并执行完整验证。

## 禁止事项

- 禁止在 Service 或 DB 根目录新增业务文件。
- 禁止创建 `platform_management/`、`knowledge_base_management/`、`autonomous_monitoring/` 等已废弃目录。
- 禁止在 `knowledge_base/`、`monitoring/` 内重复业务域前缀。
- 禁止同时保留新旧两个可导入路径。
- 禁止只移动文件而不更新动态路径、测试和文档。
- 禁止通过 `__init__.py` 通配重导出掩盖错误的模块归属。
- 禁止因某个调用方跨域使用 Repository 而复制一份数据访问代码。
- 禁止借目录整改修改接口语义、数据库表名、权限编码或业务状态。

## 验收清单

每次新增或调整后至少确认：

- [ ] Service 和 DB 模块进入正确业务域。
- [ ] 根目录未新增业务文件。
- [ ] 文件名未重复所属包前缀。
- [ ] `mgr.py` 使用符合主资源管理语义且没有重复。
- [ ] API、Worker、Agent、RAG 和公共模块导入已更新。
- [ ] 动态模块字符串和 Mock/Patch 路径已更新。
- [ ] 设计文档、实施文档和测试用例路径已更新。
- [ ] `tests/test_service_directory_structure.py` 预期清单已更新。
- [ ] `tests/test_db_directory_structure.py` 预期清单已更新。
- [ ] 不存在旧源码或兼容转发入口。
- [ ] Python 编译通过。
- [ ] 目录结构测试通过。
- [ ] 后端全量测试通过。

## 校验基线

```bash
.venv/bin/python -m compileall -q app tests
.venv/bin/python -m unittest \
  tests.test_service_directory_structure \
  tests.test_db_directory_structure
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
.venv/bin/ruff check \
  tests/test_service_directory_structure.py \
  tests/test_db_directory_structure.py
git diff --check
```

当前整改验收基线为后端全量 115 项测试通过。后续测试数量增加时以实际全量执行结果为准，不得固定依赖该数量判断成功。
