# ai-code-review 需求设计文档

## 1. 文档说明

### 1.1 项目名称

`ai-code-review`

### 1.2 项目定位

`ai-code-review` 是面向研发团队的智能代码审查 Agent。它接收 Pull Request、Merge Request、提交范围或本地代码变更，结合代码差异、仓库上下文、静态分析工具、项目规范和历史反馈，输出可验证、可定位、可执行的审查意见，并支持将结果同步回代码托管平台。

系统重点解决以下问题：

- 审查人员无法及时覆盖所有变更。
- 传统静态检查只能发现固定规则问题，无法结合业务上下文判断风险。
- 代码审查意见缺少统一严重级别、证据和修复建议。
- 审查结果分散在平台评论、聊天和本地报告中，难以统计和追踪。
- 团队规范、历史缺陷和代码所有权没有进入审查上下文。

### 1.3 文档范围

本文覆盖产品需求、用户角色、业务流程、页面模块、Agent 编排、接口、数据模型、权限、状态、异常、扩展性、评测和部署计划。

本文不规定具体模型供应商、前端框架或基础设施品牌；实现阶段通过 Provider、Model 和 Tool 适配层隔离外部依赖。

### 1.4 目标读者

- 产品经理：确认业务范围、流程和验收标准。
- 前端开发：实现项目、审查任务、结果和设置页面。
- 后端开发：实现任务编排、权限、数据和外部平台适配。
- Agent 开发：实现分析器、工具调用、证据链和结果验证。
- 测试与安全人员：设计评测集、回归规则和安全边界。

## 2. 产品目标与非目标

### 2.1 产品目标

1. 支持从代码差异到审查结果发布的完整闭环。
2. 每条问题必须尽量包含文件、行号、问题类型、严重级别、证据和修复建议。
3. 对高风险问题优先使用确定性工具和规则验证，降低模型误报。
4. 支持组织级、项目级和任务级审查规则配置。
5. 支持审查结果的忽略、确认、修复、误报反馈和重新审查。
6. 支持多代码托管平台、多语言和多模型扩展。
7. 保证代码、Token、私有仓库内容和模型请求数据的最小暴露。
8. 通过离线评测和线上反馈持续衡量准确率、覆盖率和审查时延。

### 2.2 非目标

- 不自动直接修改生产分支。
- 不以模型意见替代人工审批、分支保护和安全发布流程。
- 不默认执行具有破坏性的构建、测试、迁移或脚本。
- 不把完整仓库内容无条件发送给外部模型。
- 不在审查结果中泄露密钥、个人隐私或未授权文件内容。

## 3. 用户角色与权限

| 角色 | 主要能力 |
|---|---|
| 平台管理员 | 管理组织、成员、模型 Provider、全局规则、审计和系统配置。 |
| 组织管理员 | 管理组织成员、项目接入、项目规则、代码平台连接和审查策略。 |
| 项目管理员 | 管理项目成员、默认审查规则、Webhook、审查回写策略和忽略规则。 |
| 审查发起人 | 创建审查任务、查看结果、重新审查、处理问题和提交反馈。 |
| 普通成员 | 查看有权限项目的审查结果，确认、忽略或反馈自己负责的结果。 |
| 只读访客 | 查看已授权的项目、任务摘要和报告，不得触发审查或修改状态。 |
| Worker | 执行代码获取、解析、工具运行和 Agent 任务，不代表业务用户权限。 |

权限分为四层：

1. 组织权限：是否可以查看和管理组织资源。
2. 项目权限：是否可以访问项目、规则、连接和审查任务。
3. 操作权限：是否可以创建审查、重新执行、发布评论、修改规则和处理问题。
4. 数据范围：可见的仓库、分支、文件路径、审查结果和日志范围。

Worker 执行任务时必须携带任务创建者和项目权限快照；任务过程中不得因为权限变化扩大数据访问范围。

## 4. 支持场景与输入方式

### 4.1 Pull Request / Merge Request 审查

代码平台通过 Webhook 通知系统，系统根据 Provider、仓库和变更编号获取 PR/MR 元数据及差异，创建审查任务并在完成后回写摘要和行级评论。

### 4.2 提交范围审查

用户选择仓库、基准提交和目标提交，系统获取两者之间的差异，生成一次独立审查任务。

### 4.3 本地变更或补丁审查

用户上传标准 Patch、压缩包或选择受控目录，系统在隔离工作区中解析差异。该模式默认只生成报告，不回写代码平台。

### 4.4 定时基线审查

项目可以配置定时任务，对指定分支的新增提交或全量基线执行审查，用于发现遗留安全问题和规范偏差。

### 4.5 命令行和 API 审查

提供非页面入口，用于 CI、IDE 插件和内部工具调用。API 创建的任务与页面任务使用相同的权限、状态和结果模型。

## 5. 核心业务流程

### 5.1 总体流程

```text
创建任务
  -> 校验项目与权限
  -> 获取变更和仓库上下文
  -> 安全预检查与文件筛选
  -> 并行执行规则、静态工具和 Agent 分析
  -> 证据合并、去重、置信度评估
  -> 结果验证与审查报告生成
  -> 人工确认或自动回写平台
  -> 反馈、忽略、修复、重新审查
```

### 5.2 创建任务

1. 用户选择项目和输入类型。
2. 系统校验项目状态、代码平台连接、分支范围和操作权限。
3. 系统创建任务快照，保存规则版本、模型版本、工具版本和输入元数据。
4. 任务进入 `queued`，由 Worker 异步执行。

### 5.3 变更获取

- Provider 适配器获取仓库元数据、差异、变更文件和目标提交。
- 只读取授权仓库和授权提交范围。
- 获取失败时保留失败原因和 Provider 请求追踪 ID。
- 差异过大时按文件、模块和语言分片，不直接截断重要上下文。

### 5.4 上下文构建

上下文按优先级组合：

1. 当前变更文件和相邻代码。
2. 变更文件引用的定义、接口和测试。
3. 项目规则、语言规则和组织安全策略。
4. 代码所有者、模块说明和架构文档。
5. 相关历史审查意见和已确认缺陷。

上下文构建器必须记录来源、文件路径、行范围、摘要和截断原因，避免模型只返回无法核验的结论。

### 5.5 分析与审查

分析器采用并行执行、统一结果协议：

- 变更正确性：空指针、边界、状态转换、异常处理、并发和事务问题。
- 安全：注入、权限绕过、敏感信息、SSRF、路径穿越、反序列化和依赖风险。
- 性能：明显的 N+1 查询、重复计算、资源泄漏、无界循环和大数据量问题。
- 可维护性：复杂度、重复代码、命名、接口兼容性和架构边界。
- 测试：缺失测试、测试覆盖风险、断言不足和测试与实现不一致。
- 规范：项目规则、语言规范、提交约定和目录边界。
- 静态工具：复用项目已有 Linter、SAST、依赖扫描和类型检查结果。

Agent 不得把所有发现直接作为最终问题。每个候选问题必须经过证据检查、重复合并、严重级别校准和可评论性判断。

### 5.6 结果发布

根据项目策略选择：

- 仅保存系统报告。
- 回写 PR/MR 总结评论。
- 回写行级评论。
- 将高危问题转换为阻断状态。
- 仅在人工确认后回写。

回写必须支持幂等键，避免同一审查任务重复创建评论；回写失败不应导致审查结果丢失。

## 6. Agent 系统设计

### 6.1 Agent 角色

| Agent | 职责 | 是否允许修改代码 |
|---|---|---:|
| Orchestrator Agent | 规划任务、拆分分析器、控制预算、汇总阶段状态。 | 否 |
| Context Agent | 选择相关文件、符号、规则和历史证据。 | 否 |
| Correctness Agent | 分析功能正确性和边界风险。 | 否 |
| Security Agent | 分析安全、权限和敏感数据风险。 | 否 |
| Test Agent | 分析测试覆盖和建议测试场景。 | 否 |
| Quality Agent | 分析规范、可维护性和架构风险。 | 否 |
| Tool Agent | 选择并执行只读静态工具，解析工具结果。 | 否 |
| Review Judge Agent | 合并、去重、评级并决定是否形成最终问题。 | 否 |
| Report Agent | 生成摘要、行级评论和修复建议。 | 否 |

默认采用“只读审查”模式。未来如支持补丁建议，必须单独设计补丁生成、人工确认、沙箱验证和提交权限，不得直接复用审查 Worker 的写权限。

### 6.2 统一问题协议

每条问题至少包含：

```json
{
  "fingerprint": "stable-dedup-key",
  "category": "security",
  "severity": "high",
  "confidence": 0.92,
  "title": "权限校验发生在资源查询之后",
  "message": "当前查询可能先读取未授权资源，再进行权限判断。",
  "evidence": [
    {
      "file_path": "app/service.py",
      "start_line": 42,
      "end_line": 48,
      "reason": "资源查询未包含当前用户范围条件。"
    }
  ],
  "suggestion": "在 Repository 查询条件中前置注入租户和用户范围。",
  "verification": {
    "status": "supported",
    "sources": ["static_rule", "context_file"]
  }
}
```

约束：

- `file_path` 必须属于本次变更或明确关联的上下文文件。
- 行号必须落在目标提交的有效文件范围内；无法定位时只能作为摘要问题。
- `severity` 使用 `blocker`、`critical`、`high`、`medium`、`low`、`info`。
- `confidence` 低于项目阈值的问题默认进入待确认区，不自动回写阻断评论。
- 不允许以模型生成的不存在文件、行号、函数或工具结果作为证据。

### 6.3 工具调用安全

- 工具白名单由组织和项目配置控制。
- 默认只允许读取文件、解析 AST、执行静态检查和读取测试结果。
- 命令必须在隔离工作区执行，限制 CPU、内存、磁盘、网络和执行时长。
- 禁止执行删除、发布、推送、凭据读取和任意网络请求命令。
- 工具输出必须限制大小并进行敏感信息脱敏。
- 工具失败应记录为分析步骤失败，不得伪造成功结果。

## 7. 页面与模块设计

### 7.1 项目列表

展示项目名称、代码平台、仓库地址、默认分支、项目状态、最近审查时间、未处理高危问题数和项目成员。

功能：

- 按名称、平台、状态和负责人查询。
- 分页查看项目。
- 新建、编辑、停用、删除项目。
- 进入项目详情、规则和连接配置。

### 7.2 项目详情

页面分为概览、审查任务、问题列表、规则配置、代码平台连接、统计和审计日志。

概览展示审查次数、平均耗时、问题趋势、严重级别分布、误报率、修复率和最近任务。

### 7.3 审查任务列表

查询条件：项目、来源类型、分支、任务状态、严重级别、创建人、时间范围。

列表字段：任务编号、项目、变更标题、来源、提交范围、状态、问题数、耗时、创建人、创建时间和完成时间。

操作：查看详情、取消排队任务、重新审查、复制任务参数、导出报告。

### 7.4 创建审查任务

表单字段：

- 项目：必填。
- 来源类型：PR/MR、提交范围、本地补丁、基线任务。
- 变更编号或提交范围：按来源类型必填。
- 审查策略：默认策略、指定策略或临时策略。
- 规则集：组织默认、项目默认或指定版本。
- 模型策略：默认模型、低成本模型、深度审查模型。
- 是否回写代码平台：需要对应权限和有效连接。
- 是否阻断：需要项目管理员权限。

提交前执行项目、权限、范围、连接和资源配额校验。

### 7.5 审查详情

页面区域：

1. 任务摘要：变更标题、分支、提交、状态、模型、规则版本和耗时。
2. 文件树：按文件查看变更、语言、风险数量和工具状态。
3. 问题列表：按严重级别、类别、状态、置信度和文件筛选。
4. 差异视图：展示上下文代码、行级问题和证据来源。
5. Agent 过程：展示阶段进度、工具状态和可公开的执行摘要，不展示敏感 Prompt 或密钥。
6. 报告操作：确认、忽略、标记误报、标记已修复、重新审查、回写评论、导出。

### 7.6 规则配置

支持组织级、项目级规则继承和覆盖：

- 审查类别开关。
- 严重级别阈值。
- 置信度阈值。
- 文件包含和排除模式。
- 生成文件、依赖目录和二进制文件处理。
- 语言和静态工具配置。
- 评论格式和回写策略。
- 高风险问题阻断规则。
- 自定义规则说明和示例。

规则修改必须产生版本号，已创建任务固定使用创建时的规则快照。

### 7.7 代码平台连接

支持 Provider 抽象，至少定义仓库查询、差异获取、文件读取、评论创建、评论更新、Webhook 验证和提交状态回写能力。

Token 只保存加密引用或外部密钥服务引用；页面不得回显完整 Token。连接测试不得读取超出测试仓库范围的数据。

### 7.8 问题处理

用户可以对单条问题执行：

- 确认问题。
- 标记误报并填写原因。
- 忽略本次任务。
- 忽略该规则或文件模式（需要更高权限）。
- 标记已修复。
- 添加内部备注。

处理记录必须保存操作者、时间、旧状态、新状态和备注。

## 8. 状态设计

### 8.1 审查任务状态

| 状态 | 含义 | 可转移状态 |
|---|---|---|
| `draft` | 草稿，尚未提交。 | `queued`、`cancelled` |
| `queued` | 等待 Worker。 | `running`、`cancelled` |
| `running` | 正在获取、分析或生成报告。 | `succeeded`、`partial`、`failed`、`cancelled` |
| `partial` | 部分分析完成，存在工具或 Agent 步骤失败。 | `running`、`succeeded`、`failed` |
| `succeeded` | 审查完成且结果可用。 | `running`、`published` |
| `published` | 结果已按策略回写或发布。 | `running` |
| `failed` | 任务不可继续，需要处理失败原因。 | `queued`、`cancelled` |
| `cancelled` | 用户或系统取消。 | `queued` |

任务状态变更必须记录事件；重试创建新的执行记录并关联原任务，不覆盖原始日志。

### 8.2 问题状态

`open`、`confirmed`、`false_positive`、`ignored`、`fixed`、`reopened`。

重新审查时通过稳定指纹关联历史问题：相同问题保留处理状态，消失的问题标记为 `fixed`，重新出现的问题转为 `reopened`。

## 9. 接口设计

接口统一返回请求追踪 ID、错误码和消息；分页接口返回 `rows`、`total`、`page`、`page_size`。以下为目标接口，不代表当前知识库项目已经实现。

### 9.1 项目与连接

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/projects` | 分页查询项目。 |
| `POST` | `/api/v1/projects` | 创建项目。 |
| `GET` | `/api/v1/projects/{project_id}` | 查询项目详情。 |
| `PATCH` | `/api/v1/projects/{project_id}` | 修改项目。 |
| `DELETE` | `/api/v1/projects/{project_id}` | 停用或删除项目。 |
| `GET` | `/api/v1/projects/{project_id}/connections` | 查询代码平台连接。 |
| `POST` | `/api/v1/projects/{project_id}/connections` | 创建或绑定连接。 |
| `POST` | `/api/v1/projects/{project_id}/connections/test` | 测试连接。 |
| `DELETE` | `/api/v1/projects/{project_id}/connections/{connection_id}` | 解除连接。 |

### 9.2 审查任务

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/reviews` | 分页查询审查任务。 |
| `POST` | `/api/v1/reviews` | 创建审查任务。 |
| `GET` | `/api/v1/reviews/{review_id}` | 查询审查详情。 |
| `POST` | `/api/v1/reviews/{review_id}/cancel` | 取消任务。 |
| `POST` | `/api/v1/reviews/{review_id}/retry` | 按原快照重新执行。 |
| `POST` | `/api/v1/reviews/{review_id}/publish` | 发布或回写审查结果。 |
| `GET` | `/api/v1/reviews/{review_id}/events` | 查询任务事件和阶段状态。 |
| `GET` | `/api/v1/reviews/{review_id}/report` | 获取报告或导出文件。 |

### 9.3 问题与反馈

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/reviews/{review_id}/findings` | 分页查询问题。 |
| `PATCH` | `/api/v1/findings/{finding_id}` | 修改问题处理状态。 |
| `POST` | `/api/v1/findings/{finding_id}/feedback` | 提交误报、漏报和质量反馈。 |
| `POST` | `/api/v1/findings/{finding_id}/comments` | 添加内部备注。 |
| `GET` | `/api/v1/findings/{finding_id}/history` | 查询问题处理历史。 |

### 9.4 规则与统计

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/projects/{project_id}/rule-sets` | 查询项目规则集。 |
| `POST` | `/api/v1/projects/{project_id}/rule-sets` | 创建规则版本。 |
| `PATCH` | `/api/v1/rule-sets/{rule_set_id}` | 修改草稿规则。 |
| `POST` | `/api/v1/rule-sets/{rule_set_id}/publish` | 发布规则版本。 |
| `GET` | `/api/v1/projects/{project_id}/metrics` | 查询审查统计。 |
| `GET` | `/api/v1/audit-logs` | 查询审计日志。 |

### 9.5 Webhook 和 CI

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/webhooks/{provider}/{project_key}` | 接收代码平台事件。 |
| `POST` | `/api/v1/ci/reviews` | CI 创建审查任务。 |
| `GET` | `/api/v1/ci/reviews/{review_id}/status` | 查询 CI 状态。 |

Webhook 必须完成签名验证、事件去重和项目映射，不能直接信任请求中的用户或权限字段。

## 10. 数据模型设计

建议至少包含以下实体：

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `organization` | `id`, `name`, `status` | 组织。 |
| `project` | `id`, `organization_id`, `provider`, `repository`, `default_branch`, `status` | 被审查项目。 |
| `project_member` | `project_id`, `user_id`, `role`, `status` | 项目成员。 |
| `provider_connection` | `id`, `organization_id`, `provider`, `secret_ref`, `status` | 代码平台连接。 |
| `rule_set` | `id`, `project_id`, `version`, `config`, `status` | 审查规则版本。 |
| `review` | `id`, `project_id`, `source_type`, `source_ref`, `base_sha`, `head_sha`, `status`, `rule_version`, `model_version` | 审查任务。 |
| `review_execution` | `id`, `review_id`, `attempt`, `status`, `started_at`, `finished_at` | 可重试执行记录。 |
| `review_file` | `id`, `review_id`, `path`, `language`, `change_type`, `diff_hash` | 变更文件。 |
| `analysis_run` | `id`, `execution_id`, `analyzer`, `status`, `tool_version`, `usage` | 分析器执行记录。 |
| `finding` | `id`, `review_id`, `fingerprint`, `category`, `severity`, `confidence`, `status`, `file_path`, `start_line`, `end_line` | 审查问题。 |

| `audit_log` | `organization_id`, `project_id`, `user_id`, `action`, `target_type`, `target_id` | 操作审计。 |

数据设计约束：

- 所有业务表使用独立自增 `id`，业务编码不得替代表主键。
- 不创建实际数据库外键时，由 Service 保证组织、项目、任务和问题的数据边界。
- 删除优先采用状态删除或归档，代码审查记录默认不可物理删除。
- 差异原文、报告和工具大输出使用对象存储，数据库保存元数据、哈希和访问引用。
- Token、密钥和模型 API Key 不进入普通业务表明文列。

建议操作权限编码：

| 操作编码 | 操作名称 |
|---|---|
| `code_review:project_view` | 查看项目 |
| `code_review:project_manage` | 管理项目 |
| `code_review:review_create` | 创建审查 |
| `code_review:review_cancel` | 取消审查 |
| `code_review:review_retry` | 重新审查 |
| `code_review:review_publish` | 发布或回写结果 |
| `code_review:finding_process` | 处理审查问题 |
| `code_review:rule_manage` | 管理规则 |
| `code_review:connection_manage` | 管理代码平台连接 |
| `code_review:metrics_view` | 查看统计 |
| `code_review:audit_view` | 查看审计日志 |

前端可以使用统一权限指令控制入口，但后端必须在 Service 层固定校验操作编码。以下操作必须审计：

- 创建、取消、重试和发布审查。
- 修改、发布和回滚规则。
- 创建、测试和删除代码平台连接。
- 修改问题状态、忽略规则和反馈结论。
- 导出报告、查看敏感执行日志和修改模型配置。

## 12. 异常与降级设计

### 12.1 输入异常

- 项目不存在或已停用：拒绝创建任务。
- 提交范围无效：返回可读的基准提交、目标提交和仓库错误。
- 变更为空：允许生成空变更报告，或按项目策略拒绝。
- 文件超限：按配置分片；无法覆盖时标记 `partial`，不得静默丢弃。

### 12.2 外部平台异常

- Token 失效：任务失败并提示重新授权，不重试无效凭据。
- 限流：按 Provider 的 Retry-After 和指数退避重试。
- 评论回写失败：保留报告并标记发布失败，可单独重试发布。
- Webhook 重复：通过事件 ID 和幂等键去重。

### 12.3 模型和工具异常

- 模型超时：切换备用模型或缩小上下文，保留降级原因。
- 模型额度不足：进入等待或失败，不伪造审查结果。
- 工具不可用：其他分析器继续运行，最终标记部分完成。
- 模型输出格式错误：重试结构化输出；仍失败则丢弃该候选结果并记录异常。
- 证据无法定位：问题降级为摘要建议，禁止生成行级评论。

### 12.4 安全异常

- 检测到密钥、凭据或隐私数据：脱敏后再进入日志、报告和模型上下文。
- 工具越权访问：立即终止该工具，记录安全事件。
- Prompt Injection：将代码和文档内容视为不可信输入，不允许其改变系统规则、工具权限或输出协议。

## 13. 非功能需求

### 13.1 性能

- 普通 PR/MR 的首份报告目标在项目配置的时间预算内完成，并显示阶段进度。
- 大型变更支持分片和并行分析，单个文件失败不阻塞全部任务。
- 页面列表必须服务端分页，问题和事件列表支持筛选。
- 重复提交相同差异时可复用缓存，但必须绑定规则、工具和模型版本。

### 13.2 可靠性

- Worker 任务支持心跳、租约、超时、重试和死信处理。
- 任务状态、分析器状态和发布状态分离，避免回写失败覆盖审查成功状态。
- 所有外部调用使用超时、重试上限和幂等键。

### 13.3 安全与隐私

- 组织、项目、分支和文件路径全链路做权限过滤。
- 默认不把完整仓库发送给模型，只发送最小相关上下文。
- 日志脱敏 Token、Cookie、Authorization、私钥、数据库连接串和个人隐私。
- 对象存储报告使用短时签名 URL，并校验用户权限。
- 保留数据生命周期、导出和删除策略，支持组织级数据清理。

### 13.4 可观测性

指标至少包括：任务成功率、部分完成率、平均耗时、模型 Token、工具失败率、问题确认率、误报率、修复率、回写成功率和 Provider 错误率。

日志必须包含 `request_id`、`organization_id`、`project_id`、`review_id`、`execution_id`、阶段、组件和错误类型，不记录敏感源码原文。

## 14. 评测与验收

### 14.1 离线评测集

评测集应覆盖：

- 已确认真实缺陷。
- 安全漏洞和权限绕过案例。
- 常见误报场景。
- 多语言、多框架和多仓库结构。
- 小型、中型和超大型变更。
- 无测试、失败测试和依赖升级变更。

每条样本保存基准提交、目标提交、期望问题、严重级别、定位范围和允许的等价表述。

### 14.2 评测指标

- 问题级 Precision、Recall、F1。
- 高危问题召回率。
- 行号定位准确率。
- 证据支持率。
- 误报率和重复问题率。
- 报告可执行性评分。
- 端到端耗时、Token 和成本。
- 回写成功率和任务重试率。

### 14.3 验收标准

1. 无权限用户不能读取其他组织或项目的源码、差异和报告。
2. 创建、取消、重试和发布流程状态可追踪且可恢复。
3. 每条行级评论都能定位到有效变更行或明确降级为摘要问题。
4. Provider、模型或工具失败时能展示准确原因，不产生伪造结果。
5. 同一任务重复发布不会产生重复评论。
6. 规则、模型和工具版本能够从报告追溯。
7. 敏感信息不会出现在普通日志、评论和错误响应中。
8. 反馈和问题状态在重新审查后能够正确关联。

## 15. 配置设计

配置分为系统、组织、项目和任务四级，优先级由任务级到系统级逐级回退。

### 15.1 系统配置

- 可用模型 Provider 和默认模型。
- Worker 并发、队列和任务超时。
- 全局工具白名单。
- 对象存储和日志保留周期。
- 外部平台回调地址和签名密钥引用。

### 15.2 项目配置

- 默认分支和文件范围。
- 默认规则集和模型策略。
- 语言与工具启用项。
- 最大变更大小和并发限制。
- 评论、阻断和自动发布策略。
- 忽略路径、忽略规则和代码所有者。

所有配置修改需要版本化；任务只使用创建时的有效配置快照。

## 16. 部署与运行架构

建议拆分为以下组件：

```text
Web / CLI / CI
      |
API Gateway
      |
Review Service ---- PostgreSQL
      |             Object Storage
      |             Redis / Queue
      v
Orchestrator Worker
  |-- Provider Adapter
  |-- Context Worker
  |-- Static Tool Sandbox
  |-- Agent Runtime
  |-- Publish Worker
```

部署要求：

- API、普通 Worker、工具沙箱和发布 Worker 隔离运行。
- 工具沙箱禁止访问宿主机敏感目录，默认关闭外网。
- 队列任务支持租约和重复消费保护。
- 数据库、对象存储、队列和模型 Provider 均支持健康检查。
- 生产环境使用独立密钥管理，不在配置文件提交密钥。
- 支持灰度启用新模型、新规则和新分析器。

## 17. 实施计划

实施按完整目标拆分为可独立验收的阶段，每个阶段都保留真实权限、状态、审计和错误处理，不用演示数据替代接口。

### 阶段一：基础工程与配置

- 独立项目骨架、启动入口、配置、日志和异常。
- 组织、项目、用户和权限基础模型。
- 数据库、对象存储、队列和任务追踪基础能力。

### 阶段二：Provider 与任务管理

- 代码平台连接管理。
- Webhook 验证和事件去重。
- PR/MR、提交范围和补丁输入。
- 任务创建、取消、重试、状态和事件。

### 阶段三：上下文与工具分析

- Diff 获取和文件分片。
- AST、规则、静态检查和测试工具适配。
- 工具沙箱、超时、输出解析和证据协议。

### 阶段四：Agent 编排与报告

- Orchestrator、Context、专项分析器和 Judge Agent。
- 结构化输出、问题去重、定位验证和置信度校准。
- 报告、文件视图、问题处理和导出。

### 阶段五：平台回写与反馈闭环

- PR/MR 摘要和行级评论回写。
- 评论幂等、发布重试和状态回查。
- 误报、漏报、确认、修复和重新审查关联。

### 阶段六：规则、统计与运营

- 组织和项目规则版本。
- 统计看板、审计日志和数据保留。
- 离线评测集、线上质量指标和模型/规则灰度。

### 阶段七：扩展与生态

- 更多代码平台、语言和工具。
- CLI、CI、IDE 集成。
- 可选的人工确认后补丁建议。
- 多模型路由、成本优化和企业内部知识库接入。

## 18. 待确认事项

以下事项需要在独立项目启动时确认，不影响本文整体目标：

7. 是否允许执行项目测试，及每种项目类型的沙箱策略。
8. 评测集来源、人工标注流程和质量门槛。
