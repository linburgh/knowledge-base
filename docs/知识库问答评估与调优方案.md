# 知识库问答评估与调优方案

## 1. 文档目的

本文用于指导企业级知识库问答系统的离线评测、线上观测和持续调优，适用于当前基于 FastAPI、LangChain、pgvector、Embedding 和 Knowledge Agent 的问答链路。

本方案不以“回答看起来不错”作为唯一判断标准，而是把问答系统拆分为检索、生成、引用、业务效果和系统性能五个层面，通过统一测试集和可重复指标验证每次改动是否真正有效。

## 1.1 指标中英文对照

| 英文指标 | 中文名称 | 说明 |
|---|---|---|
| Recall@K | K 值召回率 | 正确资料是否出现在前 K 条结果中 |
| Precision@K | K 值精确率 | 前 K 条结果中相关资料所占的比例 |
| Context Precision | 上下文精确率 | 检索上下文中真正有用内容的比例及排序质量 |
| Context Recall | 上下文召回率 | 回答所需事实被检索到的完整程度 |
| RR（Reciprocal Rank） | 倒数排名 | 单个问题中第一个正确结果排名的倒数 |
| MRR（Mean Reciprocal Rank） | 平均倒数排名 | 所有问题倒数排名的平均值，正确结果越靠前越高 |
| NDCG@K（Normalized Discounted Cumulative Gain） | K 值归一化折损累计增益 | 综合考虑相关性等级和结果排名 |
| Faithfulness | 忠实度 | 答案是否有检索资料支持，是否存在幻觉 |
| Answer Relevancy | 答案相关性 | 答案是否真正回答了用户问题 |
| Answer Correctness | 答案正确性 | 答案与人工标准答案在事实和结论上的一致程度 |
| Citation Accuracy | 引用准确率 | 引用是否存在、相关并且能够支撑答案 |
| Answer Abstention | 无答案拒答率 | 知识库没有依据时能否正确拒绝猜测 |
| Embedding | 向量嵌入 / 向量模型 | 将问题和文档转换为向量用于相似度检索 |
| Rerank | 重排序 | 对初步召回结果再次排序 |
| Token | 词元 | 模型处理文本和计算用量的基本单位 |
| P50/P95/P99 | 50/95/99 分位耗时 | 反映典型、较慢和极慢请求的响应时间 |

## 2. 当前问答链路

```text
用户问题
    |
    v
问题规范化与会话上下文
    |
    v
Embedding 向量化
    |
    v
pgvector Top-K 检索
    |
    v
候选分块去重与排序
    |
    v
Knowledge Agent 调用检索、历史和引用工具
    |
    v
结构化答案与引用校验
    |
    v
会话消息、引用和运行指标落库
    |
    v
前端答案与参考资料展示
```

评测必须同时保留每个阶段的中间结果，不能只保存最终答案，否则无法区分“检索错了”和“模型答错了”。

## 3. 评测目标

评测目标分为四类：

| 目标 | 需要回答的问题 |
|---|---|
| 检索有效 | 正确资料是否被召回，是否排在前面？ |
| 答案可信 | 答案是否由资料支持，是否存在编造？ |
| 业务可用 | 是否真正解决用户问题，是否需要人工补充？ |
| 系统稳定 | 是否足够快、稳定、可追踪？ |

## 4. 评测数据集设计

### 4.1 数据集组成

每个知识库建立独立评测集，至少覆盖以下问题类型：

| 类型 | 示例 | 主要评估能力 |
|---|---|---|
| 事实查询 | 医签通支持哪些签名方式？ | 精确检索和事实回答 |
| 流程查询 | 如何完成扫码签名？ | 流程完整性和顺序准确性 |
| 条件判断 | 哪些情况下需要协同签名？ | 条件理解和边界判断 |
| 多资料综合 | 结合多个章节介绍整体方案 | 多分块归纳能力 |
| 多轮追问 | 这个产品由哪家公司开发？介绍一下这家公司 | 会话上下文和指代消解 |
| 无答案问题 | 方案是否包含价格和交付周期？ | 拒答和不编造能力 |
| 权限边界 | 未授权用户能否访问知识库？ | 权限事实和安全边界 |
| 噪声问题 | 与当前知识库无关的问题 | 相关性判断和拒答 |

每个知识库初始建议建立 100～300 条人工审核问题；正式上线前逐步扩展到 500～1000 条。问题必须来自真实业务、历史问答、用户反馈和人工构造场景，不能全部由模型自动生成。

### 4.2 标注结构

评测集建议使用 JSONL 文件维护，放在 `tests/evals/datasets/`：

```json
{
  "case_id": "visitor-guide-0001",
  "kb_name": "医签通产品与使用指南",
  "question": "访客如何访问已授权的知识库？",
  "category": "permission_boundary",
  "expected_answer": "访客只能访问已授权的知识库，未授权知识库不能直接访问。",
  "expected_chunk_ids": [101, 102],
  "expected_document_names": ["【医签通】医疗行业全场景移动签名应用解决方案.pdf"],
  "must_contain": ["授权"],
  "must_not_contain": ["可以直接访问"],
  "answerable": true,
  "difficulty": "medium",
  "reviewer": "业务评审人",
  "review_status": "approved"
}
```

标注原则：

- `expected_answer` 是事实边界和评分参考，不要求模型逐字回答。
- `expected_chunk_ids` 用于检索层评测，不参与线上回答生成。
- `must_contain` 和 `must_not_contain` 只用于稳定的关键事实，不用于限制自然语言表达。
- `answerable=false` 的问题必须有明确的拒答标准。
- 评测集中的文档版本、知识库 ID 和模型配置必须可追溯。

### 4.3 数据集分层

```text
训练或调试集：允许用于调整 Chunk、Embedding、Prompt 和 Rerank
验证集：调参过程中只做趋势观察，不作为最终结论
测试集：冻结管理，只在版本评审和发布前使用
线上回流集：来源于真实问题和用户反馈，定期人工审核后加入
```

同一问题的不同表述应尽量放在同一数据集分组中，避免语义相同的问题同时泄漏到调试集和测试集。

## 5. 检索质量指标

### 5.1 Recall@K（K 值召回率）

判断正确分块是否出现在 Top-K 结果中：

```text
Recall@K = 命中正确资料的问题数 / 可评测问题总数
```

建议至少统计：

- Recall@1
- Recall@3
- Recall@5
- Recall@10

对于多文档问题，只有覆盖全部必要资料才计为完整召回；只召回其中一部分时，另外统计部分召回率。

### 5.2 Precision@K（K 值精确率）/ Context Precision（上下文精确率）

判断 Top-K 中有多少分块对回答当前问题真正有帮助：

```text
Precision@K = Top-K 中相关分块数量 / K
```

Context Precision 更关注相关分块是否排在前面。检索出大量无关内容会增加上下文噪声，可能导致模型答非所问或产生错误归纳。

### 5.3 MRR（平均倒数排名）

MRR 衡量第一个正确结果的位置：

```text
RR = 1 / 第一个相关分块的排名
MRR = 所有问题 RR 的平均值
```

MRR 适合比较不同 Embedding、Rerank 和 Top-K 配置对排序质量的影响。

### 5.4 NDCG@K（K 值归一化折损累计增益）

对每个召回分块标注相关等级：

```text
0 = 无关
1 = 部分相关
2 = 直接支持答案
3 = 关键依据
```

NDCG@K 同时考虑相关性等级和排名位置，适合评估包含多个相近章节、不同版本制度和多份产品资料的知识库。

### 5.5 Context Recall（上下文召回率）

判断回答所需的事实是否全部被召回。对于一条标准答案，可以拆成若干事实单元：

```text
Context Recall = 被召回支持的事实单元数 / 标准答案事实单元总数
```

例如“申请条件、操作步骤、有效期、限制条件”四个事实只召回两个时，Context Recall 为 50%。

## 6. 生成质量指标

### 6.1 Faithfulness（忠实度）

判断答案中的每个事实是否能从检索上下文中得到支持，是防止幻觉的核心指标。

建议把答案拆分为原子声明：

```text
Faithfulness = 有检索依据支持的声明数 / 答案声明总数
```

重点识别以下风险：

- 资料没有出现的公司、产品、价格、时间和政策被模型自行补充。
- 把不同文档或不同产品的内容混在一起。
- 把“可以申请”改写成“已经支持”。
- 把示例、建议或背景描述改写成确定性业务规则。

### 6.2 Answer Relevancy（答案相关性）

判断答案是否真正回答了用户问题。建议采用人工 1～5 分与模型辅助评分结合：

| 分数 | 说明 |
|---|---|
| 5 | 直接、完整回答问题，没有明显无关内容 |
| 4 | 基本回答问题，少量补充内容 |
| 3 | 部分回答，需要用户继续追问 |
| 2 | 只覆盖少量相关内容，主体偏题 |
| 1 | 没有回答问题 |

### 6.3 Answer Correctness（答案正确性）

将答案与人工标准答案比较，综合事实覆盖和结论正确性。不能只做字符串相似度，应重点判断：

- 结论是否正确。
- 关键条件是否遗漏。
- 数字、时间、范围和否定条件是否正确。
- 是否将不确定内容表达为确定事实。

### 6.4 Citation Accuracy（引用准确率）

引用准确率至少包含三项：

| 英文指标 | 中文名称 | 含义 |
|---|---|---|
| Citation Presence | 引用存在性 | 需要引用的问题是否返回引用 |
| Citation Relevance | 引用相关性 | 引用片段是否支持答案 |
| Citation Completeness | 引用完整性 | 答案中的关键事实是否都有对应引用 |

当前系统应特别检查引用分块协议必须包含 `document_id`、`chunk_id`、`source_name`、`content` 等字段，避免引用整理失败后进入降级回答。

### 6.5 Answer Abstention（无答案拒答率）

对于知识库没有答案的问题，正确行为不是“尽量回答”，而是明确说明资料不足。需要统计：

- 无答案问题正确拒答率。
- 无答案问题的幻觉率。
- 有答案问题的误拒答率。

## 7. 端到端业务指标

### 7.1 问题解决率

由人工或用户反馈判断：

```text
问题解决率 = 被评审为基本解决及以上的问题数 / 有效问题总数
```

建议将 4 分和 5 分视为解决，3 分作为需要补充，1～2 分视为未解决。

### 7.2 用户满意度

前端保留点赞、点踩和可选原因：

- 回答准确。
- 回答不完整。
- 引用不相关。
- 没有回答问题。
- 其他。

用户反馈必须和知识库、问题、回答、引用、模型版本关联，避免只记录一个孤立的点赞结果。

### 7.3 人工转接率

适用于访客服务和客服场景：

```text
人工转接率 = 进入人工处理的问题数 / 有效问题总数
```

不能单独追求转接率下降。如果转接率下降但 Faithfulness 和满意度同时下降，说明系统可能在错误回答而不是解决问题。

### 7.4 无引用回答率

当前系统已有无引用回答统计能力，应按知识库、问题类型、模型版本和时间范围分别统计：

```text
无引用回答率 = 无引用回答数 / 总回答数
```

对需要事实依据的问题，无引用率应持续下降；对闲聊或明确无资料问题，可单独分类，不与事实问答混算。

## 8. 系统性能与稳定性指标

| 指标 | 说明 |
|---|---|
| P50/P95/P99 延迟（50/95/99 分位延迟） | 从请求进入到答案返回的总耗时 |
| 检索耗时 | Query Embedding、数据库检索和 Rerank 耗时 |
| 模型首 token 延迟 | 流式场景的首个可见内容耗时 |
| 模型总耗时 | 最终答案生成耗时 |
| Token 消耗 | 输入、输出和单次问答总 Token |
| 错误率 | 5xx、超时、模型调用失败和结构化输出失败 |
| 降级率 | 进入资料摘要或友好提示的请求比例 |
| 重试率 | LLM、Embedding 和工具调用重试比例 |
| 并发能力 | 固定资源下可稳定处理的并发请求数 |

当前应额外记录 Agent 的模型调用次数、工具调用次数、递归停止原因和降级原因，避免只看到一个“Agent 执行失败”。

正式调优前先冻结当前配置，生成第一版基线报告。基线至少记录：

```text

Chat 模型
Chunk size / overlap
Top-K
Rerank 是否启用
会话上下文条数
Agent max_steps / max_tool_calls
回答成功率
引用返回率
降级率
P50 / P95 延迟
```

结合此前“医签通产品与使用指南”自测，已经暴露出以下问题，必须先修复或标记后再比较模型效果：

1. Agent 的 `build_citations` 调用曾出现缺少 `document_id` 的错误，正常引用整理失败后进入降级回答；当前已移除该工具调用，后端改为根据真实检索结果生成引用。
2. 降级摘要可以返回内容，但不能把降级回答与正常 Agent 回答混在一起统计。
3. 访客权限问题、产品问题和医疗签名方案问题需要在评测集分类，否则总体分数无法说明具体能力。

基线报告必须同时列出“系统真实效果”和“数据/链路问题”，不能用数据质量问题掩盖模型效果，也不能把降级回答当作正常回答。

## 10. 调优顺序

### 10.1 第一阶段：修复数据和协议

优先级最高，目标是让评测结果可信：

- 校验知识库名称、描述、文档内容和授权范围是否一致。
- 修复检索分块输出协议，统一 `id` 与 `chunk_id`、`document_id`、`content` 字段。
- 确保引用整理使用与检索结果相同的字段协议。
- 对已存在的旧 Embedding 模型分库或重新索引，禁止混用向量。
- 记录每次回答的检索分块、模型版本和降级原因。

### 10.2 第二阶段：优化文档和 Chunk

建议顺序：

1. 清理 PDF 页眉页脚、乱码、重复标题和无意义空白。
2. 保留章节标题、页码、文档名称和业务标签。
3. 按语义和章节切分，避免把完整流程拆散。
4. 对表格、编号流程、条件规则保留完整结构。
5. 评估 `chunk_size=400/600/800` 和不同 overlap 的 Recall@K、Context Recall 和延迟。

### 10.3 第三阶段：优化 Embedding

在文档和 Chunk 稳定后比较 Embedding 模型：

- 固定同一评测集、同一 Chunk 版本和同一 Top-K。
- 重新生成全量向量，不混用不同模型结果。
- 比较 Recall@K、MRR、NDCG 和查询延迟。
- 关注中文、产品名、缩写、编号和专业术语的检索表现。

当前 Ollama `bge-m3` 接入后，需要将所有目标知识库重新向量化，再与原模型做同集对比。

### 10.4 第四阶段：混合检索与 Rerank

当向量检索已经稳定后，再引入：

```text
向量召回
    +
关键词 / PostgreSQL FTS 召回
    +
结果去重
    +
Rerank 重排序
```

Rerank 的收益必须通过 MRR、NDCG@K、Context Precision 和 P95 延迟共同判断，不能只看少量样例。

### 10.5 第五阶段：优化上下文和 Agent

最后再调 Prompt 和 Agent：

- 保持会话上下文数量可控。
- 要求答案先直接回答，再补充必要说明。
- 明确资料不足时拒答，不根据常识补充企业事实。
- 引用只能来自本次检索结果。
- 对结构化输出失败、工具失败和超时执行友好降级。
- 分开统计正常答案和降级答案。

Prompt 优化不能代替检索质量优化，也不能解决知识库文档与名称不一致的问题。

## 11. 评测执行流程

```text
冻结代码、配置和知识库版本
        |
        v
加载评测集
        |
        v
执行独立检索评测
        |
        v
执行端到端问答评测
        |
        v
保存检索结果、答案、引用和运行日志
        |
        v
计算指标与分问题类型报告
        |
        v
人工复核低分和高风险问题
        |
        v
只调整一个变量并重新运行
        |
        v
与冻结基线比较并决定是否保留
```

每轮只调整一个主要变量，例如只调整 Chunk size、只切换 Embedding、只启用 Rerank，避免无法判断收益来源。

## 13. 目标值和发布门禁

以下目标作为初始发布门禁，正式值应以第一轮基线和业务风险评审结果为准：

### 13.1 检索层

| 指标 | 初始目标 |
|---|---:|
| Recall@5 | ≥ 90% |
| MRR | ≥ 0.80 |
| NDCG@5 | ≥ 0.80 |
| Context Precision@5 | ≥ 0.75 |
| Context Recall | ≥ 0.85 |

### 13.2 生成层

| 指标 | 初始目标 |
|---|---:|
| Faithfulness | ≥ 90% |
| Answer Relevancy | ≥ 85% |
| Citation Accuracy | ≥ 95% |
| 无答案问题幻觉率 | ≤ 3% |
| 关键事实漏答率 | ≤ 10% |

### 13.3 业务和性能层

| 指标 | 初始目标 |
|---|---:|
| 问题解决率 | ≥ 80% |
| 用户满意度 | ≥ 85% |
| 降级率 | ≤ 5% |
| P95 总响应时间 | ≤ 8 秒 |
| 5xx 错误率 | ≤ 1% |

对医疗、法律、价格、交付、合规和竞品等高风险问题，除总分达标外，还必须通过人工审核，不能仅凭 RAGAS 分数发布。

## 14. 自动化落地规划

### 14.1 目录建议

```text
tests/evals/
├── datasets/
│   ├── visitor_service.jsonl
│   └── medical_signature.jsonl
├── runners/
│   ├── retrieval_eval.py
│   └── chat_eval.py
├── metrics/
│   ├── retrieval.py
│   └── generation.py
├── reports/
└── README.md
```

### 14.2 第一批自动化能力

1. 通过检索服务执行固定问题，保存 Top-K 分块和分数。
2. 计算 Recall@K、MRR、NDCG@K、Context Precision 和 Context Recall。
3. 通过问答接口执行端到端测试，保存答案和引用。
4. 校验答案非空、引用字段完整、引用分块属于本次检索结果。
5. 统计正常回答、降级回答、错误和超时。
6. 对 `must_contain`、`must_not_contain` 和无答案问题执行确定性断言。
7. 对需要人工判断的 Faithfulness 和 Relevancy 生成待复核清单。

### 14.3 评测与生产隔离

- 评测请求使用独立的评测用户和会话。
- 评测不修改正式知识库内容，不自动删除正式会话。
- 评测模型和配置必须通过显式参数传入，不能依赖运行环境中的隐式默认值。
- 评测日志中不得记录 API Key、Token、密码和完整敏感用户信息。

## 15. 当前项目的实施顺序

### 阶段一：建立可信基线

- 修复引用数据字段不一致。
- 持续核验“医签通产品与使用指南”知识库中的文档内容与名称一致。
- 建立首批 100 条人工审核评测问题。
- 完成检索结果和 Agent 运行信息记录。
- 输出当前配置下的基线报告。

### 阶段二：完成检索评测

- 实现 Recall@K、MRR、NDCG、Context Precision 和 Context Recall。
- 对 Chunk size、overlap、Top-K 做单变量对比。
- 对旧 Embedding 与 Ollama `bge-m3` 做同集对比。

### 阶段三：完成生成评测

- 实现 Faithfulness、Answer Relevancy、Answer Correctness 和 Citation Accuracy 评测流程。
- 增加无答案、追问、冲突资料和高风险问题。
- 分别统计正常 Agent 输出与降级输出。

### 阶段四：优化检索链路

- 清洗文档和完善元数据。
- 引入关键词混合检索。
- 引入并评估 Rerank。
- 以 Recall、MRR、NDCG、P95 延迟共同决定配置。

### 阶段五：建立线上闭环

- 前端增加点赞、点踩和问题未解决反馈。
- 记录用户反馈与引用、模型、知识库版本的关联关系。
- 每周整理低分样本和无答案样本。
- 经人工审核后回流评测集。
- 发布前自动执行评测门禁。

## 16. 调优原则

- 先修数据和协议，再调模型和 Prompt。
- 一次只改变一个主要变量。
- 检索指标和生成指标必须联合判断。
- 任何平均分提升都必须检查高风险问题是否退化。
- 降级回答必须可用，但不能把降级成功当作正常问答成功。
- 所有结论都必须能通过固定评测集复现。

## 17. 验收结论

当满足以下条件时，才认为一次问答调优有效：

1. 检索 Recall@5、MRR、NDCG@5 相比冻结基线提升，且没有明显增加 P95 延迟。
2. Faithfulness、Answer Relevancy 和 Citation Accuracy 达到发布门禁。
3. 无答案问题的幻觉率没有上升。
4. 访客权限、产品归属、公司名称等关键事实测试全部通过。
5. 正常回答和降级回答可以在日志和报表中明确区分。
6. 评测结果、配置、代码和知识库版本均可追溯。
