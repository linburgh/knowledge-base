# 语义解析层实现原理详解

## 阅读目标

本文用于解释 Agent 系统中的语义解析层是什么、为什么需要它，以及如何在当前知识库项目中实现。

阅读完成后，应能够理解以下问题：

1. 语义解析层解决什么问题。
2. 为什么不能只依赖关键词或意图分类。
3. 模型、确定性程序和业务 Agent 分别负责什么。
4. 如何理解“这些告警”“其中两条”“那昨天呢”等上下文表达。
5. 如何把自然语言转换成可校验、可执行的任务说明。
6. 如何处理歧义、模型格式错误和对象解析失败。
7. 如何通过测试集持续提高语义理解覆盖率。

## 基本概念

### 什么是语义解析

语义解析可以简单理解为一个“翻译器”。

它把用户说的自然语言：

> 分析一下这四条告警产生的原因。

翻译成 Agent 更容易理解和执行的任务说明：

```json
{
  "要做什么": "调查原因",
  "处理对象": "上一轮展示的四条告警",
  "时间范围": "沿用上一轮",
  "数据范围": "当前租户",
  "回答要求": [
    "直接触发原因",
    "关联因素",
    "判断依据",
    "无法确认的部分"
  ]
}
```

语义解析层只负责理解和整理任务，不直接查询数据库，也不直接生成最终业务结论。

### 什么是意图

意图通常使用 `intent` 表示，用于描述用户大致想做什么。

例如：

| 用户表达 | 粗粒度意图 |
| --- | --- |
| 今天有多少条告警？ | 查询数量 |
| 这四条分别是什么？ | 查看明细 |
| 为什么会产生这些告警？ | 调查原因 |
| 跟昨天相比有什么变化？ | 对比分析 |

意图只是任务说明中的一个字段，不是完整的语义解析结果。

如果只得到：

```json
{
  "intent": "incident_cause"
}
```

系统仍然不知道：

- 具体分析哪些告警；
- “这些”指的是哪一批数据；
- 使用哪个租户的数据；
- 时间范围是什么；
- 用户需要简要结论还是完整证据；
- 用户询问的是直接触发条件还是底层业务根因。

因此，当前项目应弱化意图分类，保留少量通用操作类型用于日志和基础路由，真正执行依赖完整的结构化任务说明。

## 核心难点

### 表达方式多样

同一个目标可以有大量不同表达：

- 为什么会这样？
- 这些告警是什么原因造成的？
- 帮我查一下异常原因。
- 这几条之间有没有关系？
- 问答成功率怎么突然下降了？

如果使用关键词规则，就需要不断增加“原因”“为什么”“造成”“导致”等匹配词，仍然无法可靠覆盖上下文、省略和组合表达。

### 上下文指代

用户经常不会重复完整对象名称，而是使用：

- 这些；
- 其中两条；
- 刚才那条；
- 严重的；
- 上一次；
- 它们。

模型需要结合上一轮结构化结果才能判断这些词指向什么。

### 真实对象绑定

即使模型理解“这四条告警”指的是上一轮结果，也不能允许模型自行生成告警 ID。

模型擅长理解语言，但不应该决定：

- 数据库主键；
- 租户 ID；
- 用户权限；
- 真实时间边界；
- 对象是否存在。

这些内容必须由确定性程序校验和绑定。

### 是否需要追问

系统不能遇到任何信息缺失都追问，也不能在关键对象不明确时擅自猜测。

低风险信息可以使用默认值：

- 未指定时区时使用系统统一时区；
- 未指定展示方式时使用默认报告格式；
- 未指定范围时使用当前授权数据范围。

会显著改变执行结果的信息必须追问：

- “它”可能同时指告警、指标或任务；
- 上下文存在两组不同的“四条告警”；
- 用户要求执行写操作但对象不明确；
- 平台范围和租户范围无法确定。

## 职责边界

语义解析不应由一个组件完成所有工作。推荐分为以下职责：

```text
用户自然语言
    ↓
上下文整理：准备最近对象、当前选择、时间和范围
    ↓
模型语义解析：理解目标、对象表达和回答要求
    ↓
确定性解析：绑定真实对象、时间、权限和数据范围
    ↓
业务 Agent：自主选择工具并完成调查
    ↓
完成度校验：检查结果是否真正回答用户问题
```

### 模型负责什么

模型负责：

- 理解用户大致要完成的目标；
- 判断用户谈论的是告警、指标、任务还是其他对象；
- 识别“这些”“刚才的”等上下文引用；
- 提取用户明确表达的时间和范围；
- 理解用户希望看到哪些内容；
- 标记无法可靠理解的歧义。

### 程序负责什么

确定性程序负责：

- 从会话状态中取得真实对象 ID；
- 校验对象是否存在；
- 校验租户和权限边界；
- 使用统一时区解析时间范围；
- 判断默认值是否可以安全使用；
- 对结构化结果执行 Schema 校验；
- 决定是否必须向用户追问。

### Agent负责什么

业务 Agent 负责：

- 根据任务说明选择工具；
- 决定调查顺序；
- 根据中间事实继续或停止；
- 区分直接证据、候选关联和未知项；
- 生成满足用户要求的最终结果。

语义解析层的存在不会把业务 Agent 变成固定工作流。它只是给 Agent 提供一个更清楚、经过校验的任务入口。

## 协议设计

### 最小任务协议

第一版不应设计几十个字段。可以先定义六个核心字段：

```python
from pydantic import BaseModel, Field


class SemanticTask(BaseModel):
    action: str = Field(description="用户希望完成的动作")
    target_type: str = Field(description="告警、指标、任务、事件等对象类型")
    target_reference: str | None = Field(
        default=None,
        description="用户所指对象的来源，不允许虚构对象 ID",
    )
    time_expression: str | None = None
    scope_expression: str | None = None
    expected_content: list[str] = Field(default_factory=list)
```

这个协议回答六个问题：

1. 用户要做什么；
2. 处理什么类型的对象；
3. 用户如何描述这些对象；
4. 用户说了什么时间；
5. 用户说了什么数据范围；
6. 最终回答需要包含什么。

### 完整任务协议

随着真实问题积累，可以扩展为更完整的协议：

```python
from datetime import datetime
from typing import Literal

from pydantic import BaseModel, Field


class TargetReference(BaseModel):
    entity_type: Literal[
        "alert",
        "metric",
        "event",
        "task",
        "evaluation",
        "knowledge_base",
        "document",
        "unknown",
    ]
    expression: str = Field(description="用户原始表达")
    reference_source: Literal[
        "explicit",
        "previous_result",
        "current_selection",
        "conversation_history",
        "unresolved",
    ]
    entity_ids: list[str] = Field(
        default_factory=list,
        description="经过程序绑定的真实对象 ID",
    )
    resolution_status: Literal["resolved", "partial", "unresolved"]


class SemanticTimeRange(BaseModel):
    raw_expression: str | None = None
    start_at: datetime | None = None
    end_at: datetime | None = None
    timezone: str = "Asia/Shanghai"
    resolution_status: Literal["resolved", "defaulted", "unresolved"]


class OutputRequirement(BaseModel):
    detail_level: Literal["summary", "normal", "detailed"] = "normal"
    include_list: bool = False
    include_causes: bool = False
    include_evidence: bool = True
    include_comparison: bool = False
    preferred_format: Literal[
        "natural_language",
        "table",
        "timeline",
        "report",
    ] = "natural_language"


class SemanticRequest(BaseModel):
    goal: str = Field(description="用户希望完成的完整目标")
    operation: Literal[
        "lookup",
        "list",
        "explain",
        "investigate",
        "compare",
        "summarize",
        "recommend",
        "execute",
        "unknown",
    ]
    targets: list[TargetReference]
    time_range: SemanticTimeRange | None = None
    scope_expression: str | None = None
    constraints: list[str] = Field(default_factory=list)
    output: OutputRequirement
    assumptions: list[str] = Field(default_factory=list)
    ambiguities: list[str] = Field(default_factory=list)
    needs_clarification: bool = False
```

`operation` 只做粗粒度分类，完整目标保留在 `goal` 中。新增用户表达时，优先增强目标理解和对象解析，不应不断增加新的意图枚举。

## 上下文整理

### 为什么需要上下文包

如果模型只收到：

> 分析一下这四条告警产生的原因。

它无法知道“四条告警”来自哪里。

因此，Harness 应在调用语义模型前准备一个小型上下文包：

```python
context_packet = {
    "current_time": "2026-08-09T20:30:00+08:00",
    "timezone": "Asia/Shanghai",
    "current_scope": {
        "scope_type": "tenant",
        "tenant_id": 103,
    },
    "current_selection": None,
    "previous_result": {
        "result_type": "alert_list",
        "entity_ids": ["1001", "1002", "1003", "1004"],
        "time_expression": "最近1小时",
        "scope_expression": "当前租户",
    },
    "recent_mentions": [
        {
            "turn_id": "turn-12",
            "entity_type": "alert",
            "entity_ids": ["1001", "1002", "1003", "1004"],
            "summary": "上一轮展示了4条活动告警",
        }
    ],
    "user_message": "分析一下这四条告警产生的原因",
}
```

### 不要传完整历史

上下文包应优先保存结构化摘要，而不是把所有对话和工具原始结果全部传给模型。

推荐包含：

- 当前用户问题；
- 上一轮结果类型；
- 上一轮返回的业务对象 ID；
- 当前页面选中的对象；
- 最近几轮提到的对象集合；
- 当前租户和权限范围；
- 当前时间、时区和上一轮时间范围。

这样既可以减少 Token，也可以降低无关历史对语义理解的干扰。

## 模型解析

### 使用结构化输出

语义解析步骤通常不需要调用业务工具，可以使用一次受限的结构化模型调用：

```python
import json

from langchain.chat_models import init_chat_model


model = init_chat_model("当前使用的模型")
semantic_model = model.with_structured_output(SemanticRequest)

semantic_request = await semantic_model.ainvoke(
    [
        {
            "role": "system",
            "content": """
你负责把用户表达翻译成结构化任务说明。

要求：
1. 只理解任务，不执行查询。
2. 不允许编造告警、指标、任务、事件或其他业务对象 ID。
3. 结合上下文判断“这些、其中、刚才的、上一次”等引用。
4. 无法判断时标记歧义，不要猜测。
5. 保留用户明确提出的时间、范围、限制和输出要求。
6. 原因调查应区分直接原因、关联因素、证据和无法确认的部分。
""",
        },
        {
            "role": "user",
            "content": json.dumps(context_packet, ensure_ascii=False),
        },
    ]
)
```

使用结构化输出后，结果直接经过 Pydantic 校验，不需要自行从自然语言中截取 JSON。

### 使用 Agent API

如果需要使用 LangChain Agent API 承载解析器，可以创建一个无业务工具的受限 Agent：

```python
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy


semantic_parser = create_agent(
    model=model,
    tools=[],
    system_prompt=SEMANTIC_PARSER_PROMPT,
    response_format=ToolStrategy(
        SemanticRequest,
        handle_errors=True,
    ),
)

result = await semantic_parser.ainvoke(
    {
        "messages": [
            {
                "role": "user",
                "content": json.dumps(context_packet, ensure_ascii=False),
            }
        ]
    }
)

semantic_request = result["structured_response"]
```

语义解析器是业务 Agent Harness 内的一项能力，不替代自主监控、自主评测或知识库问答 Agent。业务 Agent 仍然使用 `create_deep_agent` 等正式 Agent API 完成自主规划和工具调用。

## 对象绑定

### 两阶段解析

对象解析推荐分为两个阶段：

1. 模型识别引用来源；
2. 程序绑定真实 ID。

对于“这四条告警”，模型只需要返回：

```json
{
  "entity_type": "alert",
  "expression": "这四条告警",
  "reference_source": "previous_result",
  "entity_ids": [],
  "resolution_status": "unresolved"
}
```

程序再从上一轮结果中取得真实 ID：

```python
def resolve_target(
    target: TargetReference,
    conversation_context: dict,
) -> TargetReference:
    if target.reference_source == "previous_result":
        previous = conversation_context.get("previous_result") or {}

        if previous.get("result_type") == "alert_list":
            return target.model_copy(
                update={
                    "entity_ids": previous.get("entity_ids", []),
                    "resolution_status": "resolved",
                }
            )

    return target
```

### 绑定后的任务

最终交给业务 Agent 的任务应包含真实对象和确定的数据边界：

```json
{
  "goal": "调查指定四条告警的产生原因",
  "operation": "investigate",
  "targets": [
    {
      "entity_type": "alert",
      "expression": "这四条告警",
      "reference_source": "previous_result",
      "entity_ids": ["1001", "1002", "1003", "1004"],
      "resolution_status": "resolved"
    }
  ],
  "time_range": {
    "raw_expression": "沿用上一轮",
    "start_at": "2026-08-09T19:30:00+08:00",
    "end_at": "2026-08-09T20:30:00+08:00",
    "timezone": "Asia/Shanghai",
    "resolution_status": "resolved"
  },
  "scope_expression": "当前租户",
  "output": {
    "detail_level": "detailed",
    "include_list": true,
    "include_causes": true,
    "include_evidence": true,
    "include_comparison": false,
    "preferred_format": "report"
  }
}
```

## 时间解析

### 原始表达与标准时间并存

时间字段应同时保存：

- 用户原始表达；
- 标准开始时间；
- 标准结束时间；
- 使用的时区；
- 时间是明确解析、默认补充还是尚未确定。

例如用户说“今天”：

```json
{
  "raw_expression": "今天",
  "start_at": "2026-08-09T00:00:00+08:00",
  "end_at": "2026-08-09T20:30:00+08:00",
  "timezone": "Asia/Shanghai",
  "resolution_status": "resolved"
}
```

模型可以识别“今天”是时间表达，但具体日期边界必须基于 Harness 提供的当前时间和统一时区计算，不能依赖模型内部时间认知。

### 连续追问

用户说：

> 那昨天呢？

系统应理解为：

- 目标和对象沿用上一轮；
- 时间范围替换为昨天；
- 输出要求默认沿用上一轮。

因此，会话状态需要保存上一轮已解析任务，而不仅仅保存最终回答文本。

## 歧义处理

### 可以默认的情况

以下情况通常可以安全补充默认值：

- 未说明时区，使用 `Asia/Shanghai`；
- 未说明租户范围，使用当前授权范围；
- 未说明输出形式，使用默认自然语言或报告形式；
- “这些告警”能够唯一绑定上一轮告警集合。

默认值必须记录在 `assumptions` 中，便于日志和问题排查。

### 必须追问的情况

例如用户说：

> 帮我分析一下它。

而上下文同时存在告警、指标和任务，则解析结果应为：

```json
{
  "goal": "分析指定对象",
  "operation": "unknown",
  "targets": [
    {
      "entity_type": "unknown",
      "expression": "它",
      "reference_source": "unresolved",
      "entity_ids": [],
      "resolution_status": "unresolved"
    }
  ],
  "ambiguities": [
    "它可能指上一轮的告警、指标或任务"
  ],
  "needs_clarification": true
}
```

系统再向用户询问：

> 你希望分析刚才的告警、任务，还是问答成功率指标？

## Agent接入

### 调用方式

解析和绑定完成后，把任务放入业务 Agent 的状态或运行上下文：

```python
agent_result = await monitoring_agent.ainvoke(
    {
        "messages": conversation_messages,
        "semantic_request": resolved_request.model_dump(mode="json"),
    },
    context=MonitoringRuntimeContext(
        user_id=current_user.user_id,
        tenant_id=current_user.tenant_id,
        timezone="Asia/Shanghai",
    ),
)
```

自主监控 Agent 根据任务自主决定是否调用：

- `query_alerts`；
- `get_alert_details`；
- `query_metrics`；
- `query_metric_series`；
- `query_events`；
- `query_tasks`；
- `correlate_alerts`。

语义解析结果不能直接指定固定工具调用顺序，否则会重新退化为工作流。

### 完成度校验

Agent 执行完成后，还需要检查回答是否满足解析出的输出要求。

例如任务要求：

```json
{
  "include_causes": true,
  "include_evidence": true,
  "include_list": true
}
```

但结果只有告警列表，则完成度校验应判定：

```json
{
  "completed": false,
  "missing": ["原因分析", "判断证据"]
}
```

Agent 可以继续调查，或由确定性事实收敛逻辑补充缺失内容。不能因为模型已经生成了一段自然语言就默认任务完成。

## 失败降级

### 推荐三级策略

语义解析可以采用三级处理：

1. 供应商原生结构化输出；
2. 工具调用方式的结构化输出或受限结构修复；
3. 确定性最低限度解析。

最低限度解析示例：

```python
fallback_request = SemanticRequest(
    goal=user_message,
    operation="unknown",
    targets=[],
    output=OutputRequirement(),
    ambiguities=["模型结构化解析失败，无法可靠确定任务对象"],
    needs_clarification=True,
)
```

最低限度降级只能保留明确事实，不应通过大量关键词规则假装已经正确理解用户。

### 模型输出错误

常见错误包括：

- 没有返回结构化结果；
- 字段类型错误；
- 返回多个相互冲突的任务；
- 虚构对象 ID；
- 把回答内容写入任务目标；
- 忽略上下文引用。

Harness 应记录：

- 原始用户表达摘要；
- 使用的上下文对象 ID；
- 结构化解析是否成功；
- Schema 校验错误类型；
- 是否发生修复或降级；
- 对象绑定结果；
- 是否要求用户澄清。

日志不得记录完整问题答案、敏感文档内容、Token 或其他受保护数据。

## 评测方法

### 为什么需要真实表达集

Schema 只能保证格式，不能保证语义理解正确。覆盖能力主要来自持续积累的真实问法评测集。

建议至少覆盖以下类型：

| 类型 | 示例 | 预期行为 |
| --- | --- | --- |
| 明确查询 | 今天有多少条告警？ | 查询当天告警数量 |
| 明细表达 | 这四条分别是什么？ | 绑定上一轮四条告警并展示明细 |
| 原因调查 | 为什么会这样？ | 沿用上一轮异常对象并调查原因 |
| 集合筛选 | 严重的那两条呢？ | 从上一轮集合中筛选严重告警 |
| 时间追问 | 那昨天呢？ | 沿用目标和对象，替换时间范围 |
| 对比表达 | 跟上次比有什么变化？ | 形成当前与上一次的对比任务 |
| 输出限制 | 只告诉我原因。 | 不输出完整列表，保留原因和证据 |
| 多目标表达 | 列出来并分析原因。 | 同时要求明细和原因分析 |
| 模糊指代 | 帮我看看它。 | 无法唯一绑定时追问 |
| 权限边界 | 查一下其他租户的告警。 | 在绑定阶段执行权限校验 |

### 验收字段

每条语义解析用例至少校验：

- `goal` 是否保持用户真实目标；
- `operation` 是否合理；
- 对象类型是否正确；
- 引用来源是否正确；
- 真实对象是否正确绑定；
- 时间范围是否正确；
- 数据范围是否越权；
- 输出要求是否完整；
- 是否应该追问；
- 最终回答是否满足任务要求。

### 持续优化

每次线上或验收发现新的错误表达，应执行以下流程：

1. 保存脱敏后的用户原始表达；
2. 记录期望语义任务；
3. 加入语义解析评测集；
4. 判断问题来自上下文缺失、Prompt、Schema、对象绑定还是模型能力；
5. 修改对应层，不直接堆叠临时关键词；
6. 执行三个 Agent 的共性回归和本 Agent 的领域回归。

### 完整代码

代码额外提供 `happy`、`unauthorized`、`unresolved` 和 `incomplete` 四个实验场景，后面可以直接通过命令行切换：

```python
from __future__ import annotations

import argparse
import asyncio
from datetime import datetime
from typing import Literal

from pydantic import BaseModel, Field


class TargetReference(BaseModel):
    entity_type: Literal["alert", "unknown"]
    expression: str
    reference_source: Literal["previous_result", "unresolved"]
    entity_ids: list[str] = Field(default_factory=list)
    resolution_status: Literal["resolved", "unresolved"] = "unresolved"


class TimeRange(BaseModel):
    raw_expression: str
    start_at: datetime
    end_at: datetime
    timezone: str = "Asia/Shanghai"


class OutputRequirement(BaseModel):
    include_list: bool = False
    include_causes: bool = False
    include_evidence: bool = True


class SemanticRequest(BaseModel):
    goal: str
    operation: Literal["investigate", "unknown"]
    targets: list[TargetReference]
    time_range: TimeRange | None = None
    tenant_id: int | None = None
    output: OutputRequirement
    assumptions: list[str] = Field(default_factory=list)
    ambiguities: list[str] = Field(default_factory=list)
    needs_clarification: bool = False


class AgentResult(BaseModel):
    alert_ids: list[str]
    causes: list[str]
    evidence: list[str]


def build_context_packet(user_message: str, case: str) -> dict:
    """实际项目中由 Harness 从会话状态和认证上下文组装。"""
    context_packet = {
        "current_time": "2026-08-09T20:30:00+08:00",
        "timezone": "Asia/Shanghai",
        "authorized_tenant_ids": [103],
        "current_scope": {"scope_type": "tenant", "tenant_id": 103},
        "previous_result": {
            "result_type": "alert_list",
            "entity_ids": ["1001", "1002", "1003", "1004"],
            "tenant_id": 103,
            "start_at": "2026-08-09T19:30:00+08:00",
            "end_at": "2026-08-09T20:30:00+08:00",
        },
        "user_message": user_message,
    }
    if case == "unauthorized":
        context_packet["authorized_tenant_ids"] = []
    if case == "unresolved":
        context_packet["previous_result"]["result_type"] = "metric_list"
    return context_packet


async def parse_with_semantic_model(context_packet: dict) -> SemanticRequest:
    """模拟 with_structured_output(SemanticRequest) 的返回结果。

    模型只判断“这四条”引用上一轮结果，不复制、猜测或生成真实 ID。
    """
    _ = context_packet
    return SemanticRequest(
        goal="调查这四条告警的产生原因",
        operation="investigate",
        targets=[
            TargetReference(
                entity_type="alert",
                expression="这四条告警",
                reference_source="previous_result",
            )
        ],
        output=OutputRequirement(
            include_list=True,
            include_causes=True,
            include_evidence=True,
        ),
    )


def resolve_request(
    parsed: SemanticRequest,
    context_packet: dict,
) -> SemanticRequest:
    """由确定性程序完成对象、时间、租户和权限绑定。"""
    previous = context_packet["previous_result"]
    current_scope = context_packet["current_scope"]
    authorized_tenant_ids = context_packet["authorized_tenant_ids"]

    tenant_id = current_scope["tenant_id"]
    if tenant_id not in authorized_tenant_ids:
        raise PermissionError("当前用户无权访问该租户")
    if previous["tenant_id"] != tenant_id:
        raise PermissionError("上一轮对象不属于当前租户")

    resolved_targets: list[TargetReference] = []
    for target in parsed.targets:
        if (
            target.entity_type == "alert"
            and target.reference_source == "previous_result"
            and previous["result_type"] == "alert_list"
        ):
            entity_ids = previous["entity_ids"]
            if not entity_ids:
                raise ValueError("上一轮告警集合为空")
            resolved_targets.append(
                target.model_copy(
                    update={
                        "entity_ids": entity_ids,
                        "resolution_status": "resolved",
                    }
                )
            )
        else:
            resolved_targets.append(target)

    unresolved = [
        target.expression
        for target in resolved_targets
        if target.resolution_status != "resolved"
    ]
    return parsed.model_copy(
        update={
            "targets": resolved_targets,
            "tenant_id": tenant_id,
            "time_range": TimeRange(
                raw_expression="沿用上一轮",
                start_at=previous["start_at"],
                end_at=previous["end_at"],
            ),
            "assumptions": ["未指定时间，沿用上一轮时间范围"],
            "ambiguities": [f"无法绑定对象：{item}" for item in unresolved],
            "needs_clarification": bool(unresolved),
        }
    )


async def run_monitoring_agent(
    request: SemanticRequest,
    case: str,
) -> AgentResult:
    """模拟业务 Agent 调用告警、指标和事件事实工具。"""
    if request.needs_clarification:
        raise ValueError("对象未解析完成，不能启动调查")

    alert_ids = request.targets[0].entity_ids
    return AgentResult(
        alert_ids=alert_ids,
        causes=["问答成功率低于阈值并持续 5 分钟"],
        evidence=[]
        if case == "incomplete"
        else ["对应时段模型调用超时率由 1.2% 升至 18.6%"],
    )


def check_completion(
    request: SemanticRequest,
    result: AgentResult,
) -> list[str]:
    missing: list[str] = []
    if request.output.include_list and not result.alert_ids:
        missing.append("告警列表")
    if request.output.include_causes and not result.causes:
        missing.append("原因分析")
    if request.output.include_evidence and not result.evidence:
        missing.append("判断证据")
    return missing


async def run_demo(case: str) -> None:
    context_packet = build_context_packet(
        "分析一下这四条告警产生的原因",
        case,
    )
    print("0. 上下文包：", context_packet)

    parsed = await parse_with_semantic_model(context_packet)
    print("1. 模型解析：", parsed.model_dump(mode="json"))

    try:
        resolved = resolve_request(parsed, context_packet)
    except PermissionError as error:
        print("2. 边界校验：", {"stopped": True, "reason": str(error)})
        return
    print("2. 对象绑定：", resolved.model_dump(mode="json"))

    if resolved.needs_clarification:
        print(
            "3. 澄清门禁：",
            {"stopped": True, "ambiguities": resolved.ambiguities},
        )
        return

    result = await run_monitoring_agent(resolved, case)
    print("3. Agent 结果：", result.model_dump(mode="json"))

    missing = check_completion(resolved, result)
    print("4. 完成校验：", {"completed": not missing, "missing": missing})


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(description="语义解析全流程 Demo")
    parser.add_argument(
        "--case",
        choices=["happy", "unauthorized", "unresolved", "incomplete"],
        default="happy",
        help="选择正常或故障实验场景",
    )
    return parser.parse_args()


if __name__ == "__main__":
    args = parse_args()
    asyncio.run(run_demo(args.case))
```

### 逐步观察

第四步，按打印顺序观察同一个任务在不同责任层中的变化。

#### 上下文

查看 `0. 上下文包`。此时四个真实告警 ID 只存在于 `previous_result`，它们来自可信的会话状态，而不是用户文本。同时记住：

- 当前租户是 `103`；
- 用户被授权的租户列表是 `[103]`；
- 上一轮返回类型是 `alert_list`；
- 用户这一轮只说了“这四条告警”，没有说出任何 ID。

#### 模型解析

查看 `1. 模型解析`。`parse_with_semantic_model()` 理解了“这四条告警”引用上一轮结果，所以输出 `reference_source=previous_result`。但此时必须看到：

```text
entity_ids=[]
resolution_status=unresolved
```

这说明模型只负责“听懂引用关系”，没有被信任去提供真实业务 ID。

#### 对象绑定

查看 `2. 对象绑定`。`resolve_request()` 先确认租户 `103` 在授权列表中，再确认上一轮结果也属于租户 `103`，最后才把四个 ID 写入任务。对比第 `1` 步和第 `2` 步：

```text
绑定前：entity_ids=[]                         status=unresolved
绑定后：entity_ids=[1001,1002,1003,1004]    status=resolved
```

用户没有重复时间范围，因此程序沿用上一轮的时间，并在 `assumptions` 中记录这个默认决定。

#### Agent执行

查看 `3. Agent 结果`。只有当对象、租户和时间都已确定，且 `needs_clarification=False` 时，业务 Agent 才会开始执行。Demo 返回了告警列表、原因和证据三类结果。

#### 完成校验

查看 `4. 完成校验`。`check_completion()` 不评价自然语言是否“看起来不错”，而是逐项对照 `OutputRequirement`。本例要求列表、原因和证据，三项都存在才返回 `completed=True`。

### 过程对照

Demo 中最重要的不是模拟出的告警原因，而是数据在各责任层之间的变化：

| 阶段 | 输入 | 输出 | 安全边界 |
| --- | --- | --- | --- |
| 上下文组装 | 会话状态、认证上下文、用户问题 | 最小上下文包 | 只携带当前授权范围和必要的历史对象 |
| 模型解析 | 最小上下文包 | 未绑定的 `SemanticRequest` | 模型可识别引用来源，不可确定真实 ID |
| 确定性绑定 | 语义任务、会话状态、权限范围 | 已解析的 `SemanticRequest` | 程序校验租户、对象、时间和权限 |
| Agent 执行 | 已解析的任务 | 原因、证据和对象列表 | Agent 只能使用本 Harness 注册且经授权的工具 |
| 完成校验 | 输出要求、Agent 结果 | 完成状态和缺失项 | 缺少原因或证据时不得标记任务完成 |

将 Demo 接入真实工程时，`build_context_packet()` 中的固定状态应替换为 Checkpointer 或 Store 中的结构化会话状态，认证信息仍由 Runtime Context 提供；`run_monitoring_agent()` 应替换为正式自主监控 Agent Harness，事实数据由显式注册的只读工具查询。

`resolve_request()` 中的租户校验、对象绑定和时间解析不应改为由模型自由决定；`check_completion()` 也应保留为结构化的任务收敛门禁。

## 总结说明

语义解析层最核心的实现原则可以总结为三句话：

> 模型负责听懂人话。

> 程序负责确认没有理解错对象和边界。

> Agent 负责自主调查并完成任务。

语义解析层不是关键词分类器，也不是固定工作流。它是自然语言与业务 Agent 之间的一层结构化翻译和安全校验能力。

推荐先从最小协议、少量上下文和真实问题评测集开始，随着实际表达不断补充协议和上下文能力。不要一开始设计过度复杂的通用语言系统，也不要在出现新问题时继续堆叠关键词规则。
