# 后端配置环境变量改造方案

## 1. 改造目标

后端继续保留 `app.yaml` 作为配置结构和默认值来源，同时支持通过 `.env` 或系统环境变量为 `app.yaml` 中的配置项提供实际值。

本次改造不替换现有 YAML 配置机制，不要求所有配置项都必须改成环境变量，也不涉及业务 API、Service、DB 业务逻辑调整。

## 2. 配置使用规则

### 2.1 固定值配置

`app.yaml` 中没有环境变量占位符时，按现有逻辑直接使用固定值：

```yaml
default:
  debug: false
  log_level: INFO
```

### 2.2 环境变量配置

`app.yaml` 可以通过 `${变量名}` 引用环境变量：

```yaml
default:
  database_url: ${KB_DEFAULT_DATABASE_URL}

storage:
  minio_endpoint: ${KB_STORAGE_MINIO_ENDPOINT}
```

### 2.3 混合配置

固定值和环境变量可以在同一个配置文件中同时使用：

```yaml
storage:
  backend: minio
  minio_endpoint: ${KB_STORAGE_MINIO_ENDPOINT}
  minio_bucket: knowledge-base
```

配置规则如下：

- 没有占位符的配置项继续使用 YAML 中的固定值。
- 使用 `${变量名}` 的配置项从系统环境变量或 `.env` 中读取。
- `.env` 文件是可选的。
- 没有使用环境变量占位符时，即使不存在 `.env`，应用也应正常启动。
- 使用了占位符但变量不存在时，应用启动失败，并明确提示缺少的变量名。
- 环境变量只替换 YAML 中明确引用的配置项，不自动覆盖全部 YAML 配置。

## 3. 配置加载流程

```text
加载系统环境变量和可选的 .env
        ↓
读取 app.yaml
        ↓
递归替换 ${ENV_NAME} 占位符
        ↓
解析 YAML
        ↓
执行现有 Opt/Pydantic 类型校验
        ↓
应用启动
```

系统环境变量优先级高于 `.env`，避免本地文件覆盖容器或发布平台显式注入的配置。

## 4. 后端代码改造内容

### 4.1 配置加载器

主要修改文件：

- `app/config/base.py`
- `app/config/__init__.py`

改造内容：

- 在配置初始化阶段加载可选的 `.env`。
- 在 YAML 解析前处理 `${变量名}` 占位符。
- 支持嵌套配置节点递归替换。
- 对缺失环境变量输出明确异常。
- 保留现有 `Opt` 和 Pydantic 配置校验。
- 保证布尔值、整数、列表等配置类型能够正确解析。

### 4.2 依赖管理

本地直接启动时需要加载 `.env`，建议增加：

```bash
uv add python-dotenv
```

依赖增加后必须同步更新兼容导出文件 `requirements.txt`。项目依赖以 `pyproject.toml` 为声明源，不能只手工修改 `requirements.txt`，应通过 `uv export` 重新导出：

```bash
uv export --no-hashes --format requirements-txt --output-file requirements.txt
```

需要确认以下文件保持同步：

- `pyproject.toml`：增加 `python-dotenv` 依赖声明。
- `uv.lock`：通过 `uv lock` 或 `uv add` 自动更新锁文件。
- `requirements.txt`：通过 `uv export` 同步导出 `python-dotenv`。

Docker 环境不依赖应用主动读取文件，运行脚本通过 `docker run --env-file` 注入变量。

## 5. 配置文件调整

新增文件：

```text
.env
.env.example
```

`.env` 保存本地或部署环境的真实配置，不提交到 Git；`.env.example` 只保存变量名和示例值，提交到 Git。

### 5.1 必须同步修改 `etc/app.yaml.example`

`etc/app.yaml.example` 是 Dockerfile 构建镜像时复制到容器 `/etc/app/app.yaml` 的配置模板，因此它必须同步支持环境变量占位符，不能继续只保留 `127.0.0.1` 等本地开发配置。

后续应直接修改：

```text
etc/app.yaml.example
```

改造要求：

- 保留 `default`、`storage`、`chat`、`embedding` 等 YAML 配置分组结构。
- 可以继续保留不需要外置的固定默认值。
- 数据库、MinIO、模型服务地址、API Key 等部署相关配置改为 `${变量名}`。
- 不在该文件中写入真实密码、Token 或 API Key。
- 确保 Dockerfile 复制进镜像的仍然是这份模板文件。
- 容器启动时通过 `.env` 或系统环境变量为模板提供实际值。

示例：

```yaml
default:
  environment: ${KB_DEFAULT_ENVIRONMENT}
  debug: ${KB_DEFAULT_DEBUG}
  database_url: ${KB_DEFAULT_DATABASE_URL}

storage:
  backend: minio
  minio_endpoint: ${KB_STORAGE_MINIO_ENDPOINT}
  minio_access_key: ${KB_STORAGE_MINIO_ACCESS_KEY}
  minio_secret_key: ${KB_STORAGE_MINIO_SECRET_KEY}
  minio_bucket: ${KB_STORAGE_MINIO_BUCKET}

chat:
  model: ${KB_CHAT_MODEL}
  api_key: ${KB_CHAT_API_KEY}
  base_url: ${KB_CHAT_BASE_URL}
  timeout_seconds: ${KB_CHAT_TIMEOUT_SECONDS}

embedding:
  model: ${KB_EMBEDDING_MODEL}
  api_key: ${KB_EMBEDDING_API_KEY}
  base_url: ${KB_EMBEDDING_BASE_URL}
  timeout_seconds: ${KB_EMBEDDING_TIMEOUT_SECONDS}
```

如果某项保留固定默认值，也必须确保在没有 `.env` 时可以正常解析。例如：

```yaml
default:
  log_level: INFO
  request_id_header: X-Request-ID

storage:
  backend: minio
  minio_bucket: knowledge-base
```

开发环境可继续保留固定默认值，不要求所有配置项一次性环境变量化。

## 7. Docker 运行脚本调整

后端 `scripts/run-image.sh` 需要：

- 检查项目目录下是否存在 `.env`。
- `.env` 存在时增加 `--env-file .env`。
- 启动容器前先加载 `.env`，将 `KB_*` 变量中的相互引用展开后显式传入容器；不能依赖 `docker run --env-file` 自动展开变量引用。
- `.env` 不存在时允许继续使用系统环境变量。
- 构建镜像成功后再启动容器。
- 不将 `.env` 复制进 Docker 镜像。

建议使用 Docker 网络中的服务名，不要在容器配置中使用 `127.0.0.1`：

```env
KB_DEFAULT_DATABASE_URL=postgresql+asyncpg://linburgh:linburgh@postgres:5432/knowledge_base
KB_STORAGE_MINIO_ENDPOINT=http://minio:9000
```

PostgreSQL、MinIO 和后端容器需要加入同一个 Docker 网络。

## 8. 安全要求

- `.env` 必须加入 `.gitignore`。
- 真实 API Key、Token、密码不得写入 `app.yaml.example`、`.env.example` 或 Dockerfile。
- `.env` 不得复制到 Docker 镜像中。
- 启动错误和普通日志不得打印完整密钥或数据库密码。
- 环境变量值只在配置加载阶段使用，不在业务代码中散落读取。

## 9. 验证内容

后续实现后需要验证：

- 纯固定值 `app.yaml` 可以正常启动。
- 引用 `.env` 的 `app.yaml` 可以正常启动。
- 系统环境变量优先于 `.env`。
- `.env` 不存在且 YAML 没有占位符时可以正常启动。
- 使用占位符但变量缺失时能明确报错。
- `false`、整数和列表等类型解析正确。
- Docker 运行脚本可以正确注入 `.env`。
- API Key、Token 和数据库密码不会出现在日志中。

## 10. 实施顺序

1. 在 `pyproject.toml` 增加 `python-dotenv`，更新 `uv.lock`。
2. 通过 `uv export` 将 `python-dotenv` 同步导出到 `requirements.txt`。
3. 增加 `.env.example` 和 `.gitignore` 规则。
4. 改造配置加载器，实现可选 `.env` 加载和 YAML 占位符替换。
5. 修改 `etc/app.yaml.example`，保留配置结构，将部署相关值改为 `${变量名}` 占位符。
6. 修改后端 Docker 运行脚本注入 `.env`。
7. 启动 PostgreSQL、Redis、MinIO 并统一 Docker 网络。
8. 执行配置兼容性和容器启动验证。
