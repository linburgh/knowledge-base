# 文档分块上传实现说明

## 1. 背景

当前项目的文档上传入口在：

```text
app/api/v1/documents.py
```

文件保存、校验和分块读取逻辑在：

```text
app/core/services/document.py
```

早期实现是一次性读取完整文件：

```python
content = await file.read()
```

这种方式简单，但缺点明显：

- 文件会完整进入应用内存。
- 上传文件越大，单个请求占用内存越高。
- 多个用户并发上传时，内存压力会快速放大。

因此当前实现改为分块读取，每次只从上传流里读取固定大小的数据块，边读取、边校验、边写入目标存储。

## 2. 当前配置

### 2.1 单文件最大大小

配置位置：

```yaml
default:
  max_upload_size_mb: 100
```

对应文件：

```text
etc/app.yaml
etc/app.yaml.example
app/config/default.py
```

当前限制是：

```text
100 MB
```

### 2.2 单次读取块大小

代码位置：

```python
UPLOAD_CHUNK_SIZE = 1024 * 1024
```

含义：

```text
每次读取 1 MB
```

这个值不是最大文件大小，只是应用每次从上传流读取到内存中的数据块大小。

## 3. 整体流程

上传接口调用链如下：

```text
POST /api/v1/documents/upload
        |
        v
upload()
        |
        v
document_service.upload()
        |
        v
分块读取 UploadFile
        |
        v
保存文件 + 计算 hash + 返回文件元数据
        |
        v
document_service.add()
```

核心方法是：

```python
async def upload(
    file: UploadFileLike,
    knowledge_base_id: int,
) -> tuple[str, int, str]:
```

`UploadFileLike` 是 service 层定义的协议类型，只要求对象具备 `filename` 和异步 `read()` 方法。这样 service 不需要直接依赖 FastAPI 的 `UploadFile` 类型。

返回值分别是：

| 返回值 | 含义 |
|---|---|
| `object_path` | 文件保存路径 |
| `size` | 文件大小，单位 byte |
| `content_hash` | 文件内容 sha256 |

## 4. 文件名和类型校验

上传开始后，先取安全文件名：

```python
filename = Path(file.filename or "").name
```

这里使用 `Path(...).name` 的目的是只保留文件名，去掉用户可能传入的目录部分。

例如：

```text
../../a.pdf -> a.pdf
```

然后校验文件名不能为空：

```python
if not filename:
    raise BusiException("上传文件名不能为空")
```

再直接校验文件扩展名：

```python
suffix = Path(filename).suffix.lower()
allowed_extensions = set(CONF.default.allowed_file_extensions or [])
if suffix not in allowed_extensions:
    raise BusiException("不支持的文件类型")
```

允许的类型来自配置：

```yaml
allowed_file_extensions:
  - .pdf
  - .md
  - .markdown
  - .txt
  - .docx
```

## 5. 为什么先写临时文件

最终文件名里包含内容 hash：

```text
{content_hash}_{filename}
```

但 hash 必须读完整个文件之后才能得到。

如果一开始就写最终文件名，就没有办法提前知道 hash。所以当前实现先写入临时文件：

```python
temp_path = target_dir.joinpath(f".upload_{common_utils.new_request_id()}.tmp")
```

上传完成并计算出 hash 后，再改名为最终文件：

```python
content_hash = hasher.hexdigest()
object_path = target_dir.joinpath(f"{content_hash}_{filename}")
temp_path.replace(object_path)
```

这样做有几个好处：

- 文件没有完整上传完成前，不会生成最终文件。
- 中途失败时，只需要删除临时文件。
- 最终文件名可以稳定包含内容 hash。

## 6. 分块读取核心逻辑

当前核心代码：

```python
hasher = sha256()
size = 0
temp_path = target_dir.joinpath(f".upload_{common_utils.new_request_id()}.tmp")
try:
    with temp_path.open("wb") as target_file:
        while chunk := await file.read(UPLOAD_CHUNK_SIZE):
            size += len(chunk)
            if size > max_size:
                raise BusiException("上传文件超过大小限制")
            hasher.update(chunk)
            target_file.write(chunk)
except Exception:
    temp_path.unlink(missing_ok=True)
    raise
```

逐行解释：

```python
hasher = sha256()
```

创建 sha256 计算器，用于后续边读边计算文件 hash。

```python
size = 0
```

累计已经读取的文件大小。

```python
while chunk := await file.read(UPLOAD_CHUNK_SIZE):
```

每次最多读取 1 MB。只要还能读到数据，就继续循环。

```python
size += len(chunk)
```

累计当前已上传大小。

```python
if size > max_size:
    raise BusiException("上传文件超过大小限制")
```

每读一块就检查一次大小。如果累计大小超过 100 MB，立即抛出业务异常。

```python
hasher.update(chunk)
```

把当前块加入 hash 计算。sha256 支持流式更新，不需要一次性传入完整文件。

```python
target_file.write(chunk)
```

把当前块写入临时文件。

## 7. 大小限制如何生效

大小限制在 `upload()` 中直接计算并判断：

```python
max_size = int(CONF.default.max_upload_size_mb or 100) * 1024 * 1024

while chunk := await file.read(UPLOAD_CHUNK_SIZE):
    size += len(chunk)
    if size > max_size:
        raise BusiException("上传文件超过大小限制")
```

假设配置为：

```yaml
max_upload_size_mb: 100
```

那么最大字节数是：

```text
100 * 1024 * 1024 = 104857600 bytes
```

分块读取时，每读一块都会累计 `size`。一旦 `size > 104857600`，立即停止并抛错。

这意味着应用不会等完整超大文件读完才拒绝，而是在超过限制的那一块立即拒绝。

## 8. 异常清理

如果上传过程中出现异常，比如：

- 文件超过大小限制。
- 磁盘写入失败。
- 客户端连接中断。
- 其他未预期错误。

代码会进入：

```python
except Exception:
    temp_path.unlink(missing_ok=True)
    raise
```

作用是删除临时文件，避免留下半截文件。

`missing_ok=True` 表示如果临时文件不存在，也不要再抛出删除异常。

## 9. 当前实现的边界

当前实现解决了“应用内存不再持有完整文件”的问题，但它仍然是本地文件保存方式：

```python
storage_dir = Path(CONF.default.local_storage_dir or "./storage")
```

也就是说，文件现在还是先落到本机磁盘：

```text
./storage/documents/{knowledge_base_id}/
```

当前配置里已经有 MinIO：

```yaml
storage:
  backend: minio
  minio_endpoint: http://127.0.0.1:9000
  minio_access_key: linburgh
  minio_secret_key: linburgh
  minio_bucket: knowledge-base
  minio_secure: false
```

但上传代码暂时还没有切换到 MinIO 客户端。

## 10. 后续切换到 MinIO 时的思路

切到 MinIO 后，核心思路仍然不变：

```text
分块读取 UploadFile
        |
        v
累计大小并校验
        |
        v
边读边计算 hash
        |
        v
上传到对象存储
```

区别在于写入目标从：

```python
target_file.write(chunk)
```

变成 MinIO 上传。

有两种实现方式。

### 10.1 简单方式：先落临时文件，再上传 MinIO

流程：

```text
UploadFile -> 本地临时文件 -> 计算 hash -> 上传 MinIO -> 删除临时文件
```

优点：

- 实现简单。
- 可以复用当前临时文件逻辑。
- 文件大小已知后再上传 MinIO。

缺点：

- 本地磁盘会临时保存一份完整文件。
- 多个大文件并发上传时，需要关注本地磁盘容量。

### 10.2 进阶方式：直接 multipart upload 到 MinIO

流程：

```text
UploadFile -> 分块 -> MinIO multipart upload
```

优点：

- 不需要本地保存完整文件。
- 更适合大文件。

缺点：

- 实现复杂一些。
- 失败时需要 abort multipart upload。
- 如果最终 object key 依赖 hash，需要先解决“hash 未完成前不知道最终 key”的问题。

常见处理方式是：

- 先上传到临时 object key。
- 上传完成后得到 hash。
- 再 copy 到最终 object key。
- 删除临时 object。

## 11. 为什么不是“真正的前端分片上传”

当前实现是后端分块读取，不是前端分片上传。

区别如下：

| 类型 | 说明 |
|---|---|
| 后端分块读取 | 浏览器仍然提交一个完整 multipart 文件，请求到达后端后，后端按块读取。 |
| 前端分片上传 | 浏览器把一个大文件切成多个请求上传，后端负责合并、断点续传和秒传。 |

当前项目实现的是：

```text
后端分块读取
```

它能降低后端内存占用，但不提供断点续传。

如果后续要支持超大文件、断点续传、上传进度恢复，可以再设计前端分片上传协议。

## 12. 当前实现小结

当前上传逻辑具备：

- 允许文件类型校验。
- 最大文件大小 100 MB。
- 1 MB 分块读取。
- 边读边计算 sha256。
- 边读边写本地临时文件。
- 超过大小限制立即拒绝。
- 异常时自动清理临时文件。
- 上传完成后按 `hash_原始文件名` 生成最终文件。

这套实现适合当前知识库项目的 MVP 阶段：比一次性读取更稳，又比完整的前端分片上传协议简单。
