# 文档分块上传实现说明

> Worker 的任务模型、状态流转、恢复机制和学习路径见：[文档索引 Worker 说明](文档索引Worker说明.md)。

## 1. 背景

当前项目的文档上传入口在：

```text
app/api/v1/documents.py
```

文件保存、校验和分块读取逻辑在：

```text
app/core/services/knowledge_base/document.py
```

早期实现是一次性读取完整文件：

```python
content = await file.read()
```

这种方式简单，但缺点明显：

- 文件会完整进入应用内存。
- 上传文件越大，单个请求占用内存越高。
- 多个用户并发上传时，内存压力会快速放大。

因此当前实现改为分块读取，每次只从上传流里读取固定大小的数据块，边读取、边校验、边写入目标存储。

## 2. 当前配置

### 2.1 单文件最大大小

配置位置：

```yaml
default:
  max_upload_size_mb: 100
```

对应文件：

```text
etc/app.yaml
etc/app.yaml.example
app/config/default.py
```

当前限制是：

```text
100 MB
```

### 2.2 单次读取块大小

代码位置：

```python
UPLOAD_CHUNK_SIZE = 1024 * 1024
```

含义：

```text
每次读取 1 MB
```

这个值不是最大文件大小，只是应用每次从上传流读取到内存中的数据块大小。

### 2.3 MinIO 存储配置

当前项目设计中 MinIO 是必需组件，配置位置：

```yaml
storage:
  backend: minio
  local_dir: ./storage
  minio_endpoint: http://127.0.0.1:9000
  minio_access_key: linburgh
  minio_secret_key: linburgh
  minio_bucket: knowledge-base
  minio_secure: false
```

`local_dir` 不是正式文件存储目录，只是上传过程和索引解析过程使用的本地临时目录。

## 3. 有 MinIO 与没有 MinIO 的区别

### 3.1 没有 MinIO 的本地文件方案

如果没有 MinIO，上传后的原始文件通常会直接保存在应用服务器磁盘：

```text
./storage/documents/{kb_id}/{sha256}_{filename}
```

数据库中的 `object_path` 会保存本地文件路径，例如：

```text
storage/documents/1/abc123_readme.md
```

这种方式的优点是实现简单，不需要额外部署对象存储服务。单机开发或临时验证时，上手成本最低。

但它的问题也很明显：

- 应用实例和文件强绑定，换一台机器就读不到原文件。
- 多个 API 实例部署时，每台机器的本地文件不共享，索引任务可能在另一台机器执行失败。
- 容器重建、迁移或误删 volume 时，原始文件容易丢失。
- 备份需要同时处理数据库和应用机器磁盘，恢复链路复杂。
- 后续做文件预览、下载、权限链接、生命周期管理都需要自己实现。

### 3.2 有 MinIO 的对象存储方案

接入 MinIO 后，应用服务器不再长期保存原始文件。当前实现流程是：

```text
UploadFile
    -> 本地临时文件
    -> 计算 sha256
    -> 上传 MinIO
    -> 删除本地临时文件
    -> 数据库保存 MinIO object key
```

数据库中的 `object_path` 保存的是 MinIO object key，例如：

```text
documents/1/abc123_readme.md
```

索引任务执行时，再根据 object key 从 MinIO 下载到本地临时目录：

```text
MinIO object key
    -> 本地临时文件
    -> LangChain loader 解析
    -> 文本切片
    -> 写入 t_document_chunk
    -> 删除本地临时文件
```

这种方式的优势是：

- API 服务和文件存储解耦，服务实例可以横向扩容。
- 索引任务在哪台机器执行都可以从 MinIO 读取同一个原始文件。
- 容器重建不会影响已上传文件，只要 MinIO volume 保留即可。
- 文件备份、恢复、生命周期、权限控制可以交给对象存储层处理。
- 后续支持预签名下载链接、文件预览、跨服务共享对象会更自然。

代价是：

- 需要部署和维护 MinIO。
- 上传链路多了一步对象存储写入，MinIO 不可用时文档上传会失败。
- 本地开发时除了 PostgreSQL，还需要启动 MinIO。

### 3.3 当前项目为什么选择 MinIO

知识库项目的原始文档是后续重新解析、重新切片、重新向量化和问题追溯的基础资产。它不适合只挂在某个 API 容器的本地目录中。

因此当前项目把 MinIO 作为不可缺失的基础设施：

- PostgreSQL 保存结构化元数据。
- MinIO 保存原始文件对象。
- 后续向量数据库保存文本分块向量。
- 本地目录只做临时缓冲，不做正式存储。

## 4. 整体流程

上传接口调用链如下：

```text
POST /api/v1/documents/upload
        |
        v
upload()
        |
        v
document_service.upload()
        |
        v
分块读取 UploadFile
        |
        v
保存文件 + 计算 hash + 返回文件元数据
        |
        v
创建文档记录
        |
        v
创建索引任务
        |
        v
后台执行 ingestion_service.run_task()
        |
        v
从 MinIO 下载文件、解析、切片、写入 t_document_chunk
```

上传接口只创建并持久化索引任务，文档解析、切片和向量化由索引 Worker 异步执行。Worker 通过任务状态、更新时间和最大执行时间管理任务，服务重启后可以恢复失联任务，避免使用临时 `asyncio.create_task()` 导致任务永久停留在 `processing`。

核心方法是：

```python
async def upload(
    file: UploadFileLike,
    kb_id: int,
    created_by: str,
    source_type: str = "upload",
    parser: str | None = None,
) -> Any:
```

`UploadFileLike` 是 service 层定义的协议类型，只要求对象具备 `filename` 和异步 `read()` 方法。这样 service 不需要直接依赖 FastAPI 的 `UploadFile` 类型。

`upload()` 会完成完整文档入库入口流程：

- 分块读取上传文件。
- 写入 MinIO。
- 创建 `t_document` 记录。
- 创建索引任务。
- 由 `workers/indexing.py` 获取 `pending` 任务并执行解析、切片和向量化。
- Embedding 使用可配置批量大小、受控并发和重试次数；任务更新时间作为 Worker 心跳。
- 超过任务最大执行时间或达到最大重试次数时，任务和文档进入 `failed` 并记录失败原因。

返回值是文档记录。

## 5. 文件名和类型校验

上传开始后，先取安全文件名：

```python
filename = Path(file.filename or "").name
```

这里使用 `Path(...).name` 的目的是只保留文件名，去掉用户可能传入的目录部分。

例如：

```text
../../a.pdf -> a.pdf
```

然后校验文件名不能为空：

```python
if not filename:
    raise BusiException("上传文件名不能为空")
```

再直接校验文件扩展名：

```python
suffix = Path(filename).suffix.lower()
allowed_extensions = set(CONF.default.allowed_file_extensions or [])
if suffix not in allowed_extensions:
    raise BusiException("不支持的文件类型")
```

允许的类型来自配置：

```yaml
allowed_file_extensions:
  - .pdf
  - .md
  - .markdown
  - .txt
  - .docx
```

## 6. 为什么先写临时文件

最终文件名里包含内容 hash：

```text
{content_hash}_{filename}
```

但 hash 必须读完整个文件之后才能得到。

如果一开始就写最终文件名，就没有办法提前知道 hash。所以当前实现先写入临时文件：

```python
temp_path = target_dir.joinpath(f".upload_{common_utils.new_request_id()}.tmp")
```

上传完成并计算出 hash 后，使用 hash 生成 MinIO object key：

```python
content_hash = hasher.hexdigest()
object_name = f"documents/{kb_id}/{content_hash}_{filename}"
```

这样做有几个好处：

- 文件没有完整上传完成前，不会生成最终 object key。
- 中途失败时，只需要删除临时文件。
- 最终文件名可以稳定包含内容 hash。

## 7. 分块读取核心逻辑

当前核心代码：

```python
hasher = sha256()
size = 0
temp_path = target_dir.joinpath(f".upload_{common_utils.new_request_id()}.tmp")
try:
    with temp_path.open("wb") as target_file:
        while chunk := await file.read(UPLOAD_CHUNK_SIZE):
            size += len(chunk)
            if size > max_size:
                raise BusiException("上传文件超过大小限制")
            hasher.update(chunk)
            target_file.write(chunk)
except Exception:
    temp_path.unlink(missing_ok=True)
    raise
```

逐行解释：

```python
hasher = sha256()
```

创建 sha256 计算器，用于后续边读边计算文件 hash。

```python
size = 0
```

累计已经读取的文件大小。

```python
while chunk := await file.read(UPLOAD_CHUNK_SIZE):
```

每次最多读取 1 MB。只要还能读到数据，就继续循环。

```python
size += len(chunk)
```

累计当前已上传大小。

```python
if size > max_size:
    raise BusiException("上传文件超过大小限制")
```

每读一块就检查一次大小。如果累计大小超过 100 MB，立即抛出业务异常。

```python
hasher.update(chunk)
```

把当前块加入 hash 计算。sha256 支持流式更新，不需要一次性传入完整文件。

```python
target_file.write(chunk)
```

把当前块写入临时文件。

## 8. 大小限制如何生效

大小限制在 `upload()` 中直接计算并判断：

```python
max_size = int(CONF.default.max_upload_size_mb or 100) * 1024 * 1024

while chunk := await file.read(UPLOAD_CHUNK_SIZE):
    size += len(chunk)
    if size > max_size:
        raise BusiException("上传文件超过大小限制")
```

假设配置为：

```yaml
max_upload_size_mb: 100
```

那么最大字节数是：

```text
100 * 1024 * 1024 = 104857600 bytes
```

分块读取时，每读一块都会累计 `size`。一旦 `size > 104857600`，立即停止并抛错。

这意味着应用不会等完整超大文件读完才拒绝，而是在超过限制的那一块立即拒绝。

## 9. 异常清理

如果上传过程中出现异常，比如：

- 文件超过大小限制。
- 磁盘写入失败。
- 客户端连接中断。
- 其他未预期错误。

代码会进入：

```python
except Exception:
    temp_path.unlink(missing_ok=True)
    raise
```

作用是删除临时文件，避免留下半截文件。

`missing_ok=True` 表示如果临时文件不存在，也不要再抛出删除异常。

## 10. MinIO 写入流程

当前项目设计中 MinIO 是必需组件。上传流程不是把文件长期保存到本地，而是使用本地临时文件作为缓冲，然后写入 MinIO：

```text
UploadFile -> 本地临时文件 -> 计算 hash -> 上传 MinIO -> 删除临时文件
```

本地临时目录来自配置：

```python
storage_dir = Path(CONF.storage.local_dir or "./storage")
```

例如 `kb_id=1` 时，临时文件目录类似：

```text
./storage/documents/1/.upload_xxx.tmp
```

上传完成后，数据库保存的 `object_path` 是 MinIO object key：

```text
documents/1/{sha256}_readme.md
```

当前 MinIO 配置：

```yaml
storage:
  backend: minio
  minio_endpoint: http://127.0.0.1:9000
  minio_access_key: linburgh
  minio_secret_key: linburgh
  minio_bucket: knowledge-base
  minio_secure: false
```

## 11. 后续直接 multipart upload 到 MinIO 的思路

当前实现已经写入 MinIO，但仍然会先落本地临时文件。后续如果要减少本地磁盘占用，可以改为 MinIO multipart upload：

```text
分块读取 UploadFile
        |
        v
累计大小并校验
        |
        v
边读边计算 hash
        |
        v
上传到对象存储
```

流程：

```text
UploadFile -> 分块 -> MinIO multipart upload
```

优点：

- 不需要本地保存完整文件。
- 更适合大文件。

缺点：

- 实现复杂一些。
- 失败时需要 abort multipart upload。
- 如果最终 object key 依赖 hash，需要先解决“hash 未完成前不知道最终 key”的问题。

常见处理方式是：

- 先上传到临时 object key。
- 上传完成后得到 hash。
- 再 copy 到最终 object key。
- 删除临时 object。

## 12. 为什么不是“真正的前端分片上传”

当前实现是后端分块读取，不是前端分片上传。

区别如下：

| 类型 | 说明 |
|---|---|
| 后端分块读取 | 浏览器仍然提交一个完整 multipart 文件，请求到达后端后，后端按块读取。 |
| 前端分片上传 | 浏览器把一个大文件切成多个请求上传，后端负责合并、断点续传和秒传。 |

当前项目实现的是：

```text
后端分块读取
```

它能降低后端内存占用，但不提供断点续传。

如果后续要支持超大文件、断点续传、上传进度恢复，可以再设计前端分片上传协议。

## 13. 当前实现小结

当前上传逻辑具备：

- 允许文件类型校验。
- 最大文件大小 100 MB。
- 1 MB 分块读取。
- 边读边计算 sha256。
- 边读边写本地临时文件。
- 上传到 MinIO。
- 数据库保存 MinIO object key。
- 超过大小限制立即拒绝。
- 异常时自动清理临时文件。
- 上传完成后按 `documents/{kb_id}/{hash}_原始文件名` 生成对象 key。

这套实现适合当前知识库项目的 MVP 阶段：MinIO 是正式存储，本地磁盘只承担临时缓冲职责。
