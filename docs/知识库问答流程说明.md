# 知识库问答流程说明

## 1. 目标

知识库问答流程的目标是让模型基于知识库内已入库、已切片、可检索的文档内容回答问题，而不是直接依赖模型自身记忆。

当前项目已经完成知识库、文档上传、文档解析切片和基础表结构设计。问答流程后续需要在此基础上补充检索、上下文组装、模型调用、会话记录和引用落库。

## 2. 前置条件

一次问答请求能正常工作，需要满足以下条件：

- 知识库存在，且状态可用。
- 文档已经上传到 MinIO。
- 文档索引任务已经成功完成，`t_document.status = ready`。
- 文档分块已经写入 `t_document_chunk`。
- 后续向量化实现完成后，分块需要具备可检索的向量数据。
- 用户具备访问该知识库的权限。

如果知识库下没有可用分块，问答流程应该直接返回“当前知识库暂无可用内容”，不应该调用模型编造答案。

## 3. 总体流程

```text
用户提交问题
    |
    v
校验知识库、用户和问题
    |
    v
创建或读取会话
    |
    v
保存用户消息
    |
    v
问题预处理
    |
    v
检索候选分块
    |
    v
过滤、去重、排序
    |
    v
组装上下文和提示词
    |
    v
调用大模型生成答案
    |
    v
保存助手消息
    |
    v
保存答案引用
    |
    v
返回答案、引用和会话 ID
```

## 4. 请求入口

建议后续新增接口：

```text
POST /api/v1/chat
```

建议请求参数：

| 字段 | 说明 |
|---|---|
| `kb_id` | 知识库 ID |
| `question` | 用户问题 |
| `conversation_id` | 会话 ID，可为空；为空时创建新会话 |
| `user_id` | 用户 ID，后续可从认证上下文获取 |
| `top_k` | 可选，本次召回数量；默认使用知识库 `retrieval_top_k` |

建议返回结构：

```json
{
  "conversation_id": 1,
  "message_id": 2,
  "answer": "根据已入库资料，...",
  "citations": [
    {
      "document_id": 1,
      "chunk_id": 10,
      "source_name": "员工手册.pdf",
      "page": 3,
      "snippet": "引用片段...",
      "score": 0.91,
      "rank": 1
    }
  ],
  "retrieval": {
    "top_k": 5,
    "hit_count": 3
  }
}
```

## 5. 会话处理

会话用于把一次或多次问答串起来，涉及两张表：

- `t_conversation`
- `t_conversation_message`

处理规则：

- 如果请求带 `conversation_id`，先查询会话是否存在、是否属于当前用户和知识库。
- 如果请求不带 `conversation_id`，创建新会话。
- 用户问题先保存为一条 `role = user` 的消息。
- 模型回答生成后，再保存一条 `role = assistant` 的消息。
- token、耗时、模型名称、检索参数等运行信息放到 `metadata`。

第一版可以先不做复杂多轮记忆，只保存会话和消息，后续再把最近 N 轮消息纳入上下文。

## 6. 问题预处理

问题预处理用于提升检索效果，但第一版保持简单即可。

建议处理：

- 去除首尾空白。
- 校验问题不能为空。
- 限制问题最大长度。
- 记录原始问题。

后续可扩展：

- 多轮问题改写。
- 同义词扩展。
- 意图识别。
- 查询关键词抽取。

第一版不要过早引入复杂问题改写，先保证基础检索链路稳定。

## 7. 检索流程

检索的输入是：

- `kb_id`
- `user_id`
- `question`
- `top_k`

检索的输出是一组候选分块：

```text
chunk_id
document_id
source_name
page
content
score
rank
metadata
```

第一版建议先实现向量检索：

```text
问题 -> embedding -> pgvector 相似度检索 -> Top-K 分块
```

后续再扩展混合检索：

```text
向量检索
    +
关键词检索 PostgreSQL FTS
    +
去重
    +
重排序
```

重要约束：

- 检索必须先过滤 `kb_id`。
- 后续涉及权限时，必须在检索 SQL 或检索条件中前置过滤权限。
- 不能先全库召回，再在模型生成阶段过滤，否则存在越权泄露风险。
- 只检索 `ready` 状态文档产生的分块。

## 8. 候选分块处理

检索返回的候选分块不能直接全部塞给模型，需要做一次整理：

- 按分数排序。
- 去重，避免同一分块重复出现。
- 过滤空内容。
- 控制最大上下文长度。
- 必要时补充相邻分块，提升上下文完整度。

第一版可以先按 `score desc` 保留前 `retrieval_top_k` 条。

后续如果出现“命中片段准确但上下文不完整”，再考虑 Parent-Child 分块或邻近片段扩展。

## 9. 上下文组装

上下文需要结构化，方便模型回答时引用。

建议格式：

```text
[引用1]
文档：员工手册.pdf
页码：3
内容：
...

[引用2]
文档：报销制度.md
页码：
内容：
...
```

提示词核心要求：

- 只能依据给定资料回答。
- 资料不足时明确说明无法确认。
- 不要编造不存在的制度、数字、日期和来源。
- 回答中尽量标明参考资料。

## 10. 模型调用

模型调用输入：

- 系统提示词。
- 用户问题。
- 检索上下文。
- 可选的最近几轮会话。

模型调用输出：

- 答案文本。
- 可选的结构化引用标记。
- token 用量和耗时。

第一版可以先让服务端根据检索结果保存引用，不强依赖模型返回结构化 citation。也就是说，只要某个分块进入最终上下文，就可以作为候选引用落库。

## 11. 引用落库

回答引用保存到：

```text
t_message_citation
```

落库字段来自最终参与生成的分块：

| 字段 | 来源 |
|---|---|
| `message_id` | 助手消息 ID |
| `kb_id` | 当前知识库 ID |
| `document_id` | 命中文档 ID |
| `chunk_id` | 命中分块 ID |
| `source_name` | 分块来源名称 |
| `page` | 页码 |
| `snippet` | 分块内容摘要 |
| `score` | 检索或重排序分数 |
| `rank` | 引用排序 |

`snippet` 不建议保存完整大段内容，可以截取命中分块的前几百字符。

## 12. 无结果处理

如果检索不到有效分块，不应继续调用模型生成普通回答。

建议返回：

```json
{
  "answer": "当前知识库中没有检索到足够相关的内容，无法确认该问题。",
  "citations": [],
  "retrieval": {
    "top_k": 5,
    "hit_count": 0
  }
}
```

同时仍然可以保存用户消息和助手消息，便于后续分析哪些问题没有被知识库覆盖。

## 13. 异常处理

建议异常分层：

| 场景 | 处理 |
|---|---|
| 知识库不存在 | 返回业务异常 |
| 会话不存在或不属于当前用户 | 返回业务异常 |
| 问题为空 | 返回业务异常 |
| 没有可用分块 | 返回无结果答案 |
| Embedding 服务失败 | 返回业务异常，并记录日志 |
| 模型服务失败 | 返回业务异常，并记录日志 |
| 引用落库失败 | 整体请求失败，避免答案和引用不一致 |

问答链路不应吞掉模型调用失败，否则用户会误以为回答可信。

## 14. 建议模块规划

后续编码建议按下面的模块拆分：

```text
app/api/v1/chat.py
    接收问答请求，转换 DTO，调用 service

app/schemas/chat.py
    ChatRequest、ChatResponse、CitationDto

app/core/services/chat.py
    编排会话、检索、模型调用、消息和引用落库

app/core/services/retrieval.py
    处理检索、过滤、去重、排序

app/db/conversation.py
    t_conversation 基础 CRUD

app/db/conversation_message.py
    t_conversation_message 基础 CRUD

app/db/message_citation.py
    t_message_citation 基础 CRUD

app/rag/embeddings.py
    Embedding 模型封装

app/rag/retrievers.py
    向量检索、关键词检索、混合检索

app/rag/chains.py
    Prompt 和模型调用链
```

API 层只做入参接收和异常转换，不直接写检索 SQL，不直接调用模型。

## 15. 第一版落地顺序

建议按下面顺序实现：

1. 完成 conversation、conversation_message、message_citation 的 db 层基础方法。
2. 完成 chat schema。
3. 完成 retrieval service，先从 `t_document_chunk` 做简单关键词或内容匹配验证流程。
4. 接入 embedding 和 pgvector 检索。
5. 完成 chat service 编排。
6. 完成 `POST /api/v1/chat`。
7. 补充测试脚本和测试说明。
8. 再考虑混合检索、重排序、多轮问题改写。

第一版目标是先跑通闭环：

```text
用户问题 -> 检索分块 -> 组装上下文 -> 模型回答 -> 保存消息和引用
```

不要一开始就把重排序、Agent、多轮改写全部叠进去。
